# Aperture — Repo Map

Self-hosted media recommendation & watch-tracking app for Emby/Jellyfin. AI recommendations via pgvector embeddings. Integrations: TMDB, OMDb, Trakt, Seerr (Jellyseerr/Overseerr), MDBList, JustWatch, n8n, Tavily, fastCRW (self-hosted search + scrape, `packages/core/src/lib/crw.ts`), LLDAP (optional email import, `packages/core/src/lldap/`).

> **Keep this map current.** Adding/moving/renaming a route, page, core module, or table updates the relevant section here in the same change. Stale entries cause wrong-file edits.

## Repo-wide invariants

These hold everywhere; sections below reference them by name instead of restating them.

- **HNSW / `ef_search`** — pgvector's default `ef_search` is 40, and an HNSW scan never returns more rows than `ef_search`. Any query asking for >40 neighbours, or applying a post-filter (watch status, country, series scope) that pgvector resolves *after* the scan, needs `SET LOCAL hnsw.ef_search = 500` inside a transaction. It must be `SET LOCAL` so it cannot leak onto the pooled connection and change the other vector queries, which are tuned for the default. Without it a filtered `LIMIT 20` comes back nearly empty and the filter looks broken; a bare `LIMIT 400` either returns short or makes the planner drop the index and seq-scan every embedding.
- **NUMERIC arrives as a string** — pg returns NUMERIC as text, so a stored `0` arrives as `'0.0000'` and passes a truthy test, while a genuine numeric `0` fails one. Guard every score/rating column with `!= null`, never truthiness. Also `Number(null)` is **0, not NaN**, so mapping a NULL column through `Number()` silently fabricates a real zero — map NULL to `undefined` instead.
- **Absent ≠ false** — fields added by a migration are absent on older rows, and absent must preserve the pre-migration behaviour. Check `=== true` / `!= null` explicitly. Applies to `ContentItem.watched`, `evidenceSupportsCause`, `sharedIds`, the preference chain, weight shares, and `freeTier`.
- **The web bundle never imports `@aperture/core`** — server code would break it; duplicate tiny helpers instead (see `src/i18n/localeDirection.ts`). Any constant the UI needs (novelty band, threshold decisions) rides in the API response as a *decided* value and is never hardcoded in the bundle, or it drifts the first time core retunes it.
- **Parallel implementations must be mirrored** — `recommender/movies/` vs `recommender/series/`, `media/emby/` vs `media/jellyfin/`, and the two explanation generators. A fix in one usually needs the other. Where they have drifted, this file says so explicitly.
- **Duplicated predicates get split into a pure module with a test** — the recurring bug here is one rule copied into several places that then disagree, and agree only by being wrong identically. `watchedExclusion.ts`, `pending.ts`, `genrePreference.ts`, `logWindow.ts`, `crossMedia.ts`, `jobs/state.ts`, `explanationParsing.ts`, `countryMatch.ts`, `titleMatch.ts` all exist for this reason: pure, no DB, pinned by a test.
- **Never threshold a cosine band blind** — measured bands here are far narrower than they look: twin centroids span 0.898–0.993, `avgNovelty` pins into [0.8, 1.0], normalized dispersion read 0.000 for all 14 profiles, raw neighbour cosines crowd into 0.66–0.83. A measure calibrated on one population is not a measure on another. Measure the distribution before picking a number, and prefer a threshold whose failure is asymmetric toward the safe side.
- **Measure per user before reading an aggregate as a mechanism** — a per-user score averaged *across* users can show a trend that exists in no user. Similarity-by-decade over 9 users read as a clean recency bias (1930s 0.29 → 2020s 0.59, monotonic); per user the gradient *reverses*, each peaking at their own era. Control: a taste vector is equidistant from every decade the user actually watched (one 381-film user spans 0.7542–0.7596 across 50 years), so the embedding has **no** era bias — the population simply leaned recent. Same trap as watch-history Jaccard, where 1–8% pairwise overlap looks like "nobody shares taste" but is exactly what identical taste produces at ~100 watched out of 12.5k.

## Architecture (30 seconds)

pnpm monorepo, ESM everywhere, no ORM (raw SQL via `pg`):

- **`packages/core`** (`@aperture/core`) — ALL domain logic. `tsc` → `dist/`. Subpath exports: `.`, `/config`, `/db`, `/media`, `/recommender`, `/strm`, `/channels`, `/jobs`, `/watching`. Root `src/index.ts` is a giant barrel (~1090 lines).
- **`apps/api`** (`@aperture/api`) — thin Fastify HTTP layer (port 3456): routing, auth, job orchestration. Handlers call core functions; `src/lib/db.ts`, `lib/logger.ts`, `config/env.ts` are pure re-export shims of core.
- **`apps/web`** (`@aperture/web`) — Vite + React 18 SPA (dev port 3457, proxies `/api` → 3456). MUI 6, react-router 7, i18next (15 locales), d3, recharts. No central API client: raw `fetch('/api/...', { credentials: 'include' })` everywhere.
- **`packages/ui`** (`@aperture/ui`) — shared React components (MoviePoster, StarRating, BaseCarousel, RankBadge, StatusCard, TrailerModal, `getProxiedImageUrl`). Web aliases it to `src/` for hot reload; typecheck/build use `dist/`.
- **`db/migrations/`** — numbered SQL (`0001`–`0154`; `0129` is used twice, tolerated since the runner tracks filenames). Postgres + pgvector.

Applied at API startup (`RUN_MIGRATIONS_ON_START`) via `packages/core/src/migrations.ts`, or manually via `scripts/migrate.mjs` — **two runners, duplicated logic, both track `aperture_migrations`**; keep behavior in sync if touching either.

## Naming traps (easy to edit the wrong module)

Each entry is the rule. `[F-NNN]` points at the full evidence in [docs/aperture-forensics.md](docs/aperture-forensics.md) — the measurements, the failure as it presented, and the alternatives already tried and rejected. **Read the linked section before changing, reverting, or arguing with a rule**; you do not need it to write correct code. **A new entry goes here as the rule, with its evidence appended to [docs/aperture-forensics.md](docs/aperture-forensics.md) under the next free number.**

- **`discover/` vs `discovery/`** (api routes, mirrored in web/core): `discover` = browse people/studios + TMDB-external detail (`/api/discover/*`); `discovery` = missing-content engine feeding Seerr (`/api/discovery/*`). Unrelated third: `assistant/discovery/` (web-grounded chat candidates), whose grounding is multi-source via `assistant/discovery/sources/` (a `WebSearchSource` registry): Google grounding + Tavily (core `lib/tavily.ts`, `system_settings.tavily_integration`). Sources compose into one structuring pass and fall back for one another; Tavily errors log under the `tavily` provider. [F-001](docs/aperture-forensics.md#f-001)
- **A new AI role is a list, not a union.** `AI_FUNCTIONS` (core `lib/ai-capabilities/types.ts`) is the one copy; `AIFunction` derives from it. Roles are *also* a JSON-Schema `enum` on **ten** Fastify routes (`settings/schemas.ts` ×3, `setup/schemas.ts` ×7) that TypeScript cannot check against the union — adding a role means adding it there too, or its settings card silently renders "No models available" for every provider. Runtime guards use `isAIFunction`, never a hand-written `includes()`. Anything enumerating roles must iterate `AI_FUNCTIONS` (omitting one hides the spend dashboard and the pricing summary rather than erroring). **Never add a role to a SQL `CHECK`** — `0144` dropped the old one and `aiFunctionSchemas.test.ts` fails on any later migration whose `CHECK` names 2+ roles. `custom_ai_models_provider_check` deliberately stays (it guards providers, which change when an integration is written). Custom models are keyed `(provider, function_type)`, so they do not carry across roles; `getModel` and `getModelsForFunction` both go through `modelPool`. [F-002](docs/aperture-forensics.md#f-002)
- **Web Search is Google-only and holds two keys.** `getProvidersForFunction('webSearch')` returns just `google`; `AIFunctionCard` renders a label instead of a dropdown when a role has exactly one provider, and auto-corrects an off-list selection. `ProviderConfig.fallbackApiKey` sits alongside `apiKey` because Gemini's free tier is what breaks grounding. **Anything spending grounding quota must go through `withGroundingModel`/`withWebSearchModel`** (core `lib/ai-provider.ts`) or the meter undercounts: it walks `getWebSearchAttempts()`, advances **only** on a quota error, and writes every attempt to `web_search_usage`. Limits and cooldowns in `lib/webSearchQuota.ts`; counters in `lib/webSearchUsage.ts`, day windows anchored to **midnight US/Pacific**. `webCandidates.ts` cannot use the wrapper (its cascade fights the key loop) and meters by hand via `recordWebSearchCall`. An omitted `fallbackApiKey` in PATCH means "leave alone"; only an empty string clears it. [F-003](docs/aperture-forensics.md#f-003)
- **Two "cost" surfaces, only one real**: `CostEstimatorSection` *projects*; `InferenceDashboardSection` *measures*, is OpenRouter-only, and hides itself when no role uses OpenRouter. Capture is in the **provider's `fetch`** (`createOpenRouterUsageFetch(role)`, core `lib/openrouter-usage.ts`), so a new generateText/streamText call site needs no instrumentation — but `role` is baked in at provider-creation and is part of the provider cache key. `feature`/`sessionId`/`userId` ride an AsyncLocalStorage (`lib/inferenceContext.ts`) set in exactly three places: `runJob`, the chat handler, `testProviderConnection`. Unwrapped work records as `unattributed`. Cost is nullable end to end — **never treat a missing cost as zero**; the dashboard reports `pricedCalls` separately. [F-004](docs/aperture-forensics.md#f-004)
- **OpenRouter pricing resolves through its own catalog**, not `PROVIDER_MAP` (`lib/pricing-cache.ts` has no `openrouter` entry and its data file ships zero models). Use `getOpenRouterModelInfo`, **exact id only** — `:free`/`:extended` variants are priced differently. `FunctionPricing.pricingKnown` distinguishes "free" from "unpriceable"; anything rendering money must show unknown as unknown, never $0. [F-005](docs/aperture-forensics.md#f-005)
- **The assistant consumes the recommender's output, not its logic.** Of twelve tools only `getMyRecommendations` touches the pipeline (reads `is_selected` off the newest completed run). `semanticSearch`/`findSimilarContent` are bare pgvector kNN with **no** novelty term, taste boosts, diversity or reserved slots. Each item carries `source` (`ranked`|`twin`|`interest`|`acclaimed`), **derived** from `score_breakdown` by `pickSource` — never pass it through, because that object holds `twinMatch.donorId` and **the model must never receive an identity it could name**. Twin picks carry `sharedTitles` (from the *reader's own* history, so no donor leak), resolved **batched per tool call** via `resolveTwinSharedTitles`. Unknown/absent `source` reads as `ranked`. Nothing calls `ContentItemSchema.parse()`, so extra fields reach the client — `tool-ui/types.ts` mirrors the schema by hand and must be updated alongside it. [F-006](docs/aperture-forensics.md#f-006)
- **`searchMyRecommendations` is the library-scoped personalized search** (`assistant/tools/recommendations.ts`): ANN joined to `recommendation_candidates` for the newest **completed** run, re-ranked by `blendQueryAndTaste`. The join restricts to titles scored for this user *and* applies the watched exclusion for free. Rules: both terms are **min-max normalised over the fetched pool before blending, never raw** (cosine sits in a narrow band — see the cosine invariant); `QUERY_WEIGHT` is 0.6 so the request leads and taste breaks ties; `ANN_POOL_SIZE` (400) is fetched before the join and needs the `ef_search` treatment. **Search results carry no `rank`** — `recommendation_candidates.rank` is the position among everything scored, and `ContentCard` renders any `rank` as a poster RankBadge; only `getMyRecommendations` sets one, from `selected_rank`. It must call `enrichCardReasons` or cards lose their "why". **Discovery stays primary for open recommendation requests**; this is the library-scoped answer plus discovery's in-library fallback, mandatory below 8 resolved cards. A new tool also needs a `TOOL_PHASES` entry and a line in `prompts/rules/tools.ts`. [F-007](docs/aperture-forensics.md#f-007)
- **The taste brief personalises SELECTION, never RETRIEVAL.** `discovery/tasteBrief.ts` builds a profile that `discoveryResolve` hands to `gatherWebCandidates`, applied only in the **structuring pass** (`webCandidates.ts` `viewerBlock`), which has no search tool — so it can reorder and tie-break but cannot bend what was looked up. **The profile must never reach a search call**; `WebSearchSource.gather` takes **only the query** and `WebSearchContext` is deleted, because the boundary has to be the type signature — a prompt rule was tried and leaked the user's favourite films into twelve grounding queries. Precedence line stays: it may order candidates, never add, drop or re-justify them. **Tavily deliberately ignores it** (a keyword API, not a model) but does get a reasoning cue appended to the request, since its `answer` is LLM-written and there is no separate answer prompt; hence `include_answer: 'advanced'` and a **separate char budget** from `maxContentChars`. Titles are signature ones, **grouped by title** because a `watch_history` row is an *episode*. `personalized: true` in the log means only that a brief was built and will be applied at structuring. Open: the empty-text retry inside `googleGrounding`'s `PASS1_MAX_ATTEMPTS` loop is **not metered** — it sits inside one key attempt, so a retry makes two requests Google counts and writes one usage row. [F-008](docs/aperture-forensics.md#f-008)
- **The intent router decides whether the web search exists at all.** `helpers/routeIntent.ts` classifies each turn `discovery` or `library`, and `findCandidatesInLibrary` — the only tool that searches the web or writes card `reason`s — is added *only* on discovery turns. A misroute is a different engine, not a degraded answer. **A request for titles to watch is `discovery` even when personalized**; `library` means the answer is *facts about their collection*. Four rules: `prefilterIntent` is pure, exported and pinned, and a match there is final, so `RECOMMENDATION_HINTS` is checked first and wins outright; ambiguity resolves toward **discovery** (it suppresses only three list builders and keeps history/ratings/stats, so it is nearly the superset); the **error** path falls back to `library` deliberately; and a library-routed model reaching for `getWatchHistory` produces watched titles even with `excludeWatched` on, since it is in `EXEMPT_TOOLS`. [F-009](docs/aperture-forensics.md#f-009)
- **Watch history is queryable by content, not just recency.** `getWatchHistory` takes only `type` + `limit`, so intersection questions ("the French noir I watched") need the search tools. `watchStatus: 'all'|'watched'|'unwatched'` (`watchStatusCondition` in `tools/search.ts`) is on both search tools; on the semantic path it needs the `ef_search` treatment. `ContentItem.watched` is stamped by `annotateWatchedItems` and is **absent when not looked up** — the card branches on `=== true`. `withUnwatchedFilter` skips a call whose `input.watchStatus === 'watched'`, decided **per call**; only `'watched'` overrides, since `'all'` is the model's default rather than a user intent. `director`/`tag` must use `directors::text ILIKE $n` — `$n ILIKE ANY(directors)` is backwards (in `a ILIKE b` the *right* side is the pattern) and matches nothing. [F-010](docs/aperture-forensics.md#f-010)
- **There is no `language` filter, and that is deliberate**: `languages` is populated for 0.7% of movies (OMDb-only, written in two places in `enrichment/index.ts`), while `production_countries` is 99.4% populated from the media-server sync. Use **country**. `query` matches literal text in `title`/`overview` and is **not** a concept search — style goes to `semanticSearch(concept)`, fact goes to filters (almost no noir has "noir" in its title or synopsis, and there is no Film Noir genre). `semanticSearch` takes `country` for this reason, through the same `ef_search` path. Demonyms are mapped by `helpers/countryMatch.ts` (~120 nationalities → the stored name), because `production_countries` stores *"France"* while users say *"French"*; its values are deliberately **substrings** so one entry covers variants (`Germany` matches "West Germany"), and unknown input passes through unchanged. [F-011](docs/aperture-forensics.md#f-011)
- **A step is a model round trip, and the last one is wasted without a guard.** `stopWhen: stepCountIs(MAX_STEPS)` is consulted only *after* a step that called tools, so the final step's results reach the UI but never reach the model — a turn that spent every step searching ended with **no prose at all**. `prepareStep` forces `toolChoice: 'none'` on the last step (`stepNumber` is 0-indexed), which costs **no retrieval** because that step was already dead. Raising `MAX_STEPS` costs nothing on healthy turns but each step resends the system prompt *plus all accumulated tool results*, so cost grows superlinearly within a turn; raising it alone fixes nothing — the guard is what makes a higher ceiling safe. Hitting it logs `warn` "Step budget exhausted", which is a signal about the *tools*. [F-012](docs/aperture-forensics.md#f-012)
- **`semanticSearch` has no distance floor**, so its headings must not vouch for the results: they say *"Movies closest to …"* / *"The {{count}} nearest titles in your library"*, never *"matching"*. A cutoff was **deliberately not added** — see the cosine invariant; the query→item distribution has to be measured first. - **Mean-centred embeddings** (`embedding_centered`, `0154`). Every canonical text shares a register, so a large part of every cosine measures that; subtracting the library mean removes it (measured ndcg@100 20.5% → 31.9%). Five rules. (1) It is a **stored column, not a `- mean` term at each call site**, so a new query cannot forget it. (2) The mean is therefore **never stored or looked up at query time** — a profile built from the centred column is already centred. (3) **No index, deliberately** — the recommender uses a LIMIT above table size, so the planner abandons HNSW anyway. (4) A profile records its own space (`user_taste_profiles.embedding_space`); `resolveEmbeddingSpace` **refuses** (returns null, run finalizes `failed`) rather than falling back, because comparing a raw centroid against centred items is a confident number that means nothing. `buildSpaceFor` and `resolveEmbeddingSpace` are separate functions with a test pinning that anything built now is immediately servable. (5) **`isCenteringReady` is all-or-nothing** and the refresh is ONE statement — a half-filled column silently shrinks the candidate pool, and a batched refresh leaves rows centred against different means. **The interest ANN paths stay raw in both pipelines**, as do `storeEvidence` and the similarity graph: their query vector is a fresh embedding of interest *text*, which nothing centred. A raw profile stays raw until `rebuild-taste-profiles` moves it, which is the entire rollback. (6) **The rows are normalised before the mean is taken and before it is subtracted** — every other vector op here is cosine and magnitude-invariant, but centring is a *subtraction*, where `AVG` skews toward long vectors and a common mean rotates each row by a different amount, yielding wrong **directions** rather than wrong scale. `storeEmbeddings` normalises nothing, so this is load-bearing the moment vectors are not unit-length: for any one model all but one valid dimension is an MRL truncation, and some providers never return unit vectors at **any** width (`pplx-embed-v1-4b` is served int8-quantised and documented as unnormalised at its own native 2560). It is **inert on gemini-embedding-001 at native 3072** (measured norms 0.999930–1.000079) — which is exactly why it looks deletable and must not be deleted. (7) **Centring runs automatically at the end of both embedding jobs** (`centreAfterGeneration`, inside the job because each owns its own progress and calls `completeJob` itself), gated by the pure, pinned `centeringNeeded({ generated, ready, rows, centredRows })`. It was manual-only with nothing chaining it, so any sync that embedded a new film left `embedding_centered` NULL and every centred profile refusing — visible only as staleness, since a failed run leaves the previous completed one live. The gate is load-bearing: both jobs run on a **6-hour interval**, so unconditional would rewrite ~77 MB to identical values four times a day; the `!ready` half is what makes a failed centring self-healing. **A third condition catches rows LEAVING**: every embedding table is `ON DELETE CASCADE` from `movies`/`series`, so a title dropped from the media server takes its vector with it and leaves no NULL — `generated` 0 and `ready` true, while the mean still counts the departed films. The live row count is compared against the count at the last successful centring (`system_settings.embedding_centering_state`, keyed by media type **and model**, written inside `refreshCenteredEmbeddings` so the manual job records it too); an **unknown** previous count reads as needing work. **`refresh-embedding-centering` is manual-only and must stay that way** — it is the remedy for a column that is *populated but wrong* (a bad mean has no NULL to repair and reads as ready), not for routine drift, and scheduling it would both reinstate the timed full-table rewrite the gate exists to prevent and multiply the profile drift below. It never rethrows (the embeddings are good; the next pass retries). One copy in `centering.ts`, not mirrored per pipeline. Episodes have no centred column, so the series job centres series only. `refresh-embedding-centering` stays for a manual sweep. - **A centroid is a sum, and only the sum cares about magnitude.** All 31 `<=>` comparisons are cosine, which is why nothing normalizes on write; the taste vector is the sole place vectors are *summed* — `buildWeightedAverageEmbedding` (`taste-profile/builder.ts`) and its twin `weightedMeanEmbedding` (`clustering.ts`). Summing raw makes a title's influence `weight × ‖v‖`, multiplying `calculateEngagementWeight`'s whole ladder by a per-title factor; the trailing L2 normalize does **not** fix it (it rescales the finished mean). **Inert at a model's native dimension and only there** — 7 of 8 `VALID_EMBEDDING_DIMENSIONS` are MRL truncations, where Google requires manual normalization. `l2Normalize` is exported and **shared** by both paths (was a third copy): `clustering.test.ts` asserts K=1 is **bit**-identical to `buildTasteProfile`, and float multiply is not associative, so both sites must do the same operations in the same order. The guard is a **pair** of tests — scaling an item's vector must not move the centroid, *and* doubling its weight must; the first alone passes if weights are ignored. Costs a `rebuild-taste-profiles`, never a re-embed. [F-037](docs/aperture-forensics.md#f-037)
- **Changing the embeddings model deletes nothing, and the panel has to say so.** Rows are keyed `UNIQUE(<item>_id, model)` per dimension table and **every** read filters `WHERE model = $n`, so a model change starts a new set beside the old one and switching back reuses it — the staleness join carries `AND e.model = $1`, so old rows count as present. Deletion is only ever the two explicit admin routes. `lib/embeddingSets.ts` (`getEmbeddingSetsReport`) is what makes that visible. Six rules. (1) Readiness is measured with **`MOVIE_STALE_SQL`/`SERIES_STALE_SQL` imported, never re-expressed** — a set can be fully populated and still need rebuilding when `CANONICAL_TEXT_VERSION` moves, so a row count is not an answer. (2) **`decideStatus` is pure, exported and pinned**; an unmeasured set is `unknown`, **never `ready`** (asymmetric failure — "ready" wrongly promises a free switch), and `empty` outranks the null check. (3) Totals are the **embeddable** population, mirroring the job's `library_config` branch, or an instance with disabled libraries reads as permanently incomplete. (4) **Episode pending is missing-only and reads the setting** — episodes are outside the `text_version` scheme and their tables have no `text_version`/`updated_at`; with generation off, pending is genuinely 0. (5) Keyed on **(model, dimension)**, since a custom model's dimensions can be edited after embedding; `DELETE …/sets/:model` takes an optional `dimensions` querystring, **declared in the schema so Fastify coerces it**. (6) Status ships as a **decided value** (web-never-imports-core), and the panel carries the post-switch sequence — embeddings → centering → **`rebuild-taste-profiles`** → recommendations — because moving item vectors does not move a stored centroid and `isProfileStale` will not notice for up to 30 days. (7) Two dates, unequally trustworthy: `firstGeneratedAt` (`MIN(created_at)`, survives upsert) is solid; `lastGeneratedAt` reads `updated_at` for movies/series and `created_at` for episodes, and since `0138` added `updated_at` as `NOT NULL DEFAULT NOW()`, an untouched old row **reports the migration's timestamp** — a floor, not a lie. - **Embedding retrieval mode is reachable through OpenRouter, and this file said the opposite until 2026-08-28.** `input_type` and `dimensions` are both in OpenRouter's embeddings schema, and `@openrouter/ai-sdk-provider`'s `extraBody` is spread verbatim into the request body — so it is a settings argument, not a fork. Measured on one document: for `gemini-embedding-001` the **default output space IS `RETRIEVAL_QUERY`** — `search_query` returns the byte-identical vector to sending nothing, while `semantic_similarity` (**0.860**) and `search_document` (**0.910**) are each a genuinely different space, so every vector this app has ever stored is in the *query* space. That identity means "the default is this mode", **not** "the field was ignored", and the two readings are separated by evidence rather than by preference: on the same call the other two values do move the vector, so the field is provably read. Where *no* value moves it — gemini-2 — "ignored" is the only supportable reading. An earlier single-sample pass recorded all three as byte-identical and was wrong about `search_document`; for `gemini-embedding-2` `input_type` is a **no-op** — `semantic_similarity` returns the byte-identical vector to sending nothing, which means the parameter is ignored, NOT that the default is already semantic (the same identity pattern reads as "ignored" for 001's two retrieval values, and must read the same way here). Gemini-2 dropped `task_type`; its real mechanism is a **text prefix** on the document (`task: sentence similarity | query: …`), measured at cosine **0.811** from bare text, and verified byte-identical between OpenRouter and Google's native API on both bare and prefixed input — so OpenRouter is a faithful pipe. **Both mechanisms are now implemented and the model declares which one it reads** (`inputTypeMechanism`/`inputTypePrefixes` in the catalog; `resolveInputTypeDelivery` is the pure decision, pinned). Exactly one path is taken — a prefix-conditioned model is sent no parameter. Only *verified* prefixes ship: Google documents an asymmetric `title: … | text: …` form this app has never measured, so asking for it is a **400**, not a silent fallback. This library's task is symmetric (item↔item, and a taste centroid is a mean of item vectors), so `semantic_similarity` is the mode it wants, and every vector currently stored was embedded without it. **A parameter mode on OpenRouter REQUIRES a pinned upstream.** Measured on 001: `google-vertex` honours `input_type` (cosine 0.841 from unmoded), `google-ai-studio` drops it and returns the unmoded vector — each deterministic alone, a coin flip together, so unpinned it writes a mixture of two spaces into one set. `requiresProviderPin` refuses that combination at the settings route and the Save button, since no later step can repair such a set. The pin therefore **rides in the identity whenever a mode is set**, and is *not* conditioned on the delivery mechanism — `embeddingSetId` takes the config and nothing else. It briefly took the mechanism as an optional second argument so the pin could join for a parameter mode only; `getEmbeddingInvocation` passed it and the **sixteen readers** (staleness selections and counts, the recommender's `WHERE model = $n`, the centering refresh, the sets report) did not, so rows were written under one id and looked for under another — a library **permanently empty and permanently pending at once**, re-embedding and re-paying for all 12,584 movies every run, with nothing thrown. An optional argument that changes the answer is the defect. The provider rules live inside the function for the same reason (a mode is dropped for a provider that cannot send one, a pin for a provider with no routing), so writer and readers agree structurally instead of because the settings route filtered the config first. A pin with **no** mode still returns the bare `provider:model` — sound because both upstreams agree on the unmoded vector, and it is what leaves every already-stored row unchanged. **gemini-2 needs no pin**: its mode conditions the *text*, so every upstream gets a different input and cannot drop it. **One call per configuration cannot tell "these differ" from "this endpoint is nondeterministic"** — three mechanisms were confidently proposed here from single samples before repeating settled it. `ProviderConfig.embeddingInputType` carries it; `google` takes the same three modes as native `taskType` through `providerOptions` (**per call**, unlike OpenRouter's, which is baked into the model instance — hence `getEmbeddingInvocation` returns a model *and* options). **`dimensions` is deliberately not plumbed**: 7 of 8 valid dimensions are MRL truncations needing renormalisation `storeEmbeddings` does not do. **OpenRouter ships built-in models for `embeddings` ONLY** — its chat/text/exploration lists stay empty because it is a `CUSTOM_MODEL_PROVIDERS` member and that catalog is thousands of entries, but the *embedding* catalog is a handful, and an empty list meant hand-registering a model before the feature worked at all. Entries carry **no static price** (no `openrouter` table in `pricing-cache.ts`, so a number there would be the only source and would drift); `getModelsForFunctionWithCustom` enriches built-ins from the live catalog and **dedupes a custom row with the same id**, built-in winning, matching `getCurrentEmbeddingDimensions`' existing precedence. The declared `embeddingDimensions` **picks the table**, so editing one repoints every read at a different `embeddings_<n>` and the library looks emptied — pinned by `embeddingCatalog.test.ts`. The old traps still hold — **modes are different vector spaces**, so all **six** call sites must agree (library `embedMany` ×2, `embedText()`, `semanticSearch`'s query, the custom-interest re-embed, the assistant's `ToolContext`) — but the staleness trap is now handled structurally: the mode rides in the set identity, so a change starts an empty new set rather than needing a `CANONICAL_TEXT_VERSION` bump. - **The embedding set identity is one function, because two modes of one model collide.** Rows are keyed `UNIQUE(<item>_id, model)` and every read filters `WHERE model = $n`, so `${provider}:${model}` built inline in **nineteen places** meant a semantic-mode pass would `ON CONFLICT DO UPDATE` straight over the default-mode set — destroying the control it was meant to be compared against, silently. `lib/embeddingIdentity.ts` is the one home (`embeddingSetId`, pure, pinned). Seven rules. (1) **No mode must yield the byte-identical legacy string** — any decoration makes every existing row invisible to the staleness join and to the recommender; a cleared settings field arrives as `''`, not `undefined`. (2) The separator is **`~`**: `:` and `/` are already inside model ids (`:free` variants), and `#` would be silently truncated by any caller forgetting `encodeURIComponent` on the delete route's path segment — addressing the wrong set's vectors for deletion. (3) An **unrecognised mode is dropped, never forwarded** (OpenRouter's field is an unconstrained string, so a typo would be accepted, ignored, and then stored in an identity claiming a space nothing was embedded in). (4) A **provider that cannot send a mode may not store one** — the settings route 400s rather than storing it. (5) **`getEmbeddingModelInstance` is replaced, not wrapped**, by `getEmbeddingInvocation` returning `{ model, providerOptions, setId, inputType }`, so every call site is a compile error until looked at — that is how the two sites outside `packages/core` were found. (6) The set id **travels on the row** (`EmbeddingResult.setId`, `map` not `Array.fill`), so there is no second place for it to be decided. (7) The assistant's `ToolContext` holds **one `embedding` bundle**, not a model plus an id resolved separately. Switching the mode costs embeddings → centring → **`rebuild-taste-profiles`** → recommendations. (8) **Nothing may call the AI SDK `embed`/`embedMany` except `getEmbeddingInvocation`**, which returns `embedOne`/`embedBatch` with the task prefix already applied — a raw-text call produces a right-width, unit-norm, plausible-looking vector in the wrong space, which is undetectable downstream and is not a type error. Pinned by `novelty.test.ts`. [F-055](docs/aperture-forensics.md#f-055)
- **Diversity is MMR now, not a coverage sort.** The old selector blended `finalScore` against `1 − (genres covered / genres on this title)` with a plain `Set.has`, so one Drama closed Drama for the rest of the list; measured, `finalScore` spans **0.08** across the whole contender set against a diversity term spanning the full 0–1, so at `w = 0.2` genre coverage decided everything and picks overlapped heavily between users (genre coverage is a property of the *library*, not a person). Replaced by **`shared/mmr.ts`**: `(1 − w)·relevance − w·gain·max sim(d, selected)`. Four rules. (1) **`gain` = relevance spread / redundancy spread**, measured over the shortlist before selection, clamped `[0.25, 40]`, and 1 when either spread is unmeasurable. (2) It reranks a **shortlist** (`mmrPoolSize`, 15 per slot, floor 150), which is what stops a rank-3000 title taking a slot and keeps the embedding fetch to a few hundred vectors. (3) **`variety` is measured against the FINISHED list**, not incrementally — scored as it goes, the top pick reads 1.0 every time for having had nothing to differ from. (4) A title with no embedding answers **0 redundancy** and competes on relevance alone. Series **network diversity is gone** with the genre term (a series' canonical text already carries its network). Both selectors are async now; `mmr.test.ts` pins the live-shaped regression. [F-056](docs/aperture-forensics.md#f-056)
- **The evaluation harness is deliberately two instruments** (`core/src/evaluation/`, job `evaluate-recommender`, manual-only, reads only). **`neighbours.ts` is PRIMARY**: a title's ten nearest neighbours, raw and mean-centred side by side, with **country in a column** — six of the fifteen `buildCanonicalText` fields are nationality-coded, so a nationality detector shows up immediately, and `countryConcentration` makes that a number. **`metrics.ts` is a GUARD RAIL, never a target** — every metric there can only reward more of what someone already engaged with, so novelty and diversity score worse on them *correctly*, and tuning to maximise one builds the recommender nobody wants. Five rules. (1) Relevance is **graded, not asserted** (bailed = 0, finished/rewatched = 1, bookmark = 0.3), and `SKEPTICAL_RELEVANCE_WEIGHTS` re-runs barely believing favourites — **a conclusion that flips between the two weightings is an artifact and gets thrown away**. (2) The holdout is a **per-viewer count, never a shared cutoff date**, and most-recent rather than random (random leaks — hiding one film of a binge is near-duplicate lookup). (3) Aggregation is **macro, one vote per viewer**, per-viewer rows always printed, bucketed by history size. (4) **Random and rating-only baselines run through the same harness.** (5) Scope is **retrieval only**. `loadLibraryMatrix` holds the table in one normalised `Float32Array`; `meanCenter` carries **the mean it subtracted**, because a query centred with the mean of an already-centred matrix lands in a different space and still returns a confident ranking. (6) **It measures every stored embedding set, not the active one** — `loadLibraryMatrix` takes an optional `{ modelId, dimensions }` (the dimension names the table), the executor enumerates sets with rows, and the matrix carries its own `modelId` so a report can name what it measured. That is how one library answers for two models; the splits are rebuilt per set but `splitHoldout` is deterministic, so the answer key is identical. **Compare `poolSize` first** — a half-embedded set is a smaller pool and reads BETTER on percentile and deep-cutoff ndcg, so the worse model can win; the executor warns when sets differ. (7) **Seeds come from `system_settings.evaluation_seed_titles`** (newline-separated, SQL-only). The default is `popularSeedIds`, which is exactly where two models agree — a canonical, heavily-written-about film is the easy case for both — so the discriminating seeds (obscure, stylistic, non-English) must be set explicitly or the PRIMARY instrument cannot answer a model comparison. `resolveSeedIds` wraps titles in `unaccent()`, since nobody types the accent. A seed that resolves but has no vector in *this* set is logged, because a seed appearing in one dump and not the other reads as the models disagreeing rather than as missing data. [F-057](docs/aperture-forensics.md#f-057), [F-092](docs/aperture-forensics.md#f-092)
- **The evaluation report does not fit in the job log, and the part it loses is the comparison.** ~450 entries per embedding set (14 seeds × 2 variants is 392 of them) against a 500 live / 300 stored window that keeps a head plus a tail — so a two-set run, the only kind that answers anything, drops one summary table every time and leaves one set's table sitting above **another set's** neighbour dump. Three consequences. (1) `logNeighbours` puts `raw.modelId` on its heading; an unlabelled dump reads as coherent when it is not. (2) The executor **re-emits every set's figures after the loop**, numbered per row — the tail is the half that survives, so that is where a comparison has to live. (3) Figures and dumps are archived (`0156`) and exported as CSV from Admin → Recommendations → Evaluation; the write is **swallowed on failure**, since forty minutes of measurement has already happened. Storage is a table rather than a file because a container file dies on the next recreate — which is exactly when the measured change gets deployed — and because merging runs across models is then a query. **Nothing prunes**, deliberately. CSV rendering is `evaluation/csv.ts`, DB-free and pinned: a **UTF-8 BOM** (Excel on Windows otherwise mojibakes every accented title) and a formula guard applied to strings only, with a **numeric-text exclusion that is load-bearing** — NUMERIC arrives as text, so a negative cosine takes the string path, and defusing its leading minus would turn the whole column into text. [F-094](docs/aperture-forensics.md#f-094)
- **Novelty outputs the full [0,1] band.** Influence is **weight share × realized spread**, so a term confined to a narrow band hands most of its configured weight back: novelty ran [0.47, 0.84] and delivered **2.1–4.5%** of actual movement against a configured 8.1%. The stretch preserves the curve's **proportions exactly** (pinned by `novelty.test.ts`) — a scale change, not a redesign of what novelty rewards — and it retires the `scale 47–84%` caption, which the panel now suppresses when the band is full (the check stays, since a retune could narrow it again). **The spreads say which term deserves which instrument**: rating's shortfall is identical for every user, so a *fixed* gain is right; novelty's varies **2.2×** between users, so it needs a *bounded adaptive* one; similarity is already pool-adaptive — do not touch it. **Do not blanket z-score all three** — similarity's compression is an artifact of the embedding cone, but novelty's and rating's are often real information. A stored `novelty_score` from before this is on the old scale, so its bar fills differently until the next regenerate. [F-058](docs/aperture-forensics.md#f-058)
- **The spread correction goes on the WEIGHT, not the component**, which is what keeps "Quality 82%" meaning IMDb 8.2. `effectiveBlendWeights` (`shared/scoring.ts`) multiplies each configured weight by a gain for how much range its term uses. The two directions are mathematically identical (`w/spread × value` orders as `w × value/spread`) but only this one leaves the on-screen numbers alone. Six things. (1) **`TARGET_COMPONENT_SPREAD` (0.57) is not a tuning knob** — `normalizeSimilarity` produces it by construction, so similarity is the term already on scale and the other two are corrected **onto** it; it never gets a gain itself, or `normalizeSimilarity` is double-counted. (2) **Rating gets a fixed gain (`0.57/0.46` = 1.239), novelty a per-run one** — measurement decides which. (3) The novelty gain is **clamped to [0.7, 1.5]** as a guard rail against a pool with almost no novelty signal handing the ranking to noise; a spread of zero returns **1.0**, not infinity. (4) **Two passes, not one**, in both scorers — the gain is a property of the pool, so `scoreCandidates`/`scoreSeriesCandidates` return `{ candidates, weights }`. (5) **`finalizeRun` stores the EFFECTIVE weights** — that is what `0147`'s column means, and storing configured ones would leave the panel multiplying numbers that do not reproduce the match. (6) `0150` widens them `NUMERIC(3,2)` → `NUMERIC(6,4)`, because `0.25 × 1.2391` stores as **0.31** at two decimals; **no backfill is possible**, since the gain depends on a candidate pool that no longer exists. `SCORE-DIAG` logs both `weights` and `effectiveWeights`. [F-059](docs/aperture-forensics.md#f-059)
- **Re-normalising similarity inside the selection band was simulated on live data and REJECTED.** The premise is real — similarity's realised spread collapses to 0.028 across the top 50 against a pool-wide 0.57 — but renormalising one term of three hands it the whole ranking: realised influence goes to **93.6 / 2.2 / 4.3** against a configured 70.4 / 8.1 / 21.4, quality stops filtering, and 10–13 of every user's 20 picks change (*Blade Runner 2049*, *Interstellar*, *The Prestige* out; *Renfield*, *Underwater*, *Hotel Artemis* in — the dense mass of generic titles nearest a centroid once nothing can outvote proximity). **Leave the compression alone.** The only sound version re-normalises **all three** terms onto one target spread over the same band, which is a different and larger change, unmeasured, and not worth attempting without first showing the top-band ordering is actually wrong rather than merely flat. [F-060](docs/aperture-forensics.md#f-060)
- **The explanation prompt must carry enough to build a reason from.** It used to give the pick's title, year, genres and 250 chars of its own synopsis plus the **bare titles** of three neighbours — so any specific connection was the model's pretrained knowledge, fine for canonical cinema and silently unfounded otherwise. Now (`shared/explanationPrompt.ts`, shared so the two generators cannot drift): evidence rows carry **`overview`**, the pick's plot budget is 600. **`plot_full` is deliberately not used** despite being longer — it is IMDb's synopsis and routinely gives away the ending. **`keywords` and `directors` reach the prompt**, keywords being where a style is actually written down. **The raw cosine percentages on each evidence line are gone** — they sit in a band a few points wide, so 74 vs 69 reads as a grade while carrying almost nothing; order is preserved and labelled *nearest first*. Plus a **no-invention rule** (obscure titles expected; state no awards, reception, festival history or production trivia not in the data) and *"be specific rather than superlative"* in place of *"create excitement"*. `clip()` replaced `substring(n) + '...'`, which appended an ellipsis unconditionally — a complete synopsis presented as trailing off invites continuation. `getUserTasteContext` in both generators is now gated on `WATCH_HISTORY_TASTE_SQL`. [F-061](docs/aperture-forensics.md#f-061)
- **The evidence lookup gets its own history pool.** Both pipelines used to hand `storeEvidence` the same `recentWatchLimit` (default **50**) list the taste vector was built from — right for a centroid, wrong for a nearest-neighbour lookup, so for a 3,510-film viewer it searched **1.4%** of their history and the explanation model reasoned from whatever that returned. Now `EVIDENCE_HISTORY_LIMIT` (5000, `shared/evidencePool.ts`), favourites-first so a viewer past the cap loses their least-engaged tail. **Do not "simplify" it by joining `watch_history` inside the LATERAL** — an explicit id list keeps the planner on a filtered scan, whereas a join predicate beside `ORDER BY embedding <=> …` lets it pick HNSW and post-filter, and the `LIMIT 3` comes back empty (see the `ef_search` invariant). [F-062](docs/aperture-forensics.md#f-062)
- **Grounding quota is far smaller than the docs imply, and the model ceiling is not the ceiling that stops you.** `webSearch` is the only role spending Google grounded search. **Search grounding is a separate quota from the model's own, charged per model *family*, and the whole Gemini 3.x family gets `0` on the free tier** — so `gemini-3.5-flash-lite` cannot ground at all, while `gemini-2.5-flash` grounds inside a 1,500/day family allowance it can never reach because the *model* caps it at **20/day, 5 RPM**. Nastier still, `gemini-2.5-flash-lite` is no longer offered to new Google projects. `google.json`'s per-model descriptions carry this. That is what makes **`ProviderConfig.fallbackApiKeys`** load-bearing: a second key from a second **Google project** turns 20 into 40, since keys inside one project share quota. Slots are `primary`/`fallback`/`fallback2`… (the legacy scalar `fallbackApiKey` is still read, never written), dedupe drops a fallback repeating the primary, and cooldowns key on **role + slot**. The limits table applies **only when the operator ticks "these keys are on the free tier"** (`isFreeTierConfig` — absent means free, only an explicit `false` opts out) and is **subordinate to observation**: `resolveModelLimits` overlays anything a real 429 disclosed **field by field**, so a wrong default survives only until the account contradicts it, and `source` (`observed`/`freeTier`/`mixed`) rides to the panel. Observed limits apply whatever the checkbox says. Nothing throttles on any of this — rotation is driven by real 429s. Traps pinned by `webSearchQuota.test.ts`: a **token** quota also reads as PerMinute; a **grounding** refusal is also a per-day request limit (`limitIsGrounding`); an **unattributed** limit is dropped rather than guessed; **`groundingRpd: 0` is a real answer — test `!= null`, never truthily**; the family prefix match takes the **longest** hit; and `getFreeTierLimits` returns a **copy**. The observed store is in memory like the cooldowns. [F-063](docs/aperture-forensics.md#f-063)
- **Title analysis is title-scoped; the recommendation explanation is user-scoped; merging them would poison the explanation.** `analysis/` writes a critic-informed account of *the work*, cached in `title_analysis` forever and shared by every user. **Where its sources come from is a setting** (`analysis/mode.ts`): `crw` (default) retrieves **before** the model is called via fastCRW `/v1/search` + `scrapeOptions`, and the `titleAnalysis` role writes from that text; `grounding` has a Gemini model search for itself, which is metered per Google project (a few dozen titles, not a library) and Google-only. `checkModeReadiness` runs inside **`analyseTitle`** — the choke point every path goes through — *and* as a pre-flight in the job, because a guard only the settings page calls is a comment. Rules that matter when editing this: **questions, not a directive** (specific unanswered questions produce short honest output; "analyse this film" finds meditations on grief in an action programmer); **prompt order is subject → documents → task/rules**, since retrieved markdown is untrusted text; **`analyseTitle` throws on anything possibly systemic and only stores a decline it believes** (zero results, or zero chunks in grounding mode, throw — a decline is **stored** and retires the title until `ANALYSIS_PROMPT_VERSION` moves, currently **5**); the job attempts **each row at most once per run**, or the drain loop spins forever on its own failures; `CONSECUTIVE_FAILURE_LIMIT` (5) aborts a failure storm that would otherwise burn the whole budget in seconds and log success; the answer is fenced at **both** ends (`ANALYSIS_BEGIN_MARKER`) so a reasoning preamble is discarded **structurally** — a missing marker, missing grade or `finishReason === 'length'` **throws rather than declining**, since that is a fact about the model, not the title; `analysisMaxOutputTokens` (default 8,000, **0 = no ceiling**) belongs far above any real answer, with length shaped in the prompt instead; and the engine list (`CrwConfig.searchEngines`, default `google, duckduckgo, bing`) is a **cascade, one request each** — passing several to one CRW call is N× latency, not a fallback, and `sanitizeSearchEngines` never falls back to empty because empty means CRW uses Google alone. `title_analysis.retrieval_mode` records which mode wrote each row. `POST …?force=true` is admin-only and is the only route a **declined** row has. [F-064](docs/aperture-forensics.md#f-064)
- **Log AI failures through `describeAiError`** (core `lib/aiErrors.ts`), never a bare `{ err }`. `APICallError` declares `url` and `requestBodyValues` **before** `statusCode` and `responseBody`, and pino's serializer copies enumerable own properties in declaration order — so the whole ~16 KB prompt lands ahead of the only two fields that say what went wrong. It records status, retryability, model id, provider URL and the response body clipped to 400 chars, and **deliberately drops the request body** (unreadable, reconstructible, and the one field that could carry user content into a log). It unwraps `RetryError` explicitly, or the status is lost on exactly the calls that tried hardest. **`isProviderError` is a separate field from `status`** — a dropped connection is a provider failure carrying no status, so never infer "not the model" from a missing one. Applied at the analysis writer, the analysis route and `recordLlmError`. Worth knowing: a `:free` OpenRouter variant usually has exactly **one** upstream endpoint and no fallback, so `GET /api/v1/models/:slug/endpoints` is the fastest way to tell a withdrawn model from a broken config. [F-065](docs/aperture-forensics.md#f-065)
- **A free-tier model has two failure modes no retry can reach, and they need different answers**: a spare **key** answers "this account is out of quota", a spare **model** answers "this model is gone". Both live on the role's `ProviderConfig` (JSON in `system_settings.ai_config`, no migration) and are offered by one card only, gated on `AIFunctionCard`'s `supportsFallbackModels`, because `analysis/generate.ts` is the only consumer. (1) **`fallbackModels` carries a provider per entry**, so a cloud role can fall back to a local server; credentials resolve per provider at attempt time. (2) Attempts are **constructed up front** (`getTitleAnalysisModelAttempts`) — discovering a credential-less fallback halfway through a library pass is the worst possible time. (3) **Rotates on** any provider failure *and* on a contract break once that model has spent `MAX_WRITE_ATTEMPTS`. (4) **A truncation deliberately does NOT rotate** — it names a *setting* every model would hit identically, so rotating reports the wrong culprit. (5) Pacing is **one stored number, `callSpacingSeconds`, with the checkbox derived from `> 0`**, and it is **absent-means-OFF** — the exact opposite of `freeTier`, deliberately, because this one *delays real work*. (6) The gate (`lib/callPacing.ts`) is a **reservation, not a last-call timestamp** (two callers in the same millisecond would otherwise both wait the same amount and fire together), keyed on the **provider** since the limit belongs to the account, and sits before **every** request including write retries. Cancellation is polled *inside* the wait, and the wait is announced to the job console first. A backwards clock is caught by comparing against the reading that *issued* the reservation. (7) **Grounding mode paces but does not rotate models** — its characteristic failure is a spent daily quota, which `withGroundingModel` answers by rotating keys. [F-066](docs/aperture-forensics.md#f-066)
- **A per-user score averaged across users can show a trend that exists in no user** — see the per-user invariant above. [F-067](docs/aperture-forensics.md#f-067)
- **`maxCandidates` cannot usefully exceed the table it queries.** Retrieval is one `ORDER BY embedding <=> $1 LIMIT n` over *one* embedding table, so n above the row count returns no more titles and merely stops the planner using HNSW. Both sliders shipped above their tables (16K vs 12,584 movies; 50K vs ~1k series — set on the false belief that series retrieval is episode-level; `series_embeddings` is one vector per show). The web slider's max is the live count from `getLibraryItemCounts()`, the PATCH handlers cap it, and both syncs call `clampMaxCandidatesToLibrary()`. **That clamp writes `UPDATE` directly rather than through `updateConfigFor`**, because `maxCandidates` is in `SCORING_FIELDS` and the normal setter would bump `scoring_updated_at` and regenerate every user for a change that cannot alter a pick. It only ever lowers. [F-068](docs/aperture-forensics.md#f-068)
- **A vote count is a sound GATE and a worthless SCORE, and the direction is counterintuitive.** `calculateRatingScore(rating)` never sees `imdb_vote_count`. The obvious fix — Bayesian shrinkage toward the library mean — was measured and is **backwards here**: thin-voted titles average **5.95** against a library mean of 6.52, so shrinking would *raise* 2,294 obscure poorly-rated films, and only 8 films rated ≥8.0 sit under 1,000 votes at all. Vote count correlates *positively* with rating here, so as a score term it is a popularity proxy. As an *eligibility* test it is exactly right, which is what `isAcclaimed` uses it for. Same shape as idf in `twinAffinity.ts`. [F-069](docs/aperture-forensics.md#f-069)
- **Acclaimed slots are the third claimant on `selectedCount`** (`shared/acclaimedSlots.ts`, `0152`, **default 0 = off**). Why a slot and not a weight: similarity outvotes rating ~5:1, and solving for the flip needs `w_rating > 0.60` — over half the blend, applied to every pick, to rescue a handful. Three rules. (1) Fillers are ordered by the viewer's own `finalScore`, **never by rating** — an acclaim-ordered list hands every user the same titles, which is the failure this exists to answer. (2) It is measured **last**, against `selectedCount − interests − twins`, so the three features cannot over-reserve (swept in `acclaimedSlots.test.ts`). (3) It needs its own `fromAcclaimed` flag, a `CRITICAL:` prompt rule and a non-AI fallback in **both** generators, plus `acclaimedMatch` in `MovieInsights`' `fromReservedSlot` and a fourth `pickSource` value. [F-070](docs/aperture-forensics.md#f-070)
- **The preference nudge is a setting, not a constant.** `applyPreferenceAdjustment` moves a blended score toward 1.0 by a share of the *remaining* gap, scaled by franchise/genre/interest affinity — formerly a hardcoded `MAX_PREFERENCE_HEADROOM = 0.5`, easily enough to reorder a list and the only `final_score` input an admin could neither see nor change. Now `{movie,series}_preference_strength` (`0153`, default 0.50 = previous behaviour, 0 disables), in `SCORING_FIELDS`. Three things: the parameter defaults to the old constant so an un-passed call is byte-identical (`preferenceStrength.test.ts`); a negative or non-finite value is **clamped, never trusted**, since a negative share would push loved titles *down*; and `discover/scorer.ts` deliberately does **not** pass it, because an admin tuning recommendations must not silently change what gets requested from Seerr. The panel gains no "strength" caption — labelling a stored per-run delta with today's config is the fault `0147` fixed. [F-071](docs/aperture-forensics.md#f-071)
- **A weighted mean can only say "more like this", so a disliked title must weigh 0** — and the scale is 1–10, full stop (`user_ratings` carries `CHECK (rating >= 1 AND rating <= 10)`, `0053`). `calculateEngagementWeight` tried to detect the scale anyway (`rating > 5 ? /10 : /5`), which cannot work and produced a **non-monotonic** curve peaking at **5/10**. Both builders now drop the item entirely (`isDislikedRating`, `recommender/ratingBands.ts`, shared because both builders **and** `getDislikedMovieIds` encode the bands), and **both consumers filter `weight > 0`** — the total-weight-of-zero check inside `buildWeightedAverageEmbedding` is a guard, not a filter, and clustering would otherwise still place a centroid on a disliked point. **Pushing the centroid *away* is deliberately not attempted**: a negative weight in a weighted mean yields a vector that need not lie near the data at all. The mirror of a taste twin is also unbuildable — non-overlap is not anti-correlation, and watch-history Jaccard measured **0–11.5% across all 171 pairs**. An item-level dislike *penalty* at scoring time is the buildable version. [F-072](docs/aperture-forensics.md#f-072)
- **Three "similar" systems**: `movies|series/:id/similar` (simple embedding neighbours) vs `/api/similarity/*` (multi-hop graph for Explore) vs `/api/graph-playlists` (playlists built from that graph). [F-073](docs/aperture-forensics.md#f-073)
- **"Show cross-media connections" was a filter that could never match.** The Explore switch fed `crossMedia` to the graph route, whose only use was skipping connections of a different type — but the connections came from single-table kNN that stamps `type` as a literal, so the predicate was never true and the toggle's only visible effect was the refetch its dependency change triggered. **A guard against a case the query cannot produce is not a feature**, and nothing typed can catch it. Four things now. (1) Both functions take `includeCrossMedia` and query the other table with the same vector — sound because `getActiveEmbeddingTableName` derives both suffixes from one dimension call, so no re-embedding is involved. (2) **Merging is by reserved slots, not a shared `ORDER BY`** (`similarity/crossMedia.ts`, pure and pinned): the two canonical-text builders differ systematically, so film↔film and film↔series distances are two populations and a plain top-N lets one take every slot (see the cosine invariant). `CROSS_MEDIA_SHARE` is 1/3, capped at half the list. (3) **The reservation is applied twice** — inside `getSimilarMovies`/`getSimilarSeries` and again in `getGraphForSource`, because the graph draws only `connectionsPerNode` of the 6 fetched and its own re-sort would drop them; its dedupe also moved *before* selection, since skipping an already-drawn edge mid-loop spent a slot on nothing. (4) The switch is **disabled outside the Browse views**, since semantic search and the focused graph come from endpoints that never receive the flag. `crossMediaNodeCount` is logged on every graph build so a silent return to zero is visible. [F-074](docs/aperture-forensics.md#f-074)
- **Top Picks config lives in 4 places**: `routes/top-picks/`, `routes/settings/handlers/topPicks.ts`, `routes/setup/handlers/topPicks.ts`, and the `refresh-top-picks`/`auto-request-top-picks` jobs. [F-075](docs/aperture-forensics.md#f-075)
## Jobs system (how background work runs)

1. Job catalog: `apps/api/src/routes/jobs/definitions.ts` (static list; **crons there can drift — DB `job_config` via core `getAllJobConfigs()` is authoritative**).
2. Execution: `apps/api/src/routes/jobs/executor.ts` — one `switch` mapping job name → core function. Adding a job = core function + executor case + definitions entry (+ default `job_config` row if scheduled) **+ an entry in `apps/web/src/pages/jobs/constants.tsx`** and **+ an entry in core's `JOB_SCHEDULE_DEFAULTS`**.
3. Scheduling: `apps/api/src/lib/scheduler.ts` (node-cron; executor injected via `setJobExecutor` in `routes/jobs/index.ts`, which also guards against double-runs).
4. Progress: in-memory + SSE, lives in **core** `jobs/progress.ts` (`withProgress`, `subscribeToJob`); run history in `job_runs`.
5. Shared mutable state: `routes/jobs/state.ts` `activeJobs` Map is also imported by `gap-analysis` and setup, which call `runJob` directly (bypassing jobs HTTP routes).

- **The job registry is `jobDefinitions`, not core.** `getValidJobNames()` is **deleted** — it returned the keys of a *seed schedule* map, so four jobs correctly wired everywhere else still answered 404 on `/api/jobs/:name/config`, and the dialog looked normal until Save. Core cannot import the API app, so no build can see that kind of divergence. The map is now `JOB_SCHEDULE_DEFAULTS` and is only a **default cadence**, but its keys still matter: **the scheduler builds its task list from `getAllJobConfigs()`, which merges DB rows with this map and never reads `definitions.ts`'s `cron` field**, so a scheduled job absent from both is silently never scheduled. `getJobConfig` **no longer returns null** — a job with neither a row nor a default reads as manual-only. `jobDefaults.test.ts` fails on a registered job with no seed, a seed naming a dead job, and a `manualOnly` job seeded with a real cadence; it imports core through `dist`, so it only sees source changes **after a build**. [F-076](docs/aperture-forensics.md#f-076)
- **A weekly schedule can name several days, and only one reader may resolve them.** `0149` adds `schedule_days_of_week INTEGER[]`, backfilled from the scalar. **`resolveScheduleDays` is the one reader**, used by both `scheduleToCron` and `formatSchedule` — otherwise the scheduler runs on days the admin's own summary does not name. The scalar is still *written* (earliest selected day) purely so a rollback reads a sane schedule rather than a NULL meaning Sunday. **Biweekly is truncated to one day** by `normalizeScheduleDays` at the write layer, since two firings in one week are 3–4 days apart and the second is always dropped — picking Mon+Thu would quietly mean "every other Monday". Out-of-range days are **dropped, not clamped**, and the route rejects them. `ScheduleTable`'s `computeNextRun` duplicates the resolver's fallback order by hand (web-never-imports-core invariant). [F-077](docs/aperture-forensics.md#f-077)
- **`JOB_CATEGORIES` is an allowlist, and a job missing from it has no UI at all.** `apps/web/src/pages/jobs/constants.tsx` maps job name → category and `JobCategoryList` filters on it, so an otherwise perfectly registered job gets **no card** — meaning no Run button and, worse, **no Cancel button**. The Schedule tab lists everything the API returns and therefore hides the omission: the job looks present, is runnable from there, and cannot be stopped. A new job needs a `JOB_CATEGORIES` entry plus `JOB_ICONS` and `JOB_COLORS`; a new *category* needs `title`/`description` under `admin.jobsPage.categories.*`. [F-078](docs/aperture-forensics.md#f-078)
- **A job that never calls `createJobProgress(jobId, …)` has no progress record, and every progress API then no-ops in silence.** Every function in `jobs/progress.ts` opens with `activeJobs.get(jobId)` and returns when absent — correct (a finished job is evicted after five minutes) but completely quiet. Missing that one line produces **every** symptom at once and no error: empty bar and log pane, no `job_runs` row (because `completeJob` returns before `saveJobRun`), and `isJobCancelled` reducing to `undefined?.status === 'cancelled'`, i.e. **always false**, so Stop cannot work however diligently the work polls it. **The executor is not a generic wrapper** — only cases that call `createJobProgress` get progress, and those same cases must call `completeJob` (skipping it when cancelled, since `cancelJob` already filed the row). `setJobStep`'s `itemsTotal` may be left 0 and filled by the first `updateJobProgress`. `addLog` **mirrors to the container logger**. The silent early returns now warn once per job id. [F-079](docs/aperture-forensics.md#f-079)
- **Cancelling is cooperative, and the terminal state is a one-way door.** `cancelJob` only sets `status='cancelled'` and writes the `job_runs` row; work stops solely because the core function polls `isJobCancelled(jobId)` — which `enrichment/`, `mdblist/`, `studioLogos.ts`, `backupService.ts`, `explanationRefresh.ts` and all four recommendation loops do, and everything else does not. `analysis/job.ts` cancels too but will **not** appear in a grep for `isJobCancelled`: it takes an injected `shouldCancel` supplied at the executor case. Two consequences: a job that does not poll runs to completion after being cancelled and used to **flip its own status back** (the record sits in `activeJobs` for five more minutes), so `completeJob`/`failJob` now ignore a job already in a terminal status; and nothing interrupts an in-flight HTTP or model call, so for anything doing paid model calls in a loop, **check between calls, not just between users**. [F-080](docs/aperture-forensics.md#f-080)
- **A cancelled job that keeps running is not the bug; letting a second one start beside it is.** All three claim sites asked `getJobProgress(id)?.status === 'running'`, and a *cancelled* job is not running — so the check passed for precisely the case it existed to stop, and nine users were scored twice in 13 minutes. **Membership in `activeJobs` is the correct test**, since the entry is cleared by `runJob`'s `finally` — when the work exits, not when someone asks it to. `decideClaim` is one pure function in `routes/jobs/state.ts`, pinned by `state.test.ts`. The cancel handler no longer `delete`s the entry, so a cancelled job holds its slot while winding down — which makes the **409 message load-bearing** ("was cancelled and is still winding down" is a different fact from "is already running"). **Releasing must be identity-checked** (`releaseJob`), because a zombie exits *after* its replacement has claimed the name. The escape hatch is **eviction, not force**: a terminal record is dropped after five minutes and `decideClaim` admits a claim when the holder has no record. **The 409 must be visible** — `handleRunJob` was `if (response.ok)` with no `else`, so a rejected start showed nothing, and a Run button that silently does nothing is what sends an operator to `docker stop`. [F-081](docs/aperture-forensics.md#f-081)
- **A job log is trimmed from both ends.** `addLog` bounds what it keeps (`LIVE_LOG_LIMIT` 500 in memory, `STORED_LOG_LIMIT` 300 persisted), and a plain `slice(-n)` keeps the wrong half: a 200-title pass opened at "[152/200]" with every line explaining what the run set out to do already dropped, while 197 identical failures were kept. `jobs/logWindow.ts` keeps a head (`LOG_HEAD_ENTRIES` 30) plus as much tail as the budget allows and inserts **one entry naming how many were dropped**. Pure and pinned (`logWindow.test.ts`), including the small-budget cases where head + marker + tail must total exactly the limit. **The marker's count must be cumulative**: `condenseLogs` runs on *every* append past the limit, so recomputing from the list in front of it — a list already holding its own marker — reported "2 earlier entries not kept" for a job that had discarded thousands. The count rides in `data.elided` and a later pass adds to it; detection is on that field, never on the message text, which is prose. A stored log's figure is `limit − head − tail` and describes the **buffer**, not the run — do not read it as a total. [F-082](docs/aperture-forensics.md#f-082), [F-094](docs/aperture-forensics.md#f-094)

## Recommender / embeddings pipeline (order matters)

sync-users → sync-movies/series (media server → DB) → enrichment (TMDB/OMDb fields onto rows) → generate embeddings (`buildCanonicalText` — **includes enriched fields; changing enrichment output means re-embedding**) → generate recommendations (taste vector → pgvector candidates → score: similarity/novelty/rating + taste-profile boosts → MMR selection → AI explanations → `recommendation_*` tables) → outputs (STRM libraries, channels, playlists, collections).

Embedding tables are shared consumers: recommender, `/api/similarity` graph, semantic search, discovery scoring, taste-profile interests. Movies and series are **parallel pipelines** (`recommender/movies/` vs `recommender/series/`) — see the mirroring invariant.

- **A canonical-text change reaches existing rows only via `CANONICAL_TEXT_VERSION`.** Selection was once `LEFT JOIN … WHERE e.id IS NULL` (**missing, not stale**), so editing the builder did nothing to 12.5k rows and the only remedy was a TRUNCATE of every dimension table. `text_version` (`0138`, movie and series families only — **episodes excluded on purpose**, their text reads no enrichment column) makes a builder change cheap to detect; NULL predates it. Five rules: the staleness clause compares **`updated_at`, not `created_at`** (`storeEmbeddings` upserts, so `created_at` holds the first write forever); a row that survives being handled is an **infinite job**, so both loops attempt each row at most once per run and `markEmbeddingsCurrent` restamps rows whose text turned out unchanged; counts and selections must share the predicate (`MOVIE_STALE_SQL`/`SERIES_STALE_SQL`) or the bar describes a total the loop never reaches; and `buildCanonicalText` must be **deterministic**, since the skip-unchanged guard is a string comparison (pinned by `canonicalText.test.ts`). A re-embed moves every item vector, so it costs `rebuild-taste-profiles` and then a regenerate. [F-083](docs/aperture-forensics.md#f-083)
- **The canonical text is nationality-heavy by construction — do not add more proper nouns.** Of fifteen fields, **six were nationality-coded** (director, studio, cinematographer, composer, cast, country) against three describing what a title is *like* (genres, plot, keywords), so the vector partly works as a nationality detector. Three fields were removed: **content rating** ("NR" tracks age and non-US origin, not the work), **awards** (same rule that keeps scores out, and award prose clusters award films together regardless of subject), and **composers** — but **not cinematographers**, since the below-the-line argument holds for photography as a style signal and not for a single composer credit appearing on two or three titles. `MAX_KEYWORDS` deliberately **stays at 18** (coverage is uneven, so raising it trades one dilution for another). This reduces rather than removes the effect — five nationality-coded fields remain. **The plot-widening this entry credits as the bigger lever never happened**: `plot_full` is the blurb on a real library, so proper nouns are ~a quarter of the median document, not ~2%, and these three removals carry the whole load alone. [F-084](docs/aperture-forensics.md#f-084), [F-089](docs/aperture-forensics.md#f-089)
- **`plot_full` is OMDb's `plot=full`, and it replaces the overview in the vector rather than joining it.** Same request and quota as `plot=short` (which returns roughly what the media server already syncs into `overview`), but it is IMDb's user-submitted synopsis — longer and different in kind. Stored as its own column (`0139`) because `movies/sync.ts` rewrites `overview` every pass. Three rules: use it **instead of** the overview, never alongside, or plot weighs twice against genre/crew/keywords; use it **only when actually longer** (OMDb falls back to the blurb, so non-null proves nothing — the naive `plotFull || overview` returns a *shorter* value and `canonicalText.test.ts` caught it); and the cap is **4000 chars** (`PLOT_CHARS`) — 1000 kept only the setup, the most interchangeable part of any story, while uncapped makes cosine partly measure *"does this title have an IMDb synopsis"*. In the UI it is opt-in behind "Read full synopsis" (spoilers). `0139` also **clears `omdb_enriched_at`**, since the stamp records that OMDb was asked, not what for. **Measured since: on this library `plot=full` is the blurb** — 99.7% populated, but p50 431 chars, 0.75% over 2,000, none over 5,000 — so the cap is nearly never reached and proper nouns are ~a quarter of the median 905-char document rather than the ~2% F-084 assumes. Trimming is exhausted (cast 3, studios 2, cinematographers 2, keywords 18); a wider plot source is the only lever left, and every candidate reintroduces the coverage asymmetry the cap bounds. [F-085](docs/aperture-forensics.md#f-085), [F-089](docs/aperture-forensics.md#f-089)
- **`tmdb_rating`/`tmdb_vote_count` and `imdb_rating`/`imdb_vote_count` cost no extra request** (`0140`) — they ride on responses enrichment already fetches and parses. **Vote counts are half the point**: 8.2 from 22,000 votes and 8.2 from six are not the same claim. Both parsers are traps: `"N/A"` must become **null, not 0**, or unrated titles sort below genuinely bad ones; and `imdbVotes` is thousands-grouped, where `parseFloat('545,163')` returns **545** (pinned by `ratings.test.ts`). Every badge guard uses `!= null` (NUMERIC invariant). Ratings stay **out of the canonical text** — a bare "82" embeds as noise. **TMDB has no awards API**, so OMDb's `awards_summary` remains the only structured source. [F-086](docs/aperture-forensics.md#f-086)
- **Ratings refresh is a separate module and job, because metadata and ratings want opposite selection rules.** `needsEnrichmentSql` has **no TTL** — right for a plot or a cast list, wrong for a rating, and one shared predicate let the field that never changes set policy for the field that changes weekly. The error is **biased, not random**: a new release's rating starts high and decays as the vote base widens, so a frozen copy systematically *overrates* recent films, and rating is a quarter of the blend. Emby is not an independent second opinion (its rating-sync plugin reads OMDb and MDBList). Six things (`ratings/`, `0148`, job `refresh-ratings`): the IMDb source is a **bulk file, not an API** (`title.ratings.tsv.gz`, 8.2 MB, daily, no key) so **one request covers all ~12.5k titles**; `RATING_SOURCE_IDS` is **the one copy** and the job's step count derives from it (a hand-written number is the second copy that stops matching); `imdb_ratings_refreshed_at` is stamped on **every row we looked for, not only the ones we found**, since a title with no votes is absent from the file entirely; **OMDb still writes those columns but only while that stamp is NULL** (conditional rather than deleted, because the source is opt-in on licence grounds, and the clobber it prevents is latent until the next stamp clear); and `parseRatingsLine` is pure and pinned (`imdbDataset.test.ts`) — the `wanted` set is checked **first** (rejecting ~99% of 1.5M lines and disposing of the header for free), `indexOf` rather than `split`, and `Number()` with an explicit empty-string guard since **`Number('')` is 0, not NaN**. [F-087](docs/aperture-forensics.md#f-087)
## Auth model

`plugins/auth.ts`: `x-api-key` header (takes precedence) or `aperture_session` cookie. `requireAuth`/`requireAdmin` — **`requireAdmin` has no bypass**; server-side callers that need to act without a logged-in user call the domain function directly (`routes/jobs/startJob.ts` is the one for jobs, used by the setup wizard) rather than replaying an HTTP request through `fastify.inject`. API-key users are forced `provider:'emby'`, `collectionsEnabled:false`.

- **Sessions are bearer tokens, not row ids**: the cookie holds 32 random bytes; `sessions.token_hash` stores only its sha256, and `sessions.id` is unrelated. 30-day absolute lifetime plus a 7-day idle timeout (`last_seen_at`, rewritten at most every 5 min). `is_enabled` is enforced on *both* the login path and every session lookup, and `PUT /api/users/:id` revokes sessions when it disables an account — a disabled user loses access immediately. The `cleanup-auth-state` job sweeps expired/idle rows, deliberately with a 1-day grace margin so the auth plugin stays the only thing that decides a session is dead.
- **Brute-force controls are two-layer, on different axes**: `@fastify/rate-limit` keyed on **IP alone** for `/api/auth/login` (folding the username in widens the keyspace, so a spray rotating usernames would get a fresh bucket per request and never trip it), plus DB-backed per-account lockout in `apps/api/src/lib/loginAttempts.ts` with progressive backoff, which is what covers one account attacked from many IPs. **Only `InvalidCredentialsError` counts toward the lockout** — the providers throw it on 401 and a plain `Error` otherwise, so a media-server outage returns 503 instead of locking out every user who retries.
- **Deployment posture lives in `apps/api/src/config/security.ts`**, not scattered env reads: `DEPLOYMENT_MODE` (`direct` default, or `proxy`/`tunnel`/`cloudflared`), `TRUST_PROXY`, `HOST`, `COOKIE_SECURE` (defaults on in production — *not* derived from `APP_BASE_URL`), `API_DOCS` (`public|admin|off`, admin-only in production), `ALLOW_PASSWORDLESS_LOGIN` (production gate over the `allow_passwordless_login` admin toggle), `SETUP_ALLOW_REMOTE`, `CSP_REPORT_ONLY`. All booleans parse case-insensitively via `envFlag`. `helmetOptions()` and `config/rateLimits.ts` live here too so `security.test.ts` asserts the objects the server actually registers.
- **`TRUST_PROXY` is load-bearing and `=true` is a footgun**: it trusts `X-Forwarded-For` from anyone, so a caller can forge their address to mint rate-limit buckets and look local to the setup guard — pin the proxy (`TRUST_PROXY=172.18.0.1`) instead. Leaving it unset *behind a proxy* is worse: every visitor collapses to the proxy's address, so the login limiter becomes one global bucket and `isTrustedSetupSource` sees the whole internet as local. `DEPLOYMENT_MODE=proxy` supplies a loopback default; an explicit `TRUST_PROXY` always wins.
- **`config/deploymentPosture.ts` is the one source of truth for "is this exposed correctly"** — the boot warnings and `GET /api/settings/deployment` (Settings → System → Deployment) both render its `findings`, so they cannot drift. Findings are stable ids translated under `settingsDeployment.findings.*`; a new one needs `title`/`detail`/`fix` in en or the panel shows a raw key (there is a test for exactly that). Crucially it is **evidence-based, not config-only**: `noteRequest` samples live traffic from the access-log hook, because an instance behind a tunnel with no trusted proxy looks perfectly healthy from config alone — seeing `X-Forwarded-For` while trusting nothing is the only reliable tell.
- **Trusted proxies are editable at runtime** (`config/proxyTrust.ts`, `PATCH /api/settings/deployment`), stored in `system_settings.trusted_proxies`. This works because **Fastify accepts a *function* for `trustProxy` and consults it per request** — the value being passed at construction does *not* freeze the decision. (An earlier reading of `Request.buildRequest` concluded it did, which is why the panel first shipped read-only; `security.test.ts` pins the dynamic behaviour now.) Matching delegates to `proxy-addr`, the same library Fastify uses, so CIDRs behave identically to the static form. `TRUST_PROXY` still wins outright when set — the UI goes read-only — because it must also be available *before any admin exists*, which is the only way the first-run setup guard can be protected behind a tunnel.
- `@fastify/helmet` sets the CSP — `imgSrc` is deliberately wide because TMDB posters load direct from `image.tmdb.org` and `getProxiedImageUrl` only proxies media-server URLs; `styleSrc`/`fontSrc` must keep the Google Fonts hosts that `index.html` pulls; Swagger UI gets a relaxed CSP scoped to `/openapi` because it bootstraps inline. `connect-src 'self'` also fences assistant-ui's cloud path (see the comment at the `useChatRuntime` call site).
- **First-run setup is network-restricted**: a plugin-scoped `onRequest` hook in `routes/setup/index.ts` refuses `/api/setup/*` from non-local addresses until setup completes (admins and `GET /api/setup/status` always pass). Before that hook existed, whoever reached a fresh instance first could configure it and become admin.

## Web conventions

- Provider tree (App.tsx): `I18nextProvider > RtlProviders > BrowserRouter > SetupProvider > AuthProvider`; authed pages additionally get `ViewModeProvider > UserRatingsProvider > WatchingProvider > AssistantDockProvider` + floating `AssistantModal`.
- Route table lives in `apps/web/src/App.tsx`; shell is `components/Layout.tsx` (sidebar items feature-gated by watching/collections flags).
- **The admin console is generated from one registry, and that is what stops it drifting.** `pages/admin/nav/registry.ts` is pure data (no JSX, no React) listing 8 groups and 42 entries; `elements.tsx` holds the icon and the `lazy` component for each, keyed by the same id; `routes.tsx` builds the `<Route>` table from it; `search.ts` builds the palette index from it. Adding a section means an entry **and** an element — omit the entry and the section gets no route at all, which is the opposite of the `JOB_CATEGORIES` failure where a missing key leaves a job present-but-crippled. Seven things. (1) Depth is capped at **two** (group → leaf) permanently; a group past ~12 leaves splits rather than growing a third tier — three stacked scrollable tab strips is what this replaced. (2) `registry.test.ts` runs under `node --import tsx --test` (`pnpm --filter @aperture/web test`, the web package's first test runner) and pins: unique ids and paths, exactly one index route, entry↔element parity, every i18n key resolving in `en`, **every barrel export in `settings/components/index.ts` having a home**, every legacy redirect target existing, and **every declared field anchor existing as an `id` in a section**. (3) Search has three tiers — sections free from the registry, ~33 `fields` opted in with anchors, and **every job** — and matches translated titles/blurbs **plus untranslated `aliases` written in the registry rather than in `translation.json`**, so `omdb` and `pgvector` keep working in all 15 locales. **The jobs tier is not optional the way fields are**: 28 jobs are the largest set of named, runnable things in the console, and unindexed they sent every job name to a settings page that merely mentioned the word — `sync movies` reached Libraries, `rebuild taste profiles` reached a slider labelled "Borrowed from a taste twin", `studio logos` reached **nothing**, and `full reset recommendations` put the destructive database purge on top. They are read from `pages/jobs/registry.ts`, the same array the page renders, which is why that module was split out of `constants.tsx` (JSX icons) — a search index built from a second list would drift, and the failure mode is a job that is findable but has no card. **A `#job-…` link must also open the tab holding it**: the page unmounts inactive `TabPanel`s, so a global job's anchor did not exist and the scroll silently did nothing; `jobTabIndex` derives the tab from the same three arrays. **The result floor is relative, never absolute** — only results matching as many query tokens as the best result survive, which took `api key` from 15 rows to 2 while never turning "few results" into "none". Hyphens tokenise like whitespace so a kebab id pasted from a log searches as its words. **The query is tokenised and scored per word, never matched whole.** Matching the whole string looks reasonable — settings names are often two words — but nobody types a label verbatim; they name the area and the thing, and those words sit in *different* indexed strings. `ai embedding model`, `novelty weight`, `backup database` and `trusted proxy` each returned **zero**. So each entry's haystack also carries its **group label** (weight 40) and each field's carries its **parent section title** (45) — that is what makes "novelty weight" reach a slider labelled "Genre Discovery". Ranking is **tokens matched first, score second**, so a result answering the whole phrase beats one scoring higher on part of it, and a stray word degrades to the best partial match instead of nothing. Pinned by `search.test.ts` against the real registry and the real English strings. (4) The palette is ⌘⇧K, separate from `GlobalSearch`'s ⌘K, because content results arrive from a debounced API call and these are local and instant. **Which palette a keystroke belongs to is decided once, by `lib/searchShortcut.ts`, and neither listener may decide for itself.** Both listen on `window`, and `preventDefault()` does not stop a sibling listener on the same target — so the only thing separating them was a case comparison on a letter (`e.key === 'k'` here, either case there). **Letter case is not a signal of Shift**: with Caps Lock on, Caps and Shift cancel and ⌘⇧K arrives as lowercase `'k'`, both matched, and both palettes opened stacked (reproduced in a browser). `shiftKey` is the only field that answers it. Two smaller rules inside the resolver: **Ctrl+Alt is AltGr**, which types a character, so it is not a shortcut; and a non-Latin layout (`'л'`, `'ק'`) falls back to `e.code === 'KeyK'` — but **only** as a fallback, since matching `code` first would give a Dvorak typist's Ctrl+V the palette. Pinned by `searchShortcut.test.ts`, which also scans `apps/web/src` for anything comparing the K key by hand (verified to fail on an injected violation). (5) `MediaTypeCard` in `RecommendationConfigSection` renders **twice**, so its anchors are namespaced by an `idPrefix` prop (`rec-movie-*`/`rec-series-*`) — a bare id would be duplicated and every jump link would land on the movie copy. (6) Old addresses (`/admin/settings?tab=…`, `/admin/users`, `/admin/jobs`, `/admin/translations`, `/admin/gaps`) redirect via the **frozen** `legacyRoutes.ts`; it never grows. (7) Admin lives in the **app bar** (`AdminMenuButton`, admin-only, left of the avatar), not the sidebar. `RunningJobsWidget` stays beside it deliberately — it is a live progress bar and self-hides at rest, so a count badge could not replace it. (8) **A precondition is declared once, on the entry.** `gate` is read by the route *and* the nav column (dimmed with a reason, never disabled — the old tab was unclickable, so the only way to learn what it needed was to hover it); `GATE_TOOLTIP_KEYS` is a `Record<AdminGate, …>` so a new gate without an explanation is a type error. Only a **pass** is cached: configuring TMDB is one of the things you come here to do, and caching the negative would leave the section refusing until a reload. (9) **`hooks/activeJobs.ts` is the one poll of `/api/jobs/active`** — the app bar widget and the nav column's Jobs badge both read it, reference-counted, and an in-flight response is dropped if the last subscriber left (it would otherwise refill the cache the cleanup just emptied). (10) The hash-scroll effect keys on **`location.key`**, not just path and hash: searching for the same field twice changes neither, and keying on those alone made the second search do nothing. (11) **The nav rail is capped, not fixed, and the cap only works because of the flex chain.** The chain is `maxHeight: calc(100vh - 112px)` + `flexDirection: column` on the Paper, then `flex: 1; minHeight: 0` on both the wrapper and the scrolling list. **`minHeight: 0` is load-bearing**: a flex item defaults to `min-height: auto` and refuses to shrink below its content, so `overflowY: auto` never engages. It first shipped with `height: 100%` on the child of a `maxHeight`-only parent, which resolves to `auto` and overflowed silently; the fix at the time was a *definite* `height`, which was wrong in the other direction and stayed wrong for a release — measured, a collapsed 676px column sat in a 788px box with 112px of dead space, and an expanded 1461px one sat in the same 788px box behind a scrollbar, because the height never moved at all. **The real cause of the scrollbar was not the height but the expansion**: `expanded` was a *list* and nothing ever removed from it, so browsing accumulated open groups until forty rows were in a viewport-height box — while the component's own docstring claimed only the current group was open. One group at a time (`AdminGroupId | null`) removes the inner scrollbar in seven of eight groups; the effect keys on the active **entry** as well as the group, or someone who collapsed the group they are standing in and then jumped elsewhere inside it arrives with the selected row hidden. **Integrations is at eleven entries and is the one group that still scrolls on a short screen — it is the next to split**, per the registry's own two-level rule. (12) **The content pane has an error boundary** (`AdminErrorBoundary`, reset on path change). Every destination is one lazy component in one outlet, so without it a single section throwing unmounts the sidebar, the app bar and the nav column together — a white screen naming nothing. It also carries the reload prompt for the other failure lazy routes introduce: hashed chunk filenames plus image-swap deploys mean a tab left open across a deploy asks for a file the new build does not serve. (13) **An `id` written one line below an opening tag is a JSX child, not a prop.** React renders it as literal text, the element never gets the attribute, and TypeScript, eslint and a source-text search for the anchor all pass — the only tell is `id=rec-movie-max-candidates` printed on the page. `registry.test.ts` throws on that shape specifically, because it is the one way a promised anchor can pass every other check and still not exist. (14) The subtree ends in a **catch-all redirect** — an unmapped `/admin/*` still matches the shell, so without it the frame renders around an empty outlet, which is a blank page rather than a wrong one.
- **A page's title lives in the app bar, not on the page**: at `md`+ the bar's left half was empty (hamburger and wordmark are mobile-only, jobs widget/search/avatar are pinned right) while every page spent ~80px repeating the same words below it. `components/PageHeading.tsx` publishes them through `hooks/PageHeaderProvider` (mounted by `Layout`, above both the bar and the `<Outlet/>`) and renders the familiar block only below `md`, where the bar has no room. Three traps: (1) the outer wrapper **stays in the tree** at every width — most callers sit it beside a toolbar in a `space-between` row, and removing it would leave one child, which flexbox puts at the *start*; (2) `icon` is rendered in the page block only and never published, because the header lives in state and an element prop is a new object every render, so publishing it would loop; (3) only **one** publisher per route — `AdminShell` publishes each section's registry title, *except* for the five entries flagged `ownsHeading` (Overview, Users, Jobs, Translations, Gap analysis), which were pages before they were leaves and still announce themselves. The shell expresses "don't publish" by **not mounting** its `AdminHeaderPublisher`, never by publishing an empty title: React runs child effects before parent ones, so a parent publishing `''` blanks the bar the child just filled in. A page with no `PageHeading` and no `usePageHeader` shows an empty bar; the always-full-viewport surfaces (`/assistant`, `/explore`) call `usePageHeader` directly and skip the block entirely.
- Hooks pattern: `XProvider.tsx` + `x-context.ts` + `useX.ts` triplets in `src/hooks/`.
- **New UI string**: add to `src/i18n/locales/en/translation.json` (en is source of truth), use `t('ns.key')`, then `pnpm i18n:sync` to stamp placeholders into the other 14 locales. RTL locales: ar, he — use logical CSS properties. Server error strings: wrap with `lib/withServerMessageDetail.ts`. Authoritative guide: `src/i18n/CONVENTIONS.md`.
- **Never write the product name in a UI string — write `{{appName}}`.** The instance is renamable (Settings → System → Instance name, stored as `system_settings.app_name`, served by public `GET /api/branding`), and the rename reaches all 15 locales at once because i18next fills the placeholder from `interpolation.defaultVariables`. That is set to the default in `i18n/config.ts` and overwritten by `lib/branding.ts` once the fetch lands — safe to assign late because i18next reads `defaultVariables` off the shared options object *at interpolate time*, not at init; the `changeLanguage` nudge afterwards is only there to re-render what's already on screen. `GET` is deliberately unauthenticated (login and setup render the name before any session). The few spots with no translation to interpolate into — logo `alt` text, `document.title`, the `formatJobName` fallback — call `useAppName()`/`getAppName()` instead; note the job fallback must resolve the name *per call*, since a module-level const would freeze the default before the fetch resolves. **The `<title>` can't wait for that fetch** — a tab (or a bookmark taken right then) would show the default on every cold load — so `plugins/static.ts` stamps the name into the shell on the way out: it reads `apps/web/dist/index.html` once at boot, rewrites the `<title>` element per request, and serves it from both `GET /` and the SPA fallback. That is also why `@fastify/static` is registered with `index: false` — otherwise a directory request would answer off disk and skip the rewrite. Falls back to the default if the DB read throws, so a database outage can't stop the shell booting. Left alone on purpose: `/aperture-libraries` and `/mnt/ApertureLibraries/` are real paths, and `helperApertureLibs` is a key name.
- Client caches to remember when changing API shapes: `WatchingContext` (localStorage, versioned — bump version on shape change), `ViewModeProvider` (localStorage + server prefs).
- **Breakpoints lie inside the main pane**: MUI breakpoints are *window* media queries, but `Layout.tsx` shrinks `<main>` with `marginInlineEnd: dockWidth` when the assistant is docked, and `MediaDetailModal` renders a whole page inside a dialog. A grid keyed on `md`/`lg` therefore keeps its full-desktop column count in a half-width pane (this is what shrank Related Movies to ~110px posters). Size in-pane grids off their container — `gridTemplateColumns: 'repeat(auto-fill, minmax(Npx, 1fr))'`, or MUI 6's `theme.containerQueries` — rather than subtracting `dockWidth` from a breakpoint, which still gets the dialog case wrong.
- **Assistant surfaces**: three containers share `AssistantChatSurface` — the dock (Fab default, md+), the dialog (opt-in via the header toggle, and the fallback below md), and the `/assistant` page. Only the page renders the conversation list inline (`sidebarInline`); the floating pair use the history drawer. The header's expand button routes to `/assistant` carrying `{ conversationId }` in the route state, which `useAssistantChat(active, initialConversationId)` seeds — without it the page would resume whichever conversation was updated last.
- **The sidebar has three states, and `collapsed` is not the one to branch on**: `Layout.tsx` renders one `renderDrawer({ labels, collapsible })` for both drawers. Below `md` it's a temporary overlay, always `DRAWER_WIDTH` and labelled regardless of the rail preference (`collapsible: false` — an overlay you dismiss has nothing to collapse). At `md`+ it's a permanent rail whose paper widens to `DRAWER_WIDTH` on hover **without** the nav Box or `<main>` changing width — the paper is `position: fixed`, so the flyout floats over the page and content never moves. Branch on **`labels`** (`!collapsed || flyout`), never on `collapsed`, or the flyout renders icons. The flyout is gated on `(hover: hover) and (pointer: fine)` so a touch screen gets taps instead, opens instantly on `onFocus` for keyboard users, and is delayed both ways so brushing past doesn't trigger it. Default collapse state follows `lg` until the user toggles once; `sidebarCollapsed` is **absent** from `/api/auth/me/preferences` until then, which is the "has a preference" signal (`hasSidebarPreference`).
- **The welcome guide is route-gated and snoozed, not "first visit"**: `components/WelcomeModal.tsx` explains the recommender only, so `useWelcomeModal` opens it by itself on `/recommendations` alone (`WELCOME_ROUTE`) — the user menu's "How it works" still opens it anywhere. It is a **controlled dialog only**; `Layout.tsx` mounts exactly one, and `onClose` always receives an explicit `WelcomeDismissal` (`session` | `day` | `week` | `never`), never MUI's close event. Three storage keys back that: the pre-existing `aperture-welcome-dismissed` (still the "never" flag, so anyone who already ticked the box stays dismissed), `aperture-welcome-snooze-until` (epoch ms, localStorage) and `aperture-welcome-session-snooze` (sessionStorage, holding the user id — the closest a browser gets to "until I sign in again"). A plain close snoozes for the session; showing the guide on every refresh is what made it feel like nagging.
- **The detail page states each fact once, and the hero is where the duplicates were resolved.** `pages/media-detail` rendered the same information twice in three separate places: genre chips in `MediaHero` *and* an identically-sourced "Genre Analysis" chip row in `MovieInsights`; the star rating in the hero *and* a "Critic Ratings" panel of IMDb/TMDB/RT/Metacritic badges in `MediaInfoCard`, several screens down; and `awards_summary` in its own sidebar card. All three now render once, at the top — the rating line carries every score, the awards sit on the line under it, and director/writer moved up beside them, out of the info card (which is now cast, secondary crew, studios, languages, countries and links). Four things to keep straight. (1) The genre classification comes from `insights.genreAnalysis`, whose two lists **partition the title's genres exactly** — both insights routes filter the item's own `genres` column against the viewer's top-10 watched genres — so styling the hero chips by set membership can never leave one unaccounted for, and the panel keeps only the *counts*. It rides a later request than the media, so chips restyle when it lands and stay neutral for a title no run scored. Colour is explained by per-chip tooltips, since deleting the panel's chips also deleted the only legend. (2) `hasCriticRatings` and `personPath` live in `pages/media-detail/helpers.ts` rather than beside the components: a module exporting both a component and a plain function trips `react-refresh/only-export-components`, and lint runs at `--max-warnings 0`. (3) Every rating guard is `!= null`, never truthiness — pg returns NUMERIC as a string, so a stored `0` arrives as `'0.0'` and passes a truthy test while a genuine numeric 0 fails one; the panel this replaced had one guard of each kind. (4) `MovieInsights` now opens **expanded for both variants** (it was collapsed for a scored-but-not-picked title): a panel whose whole content is an explanation reads as empty when it is shut.
- **Item detail in a dialog**: `components/MediaDetailModal.tsx` renders the *route page* `pages/media-detail` (which now takes optional `id`/`onBack`/`onOpenMedia` instead of only reading `useParams`), hosted by `hooks/MediaDetailModalProvider`. Chat cards call `useMediaDetailModal()`; a **null** opener means "no host mounted, navigate instead" — that's how the docked assistant keeps routing the main pane while the /assistant page and the floating dialog open in place (`AssistantChatSurface` prop `openMediaInModal`). Related titles / insight evidence inside the dialog swap the target rather than route, or they'd move the page under the dialog. `MediaBackdrop`'s `mx/mt: -3` is why the dialog content keeps `p: 3`.

## When you touch X, check Y

- **New/changed core or ui export** → rebuild packages before typecheck; check `packages/core/src/index.ts` barrel (exports won't resolve until added there or to a subpath export in core `package.json`).
- **Schema change** → new `db/migrations/NNNN_*.sql`; check both migration runners; grep for the table name across core (raw SQL is duplicated in many modules).
- **Enrichment fields** → re-embedding may be required (canonical text), similarity `reasons.ts`, gap analysis, top picks all read enriched columns.
- **Series/watching changes** → `watching/tmdbTotals.ts` caches TMDB totals on `series` rows (`tmdb_total_episodes/seasons`, `tmdb_status`); Watching page, upcoming episodes, and MyWatchHistory grids all read them.
- **Media-server calls** → implement in BOTH `media/emby/` and `media/jellyfin/`; interface is `media/MediaServerProvider.ts`.
- **Movie-side recommender/sync fix** → check the series mirror (and vice versa).
- **New/moved admin section** → add an entry to `pages/admin/nav/registry.ts` **and** an element to `elements.tsx`; run `pnpm --filter @aperture/web test`, which fails until the section has a home.
- **Renaming/removing an API route** → grep `apps/web/src` for the literal `/api/...` string (no typed client to catch it).
- **Integration client changes** (tmdb/omdb/trakt/mdblist/seerr/justwatch) → they log to `errors/` (`api_errors`) and often have DB caches with TTLs; check retry gating (`shouldAutoRetry`).
- **Job behavior** → schedule comes from DB `job_config`, not `definitions.ts`; progress API is in core.

## Workflow notes

- Work happens directly on `dev` (no feature branches). `main` is a stale upstream mirror; `.github/workflows/sync-dev.yml` force-resets `dev` to `main` on pushes to `main`. Pushing to `origin/dev` triggers the Docker build — don't push without being asked.
- **Never open the live site right after a push.** A push only starts the image build; the running instance changes when the operator manually pulls it. So the browser will be showing the *old* build, and "verified" would be a lie. Browser checks (`claude-in-chrome` against the deployed instance — the local dev server can't be started here) happen only when the operator says the new image is deployed. A push is the end of the turn, not the cue for a screenshot.
- Docker: `docker/Dockerfile` (4-stage; copies built dists + `db/`); compose variants per platform (dev/prod/external-db/windows/unraid/synology/qnap). Runtime data in `data/` (gitignored except `.gitkeep`s); operator i18n overrides mount at `/config/i18n`.
- Docs for humans live in `docs/` (admin guides, feature docs, screenshots).
