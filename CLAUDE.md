# Aperture — Repo Map

Self-hosted media recommendation & watch-tracking app for Emby/Jellyfin. AI recommendations via pgvector embeddings, plus integrations: TMDB, OMDb, Trakt, Seerr (Jellyseerr/Overseerr), MDBList, JustWatch, n8n, Tavily, fastCRW (self-hosted search + scrape, `packages/core/src/lib/crw.ts`), LLDAP (optional email import, `packages/core/src/lldap/`).

> **Keep this map current.** When you add/move/rename a route, page, core module, or table, update the relevant section here in the same change. This file is the primary navigation aid — stale entries cause wrong-file edits.

## Architecture (30 seconds)

pnpm monorepo, ESM everywhere, no ORM (raw SQL via `pg`):

- **`packages/core`** (`@aperture/core`) — ALL domain logic. Built with `tsc` → `dist/`. Subpath exports: `.`, `/config`, `/db`, `/media`, `/recommender`, `/strm`, `/channels`, `/jobs`, `/watching`. Root `src/index.ts` is a giant barrel (~1090 lines).
- **`apps/api`** (`@aperture/api`) — thin Fastify HTTP layer (port 3456): routing, auth, job orchestration. Handlers call core functions; `src/lib/db.ts`, `lib/logger.ts`, `config/env.ts` are pure re-export shims of core.
- **`apps/web`** (`@aperture/web`) — Vite + React 18 SPA (dev port 3457, proxies `/api` → 3456). MUI 6, react-router 7, i18next (15 locales), d3, recharts. **Never imports `@aperture/core`** (server code would break the bundle — duplicate tiny helpers instead, see `src/i18n/localeDirection.ts`). No central API client: raw `fetch('/api/...', { credentials: 'include' })` everywhere.
- **`packages/ui`** (`@aperture/ui`) — shared React components (MoviePoster, StarRating, BaseCarousel, RankBadge, StatusCard, TrailerModal, `getProxiedImageUrl`). Web aliases it to `src/` for hot reload, but typecheck/build use `dist/`.
- **`db/migrations/`** — numbered SQL files (`0001`–`0143`; `0129` is used twice, which the runner tolerates since it tracks filenames). Postgres + pgvector.

## Commands

```
pnpm dev                # api + web concurrently (kills stale 3456/3457 first)
pnpm build              # pnpm -r build (topo order)
pnpm typecheck          # builds packages/* FIRST, then pnpm -r typecheck
pnpm lint / validate    # eslint --max-warnings 0 / lint + typecheck
pnpm db:migrate|db:status
pnpm --filter @aperture/web i18n:sync   # propagate new en strings to 14 locales
```

**Critical:** apps consume the compiled `dist/` of core/ui. After adding/changing any export in `packages/core` or `packages/ui`, run `pnpm --filter "./packages/*" build` or app typecheck fails with TS2305/TS2307.

## Database

- Pool + helpers: `packages/core/src/lib/db.ts` (`query`, `queryOne`, `transaction`). Env: `packages/core/src/config/env.ts` (`DATABASE_URL` required; `@db:`→`@localhost:` rewrite unless `DOCKER_ENV`).
- Migrations: add next-numbered `NNNN_name.sql` to `db/migrations/`. Applied at API startup (`RUN_MIGRATIONS_ON_START`) via `packages/core/src/migrations.ts`, or manually via `scripts/migrate.mjs` — **two runners, duplicated logic, both track `aperture_migrations`**; keep behavior in sync if touching either.
- Key tables: `movies`, `series`, `episodes`, `watch_history` (+ `playback_progress`), `users`, `sessions`, `user_settings`/`user_preferences`/`user_ratings`, `user_watching_series`, `user_taste_profiles` (+ franchise/genre/interest tables), `recommendation_runs/candidates/evidence`, `recommendation_config`, embedding tables (per-dimension, e.g. 1536/3072/4096 — resolve via `getActiveEmbeddingTableName` in `core/src/lib/ai-provider.ts`), `discovery_pool/candidates/requests`, `gap_analysis_runs/results`, `channels`, `graph_playlists`, `strm_libraries`, `library_config`, `top_picks_config`, `job_config`/`job_runs`, `system_settings`, `api_errors`, `api_keys`, `web_search_usage`, `llm_inference_calls`, `assistant_conversations/…`, caches (`title_analysis`, `tmdb_collection_cache`, `tmdb_poster_cache`, `justwatch_chart_cache`, `person_tmdb_profile_cache`, `person_media_server_cache`, `similarity_validation_cache`).
- ALL integration config (media server, TMDB key, Trakt, Seerr, MDBList, AI providers, output paths…) lives in `system_settings`, accessed through `packages/core/src/settings/systemSettings.ts` and `core/src/lib/ai-provider.ts` — never read env directly for these.

## Naming traps (easy to edit the wrong module)

- **`discover/` vs `discovery/`** (both in api routes and mirrored in web/core): `discover` = browse people/studios + TMDB-external detail (`/api/discover/*`); `discovery` = missing-content suggestion engine feeding Seerr requests (`/api/discovery/*`). There is also `assistant/discovery/` (web-grounded chat candidates) — unrelated. Its web grounding is **multi-source** via `assistant/discovery/sources/` (a `WebSearchSource` registry): Google grounding (Gemini `google_search`) + Tavily (core `lib/tavily.ts`, config in `system_settings.tavily_integration`, `/api/settings/tavily`). Sources compose (combined into one structuring pass) and fall back for one another; Tavily errors log under the `tavily` provider in `api_errors`.
- **A new AI role is a list, not a union — `AI_FUNCTIONS` (core `lib/ai-capabilities/types.ts`) is the one copy, and `AIFunction` is derived from it.** The roles are also a JSON-Schema `enum` on **ten** Fastify routes (`settings/schemas.ts` ×3, `setup/schemas.ts` ×7), and TypeScript cannot check a hand-written copy of a union against the union. `titleAnalysis` shipped present in the type, in every handler and on the settings card while missing from all ten, so `GET /api/settings/ai/providers|models?function=titleAnalysis` answered **400** — and the card reads a 400 as `data.models || []`, which renders as **"No models available", for every provider**, with the "+ Add custom model" escape hatch rejected by the same rule. The role looked fully configurable and could not be configured at all. Three more copies were runtime `if (!['embeddings', …].includes(fn))` guards (two in `setup/handlers/ai.ts`, one in `settings/handlers/aiConfig.ts`), now `isAIFunction`. Two further places *omitted* a role rather than rejecting it, which is the quieter failure: `getOpenRouterRoles` (`routes/inference/`), where `configured: roles.length > 0` hides the entire measured-spend dashboard — so a library-wide analysis job billed to OpenRouter would have reported nothing — and the pricing summary behind the Cost Estimator. Both iterate `AI_FUNCTIONS` now, and `aiFunctionSchemas.test.ts` walks both schema modules structurally and fails on any role enum that is not the shared list. **The sixth copy was in SQL, where no build could ever see it**: migration `0089` put `CHECK (function_type IN ('embeddings','chat','textGeneration','exploration'))` on `custom_ai_models` and nothing revisited it, so the database rejected *both* later roles from the day they existed. `webSearch` never surfaced it because Google is not a custom-model provider and no request could reach the insert; `titleAnalysis` broke the only path that role has, since it points at a local or OpenRouter model and those catalogs ship zero built-ins — the dialog validated the model, reported "Model validated successfully!", then took a bare **500** from the constraint with the real cause visible only in the container log. `0144` **drops** it rather than extending it, because a sixth copy would drift exactly as the first five did; the guards that replace it are both derived (the route schema enum, plus `isAIFunction` inside `addCustomModel`), and `aiFunctionSchemas.test.ts` now also fails on any migration after `0144` whose `CHECK` names two or more roles. The `custom_ai_models_provider_check` constraint is deliberately left in place: same shape, but it guards a set that changes when an integration is written rather than when a role is named, and it has been maintained (`0090`, `0092`). Two things are deliberately **not** shared. Custom models are keyed `(provider, function_type)`, so an LM Studio or OpenRouter model added under Text Generation does not appear under Title Analysis — the three catalogs shipping zero built-ins (`openai-compatible`, `openrouter`, `huggingface`) need one added per role, which is the normal flow and not the bug above. And `getModel` read `textGenerationModels` only while `getModelsForFunction` fell back to `chatModels` — only Ollama publishes the former, so any cloud model picked for a writing role looked *unknown* when looked up again, losing its display name and its catalog price; both go through `modelPool` now.
- **The Web Search role is Google-only, and the settings card knows it**: `getProvidersForFunction('webSearch')` returns just `google`, and `AIFunctionCard` renders a **label instead of a dropdown whenever a role offers exactly one provider** (it also auto-corrects a selection that isn't on the list, which is what stopped an unconfigured card sitting on the OpenAI default). The role holds **two** keys — `ProviderConfig.fallbackApiKey` alongside `apiKey` — because Gemini's free tier is what usually breaks grounding. Anything spending that quota must go through **`withWebSearchModel`** (core `lib/ai-provider.ts`): it walks `getWebSearchAttempts()` (primary, then fallback, keys parked by a recent 429 last), moves to the next key **only** on a quota error, and writes every attempt to `web_search_usage`. Free-tier limits, `429 RESOURCE_EXHAUSTED` classification (per-minute vs per-day) and the in-memory cooldowns live in `lib/webSearchQuota.ts`; the DB counters and the `/api/settings/ai/web-search/usage` summary in `lib/webSearchUsage.ts` — day windows are anchored to **midnight US/Pacific** and filtered by model, because that is how Google's RPD works. Call sites: `assistant/discovery/sources/googleGrounding.ts` and core `channels/webExpand.ts` use the wrapper; `assistant/discovery/webCandidates.ts` can't (its strict→lenient→text cascade would fight the key loop) so it meters by hand via `recordWebSearchCall` — **a new consumer that skips both will silently undercount the meter**. The fallback key is not in `ai_provider_credentials` (that store is per provider, shared across roles), so the PATCH handler treats an omitted `fallbackApiKey` as "leave it alone" and only an empty string clears it.
- **Two different "cost" surfaces, and only one of them is real**: `CostEstimatorSection` *projects* spend (published per-million prices × assumed call volumes); `InferenceDashboardSection` *measures* it. The measured one is OpenRouter-only because OpenRouter is the only provider that returns spent credits on every response, and it hides itself when no role uses OpenRouter. Capture happens in the **provider's `fetch`**, not at call sites: `createProviderInstance(config, role)` hands OpenRouter a `createOpenRouterUsageFetch(role)` (core `lib/openrouter-usage.ts`) that tees the response, reads `usage` out of the JSON body or the last SSE chunk, and writes `llm_inference_calls`. So **a new generateText/streamText call site needs no instrumentation at all** — but note the `role` is baked in at provider-creation time and is therefore part of the provider cache key. Everything else (`feature`, `sessionId`, `userId`) rides an AsyncLocalStorage (`lib/inferenceContext.ts`) established in exactly three places: `runJob` in `jobs/executor.ts` (tags `job:<name>`, which is what attributes nearly all background inference), the chat handler (`assistant.chat` + conversation id — it wraps `createUIMessageStream`, which invokes `execute` **synchronously**, so the scope covers the whole turn), and `testProviderConnection`. Unwrapped work still records, just as `unattributed`. Cost is nullable end to end and sums skip nulls, so the dashboard reports `pricedCalls` separately — never treat a missing cost as zero.
- **The estimator read $0.00 for every OpenRouter setup**: `PROVIDER_MAP` in `lib/pricing-cache.ts` has no `openrouter` entry *and* `ai-capabilities/data/openrouter.json` ships zero models (they're all user-entered), so `findModelPricing` returned null and the fallback `model?.inputCostPerMillion ?? 0` produced a confident zero. Fixed by resolving OpenRouter through its own catalog (`getOpenRouterModelInfo`, exact id only — `:free`/`:extended` variants are priced differently). `FunctionPricing.pricingKnown` now distinguishes "free" from "nobody could price this"; anything rendering money from it must show the unknown case as unknown, not as $0.
- **The assistant consumes the recommender's output, not its logic.** Of its twelve tools exactly one touches the pipeline — `getMyRecommendations` (`assistant/tools/recommendations.ts`), which reads `is_selected = true` off the newest completed run, so twin and interest fillers do appear in chat. Everything else is a different engine: `semanticSearch`/`findSimilarContent` are bare pgvector kNN over the same embedding tables with **no** novelty term, taste-profile boosts, diversity selection or reserved slots, and the discovery tools are web-grounded. So a niche request answered in chat is served by exactly the mechanism the taste-twin feature exists to compensate for. Each recommendation item now carries `source` (`ranked` | `twin` | `interest`), **derived** from `score_breakdown` by `pickSource` rather than passed through it, because that object also holds `twinMatch.donorId` and the model must never receive an identity it could name; the enum plus a rule in the tool description is the whole fact it needs. A twin pick also carries `sharedTitles` — the same overlap the insights panel renders, resolved through the same `lib/twinShared.ts` the insights routes use. Those are titles from the **reader's own history**, so naming them leaks nothing about the donor, and they are what lets chat explain a borrowed pick concretely rather than gesturing at "someone with similar taste". Resolution is **batched per tool call** (`resolveTwinSharedTitles`), not per item — the tool returns up to 50 picks and a per-item lookup would put 50 round trips inside one chat turn. Unknown or absent markers read as `ranked`, which is what makes pre-slot runs behave. Nothing calls `ContentItemSchema.parse()`, so extra fields survive to the client — `tool-ui/types.ts` mirrors the schema by hand and has to be updated alongside it.
- **Chat's personalized search reuses the pipeline's output instead of re-implementing it.** `searchMyRecommendations` (`assistant/tools/recommendations.ts`) is the answer to "chat is bad at recommending": ANN over the embedding table for the request, joined to `recommendation_candidates` for the newest **completed** run, then re-ranked by `blendQueryAndTaste`. That join is doing three jobs at once — it restricts to titles the recommender scored *for this user*, and because the pool is by construction what they have **not** seen, it applies the pipeline's watched exclusion for free. Three things are load-bearing. (1) **Both terms are min-max normalised over the fetched pool before blending, never used raw** — cosine here sits in the same narrow high band that made centroid similarity useless for twins, so a raw weighted sum would let `final_score`'s wider spread decide everything; `tasteBlend.test.ts` pins that a compressed term still moves the ranking, and that a flat term contributes 0 rather than NaN. (2) `QUERY_WEIGHT` is 0.6 — the request leads, taste breaks ties, because a ranking that puts general taste first answers a question the user didn't ask. (3) `ANN_POOL_SIZE` (400) is fetched before the join, since watched titles drop out of it — and it is paired with `SET LOCAL hnsw.ef_search = 500` inside a transaction, because **pgvector's default `ef_search` is 40 and nothing else in this repo raises it**: an HNSW scan never returns more rows than `ef_search`, so a bare `LIMIT 400` either comes back short or makes the planner drop the index and sequentially scan every embedding. Any new query asking for more than 40 neighbours needs the same treatment, and it must be `SET LOCAL` so it cannot leak onto the pooled connection and change the other vector queries, which are tuned for the default. A new tool also needs its `TOOL_PHASES` entry (`helpers/status.ts`) and a line in `prompts/rules/tools.ts`. Two things this got wrong on the first pass, both user-visible within a day. (1) It passed `recommendation_candidates.rank` as the card's `rank`, and `ContentCard` renders any `rank` as a **RankBadge on the poster** — but that column is the position among *everything the run scored*, so the first two cards read "2012" and "449" as though they were match positions. Search results carry no rank now (`semanticSearch` omits it too); only `getMyRecommendations` sets one, from `selected_rank`. (2) The tool shipped with **no `reason`**, and the prompt rule made it the default for "find me something" — which diverted open requests off the web-discovery path, the only thing that writes per-card reasons, so cards lost their "why". It now calls `enrichCardReasons` like discovery does, and the rule was walked back: **discovery stays primary for open recommendation requests**, and this is the library-scoped answer plus discovery's in-library fallback (replacing `getTopRated`, which sorts by raw rating and knows nothing about the user). `DISCOVERY_PROMPT` now makes the follow-up call **mandatory below 8 resolved cards**, not merely permitted: the old rule was a `MAY` plus a fallback that only fired at *zero*, so a French-noir turn resolving **5 of 19** web candidates satisfied neither branch and the model — having already produced an answer — declined the option. The two tools fail in opposite directions, which is the whole point: `findCandidatesInLibrary` is capped by *the intersection of what the web names and what this library holds*, while `searchMyRecommendations` searches the library itself, so a thin resolve is precisely when recall is missing. A threshold rather than "always" because a healthy turn (9 of 20) would otherwise pad a good answer with weaker picks and spend another embedding + ANN + enrichment call.
- **The taste brief personalises SELECTION, never RETRIEVAL — and an instruction saying so was not enough.** `prompts/context/user.ts` puts both taste synopses and the last ten watches in the chat prompt, but the discovery pipeline's model calls are *separate* and see only the user's message — so "find me something arthouse" searched the web for exactly that, with no idea who was asking. `discovery/tasteBrief.ts` builds a short profile that `discoveryResolve` fetches and hands to `gatherWebCandidates`, which applies it in the **structuring pass** (`webCandidates.ts` `viewerBlock`, prefixed to `structurePrompt`). That call has no search tool: the titles it may return are exactly the ones the sources already retrieved, so a profile there can reorder and tie-break but cannot bend what was looked up. Four rules. (1) **The profile must never reach a search call.** It did, in the first version — two channels, task instructions plus profile in `system`, the question alone as the user message, and an explicit *"do NOT search for the titles in it"* rule. Measured on the live instance, the request "suggest me french film noir movies based on my history" produced **twelve** search queries, every one of them `French film noir` + a descriptor of the user's favourite Lynch film (`surreal`, `dreamlike`, `fragmented narrative`, `puzzles`, `non-linear`, `ambiguous endings`), one naming *Inland Empire* outright — against 6 grounding sources, where a clean "series like Twin Peaks" turn on the same build got 9 from 4 queries. A system message is still context and `google_search` draws on all of it; worse, the user's own *"based on my history"* reads as permission, so the rule loses exactly when personalisation is wanted. `WebSearchSource.gather` therefore takes **only the query** and `WebSearchContext` is deleted — the boundary is the type signature, not a sentence in a prompt. (2) The precedence line stays in the new location: unstated, personalisation quietly overrides the question and "a good horror film" starts returning arthouse dramas. It may order candidates, never add, drop or re-justify them. (3) **Tavily deliberately ignores it** — it is a search API, not a model, and pasting profile prose into a keyword query degrades results; a new source must make the same call for itself. What Tavily *does* get is a **reasoning cue appended to the request**, because its `answer` is LLM-written from the retrieved results and there is no separate answer prompt — one string serves both retrieval and synthesis. That matters because the structuring pass omits any title arriving without a real "why", and bare snippets are exactly what a plain query returns: **Tavily can supply half the grounding text and none of the candidates**, and every log line looks identical either way (nothing tracks per-candidate provenance — to test, disable the Web Search role and see whether Tavily alone still yields a healthy `candidateCount`). Hence also `include_answer: 'advanced'` rather than a bare `true` (credits are charged on `search_depth`, so the longer answer is free), and the answer gets **its own char budget** — `maxContentChars` is a per-*snippet* cap and applying it to the answer meant lowering it to trim snippet bloat destroyed the only reasoned part of the response, removing it entirely at the 100-char floor. Fails soft to null, which restores the previous un-personalized behaviour. (4) The titles it carries are **signature** ones (favorite → play count → recency, mirroring `recommender/movies/taste.ts`, gated on `WATCH_HISTORY_TASTE_SQL`; both inlined because neither is exported from a core barrel) and it **groups by title**, because a `watch_history` row is an *episode* — the ten most recent rows on the live instance held `Silo` four times, so the old `last_played_at DESC` list could name one show six times. **Establishing the brief's influence took two attempts, and the first inference was wrong**: a "like Meshes of the Afternoon" request issued twelve grounding queries, six of them `«Title» + seed + "comparison"`, matching the six-entry list in count — but five of those titles appear in *no* watch history on the instance, so the model was working from its own knowledge, and the `(1932 film)` suffix was Wikipedia's disambiguator rather than this file's `Title (Year)`. The French-noir turn above is the real proof, because *Inland Empire* appears nowhere in the request and the call carried no conversation history. `personalized: true` in the `web-candidates` log now means only that a brief was **built and will be applied at structuring** — it says nothing about retrieval, which no longer receives it. Note also that a longer query list costs **no extra quota**: Gemini's free tier limits requests per day, so twelve queries inside one grounded call meter identically to six — a bad title list costs relevance and context, never spend. **Open, and measured: the empty-text retry is not metered.** `recordWebSearchCall` fires once per *key attempt* in `withWebSearchModel` ([ai-provider.ts:623](packages/core/src/lib/ai-provider.ts:623)), but `googleGrounding`'s `PASS1_MAX_ATTEMPTS` loop sits **inside** that attempt, so a grounding call that returns empty and retries makes two requests Google counts and writes one row to `web_search_usage`. Seen live: "suggest me french noir movies **based on my watched history**" returned zero queries and zero text on attempt 1 — a soft refusal at the deictic phrase, absorbed silently — then produced twelve queries on attempt 2. Fixing it is not just a counter: the retried request succeeded at HTTP level and returned nothing, which is neither `ok` nor `rate_limited` nor `error`, so it likely wants a new status rather than being folded into an existing one.
- **The intent router decides whether the web search exists at all, and its axis is the *answer*, not the wording.** `helpers/routeIntent.ts` classifies each turn `discovery` or `library`, and `findCandidatesInLibrary` — the only tool that searches the web or writes card `reason`s — is added *only* on discovery turns (`handlers/chat.ts`). So a misroute is not a degraded answer, it is a different engine, and nothing downstream can recover it. The taxonomy originally read *any* reference to the user's collection as a library question, which sent **"suggest film noir movies based on my history"** to `library`: the user asked for personalized recommendations and got thirty films they had already watched. The rule now is that a request for titles to watch is `discovery` **even when personalized**, because the discovery path *is* the personalized one — `discovery/tasteBrief.ts` feeds the profile into the grounding call, so "based on my history" says how to aim the search, not what kind of answer to give; `library` means the answer is *facts about their collection* (history listing, counts, ratings, do-I-own-X, what to resume). Four things are load-bearing. (1) There are **two layers, and only one is appealable**: `prefilterIntent` (pure, exported, pinned by `routeIntent.test.ts`) decides with no LLM at all, so a bad match there is final — which is why `RECOMMENDATION_HINTS` is checked first and wins outright, and why `LIBRARY_HINTS` no longer matches bare taste statements (`i like|i love|i watch`), which used to let "I like noir, what's good" hard-route away from the web. (2) **Ambiguity resolves toward discovery** because a discovery turn suppresses only three list builders (`DISCOVERY_SUPPRESSED_TOOLS`) and keeps history/ratings/stats, while a library turn has no web tool — discovery is nearly the superset. (3) The **error** path still falls back to `library`, deliberately: a routing failure is not a routing doubt, and `DISCOVERY_PROMPT` orders a web search that a counting question doesn't want. (4) A library-routed model reaching for `getWatchHistory` produces watched titles **even with `excludeWatched` on**, since it is in `EXEMPT_TOOLS` — and because every tool returning `items` renders as cards, a lookup the model intended as context becomes the visible answer. That last one is a design gap, not a bug: there is no way to call a tool privately.
- **The chat can query watch history by content, not just by recency — `getWatchHistory` alone could not, and that produced confident false negatives.** Its entire input schema is `type` + `limit` (`tools/history.ts`), ordered `last_played_at DESC`: no genre, era, country, director or concept, and `limit` is unclamped, so "more rows" was never the fix. Meanwhile `searchContent`/`semanticSearch` search the **library** and touched `watch_history` only to *exclude*, and `ContentItem` had no watched marker — so "list me the french film noir movies I watched" asked for an intersection the model could compute from nothing but a 50-row recency sample, and it answered *"you haven't watched any"*, three times, twice with the unwatched filter off. Three pieces fix it, all small because the machinery existed. (1) **`watchStatus: 'all' | 'watched' | 'unwatched'`** on both search tools (`watchStatusCondition` in `tools/search.ts`) — the `NOT IN` half was already written in three places; this adds the `IN` half. On the semantic path it must run inside a transaction with `SET LOCAL hnsw.ef_search = 500`: pgvector post-filters a WHERE predicate and an HNSW scan never yields more rows than `ef_search` (default 40), so a filtered `LIMIT 20` comes back nearly empty and the filter looks broken. (2) **`ContentItem.watched`**, stamped by `annotateWatchedItems` (one round trip per result page, `helpers/unwatched.ts`). It is **absent when not looked up**, which is not the same as false — the card branches on `=== true`, and the schema description tells the model the same. (3) `withUnwatchedFilter` skips a call whose `input.watchStatus === 'watched'`: same reasoning as `EXEMPT_TOOLS` but decided **per call**, since one tool now serves both kinds of request. Only `'watched'` overrides — `'all'` is the model's default, not a user intent. Also added a `country` filter (see the next entry — the `language` filter added alongside it was a mistake and is gone), and fixed `director`/`tag`, which used `$n ILIKE ANY(directors)` — backwards, since in `a ILIKE b` the *right* side is the pattern, so it asked whether the literal string `%Nolan%` matches the pattern `Christopher Nolan` and matched nothing. They now use `directors::text ILIKE $n`, the form `actor`/`studio` always used.
- **"French film noir" was inexpressible, and the tool surface hid that behind three separate silent zeroes.** Asked to list them, the chat ran ten `searchContent` calls, every one returning 0 rows, then exhausted `stopWhen: stepCountIs(5)` and ended the turn with **no prose at all** — the user saw five "No results found" strips and a semantic carousel of Kurosawa and Turkish prison drama. Three compounding causes, none visible from the logs (which record tool names and result counts but not arguments). (1) **`languages` is populated for 88 of 12,584 movies — 0.7%.** It is written in exactly two places, both in `enrichment/index.ts`, both from OMDb's `Language` field; no media-server sync path touches it. `production_countries` by contrast is 99.4% populated (`movies/sync.ts` writes it from Emby's `ProductionLocations`) and holds **1,688** French films. The `language` filter shipped with the description *"use for 'French films' etc."*, which routed the one phrasing that mattered at the one column that is empty — so the filter is now **deleted**, not documented around: a parameter that works on an OMDb-enriched instance and silently returns nothing everywhere else is worse than an absent one. (2) **`query` matches literal text in `title`/`overview`**, but the prompt rule said *"French film noir" → country: "France" + query or genre for the noir part*. Almost no noir has "noir" written in its title or synopsis and there is no Film Noir genre, so both branches of that instruction returned zero. The rule now routes style→`semanticSearch(concept)` and fact→filters, and `query`'s own description says outright that it is not a concept search. (3) **`semanticSearch` had no `country`**, so the only tool that understands "film noir" as a *style* could not be scoped to France — which is why it answered with *Stray Dog*. It takes `country` now, through the same `hasPostFilter` → `SET LOCAL hnsw.ef_search = 500` path the watch-status filter uses, since a country predicate post-filters the ANN scan identically. The remaining trap is the demonym: `production_countries` stores *"France"* while a user says *"French"*, and `'{France,Italy}' ILIKE '%French%'` is **false** — a prompt can ask the model to say "France" but a rule that must win against the user's own wording every turn is not a fix, so `helpers/countryMatch.ts` maps ~120 nationalities to the stored name. Its values are deliberately **substrings rather than exact names** so one entry covers the variants: `United States` matches "United States of America", `Germany` matches "West Germany", `Czech` matches Czech Republic / Czechia / Czechoslovakia. Unknown input passes through unchanged. The reason the turn produced *nothing at all* rather than a bad answer was separate, and is the next entry.
- **A step is a model round trip, and the last one was always wasted.** `stopWhen: stepCountIs(MAX_STEPS)` in `handlers/chat.ts` is consulted **only after a step that called tools**, so the final step's results are fetched, streamed to the client as cards, and then never sent back to the model — the loop ends with nobody left to read them. A turn that spent every step searching therefore ended with **no prose at all** (five "No results found" strips and silence), because tool results reach the UI through `renderToolResult` independently of the model composing anything from them. Three consequences. (1) The effective tool budget was always `MAX_STEPS - 1`, since results from the last step cannot influence output; `prepareStep: ({ stepNumber }) => stepNumber === MAX_STEPS - 1 ? { toolChoice: 'none' } : undefined` therefore costs **no retrieval** — it repurposes a step that was already dead into the one that writes the answer. `stepNumber` is 0-indexed (`stepNumber: steps.length` in the SDK). (2) Raising `MAX_STEPS` does **not** cost tokens on healthy turns — a two-step turn pays for two steps whatever the ceiling — but each step resends the entire system prompt *plus all accumulated tool results*, so late steps are much more expensive than early ones and the cost grows superlinearly within a turn. Raising it alone also fixes nothing: a model looping on failing searches burns 10 as easily as 5. The guard is what makes a higher ceiling safe, because a turn can no longer end without prose. (3) Hitting the guard logs `warn` "Step budget exhausted" — reaching it means every search was spent, which is a signal about the *tools*, not the model, and it was previously invisible.
- **A carousel heading can assert a claim the retrieval cannot support.** `semanticSearch` is bare kNN with no distance floor — it returns its k nearest however far away they are — and it titled them *Movies matching "{{concept}}"* over *Found {{count}} titles matching your search*. For a query with no good match in the library that is the UI vouching for results it has no basis to vouch for. The strings now say *Movies closest to "…"* / *The {{count}} nearest titles in your library*: same rows, a claim that is true. A **distance cutoff was deliberately not added** — this repo has twice measured a cosine band far too narrow to threshold blind (twin centroids spanning 0.898–0.993, `avgNovelty` pinned in [0.8, 1.0]), so the query→item distribution has to be measured before any number is picked. Note also the separate case the headings cannot fix: on a broad tool call the cards are *honest but are not the answer* — a request for French drama answered by `searchContent(genre: "Drama", watchStatus: "watched")` renders 50 dramas of every nationality under prose naming nine French ones. That is what `format: 'brief'` plus an explicit display call would solve, and it costs a step the budget above does not have.
- **The enrichment job could not tell "already done" from "never asked", and that froze OMDb out of an entire library.** `enrichment_version` (migration `0068`) records which *schema* version was current when a row was touched — **not which sources answered**. `enrichMovie`/`enrichSeries` stamp it and `enriched_at` on every pass, whether OMDb ran, was disabled, held no key, was skipped for a missing `imdb_id`, errored, or found nothing; the selection then reads `WHERE enriched_at IS NULL OR COALESCE(enrichment_version, 0) < $current` and excludes that row **forever**. So a library enriched before OMDb was configured is stamped complete, and adding the key afterwards does nothing at all. Measured live: `movies.languages` populated for **88 of 12,584** rows (0.7%), with `rt_critic_score`, `metacritic_score` and `awards_summary` equally bare — while `getEnrichmentVersionStatus` reported **zero outdated**, because by its own definition they were. Four things are load-bearing. (1) The fix is `omdb_enriched_at` (migration `0136`), stamped only when the call was **attempted and did not throw**. "Not found" counts as attempted — OMDb genuinely has no entry for some titles and retrying them every pass would never end — while an error does not, so a transient outage retries next run. That distinction needs the discriminated `OmdbOutcome`, since `data: null` alone cannot express it. (2) The predicate is now **one function**, `enrichment/pending.ts`'s `needsEnrichmentSql`, split out of `index.ts` so it is testable without a database (same reason as `watchedExclusion.ts`). It previously lived in four places — two counts and two selections — which agreed only by being wrong identically, and that is exactly why nothing looked broken: the progress counter said nothing was pending and the selection returned nothing, in perfect agreement. Keep them on the shared builder or a count that drifts from the selection makes a run appear to stall or finish early. (3) The OMDb clause is **conditional on OMDb being usable**, and the guard matters in the other direction too: with OMDb off nothing could ever satisfy it, so every row would stay permanently pending and each pass would re-run TMDb across the whole library without the job ever reaching "nothing to do". (4) `0136`'s backfill reads evidence from `awards_summary`/`languages` **only** — `rt_critic_score`/`metacritic_score` are written by `mdblist/enrichment.ts` as well, and `production_countries` by `movies/sync.ts` on every sync, so none of those prove OMDb ran. Two consequences worth remembering: `clearEnrichmentData` clears the new column too but is **still called by nothing** (no route, no job, no button — the only enrichment "clear" in the API is `clear-interrupted`, which clears a stuck *run record*), and the cost of a backfill is set by the OMDb tier, since `omdb/client.ts` throttles to 10 req/sec against a 1,000/day free cap versus 40 on patron — the same job is a two-week trickle or a single pass depending on the key.
- **"Attempted and did not throw" was the wrong boundary, because the OMDb client never threw.** The first thing the fixed job did on the live instance was fail every request with `HTTP 401` and log every title as `OMDb: not found` — stamping the whole library complete again, one migration after `0136` unstamped it. `omdbRequest` returned `null` for a non-OK response *exactly* as it does for a genuine "Movie not found!", so `OmdbOutcome` read a transport failure as an answer. Five things came out of fixing it, and the last is the one that bites. (1) **A null return now means "OMDb has no entry" and nothing else**; every other outcome throws `OmdbRequestError`. The classification is pure and pinned in `omdb/failures.ts` — same split-for-testability as `pending.ts`. (2) **OMDb answers 401 for both an invalid key and an exhausted daily quota**, and only the JSON body separates them; the client read `response.status` and returned before touching it, so the logs could say nothing but "HTTP 401" for two faults with opposite fixes. `errors/omdb.ts` had *already* recorded this in a comment and defined both body patterns — the client just never called `parseApiError`, which is also why OMDb was the one integration whose outages never reached the API Errors page. `testOMDbConnection` had the same hole and returned `API returned status 401`, from the one button whose entire job is to say what is wrong. (3) OMDb also returns auth and quota errors as **HTTP 200 with `Response: "False"`**, so the old "False means not found" branch retired rows on the strength of a reply saying the key was invalid; `isNotFoundBody` is a closed list and anything unrecognised is a failure. (4) A bad key is a fact about the *account*, so the client **latches** it for ten minutes rather than making one doomed round trip per library item (a full pass of `OMDB ✗ … (HTTP 401)` is what this looked like). It expires because the fix is often activating the existing key at omdbapi.com, which changes nothing the code can observe. Keys are `.trim()`ed on write and read — a pasted newline reaches OMDb as a different string while looking perfect in the settings field. (5) **`enrichMetadata`'s `while (true)` loops only exit when the pending selection empties, so not stamping a failed row spins them forever** — and over-stamping was what had been holding that together. Both loops now attempt each row at most once per run (`attemptedMovieIds`/`attemptedSeriesIds`); the rows stay pending for the *next* run, which is the entire point of not stamping them. Any future "leave it pending" outcome needs the same guard. Migration `0137` clears stamps carrying no OMDb evidence, the inverse of `0136`'s test and deliberately over-broad: it also clears genuine not-founds, because an extra request is cheap and a wrongly retired row is permanent.
- **A library row has three names, and the assistant used to know only one.** `movies`/`series` carry `title`, `original_title` and `sort_title`; on the live instance **12,563 of 12,584 films have an original title and 3,739 (30%) differ from the title** — *Elevator To The Gallows* is stored beside *Ascenseur Pour L'échafaud*. The ingest was never the problem: `MOVIE_LIST_FIELDS`/`SERIES_LIST_FIELDS` request `OriginalTitle` and `SortName`, both Emby and Jellyfin mappers read them, `movies/sync.ts` writes them on insert **and** both update paths, and `0060` already trigram-indexes `original_title`. Every *reader* compared `title` alone. Three distinct failures came out of that, and the fuzzy one was the least damaging: (1) `resolveCandidates` Tier 3 searched `title` only; (2) **`idMatchValid` threw away correct ID hits** — an exact `imdb_id` match was rejected because the row's English title had no overlap with the candidate's French one, so tiers 1 and 2 were defeated too; (3) `normalizeTitle` stripped `[^a-z0-9]`, which **deletes** accented letters rather than folding them, so `"L'échafaud"` → `l chafaud` while `"L'echafaud"` → `l echafaud` — the same film failing to match itself. All title comparison now goes through `helpers/titleMatch.ts` (NFD + combining-mark strip, plus a ligature map for `æ ø ß ł đ þ` which have no decomposition), which also replaced **three** identical copies of the normalizer in `resolveCandidates`, `webCandidates` and `discoveryResolve` — they must agree, or a title survives dedupe and then fails to match. The SQL half is `anyTitleMatchesSql`/`titleMatchRankSql`: all three columns, wrapped in `unaccent()` (migration `0134`; safe because `0060` already creates `pg_trgm`, so contrib is present) so an unaccented source string still finds the accented row. Localized title outranks original outranks sort — the name on the poster must win. Applied to all five lookups: Tier 3, `getContentDetails` ×2, the `findSimilarItems` seed ×2, and `searchContent`'s text filter. Two things to keep in mind: `unaccent()` is STABLE, so it **costs the trigram index** and falls back to a seq scan (milliseconds at 12.5k rows, inside a tool call taking tens of seconds — `0134` records the IMMUTABLE-wrapper recipe if the library grows), and a non-Latin title normalizes to **empty**, which `titlesOverlap` deliberately treats as *no match* while `idMatchValid` treats as *trust the id* — the two callers want opposite defaults, so the helper stays out of it.
- **A tool call can now be private: `format: 'cards' | 'brief'`.** Every tool result carrying `items` renders as a wall of posters, so a model calling a tool to *inform itself* made a lookup the visible answer — most starkly when it fetched fifty recent plays, found no French noir among them, and announced none had been watched with fifty unrelated posters underneath. `brief` (on `getWatchHistory`, `getUserRatings`, `searchContent`, `semanticSearch`) returns `{ id, brief, count }` and **no `items` key at all**. That omission is the whole mechanism: `Thread.tsx`'s `renderToolResult` dispatches on shape (`carousels` → `items` → `contentId` → `people` → `movieCount` → `studios`) and falls through to `return null`, so there is **no client change and both renderers agree for free** — a brief result must never accidentally carry one of those keys. It is also far cheaper: a `ContentItem` hauls a poster URL, synopsis, director and action hrefs that a lookup never uses. Only the model can know why it is calling, which is why this is an input rather than a per-tool flag — `getWatchHistory` is genuinely the answer to "what have I watched" and genuinely context before a recommendation. The search tools build their brief **after** `annotateWatchedItems`, so a private lookup can answer "have they seen these?", which is the main reason to make one; they also keep a `yearById` map because `ContentItem` folds the year into `subtitle`. `FORMAT_PARAM_DESCRIPTION` and `briefResult` live in `tools/utils.ts`, and there is a matching rule in `prompts/rules/tools.ts` — a new lookup-prone tool needs both.
- **Episode embeddings had no reader for their entire existence, and now have exactly one.** `episode_embeddings_*` is the largest embedding table on any real library — one row per episode against one per show, measured live at **16,591 rows / 535 MB against 987 series / 33 MB** — and `generateMissingSeriesEmbeddings` filled it unconditionally via `includeEpisodes = true`, a default parameter no caller ever passed. Nothing read it. `getEpisodeEmbedding` and `getSeriesEpisodeEmbeddings` (the latter commented *"for computing series taste from episodes"*) were exported through three barrels and called by nothing; every other reference was a count, a `DELETE` or a `TRUNCATE`. So every new episode bought an embedding call for an index with no consumer. Note the fear that motivates aggregating them is unfounded in the other direction too: **nothing pools episode vectors into the series vector**, so a 20-season show and a 6-episode miniseries contribute exactly one vector each — `buildSeriesCanonicalText` describes the show and its only trace of episodes is the literal string `"5 seasons, 62 episodes"`. Where episode *count* could have skewed things is the taste profile, and that was already handled: `calculateEngagementWeight` uses `log10(episode count)` precisely so a 400-episode show cannot outvote five finished miniseries. The reader is now `searchEpisodes` (`assistant/tools/episodes.ts`), which is the **only** tool that knows what happens inside an episode — "the one where they get stuck in the desert" is unanswerable from the series index however good it is. Six things are load-bearing. (1) **`ContentItem.id` is the EPISODE id**, because `ContentCarousel` keys React on it and two episodes of one show would collide; navigation travels separately as `episode.seriesId`, which `ContentCard` prefers when present. No `'episode'` member was added to the `type` enum on purpose — type drives watched lookups and detail routes throughout the client, and a third value would need handling in every one of them to fix a problem the extra field already solves. `tool-ui/types.ts` mirrors it by hand, as always. (2) The tool is in **`EXEMPT_TOOLS`**: an episode id matches neither a movie nor a series, so `withUnwatchedFilter` is a silent no-op on it — and it *should* be, since "which episode of X was the desert one" is asked about a show the user has by definition been watching, so filtering on the parent would empty the answer. Episode-level watch status is a tool parameter instead. (3) Any post-filter needs `SET LOCAL hnsw.ef_search = 500`, and **series scoping is the worst case in the repo** — one show is a fraction of a percent of the episode index, so at the default 40 the filter returns nothing and looks broken. (4) The subtitle puts the **year first** because `ContentCard`'s `splitMeta` only lifts a leading four-digit segment into the title parens; any other order silently drops it into the meta line. (5) `createEpisodeTools` returns `Promise<ToolSet>` and reads the setting **itself**, mirroring `createN8nTools` — a conditional spread at the call site instead made every tool `T | undefined` in the merged object and broke `onStepFinish`'s typing. (6) Generation is governed by `system_settings.episode_embeddings_enabled` (**default on**, Settings → AI Config → Episode Embeddings), and with it off the tool is absent rather than empty, so the model says it cannot search episode content instead of reporting a confident false negative. Disabling and deleting are **separate actions** (`PATCH` vs `POST /api/settings/ai/embeddings/episodes/clear`): the first is free to reverse, the second costs a re-embed of every episode. Episodes remain excluded from the `text_version` staleness scheme, so their selection is still missing-only.
- **Version identity is a fork problem, and there were five disagreeing strings.** `routes/api.ts` said `0.1.0`, `routes/health` said `0.7.8`, two OpenAPI examples said `0.7.8`, and `apps/api/package.json` said `0.7.8` — nothing read anything else. `config/version.ts` is now the only source. It exposes **two fields rather than one string**, deliberately: `APP_VERSION` is the upstream lineage this fork tracks (dgruhin-hrizn/aperture) and `APP_BUILD` is the fork build. Joining them forces a SemVer question with no good answer — `0.7.8-mod.412` is a *pre-release* and sorts **below** plain `0.7.8`, which is backwards for something that is 0.7.8 plus work, while the semantically-correct `0.7.8+mod.412` uses a `+` that is **illegal in a Docker tag**. Keeping them apart sidesteps it; `fullVersion()` still joins with `-` for single-string surfaces, where the mis-sort costs nothing because nothing resolves ranges against this app. Both come from Docker build args set by CI: `APP_BUILD` is `mod.<commits>.g<shortsha>` (`git describe` shape — count for a monotonic build number, SHA so a history rewrite can't create a collision). **`fetch-depth: 0` on both build jobs is load-bearing** — `actions/checkout` defaults to depth 1, which would make `git rev-list --count` return 1 and every build `mod.1`. Outside CI the args are empty and the code falls back to `dev`, so a hand-built image never claims to be a release. The `ARG`s sit in the runtime stage, after the build stages, so bumping a version does not invalidate their layer cache.
- **Assistant suggestion chips read the same picks and must use the same rule**: `assistant/jobs/refreshSuggestions.ts` selected every `is_selected` row a user had *ever* been given — no `status='completed'`, no media type, no newest-run bound — so a chip could name a film from a run superseded weeks ago, which `pruneOldRecommendationRuns` guarantees is still lying around (it keeps selected rows on old runs by design). Now pinned to the newest completed movie run and ordered by `selected_rank`, not `final_score`: rank is what the user sees on their recommendations page, and `final_score` would systematically bury reserved-slot picks, since a twin pick is by construction the one the ranking did not choose.
- **Assistant tool results are post-processed**: `assistant/helpers/unwatched.ts` wraps every tool (`withUnwatchedFilter`, on when the request carries `x-exclude-watched` from the composer's "unwatched only" checkbox) and strips watched items out of any `items`/`carousels[].items` it finds. Tools that report on what the user *has* watched are listed in `EXEMPT_TOOLS` — add new ones there or they'll come back empty.
- **Assistant chat status line**: the whole turn runs inside `createUIMessageStream`'s `execute` in `assistant/handlers/chat.ts` so each phase can emit a transient `data-status` part (`assistant/helpers/status.ts`). `withStatusEvents` is a **third** cross-cutting tool wrapper alongside `withUnwatchedFilter`/`withToolErrorHandling` — a new tool needs a `TOOL_PHASES` entry or it reports the generic "Working on it…". Phase names are i18n key fragments resolved as `assistant.status.<phase>`, never English. `discoveryScouting`/`broadening` cover web-facing work and their wording must stay ambiguous about that. Client side: assistant-ui renders `data-*` parts as `null`, so they're caught in `useChatRuntime({ onData })` and passed via the `assistantStatus.ts` module store to `Thread.tsx`'s `LoadingIndicator`. Note `toUIMessageStream` needs `sendStart: false` (a second `start` opens a second assistant message) **and** its own `onError`, or mid-stream provider failures lose the coded `AI_ERROR:` text.
- **A chat answer has two renderers, and prose always goes first**: a live turn comes from the assistant-ui runtime (`AssistantMessage`), a reloaded one is rendered by hand from the DB (`HistoricalAssistantMessage`) — the runtime deliberately starts empty. They must agree, and they didn't: the model calls tools before it writes, so parts arrive tool-first, while the save path (`AssistantChatSurface`'s `MessageSaver`) splits a message into a text column and `tool_invocations` and the historical renderer draws text first. `OrderedMessageParts` (`Thread.tsx`) hoists text-part **indices** above the rest and renders each via `MessagePrimitive.PartByIndex` — DOM order, not CSS `order`, so selection and screen readers match. A change to one renderer needs the same change in the other. **Those indices must come from `useAssistantState(({ message }) => message.parts)`, never `useMessage`**: assistant-ui has two independent `useSyncExternalStore` subscriptions (the legacy message runtime behind `useMessage`/`useThread`, and the api store behind `useAssistantState`), `PartByIndex` resolves its index against the api store's part map, and there is no ordering guarantee between two stores — reading the list from the legacy one tore mid-stream, `PartByIndex` threw `tapLookupResources: Resource not found`, and since the app had no error boundary anywhere that unmounted the entire SPA. `ThreadErrorBoundary` now wraps `Thread` inside `AssistantRuntimeProvider` so a chat render error can only cost the chat. Because prose now sits on top of a card list several screens long, `ThreadScrollControls` scrolls the start of the answer to the viewport top once per turn (when prose appears, or at turn end), skipping it if the reader has scrolled away; both renderers tag their outer row `data-aperture-answer` so it can find the last answer, and a row with no parts yet is `display:none`, so the lookup skips zero-height boxes.
- **Chat cards remember the request**: `assistant/helpers/requestContext.ts` (`withRequestContext`, the **fourth** cross-cutting tool wrapper, applied outermost in `chat.ts` so it stamps the finished result) copies `latestUserText` onto every `items`/`carousels[].items` container as `request`. It rides along in the persisted `tool_invocations`, so it survives a conversation reload. Its consumer is the chat's "create playlist from these" dialog, which posts `chatContext: { request, reasons }` to `/api/graph-playlists/ai-name|ai-description`; that switches core's `PlaylistTextMode` to `'chat'` (`lib/ai-playlist-generation.ts`), whose prompts treat the request as the brief. The field is optional end-to-end — the Explore-graph `CreatePlaylistDialog` posts without it and stays in `'graph'` mode, which claims the playlist came from a similarity exploration. Both routes also take an optional `userNotes` (the current contents of the box being generated into), sent by *both* dialogs' sparkle menus and orthogonal to mode.
- **Channel generation is two-phase**: the web refresh button calls `POST /api/channels/:id/preview` (builds the list, writes nothing), then `POST /api/channels/:id/generate` with `{ itemIds }` — that body makes the writers skip generation and push exactly the approved set (`ChannelUpdateOptions.itemIds`). A bodyless `generate` still generates-and-pushes, which is what the scheduler path (`processAllChannels`) does. **`preview` is not cheap**: besides `buildChannelItems` it runs `generateChannelPickReasons` (core `channels/reasons.ts`) — one text-generation call per 8 non-seed picks — to write the "why this is here" note on each preview card. Fails open (no writing model → no notes, never an error), and seeds are excluded by design.
- **A channel's description is media-server metadata, not just a DB column**: it ships as the playlist/collection Overview. `updateChannelPlaylist`/`updateChannelCollection` pass it on every generate, and `syncChannelDescription` (core `channels/describe.ts`, called from `PUT /api/channels/:id`) pushes it alone when the text is edited and saved — editing a description must never re-write the item list. An empty description leaves the server's existing overview alone rather than blanking it. Renaming a channel still orphans the old Box Set/playlist, since lookup is by name.
- **One dialog, two i18n namespaces**: `pages/playlists/components/PlaylistDialog.tsx` is the editor for *both* playlists and collections — `pages/collections/` renders it with `i18nNamespace="collections"` and every label goes through `pt(key)`. So a new string must be added to **both** `playlists` and `collections` in `en/translation.json` (the two blocks are near-duplicates that differ only in the words "playlist"/"collection"), or one surface renders a raw key. Its AI sparkle buttons post to `/api/channels/ai-preferences|ai-name|ai-description`.
- **Every AI sparkle button offers "build on what I wrote"**: all five text-generation routes (`channels/ai-preferences|ai-name|ai-description`, `graph-playlists/ai-name|ai-description`) take an optional `userNotes` — whatever is already in the box. Sent only for "build on what I wrote", omitted for "start fresh", which is what lets a re-roll escape its own last answer. Core puts it at the head of the prompt (`buildUserNotesBlock` in `lib/ai-playlist-generation.ts`, above even the chat request) and `hasUserNotes` on `generatePlaylistText` adds the rule that stops the model treating it as one more input to overwrite. The button becomes a menu only when its own box is non-empty; labels are the shared `aiBuildOnNotes`/`aiStartFresh` keys.
- **One AI-explanation setting, three surfaces that must agree**: `getEffectiveAiExplanationSetting(userId)` (core `lib/userSettings.ts`, three-tier: global → admin grants override → user's choice) now gates *generation* in both pipelines, the NFO `<plot>` credit line in `strm/*/nfo.ts`, and whether `/api/recommendations/:userId/(movie|series)/:id/insights` returns `aiExplanation` for `MovieInsights.tsx` to render. Gating generation is what makes the toggle mean something: before, every run paid for a text-generation call whose only consumer was a column the web app never selected. Consequence to keep in mind — **turning it back on does not backfill**; runs made while it was off have `ai_explanation` NULL forever, so both the plot and the panel stay bare until the next run. The insights route deliberately resolves the **target user's** setting, not the viewing admin's. The credit line's brand comes from `getAppName()` passed down as `NfoGenerateOptions.appName` (the generators stay pure and fall back to `DEFAULT_APP_NAME`) — it used to be a hardcoded "Aperture" that contradicted the renamed instance shown everywhere else. `strm/nfo.test.ts` pins all of this.
- **A reasoning model spends the explanation's token budget on thinking, and one truncated character used to discard the whole batch.** Both generators ask for ten explanations as one JSON object, and a `JSON.parse` failure replaced *all ten* with `generateFallbackExplanation` — a template so plausible ("Based on your enjoyment of X, this Drama shares similar qualities you'll likely appreciate") that the page reads as a model that has quietly got worse rather than one that never spoke. Measured live on DeepSeek V4 Flash: three parse errors of the form *"Unterminated string in JSON at position 3068"*, with `llm_inference_calls` showing `completion_tokens` pinned at exactly **3000** on those calls and `reasoning_tokens` of 2079 and 2283 — leaving ~700–900 tokens for ten explanations that need ~1,200. Reasoning is billed from the **same ceiling as the prose**, and it swung 0→2,283 across twenty consecutive calls, which is why the failure was intermittent and why most runs looked fine. Five things. (1) `shared/explanationParsing.ts` is now the one home for both the numbers and the reading; the two generators held **identical private copies** of `getExplanationBatchSize`, which is exactly how one could have been raised without the other. (2) The large-context ceiling is **16000**, not a number close to the observed sum: `maxTokens` is a cap, not a reservation, so headroom is free on a healthy call and is the whole answer on a bad one. The Groq/Ollama tiers are deliberately **not** raised — theirs are bounded by the model's whole context window, so a bigger output budget trades this bug for a worse one. (3) `parseExplanationResponse` tries strict JSON first and salvages entry-by-entry only when that fails, keeping every finished explanation and skipping the half-written one a truncation ends on; it handles the reversed key order and decodes escapes, so a `\"noir\"` doesn't terminate an entry early. **The first version of that salvage was a regex, and it produced a second and worse incident — see the next entry.** (4) **`finishReason === 'length'` is the direct tell** and is logged whenever the strict reader rejected the response; token counts are deliberately *not* repeated in that log, since `llm_inference_calls` already records them with the reasoning split. (5) A degraded batch is no longer silent — it used to be indistinguishable from success.
- **Recovering from a broken response is inference, and inference that reaches the page has to be a whole sentence.** The salvage above shipped and immediately caused a worse failure than the one it fixed: every explanation on the detail page became a sentence fragment — *"If"*, *"Given how much you loved the quiet human connection of"* — while the job logged `generated: 20` and no warning at all. Three things combined. (a) The model writes film titles in bare double quotes **because the prompt does**, on every line (`"${m.title}"`, `"${e.title}"`), and does not escape them, so the document is not valid JSON and salvage has to read it. (b) The salvage pattern's string body `(?:[^"\\]|\\.)*"` stops at the first unescaped quote, so `...the moral murk of "Parasite", this...` matched up to the quote before the title and stored the lead-in as a finished explanation. (c) The caller's only check was `byIndex.size < movies.length` — ten fragments is not a short batch, so nothing warned. **Measured on the affected run**, and the numbers are worth keeping because they show the failure is per *response* rather than per explanation: `selected_rank` 1–10 were fragments of 2–107 characters containing **no** double quote at all, 11–20 were 414–483 characters and every one contained quotes. The split falls exactly on the batch boundary (`batchSize` 10) — one document failed to parse and had every quote-carrying entry cut at its first title, the next parsed strictly and kept everything. So "titles in quotes render fine" and "titles in quotes broke it" are the same fact seen from either side of a batch, which is why this looked intermittent and unrelated to quoting. Across every stored run on the instance exactly one batch was affected. Four rules now. (1) **Where a string ends is decided by structure, not by the first quote**: `isValueEnd` accepts a quote only when what follows is `}`/`]`, a comma introducing the next `"key":`, or nothing at all. A bare `"\s*[,}\]]` lookahead is *not* enough and fails on the commonest phrasing there is — in `I loved "Heat", but colder` the quote after Heat is followed by a comma. (2) **Anything salvaged must still read as a finished sentence** (`looksComplete`: 40 chars and terminal punctuation, closing quotes allowed after it). This applies to the salvage path **only** — a strict parse returns exactly what the model wrote, so a terse explanation there is its judgement and not a reading error. The guard is what covers the genuinely ambiguous case, where a response ends right after a quoted title and the final quote is equally plausibly a terminator or a title close. (3) **`describeExplanationBatch` is shared** by both generators, because the condition that let this through was duplicated and the whole point of the module is that the two cannot drift; it reports any response the strict reader rejected, not merely a short one, and puts `finishReason === 'length'` first because that is a cause rather than a symptom. (4) The prompt now says not to write double quotes in the explanation text — worth doing at the source, but it is a request, so the reader holds regardless. `explanationParsing.test.ts` pins the exact live shapes.
- **Explanations can be re-run alone, without re-scoring anything** (`recommender/explanationRefresh.ts`, job `refresh-recommendation-explanations`, `POST /api/recommendations/:userId/explanations`). The picks, scores, diversity selection and evidence are already stored; the explanation is a separate text-generation call on top, and it is the *only* part of the pipeline that depends on which writing model is configured — so rewriting a paragraph used to mean regenerating everything, minutes of work for a different set of picks. Four things are load-bearing. (1) It targets the **newest `status='completed'` run** per user per media type, the same resolution every reader uses. That is not just tidiness: `thinSupersededCandidates` strips non-selected rows from every *other* run, so an older one holds only its ~20 picks. (2) That mattered because `normalizedSimilarity` used to be unstored, leaving `buildRunSimilarityScale` to recompute it from the run's own pool — and against a *thinned* run the scale came from the top slice of the distribution, whose mean is nothing like the pool's. Migration `0141` stores it, so that path now only runs for older rows (`resolveNormalizedSimilarity` prefers the column and treats NULL as "predates 0141", never as zero); the newest-completed-run rule stands on its own merits regardless. (3) `score_breakdown` is where `interestText` and the twin flag are recovered from, so a reserved-slot pick is still explained by the interest or the kindred viewer rather than by a similarity ranking that did not choose it — and the donor id stays in the column, only the flag travels. (4) Every score column is read through a `Number.parseFloat` helper, because **pg returns NUMERIC as a string** and `'0.0000'` is truthy. The AI-explanation setting gates it per user exactly as it gates the pipelines. (5) It is **cancellable**, which for a job of this shape is not optional — it is minutes long and every step is a paid model call. `isJobCancelled` is polled once per user × media type *and* between batches inside both generators (the optional `shouldCancel` argument on `generateExplanations`/`generateSeriesExplanations`, which the pipelines don't pass since they have no job id there), so the worst case is one in-flight request rather than one whole user. A cancelled run stores the explanations it already paid for and leaves the rest on their previous text, and it deliberately **does not call `completeJob`** — `cancelJob` has already written the `job_runs` row.
- **"Favorited" and "watched" are three different questions, not two** (`recommender/watchedExclusion.ts`): `WATCH_HISTORY_TASTE_SQL` (`played OR is_favorite`) answers *what shaped your taste*; `WATCH_HISTORY_EXCLUDABLE_SQL` (`played OR ≥5% progress`) answers *have you seen it* and is shared with `discover/filter.ts` and the STRM safety net — **never fold `is_favorite` into it**, or a bookmarked title silently becomes unrequestable in Seerr. The third question, *should we recommend it*, is the recommender-only `getExpandedFavoritedMovie|SeriesIds`, unioned into `excludeIds` in both pipelines' `!includeWatched` branch: a favorite is already found, so offering it back spends one of ~20 discovery slots on the user's own bookmark. Series favorites are recorded per **episode**, so the series helper means "has a favorited episode" — a show favorited on the server with nothing played leaves no `watch_history` rows and needs no exclusion. `watchedExclusion.test.ts` pins the split. Consequence worth remembering: because a favorite is taste input *and* (before this) a candidate, `storeEvidence`/`storeSeriesEvidence` used to match a pick against **itself** at cosine 1.0 and burn one of its three evidence slots — the LATERAL joins now carry an explicit `<> sel.selected_*_id`, which matters beyond the UI because `explanations.ts` feeds those same rows to the model under "use this data, don't invent connections".
- **Series engagement weighting lives in two places and must agree**: `taste-profile/builder.ts` `calculateEngagementWeight` (log10 episode count × completion × favorites × rating × 180-day recency half-life) feeds the taste vector *and* the clusters — the primary retrieval path; `series/pipeline.ts` `getSeriesWatchHistory` has its own simpler weight feeding only the fallback single centroid. Both now call the shared **`completionMultiplier`** (exported from the `taste-profile` barrel): `>0.9 → 1.5`, `>0.5 → 1.2`, `≥0.25 → 1.0`, `≥0.1 → 0.4`, else `0.25`. The sub-1.0 bands are the point — bonuses alone left forty abandoned shows outvoting five finished ones ~2.5:1, because people sample far more than they finish. **The denominator is `series.total_episodes` (what the media server holds), never `tmdb_total_episodes`** — a user who owns one season of five and watched it finished everything available and must not be penalised for content they don't have; the 0.25–0.5 band stays neutral for the same reason (season two arrived and they never noticed). `engagement.test.ts` pins the bands and the 9:1 ratio.
- **What counts as a watched episode was three different things**: the sync stores episode rows for played ∪ in-progress (`position > 0`) ∪ favorited-unplayed (`media/emby/series.ts`), so an episode quit after 30 seconds used to inflate both `episodeCount` and `completionRate` for exactly the shows the user bounced off. Both builder queries now gate on `WATCH_HISTORY_TASTE_SQL`, matching `series/pipeline.ts`, `genreFamiliarity.ts` and `eraDiagnostics.ts`.
- **Favoriting a *show* marks the Series item, not its episodes**, so it produces no `watch_history` rows anywhere. Series-level favorites reach the taste profile through `user_watching_series` (the bidirectional mirror maintained by `watching/favoriteSync.ts`) via `getFavoritedSeriesWithoutHistory`, appended inside builder's `getSeriesWatchHistory` and de-duped by a `NOT EXISTS`. **That mirror only refreshes while the Watching feature is enabled** — with it off the table goes stale and flagged shows silently stop contributing. Same table is unioned into `getExpandedFavoritedSeriesIds` so a flagged show isn't recommended back.
- **Changing how taste is calculated does not reach anyone until their profile goes stale.** `getUserTasteProfile` only rebuilds when `isProfileStale` says the profile has aged past its own `refresh_interval_days` (30 by default), so after shipping a change to `builder.ts` — the engagement ladder, which rows feed the vector, clustering — most users keep scoring against the old maths, and the logs say `✅ Using stored taste profile` rather than anything that looks wrong. **The full-reset recommendation jobs do not help**: they clear `recommendation_*` and regenerate, reading whatever profile already exists. The sweep is the manual **`rebuild-taste-profiles`** job (core `taste-profile/rebuildAll.ts`), which is the per-user Settings button applied instance-wide. It honours `is_locked` (an admin job must not overwrite a profile its owner pinned; the per-user endpoint passes `skipLockCheck: true` because there the caller owns it), and detects a no-op build by comparing `auto_updated_at` across the call, since `getUserTasteProfile` returns the *stale* profile rather than null when a build yields nothing.
- **"Generate recommendations" and "Full reset" run the same pipeline; only the wipe differs.** `clearAndRebuildAllRecommendations` is `clearAllRecommendations()` plus the same per-user loop `generateRecommendationsForAllUsers` runs — neither was ever incremental, and the description "rebuilds from scratch" describes both. (The reset also selects on `is_enabled` alone, so it regenerates for users who have that media type *disabled*.) The scheduled job now opts into `recommender/activityGate.ts` via `skipIfUnchanged`, the **only** caller that does: a manual regenerate means someone asked for work. Three things there are load-bearing. (1) **A skip writes no run row at all** — `/api/recommendations` serves the newest `status='completed'` run, so an empty one blanks the page; that is why `runId` is now `string | null`. (2) The **watch-history sync moved above** the gate and the run record, or the gate would judge people on data it was about to refresh. (3) The catalogue signal is a **count against `newCandidateThreshold`, not a timestamp**, because `MAX(movies.created_at)` is global — one new film would regenerate all eighteen users and the gate would never fire. Never gate on `movies.updated_at`: the sync rewrites every row every few hours. `maxRunAgeDays` is the backstop for inputs nobody enumerated, and every failure path regenerates, so a bug here can only cost compute. `activityGate.test.ts` pins the comparison directions.
- **Both gate thresholds are admin-editable per media type** (`recommendation_config`, Settings → AI Config → Algorithm → "When to regenerate"; defaults movie 12 / series 6 arrivals, 35 days each — series lower because shows arrive far less often than films, so a shared threshold would never accumulate). `DEFAULT_GATE_THRESHOLDS` in `activityGate.ts` is only the fallback for a config read that throws; `decideRegeneration` takes them as an argument so the arithmetic stays pure. The trap this created: the gate's `config` signal now reads **`recommendation_config.scoring_updated_at`, not `updated_at`** — the table has an updated_at trigger, so leaving it would mean lowering a threshold to *save* compute immediately regenerated everyone. `updateConfigFor` (the one setter both media types share) bumps `scoring_updated_at` only when a weight or pool size actually **changes value**; presence is not enough, because the settings page PATCHes the whole media-type object on every save. A new column therefore has to be classified into `SCORING_FIELDS` or it silently becomes free of that consequence.
- **A biweekly job is a weekly cron plus a dropped firing.** Cron cannot express "every other week", so `scheduleToCron` returns the *identical* expression for `weekly` and `biweekly`, and `scheduler.ts` calls `isScheduledRunDue` before the executor to skip a firing whose last **completed** run is under `BIWEEKLY_MIN_DAYS` (13, not 14 — two firings are 14 days apart give or take clock drift and DST, and 14 would round the wrong way and slip a whole week). Only failed/cancelled runs don't count, so a bad night retries next week instead of waiting a fortnight; only the *scheduled* path is gated, since clicking Run is someone asking for the work. Consequences elsewhere: `calculateRunsPerWeek` returns **0.5** (fractional on purpose — the cost estimator multiplies it), and `ScheduleTable`'s next-run column has to push past the skipped week itself or it names a date the job won't run, which is why `computeNextRun` now takes `lastRun` and is shared with the sort key.
- **`status='completed'` on a recommendation run means "produced picks", and five surfaces depend on that.** The newest completed run is what `/api/recommendations`, the dashboard, `userPreferences` and **both STRM writers** read. Both pipelines have three early returns — no watch history, no taste profile ("may be missing embeddings"), no candidates — which used to finalize as `'completed'` with zero selections, so a transient condition became the newest completed run for every user at once. The blank recommendations page was the mild symptom: the STRM writer builds `expectedFolders` from that run and then `fs.rm`s every directory not in it, so an empty run **deletes the user's generated library from disk**. All six sites now finalize as `'failed'` with a reason, which the `status='completed'` filter skips for free — no read-side changes, and the run history explains itself. Keep it that way: a new early return that reports success will silently wipe libraries.
- **Nothing pruned `recommendation_runs` until now** — every scheduled run appended a run plus its candidates and evidence, and only the full reset and the per-user regenerate button ever deleted, both all-or-nothing. `pruneOldRecommendationRuns` keeps the newest `RECOMMENDATION_RUNS_TO_KEEP` per user per media type, runs *after* `finalizeRun` so the kept prefix includes the run just made, skips rows with a `channel_id`, and swallows its own errors — housekeeping must never fail a run that already produced good picks. It now has a **second phase**, `thinSupersededCandidates`, described in the next entry.
- **The insights panel explains any scored title, not just the `selectedCount` picks — three things had to change together.** (That count is `recommendation_config.{movie,series}_selected_count`, admin-editable at Settings → AI Config → Algorithm → Recs Per User, range 1–100. Column default is 20 as of migration 0132, but an instance created before that keeps whatever its row already held — so never write a number into docs or copy as though it were structural.) (1) `storeCandidates` (core `recommender/storage.ts`) kept `allCandidates.slice(0, 100)` and discarded the rest, so about a hundred films per user had stored scores and every other title reported *"was not considered in your recommendations"* despite having been scored and ranked; it now stores the whole pool, which is what `storeSeriesCandidates` has always done — the two pipelines had silently drifted, and series was the correct one. (2) `MovieInsights.tsx` returned `null` unless `isSelected`, so the stored rows were invisible regardless; it now renders a calmer "How This Fits Your Taste" variant for a non-pick, collapsed by default. (3) `pruneOldRecommendationRuns` gained `thinSupersededCandidates`, which deletes non-selected rows from every run **except the newest `status='completed'` one** — without it the full pool would be retained `RECOMMENDATION_RUNS_TO_KEEP` times over. That status filter is load-bearing: readers resolve the newest *completed* run, so a failed run sitting on top would otherwise let the sweep thin the very run the panel reads. With no completed run the subquery is NULL and the delete no-ops, which is the safe direction. Consequences worth remembering: an old run legitimately holds only its selected picks while the newest holds thousands (deliberate, not damage); `rank` is the position among everything scored and is rendered against `recommendation_runs.candidate_count`, surfaced as `totalCandidates` by both insights routes; and movie rows now leave `score_breakdown` NULL unless it carries `selectionScore`/`interestMatch`, because the four score keys it used to copy in all have their own columns and that duplication stops being free at twelve thousand rows. `buildCandidateRows` is pure and pinned by `storage.test.ts`. Still picks-only, by design: `ai_explanation` and `recommendation_evidence` — widening evidence means a LATERAL kNN per candidate.
- **Taste twins are behavioural, and the embedding version of the same idea does not work here.** A "twin" is another viewer whose watch history overlaps a user's far more than chance; a bounded few of their titles earn reserved slots (`recommender/twinAffinity.ts` for the SQL, `recommender/shared/twinSlots.ts` for the pure maths, wired into both pipelines beside the interest slots). The obvious implementation — cosine between `user_taste_profiles.embedding` centroids — was measured and rejected: across all 153 pairs on the live instance those cosines span **0.898–0.993**, with unrelated viewers above 0.95, because a centroid is the mean of ≤150 item vectors that already sit in a narrow cone (`clustering.ts` records item→own-centroid distance 0.238–0.254 for *every* user). Compression is the arithmetic working, not a defect, so there is nothing to "fix" in profile generation — and note there is no profile *text* to rewrite either; the column is a weighted mean of item embeddings. Mean-centring against the population centroid does reopen the range (top-25 spread 0.578→0.305 vs 0.993→0.928 raw), which is a live option for a secondary signal but is not what ships. Five things are load-bearing:
  1. **Donors ≠ recipients.** Only `is_enabled AND movies|series_enabled AND NOT provider_disabled` may *receive*, but anyone with watch history is valid *evidence* — most users on this instance have recommendations switched off during testing, and the single strongest pair (333 shared titles, ~2× the next real pair) has a donor among them. Collapsing the two populations deletes that relationship.
  2. **The idf denominator counts everyone with history**, not just recipients. Rarity is better estimated with more observers; narrowing it only loses precision.
  3. **idf ranks *pairs* and must never rank *titles*.** A shared title necessarily has ≥2 viewers so its idf varies, which is why affinity discriminates well. An unwatched candidate almost always has exactly one viewer — 46 of 48 sampled — so every candidate ties at `ln(N/1)` and ordering by it is arbitrary. Fillers are therefore ordered by the pipeline's own `finalScore`; the twin decides what is *eligible*, the ranking decides what is *good*. Same pinning pathology as `avgNovelty` in [0.8, 1.0] and normalized dispersion reading 0.000 for all 14 profiles — a measure calibrated on one population is not a measure on another.
  4. **The bar is derived per run, never stored**: `median + k·MAD` over every pair. Absolute affinities are uninterpretable (the strongest real pair scored 0.198 against a body of 0.03–0.09, because most of anyone's watch mass is on titles nobody else touched), and enabling viewers changes N, which shifts every idf. Raw MAD, no 1.4826 factor — the distribution is right-skewed and pretending otherwise would be false precision. Zero spread returns null rather than the median, which would admit half the population.
  5. **Both knobs are in `SCORING_FIELDS`.** `{movie,series}_twin_threshold_k` (1–4, default 2.0) and `_twin_max_slots` (0–10, default 4, 0 disables — there is no separate toggle) are admin-editable at Settings → AI Config → Algorithm → Taste Twins. Omit either from `SCORING_FIELDS` and editing it would not bump `scoring_updated_at`, so the activity gate would see no change and the new value would sit unused until `max_run_age_days` fired.
  Slots come *out of* `selectedCount` and are computed against `selectedCount − reservedInterestSlots`, so the two slot features can never over-reserve (pinned by a sweep in `twinSlots.test.ts`). Explanations get the same treatment interest picks do — a `fromTasteTwin` flag, a prompt line, a `CRITICAL:` rule and a non-AI fallback — because a twin pick is precisely the item similarity did *not* choose, and without it the model invents a watch-history justification. **Copy never names the donor**: `score_breakdown.twinMatch` stores `donorId` and the panel says "someone here whose taste closely overlaps yours". Known blind spot: the activity gate cannot see twin-driven change, so a user whose own history is unchanged but whose twin watched fifty new films is skipped until `maxRunAgeDays`.
- **`selectedCount` is a budget, and every spender must be visible.** Three things draw from it: top-ranked picks, interest slots and twin slots. Both slot features shipped with an admin ceiling *and* a hardcoded `*_SLOT_SHARE` of 0.2 sitting underneath it, so a ceiling of 4 against a 10-item list silently produced 2 and the settings page gave no hint why. Both shares are now deleted: `computeReservedInterestSlots(selectedCount, interestCount, maxSlots)` and `computeReservedTwinSlots(remaining, twinCount, maxSlots)` are bounded only by things an admin can see — what exists (interests written, twins that cleared the bar), the configured ceiling, and the list length. Four consequences. (1) **`{movie,series}_interest_max_slots`** (migration 0133, default 3) had to exist, because making twins honest while interests stayed two hidden constants would just move the surprise; it is in `SCORING_FIELDS` alongside the twin columns. (2) Removing `INTEREST_SLOT_SHARE` **raises** interest slots on short lists — at `selectedCount` 10 the old share capped them at 2 and the setting now delivers 3. (3) The ordering in both pipelines is load-bearing: twins are measured against `selectedCount − reservedInterestSlots`, which is the only thing left keeping the sum inside the budget now that nothing scales either ceiling down. A sweep in `twinSlots.test.ts` pins it across every combination. (4) The UI enforces the budget in the *controls* — each slider's max is `selectedCount` minus the other's value, lowering Recs Per User clamps both, and a readout shows the ranked/interests/twins split live. That clamp is why `updateMovieConfigField`/`updateSeriesConfigField` had to become functional `setRecConfig(prev => …)` updates: they close over `recConfig`, so three sequential calls in one handler previously left only the last one standing.
- **The insights panel holds two kinds of "evidence" and only one of them is a reason.** `recommendation_evidence` (written by `storeEvidence`) is a LATERAL kNN run *after* selection: the pick's three nearest neighbours in the reader's own history by embedding cosine. For a ranked pick that is a fair account of why it is there. For a **reserved-slot** pick it is not — the ranking is exactly what did not choose it — so labelling it "Why We Think You'll Like This / Based on your history with similar movies" asserted a cause that was false, directly under a banner saying the scores did not put the film in the list. `MovieInsights.tsx` now switches that heading to a non-causal one (`closestInLibrary*`) whenever `scoreBreakdown` carries `twinMatch` **or** `interestMatch`; same rows, different claim. The actual reason for a twin pick is new: `twinMatch.sharedIds`, the highest-idf titles both viewers watched, which is the quantity the affinity score is literally made of (`SHARED_TITLE_SAMPLE` = 6 in `twinAffinity.ts`, collected by an `array_agg(... ORDER BY idf DESC)` slice in the pairs CTE). Four things to keep straight: ids are stored, never names, and resolved on read by `lib/twinShared.ts` (shared by both insights routes, `array_position` to preserve rarest-first order) so a re-matched film can't freeze a stale title in JSONB; `sharedTopIds`/`sharedIds` is **optional end to end** and nothing in the slot arithmetic reads it, so display data can never cost someone a recommendation; runs generated before this shipped have a `twinMatch` with no `sharedIds` and fall back to the bare anonymous line; and the explanation model is still fed the *similarity* evidence, which is why its prose reaches for watch-history corroboration even on a borrowed pick.
- **A score of 0 and a score never taken are different, and NUMERIC-as-string hid that.** `diversityScore` is measured relative to what is already selected, so it only exists for candidates `applyDiversityAndSelect` actually walked — never for the thousands scored but not picked, and never for reserved-slot fillers, which are appended after it returns. Both kept the 0 they were initialised with, and the panel rendered a confident red **"Variety 0%"** for precisely the picks whose variety was never assessed. Both writers now store `null` there, keyed on `selectionScore !== undefined` (the mark the selector leaves on everything it ranked) — `measuredDiversity` in `storage.ts` for movies, the same condition inline in `storeSeriesCandidates`. The column was already nullable, so no migration. The reason this wasn't caught by the existing guard: both insights handlers wrote `candidate.diversity_score ? Number(…) : null`, and **pg returns `NUMERIC` as a string**, so a stored `0` arrives as `'0.0000'` and passes a truthy test. All four score guards are now explicit `!= null` checks. Anything new reading a NUMERIC column here needs the same care.
- **The insights panel printed four numbers on three different scales and claimed they were one calculation.** Under the heading *"How We Calculated Your Match"*, a live pick read **Taste Match 78 / Discovery 72 / Quality 85** beneath a headline of **90** — which no weighted average of those three can produce, since a weighted average cannot exceed its largest input. Three separate causes, all now fixed by migration `0141` (`normalized_similarity`, `base_score`, both nullable and **deliberately not backfilled** — neither value is recoverable, since `normalizeSimilarity` needs the run pool's mean and stdev and the preference nudge is not invertible). (1) **`similarity_score` holds the RAW cosine and the blend never reads it.** `calculateBaseScore` consumes `normalizeSimilarity()`, which was computed per run and thrown away — so the bar labelled Taste Match was not an input to the number above it. Both are stored now and the panel draws the normalized one, falling back to raw for pre-0141 rows. Keep the raw value: it is what the *evidence* badges show, and those are item-to-item distances, comparable with each other and with nothing else on the page. This is also the same fact behind "why is a 74% evidence match lower than a 78% taste match" — the taste figure is distance to a **centroid**, a mean of ≤150 item vectors that by construction sits closer to everything in the cone than any two items sit to each other. (2) **`applyPreferenceAdjustment` overwrote `finalScore` in place**, moving it by up to half the remaining headroom, so even a correctly-scaled similarity left an unexplained gap; `baseScore` is captured before the nudge in both pipelines and the panel renders *blended → preferences ± → match* as an explicit chain, shown only when the column is non-null. (3) **Variety was rendered as a fourth component of a score it is not part of** — diversity feeds `selectionScore` (the ordering), never `finalScore` — so it moved to its own heading below. Also: the Discovery bar is filled against `[NOVELTY_ALIEN_FLOOR, NOVELTY_PEAK]` rather than 0–100, because that curve is peaked rather than a fraction and floors near 0.47, so drawn raw the *lowest possible* discovery score looks like a half-full bar. The bounds ride in the response as `scoreScales.novelty` from core's own constants (the two are barrel-exported for this one purpose) — **the web app must not hardcode them**, since it never imports `@aperture/core` and they would drift the first time the curve is retuned. The displayed *numbers* stay the real score values throughout; only bar fills are rescaled, or the arithmetic would stop closing. Storing `normalized_similarity` also retires the fragility documented under `explanationRefresh`: `buildRunSimilarityScale` now only runs for pre-0141 rows.
- **The explanation model was given a pairing and asked to supply a reason, with nothing to build one from.** The prompt carried the pick's title, year, genres and 250 characters of its own synopsis, plus the **bare titles** of its three nearest neighbours in the viewer's history — no synopsis for those three, no themes, no crew. So "both are Korean masterpieces about the poor infiltrating the lives of the wealthy" was entirely the model's pretrained knowledge of two famous films; the pipeline contributed only the fact that they were close in vector space. Fine for canonical cinema, silently unfounded for anything obscure, and the one remaining instruction shaping the prose was *"Create excitement"*. Six changes, mirrored in both generators. (1) **Evidence rows now carry `overview`**, and the pick's own plot budget rose 250→600 (`shared/explanationPrompt.ts`, shared for the same reason `explanationParsing.ts` is — the two generators are near-duplicates and drifting constants would be invisible). `plot_full` is deliberately **not** used despite being longer and more specific: it is IMDb's synopsis, which routinely gives away the ending — the web UI hides it behind a button for exactly that reason — and handing it to a model instructed not to spoil is a rule that only has to fail once. (2) **`keywords` and `directors` reach the prompt**, keywords being where a style is actually written down (almost no noir has "noir" in its title or synopsis, and there is no Film Noir genre — the same gap that forced a country filter onto the assistant's search tools). (3) **The raw cosine percentages on each evidence line are gone.** They sit in a band a few points wide, so 74 versus 69 reads as a meaningful grade while carrying almost nothing, and the only thing a model can do with such a number is repeat it. Order is the usable part and is preserved, labelled *nearest first*. (4) A **no-invention rule**: obscure titles are expected, work only from the data given, and state no awards, reception, festival history or production trivia that is not in it. (5) *"Create excitement"* became *"be specific rather than superlative"* — naming what two films share is both more persuasive and checkable. (6) `clip()` replaced `substring(n) + '...'`, which appended an ellipsis unconditionally: a complete synopsis presented as though it trailed off is an invitation to continue it, which is the exact failure the rest of this is trying to reduce. Also note `getUserTasteContext` in both generators counted **every** `watch_history` row, including titles abandoned after two minutes, so a genre someone kept bouncing off could be presented as a favourite; both queries are now gated on `WATCH_HISTORY_TASTE_SQL` like everything else in the recommender.
- **The evidence lookup searched 1.4% of a real viewer's history.** Both pipelines handed `storeEvidence` the *same* list they built the taste vector from — `recentWatchLimit`, default **50**, favourites-first. That is right for a centroid (a weighted mean whose tail contributes almost nothing) and wrong for a nearest-neighbour lookup: for a viewer with 3,510 watched films, whatever genuinely sat closest to a pick was usually not in the candidate set at all, and the three titles shown under *"based on your history with similar movies"* were the nearest among a handful of favourites — which the explanation model, instructed to use exactly those and invent nothing, then reasoned from. Both pipelines now fetch a separate pool at `EVIDENCE_HISTORY_LIMIT` (5000, `shared/evidencePool.ts`). The limit exists only to bound the `uuid[]`, not because more history is worse — for this lookup it is strictly better — and ordering is still favourites-first so a viewer past the cap loses their least-engaged tail. **Do not "simplify" it by joining `watch_history` inside the LATERAL**: an explicit id list keeps the planner on a filtered scan, whereas a join predicate beside `ORDER BY embedding <=> …` is exactly the shape that lets it pick the HNSW index and post-filter, and an HNSW scan never returns more rows than `ef_search` (default 40) — watched titles are a small fraction of the index, so the `LIMIT 3` would come back empty and the evidence would silently vanish.
- **One grounding role, and the free tier is far smaller than the docs imply — and the model ceiling is not the ceiling that stops you.** `webSearch` (assistant discovery, plus `channels/webExpand.ts`) is the only role that spends Google grounded search. `titleAnalysis` was the second until it moved to self-hosted retrieval — see the next entry — so this machinery now serves one consumer, and stays role-parameterised only because a self-hosted grounding source is planned for discovery too. **The measured numbers matter more than the design**, and they were transcribed from a live free-tier account's AI Studio rate-limit page on 2026-08-17 into `FREE_TIER_MODEL_LIMITS` / `FREE_TIER_GROUNDING_RPD` (`webSearchQuota.ts`). Read together they say something neither says alone. **Search grounding is a separate quota from the model's own, charged per model *family*, and on the free tier the whole Gemini 3.x family gets `0`** — the page lists four search-grounding buckets (Default, Gemini 2, Gemini 2.5, Gemini 3 → 1,500 / 1,500 / 1,500 / **0** per day) against per-model *map* grounding, which is what identifies them as family buckets. So `gemini-3.5-flash-lite` has **500 requests/day and cannot ground at all**, while `gemini-2.5-flash` grounds inside a 1,500/day allowance it can never reach because the *model* caps it at **20/day, 5 RPM**. Twenty grounded turns a day, and only from a 2.x model. That combination is nastier than it looks, because `gemini-2.5-flash-lite` is **no longer offered to new Google projects**: a fresh project can select 3.x, which is useless for grounding, and 2.5 Flash Lite, which it cannot have. `google.json`'s model descriptions carry this per model — the 3.5 Flash Lite entry used to recommend itself for Web Search, which was exactly backwards. It is also what makes `ProviderConfig.fallbackApiKeys` load-bearing rather than a nicety: a second key from a second **Google project** turns 20 into 40, since keys inside one project share quota. Slots are `primary`/`fallback`/`fallback2`… (the legacy scalar `fallbackApiKey` is still read, never written), dedupe drops a fallback repeating the primary, and cooldowns key on **role + slot**. **Anything spending grounding quota must go through `withGroundingModel` or the meter undercounts.** **The table shipped, was deleted, and came back gated — the gate is the whole point.** The first one claimed `rpd: 1000` for flash-lite where the account enforces 20, drawing a 1.2%-full green bar at 60% of the real day; it was deleted because Google has *withdrawn* the published per-model table and the numbers genuinely differ per account **and per tier**, so one operator's figures are wrong for everyone else. Two things make a table safe now. It applies **only when the operator ticks "These keys are on the free tier"** (`ProviderConfig.freeTier`, read through `isFreeTierConfig` — absent means free, only an explicit `false` opts out, and it is stored only when false); untick it and the meter shows bare counts, because a paid project's real budget is many times the free one and a bar claiming otherwise reads as full on a day that has barely started. And it is **subordinate to observation**: `resolveModelLimits` lays anything Google's own 429 disclosed over the defaults **field by field**, so a wrong default can only survive until the account contradicts it, and `source` (`observed`/`freeTier`/`mixed`) rides to the panel so the line under the bars says which it is showing. Observed limits apply **whatever the checkbox says** — a paid tier has limits too, just larger — so unticking withdraws an assumption, it does not blind the meter. Nothing throttles on any of this: key rotation and cooldowns are driven by real 429s. Traps pinned by `webSearchQuota.test.ts`: a **token** quota also reads as PerMinute, so without the token check a 250,000 TPM ceiling lands on the requests-per-minute bar; a **grounding** refusal is also a per-day request limit, so without `limitIsGrounding` a 1,500/day search allowance lands on a bar measuring a 20/day model (the ordinary quota ids and Gemini model ids contain neither "grounding" nor "search", which is what keeps the guard from firing on them); an **unattributed** limit is dropped rather than guessed at; `groundingRpd: 0` is a **real answer** and must be tested with `!= null`, never truthily, or "none" renders as "unknown"; the family prefix match takes the **longest** hit, so `gemini-2.5-*` is not read as plain `gemini-2` when the two buckets diverge; keys are restricted to models `google.json` can actually offer, since Google is not a custom-model provider and an id nobody can pick is an id nobody can check; and `getFreeTierLimits` returns a **copy**, because callers hand it straight into an API response. The observed store is in memory like the cooldowns — losing it costs a gauge until the next 429, whereas persisting risks showing a stale limit after a tier upgrade. Note also the grounding allowance is charged against the whole family across every consumer of that Google project, and nothing here meters it separately, which is why the panel states it as a caption rather than drawing a fill level for a budget it does not count. One open problem remains: the empty-text retry inside `googleGrounding`'s `PASS1_MAX_ATTEMPTS` loop sits *inside* one key attempt, so it makes two requests Google counts while writing one `web_search_usage` row.
- **Title analysis is title-scoped; the recommendation explanation is user-scoped; merging them would poison the explanation.** `analysis/` writes a critic-informed account of *the work* — how it was made, what its makers were attempting, what tradition it sits in, what critics disagree about — cached in `title_analysis` forever and shared by every user. **Where its sources come from is a setting, not a fact** (`analysis/mode.ts`, Settings → Integrations → Retrieval). `crw` — the default — retrieves BEFORE the model is called: `lib/crw.ts` posts to fastCRW's `/v1/search` with `scrapeOptions`, which runs a SearXNG metasearch *and* fetches each hit as clean markdown in one call, and the `titleAnalysis` role — an ordinary writing role, typically a local LM Studio model via `openai-compatible` — writes from that text. That replaced a grounded Gemini call for two reasons. Cost: at a measured 20 grounded requests/day the library was ~2 years of work per key (13,576 titles), where self-hosted is bounded by GPU time — roughly 1–3 min/title, so weeks. And **honesty**, which matters more: this prompt used to be made *entirely* of outside knowledge, the one thing the explanation prompt forbids, and one prompt could not hold both rules. Now it can, because the outside knowledge is *in* the prompt and "use only the sources" is checkable rather than hopeful. The alternative is `grounding`: a Gemini model searches for itself, which is better retrieval and no infrastructure but is metered per day per Google project — a few dozen titles, not a library — and it is Google-only, since no other provider grounds natively (`checkModeReadiness` refuses the combination rather than letting a model produce confident unsourced prose about every film). **`title_analysis.retrieval_mode` records which one wrote each row**, so the two are comparable on a real library instead of arguable: `SELECT retrieval_mode, model, count(*), count(analysis) FROM title_analysis GROUP BY 1,2`. `POST /api/analysis/:type/:id?force=true` re-runs a cached title and is **admin-only** — it is the only way to run both modes over the same title, and also the only way to spend unboundedly by holding a button. Because grounding mode spends the same quota Web Search does, `titleAnalysis` stays in `isGroundingRole` for key handling and out of the credential-donor loop even though it usually points at a local model: a setting whose safety depends on another setting is not a safe setting. Eighteen things are load-bearing. (1) **Questions, not a directive.** "Analyse this film" makes a model comply at a fixed register and find meditations on grief in an action programmer; specific questions with no answers produce short output instead — measured by hand, *Love Actually* returned ~250 words and *Dancer in the Dark* ~900, both correct. The register rule is explicit for the same reason: the failure is not analysing a genre film, it is analysing one *as if it were Tarkovsky*. Reception figures ride along as **calibration, marked not to be quoted back**, which stops a Criterion essay about a Metacritic 46. (2) **Prompt order is subject → documents → task/rules**, so the last thing the model reads is ours and not a scraped page. Retrieved markdown is untrusted text entering a prompt whose output is stored forever and shown to every user; the fence says so outright, but the structural defences (fixed output shape, closed question set, instructions last) are what carry it. (3) **`sourceFloor.ts` gained a signal grounding could not give it.** It sees real domains now, which catches the failure that only appears with in-house search: for an obscure title a metasearch returns IMDb, JustWatch and "where to watch" SEO — plenty of characters, zero criticism, and a count-based floor reads that as healthy. `LISTING_DOMAINS` is deliberately short and excludes Wikipedia, RT, Metacritic and Letterboxd (all carry writing), and the rule fires only when **every** substantive source is a listing. Every threshold still errs toward keeping, because a decline is **stored** and retires the title until `ANALYSIS_PROMPT_VERSION` moves. (4) **`budget.ts` is the new hard limit.** Google compressed the web server-side; CRW hands back whole articles, and 6 × 12,000 chars is ~18k tokens. Allocation is water-filling (a short document is never cut to reserve room a long one will not get) and documents are **dropped whole rather than shredded** — fragments are worse input *and* they lie to the floor, which counts sources. `clip` reserves the truncation marker inside the limit; appending it after slicing overshot the budget, which a test caught. (5) **`analyseTitle` throws on anything that might be systemic and only stores a decline it believes.** Zero results, or results carrying zero text, **throw** — a working metasearch finds something for nearly any released title, so nothing at all is far likelier to mean SearXNG's upstream engines are throttling or serving CAPTCHAs, and an afternoon of that would otherwise write permanent declines across the library. Sources that are present but *thin* do reach the floor, because there the web genuinely answered and answered poorly. (6) **A row existing means the attempt happened; its contents say what came of it.** `analysis IS NULL` is a decline, no row at all is "never asked or failed in transport". `prompt_version` makes improving the prompt a config change rather than the migration `0137` and `0139` both had to be — it is at **4** now, and every bump re-analyses the whole library, so it is only for changes that would make a stored row wrong or unusable. (7) The job attempts **each row at most once per run** (`attempted` set), or the loop reading until the pending selection empties spins forever on the very failures step 5 leaves pending — the shape that made `enrichMetadata` non-terminating. Cancellation is polled **between titles**. (8) `sourceBudgetChars` lives on the **CRW settings card** although it is really a property of the model's context window, because an operator tunes retrieval volume and how much the model can swallow as one decision. (9) The commonest setup mistake is the **base URL**: fastCRW ships its own compose project, so it sits on a different Docker network and `http://crw:3000` will not resolve — the published host port (`host.docker.internal:3000`) is what works. Test runs a real one-result search rather than a health ping, because the documented footgun (bare container, no search sidecar) passes a health check. (10) **A search that is blocked answers `200 {results: []}`, and three things now read that correctly.** Measured live against the `crw-camofox` fork (Camofox/Firefox driving Google directly, no SearXNG): a first-boot browser profile on a datacenter address was handed Google's `/sorry/index` interstitial, and the call came back a well-formed empty success — indistinguishable from "the web has nothing on this title". So `CrwSearchResponse` carries **`warnings`** (`readCrwWarnings`, which reads the plural list inside `data` *and* the singular scalar beside it — engine-level failures and partial scrape failures have different shapes and neither implies the other); `crwSearch` logs them at **warn**, since they arrive on a 200 and nothing else in the pipeline would ever mention them; both of `retrieveSources`' throws repeat them, because those are the lines an operator actually reads in a job log. And `describeTestOutcome` makes **zero results a FAILED connection test** — the probe query is banal by design, so an empty answer cannot mean "hard question", and the old *"Connected. Search returned 0 result(s)."* rendered a green tick over a retrieval service that could not retrieve. It is pure, so the decision is testable without stubbing `fetch` (`lib/crw.test.ts`, run by `test:analysis`). (11) **The timeout default is set by a number the service prints at boot, not by taste.** CRW's ladder is HTTP → LightPanda → heavy browser, and with `auto_extend_deadline_for_ladder` on (its shipped default) one page reaching the heavy tier gets the whole ladder: a stock deployment logs `deadline_ms_default=15000 ladder_min_ms=82500 effective_default_ms=82500`, and search runs *before* any of that. The old 90s default sat under the worst case with the search leg unaccounted for, and a timeout **throws — which writes no row**, so the title silently stays pending and the work is lost rather than retried loudly. Now 180s. Note most of that 82.5s is fixed per-tier overhead (`2 × 28s`), so lowering the heavy tier's own budget buys far less than it looks like it should. (12) **`checkModeReadiness` was called only by the settings page, to draw a badge — so it described the configuration without governing it, and a guard nothing calls is a comment.** Measured live: retrieval left on `grounding` while the role pointed at an OpenRouter model, which cannot ground. Every call logged `webSearchQueries: 0, groundingChunks: 0`, the model wrote 8,023 characters from its own memory, `sourceFloor` correctly judged that unsupported — and the **decline was stored**, retiring the title until `ANALYSIS_PROMPT_VERSION` moves. Roughly one title a minute, permanently, from a search that never happened, with CRW's log idle throughout. Two fixes, both needed: the check now runs inside **`analyseTitle`** (the choke point every path goes through, including the detail-page button) *and* as a pre-flight in `generateTitleAnalyses`, because discovering it per title would spend the whole budget on identical failures. And the branches were **asymmetric** — `retrieveSources` throws when the metasearch returns nothing, while the grounding branch happily wrote from zero chunks; zero chunks now throws too, so both modes leave the title pending instead of recording "the web has little on this film" on the strength of a search that did not occur. Migration `0145` deletes the rows already written (`analysis IS NULL AND retrieval_mode='grounding' AND source_count = 0` — a genuine grounded decline has chunks and is kept). (13) **A job whose unit of work takes minutes needs a label, not just a bar.** `updateJobProgress` has a fourth argument, `currentItem`, and this job passed nothing into it while reporting only *after* each title finished — so the console showed a counter that moved once every 45s–3min and a run that was working looked exactly like one wedged. It now reports the title **before** starting it. Cancellation had the matching problem: polled only between titles, Stop did nothing observable for minutes. `analyseTitle` takes an optional `shouldCancel` polled at the one seam inside a title — after retrieval, before inference — and throws `AnalysisCancelledError`, which the job distinguishes from a failure (both leave the row unwritten and pending; only one ends the run). (14) **The answer had a closing delimiter and no opening one, so a preamble was indistinguishable from the analysis.** The first real pass stored the writing model’s *thinking* as the analysis: the role pointed at `nvidia/nemotron-3.5-lightning:free`, which writes its scratchpad as ordinary content rather than as a separate reasoning part, and for *Spring, Summer, Fall, Winter... And Spring* it produced 8,852 characters beginning "Here’s a thinking process:", enumerated the task and each source, and ran out of tokens mid-sentence inside source [5] without writing any analysis. The detail page rendered that under "About this Film". The tell that it was systemic rather than one bad response: the three titles that "succeeded" stored **8,852 / 8,149 / 8,318** characters, all pinned just under a 2,000-token ceiling — a uniformity no real answer has, since the prompt asks for length to follow the work. Three independent guards missed it, and each reason is worth keeping. `writeFromSources` never read **`finishReason`**, so `'length'` — the SDK stating outright that the answer was cut off — was returned and dropped. `parseAnalysisResponse` looked for the closing `SOURCES:` line, did not find one, and **fell back to returning the whole raw string** with a null grade: the contract’s own failure signal was computed and then discarded. And `decideAnalysisFloor` only measures whether text is too **short** (`MIN_ANALYSIS_CHARS` 400), so a runaway is invisible to it by construction. This is `explanationParsing` in a second module — reasoning billed from the same ceiling as the prose, failing into confident-looking output rather than an error — and the lesson did not travel because the two share no code. **The first fix was wrong and is worth recording as such**: it rejected any response without the closing line, which converted a whole class of capable models into permanent failures and amounted to telling the operator to change models. The role is deliberately a free choice of provider and model, so a design that only works for models which keep reasoning out of the content stream is a broken design, not a wrong model. What ships instead is an **opening delimiter** (`ANALYSIS_BEGIN_MARKER`, prompt version 3): the answer is fenced at both ends, so whatever precedes it is discarded **structurally** rather than guessed at. Five things are load-bearing. (a) `afterBeginMarker` takes the **last** occurrence before the closing line, so a model that quotes the instruction back while reasoning still lands on the real marker. (b) Only `<think>`-style *delimited* reasoning is stripped; a prose preamble is deliberately **not** detected, because guessing where thinking ends and prose begins is the salvage regex that shipped in `explanationParsing` and caused a worse incident than the one it fixed. The marker makes that guess unnecessary. (c) A missing marker, a missing grade or `finishReason === 'length'` **throws rather than declining** — a decline is permanent, and "the model did not follow the format" is a fact about the model, so declining would retire the library over a settings mistake. (d) The writers **retry an unusable response** (`MAX_WRITE_ATTEMPTS` 3), not merely an empty one, since a one-off formatting slip should not cost a title. (e) Streaming is a red herring here and was checked: this path uses `generateText`, which is already non-streaming. Buffering changes when bytes arrive, never what they are — the separation that *does* exist is provider-side (reasoning returned as its own field, which the SDK surfaces outside `.text`), and the marker is what covers every provider that offers none. (15) **`maxOutputTokens` was hardcoded at 2,000 and invisible, which is most of why (14) happened.** It sat near the length of a legitimate long answer (~900 words is ~1,200 tokens) rather than far above it, and a reasoning model bills its scratchpad from the same allowance — so the budget was spent before the answer began. The only way to discover the number existed was to hit the bug. It is now `analysisMaxOutputTokens` on the Retrieval settings card (default 8,000, **0 means no ceiling**), beside `sourceBudgetChars` for the reason that one is there: how much text goes in and how much may come out are one decision about one context window. **The distinction it encodes matters more than the number.** Asking the prompt for a length is an editorial instruction and yields a finished piece of writing; a token cap is a guillotine that yields a broken one. So this belongs far above any answer worth having, and length is shaped in the prompt. 8,000 rather than the 16,000 used for explanations because this role usually points at a *local* model whose output shares one window with an ~16,000-character prompt of article text. Truncation now throws and leaves the title pending, which is what makes any default cap safe rather than silently destructive. (16) **A failure storm burns the whole budget in seconds and reports success.** In the same run the retrieval service became unreachable after title 3 (during testing, by stopping it — but the code cannot tell that from a crash and must not care): every remaining title failed in ~10ms with `fetch failed`, so the pass consumed its entire 200-title budget in **six seconds**, wrote 197 identical stack traces, and logged `✅ Title analysis pass complete`. Nothing was harmed — a failure stores no row, so all 197 stayed pending exactly as designed — but the run was worthless and said so nowhere. `CONSECUTIVE_FAILURE_LIMIT` (5) now aborts by throwing, which the executor files as a failed job. It counts **any** failure rather than transport specifically, because the storms this job can suffer are indistinguishable from inside the loop and want the same response: retrieval unreachable, its metasearch blocked (which answers `200 {results: []}` for every title), or the writing model unable to follow the contract. One hard title is isolated; five in a row is a system. The counter resets on any title that produces a row and lives outside the media-type loop, since an outage does not respect that boundary. **Note what this does not fix**: cancellation is polled between titles and at one seam inside a title, so with a 180s retrieval timeout Stop can appear dead for minutes — which is exactly what makes an operator reach for `docker stop` instead, and that is what produced the storm. (17) **The first output nobody could bear to read was formatted, not written, badly.** Three faults, all in the presentation layer of a prompt that was producing good prose. The rule said *"write continuous prose"*, which a model obeys literally: 900 words in one block, rendered at full panel width, so a desktop line ran past 200 characters — about three times the measure the eye tracks — and the result was exhausting regardless of quality. The prompt now asks for paragraphs of three or four sentences separated by a blank line (the panel already split on `/
{2,}/`, so nothing client-side needed inventing) and the text is capped at **`78ch`** with `lineHeight: 1.75`. Sources were stored as `{title, domain}` and shown as dead chips: the original reasoning — Google's grounding citations are short-lived `vertexaisearch` redirects, so a link table in a cache living for months would rot — was correct for grounding and stopped being true the moment retrieval moved in-house, where CRW returns ordinary article URLs. `AnalysisSource.url` is now carried through `budgetSources` (which spreads, so it survived for free) into the JSONB, and the chip becomes a link **only when the row has one** — grounding-mode rows and everything written before this deliberately have none, so the panel must treat a missing link as normal rather than broken. And the heading was *"About This Film"* over a standing disclaimer explaining that the text discusses how the work is made rather than what happens in it. Both are gone: it is **Film Analysis / Series Analysis**, and the notice was hedging about a risk the design already removes — the question set is pre-viewing by construction, which is the whole reason spoilers are handled structurally here, so a permanent apology on every title was the worse trade. (18) **The analyses read as though every title had arrived from nowhere.** The four questions asked about craft, intent, tradition and critical disagreement — nothing about the circumstances the work was actually made under. *Fanny and Alexander* is the case that made it obvious: conceived as the last thing Bergman would direct, shot as a television serial and cut down for cinemas, the most expensive Swedish production of its day. All of that was on the Wikipedia page, all of it **was retrieved**, and none of it was used, because nothing asked for it. `CIRCUMSTANCES_QUESTION` is shared by both question lists (one constant, so the movie/series drift this file warns about everywhere else is structurally impossible) and it **names its own test — did this shape the work** — rather than inviting background, so an unremarkable production has nothing to answer and the existing skip rule removes it. Awards stay out of scope: they are already on the page as reception data the model is told not to quote back. The search query changed with it — `production history` in, **`review` out**, since that word is what surfaces the aggregator and listicle pages `sourceFloor.ts` exists to catch.
- **Three "similar" systems**: `movies|series/:id/similar` (simple embedding neighbors) vs `/api/similarity/*` (multi-hop graph for Explore) vs `/api/graph-playlists` (playlists built from that graph).
- **Top Picks config lives in 4 places**: `routes/top-picks/`, `routes/settings/handlers/topPicks.ts`, `routes/setup/handlers/topPicks.ts`, and the `refresh-top-picks`/`auto-request-top-picks` jobs.
- Version strings drift: `routes/api.ts` says `0.1.0`, `routes/health` hardcodes `0.7.8`.

## Jobs system (how background work runs)

1. Job catalog: `apps/api/src/routes/jobs/definitions.ts` (static list; **crons there can drift — DB `job_config` via core `getAllJobConfigs()` is authoritative**).
2. Execution: `apps/api/src/routes/jobs/executor.ts` — one `switch` mapping job name → core function. Adding a job = core function + executor case + definitions entry (+ default `job_config` row if scheduled) **+ an entry in `apps/web/src/pages/jobs/constants.tsx`**, see below.
3. Scheduling: `apps/api/src/lib/scheduler.ts` (node-cron; executor injected via `setJobExecutor` in `routes/jobs/index.ts`, which also guards against double-runs).
4. Progress: in-memory + SSE, lives in **core** `jobs/progress.ts` (`withProgress`, `subscribeToJob`); run history in `job_runs`.
5. Shared mutable state: `routes/jobs/state.ts` `activeJobs` Map is also imported by `gap-analysis` and setup, which call `runJob` directly (bypassing jobs HTTP routes).

- **`JOB_CATEGORIES` is an allowlist, and a job missing from it has no UI at all.** `apps/web/src/pages/jobs/constants.tsx` maps job name → category, and `JobCategoryList` renders `jobs.filter(j => category.jobs.includes(j.name))` — so a job registered perfectly in `definitions.ts` and the executor still gets **no card**, which means no Run button and, far worse, **no Cancel button**, since Cancel lives on the card. The Schedule tab lists everything the API returns and therefore hides the omission: the job looks present, is runnable from there, and cannot be stopped. A new job needs a `JOB_CATEGORIES` entry plus `JOB_ICONS` and `JOB_COLORS` (missing ones fall back to a grey dot and no icon), and a new *category* needs `title`/`description` under `admin.jobsPage.categories.*` or the header renders raw keys.
- **A job that never calls `createJobProgress(jobId, …)` has no progress record, and every progress API then no-ops in silence.** `jobs/progress.ts` keeps an in-memory `activeJobs` map, and *every* function there opens with `activeJobs.get(jobId)` and returns when it is absent — correct (a finished job is evicted after five minutes and late calls must not resurrect it) but completely quiet. `generate-title-analysis` was registered perfectly everywhere else — `definitions.ts`, the executor switch, `JOB_CATEGORIES` — and missed this one line, which produced **every** symptom at once and no error anywhere: `updateJobProgress` and `addLog` did nothing, so the card showed an empty bar and an empty log pane; `completeJob` returned *before* `saveJobRun`, so no `job_runs` row was ever written and the history dialog read "No run history found for this job"; and `isJobCancelled` reduced to `undefined?.status === 'cancelled'`, which is **always false**, so Stop could not work however diligently the work polled it. The job ran correctly and reported nothing. Three consequences worth keeping: the executor is **not** a generic wrapper — only the cases that call `createJobProgress` themselves get progress, and those same cases must call `completeJob` (which is what writes `job_runs`), skipping it when the run was cancelled since `cancelJob` already filed the row; `setJobStep`'s `itemsTotal` may be left 0 and filled by the first `updateJobProgress`, which is what a job that has to count its own workload needs; and `addLog` **mirrors to the container logger**, so wiring it is what makes a long job legible in `docker logs` as well as in the console. The silent early returns now warn once per job id (`missingProgress`), because a mandatory registration that nothing checks is a bug waiting for the next job.
- **Cancelling is cooperative, and the terminal state is now a one-way door.** `cancelJob` only sets `status='cancelled'` and writes the `job_runs` row; the work stops solely because the core function polls `isJobCancelled(jobId)` — which `enrichment/`, `mdblist/`, `studioLogos.ts`, `backupService.ts` and `explanationRefresh.ts` do, and everything else does not. Two consequences. (1) A job that does not poll keeps running to completion after being cancelled, and used to then call `completeJob` and **flip its own status back** — the record still sits in `activeJobs` for five minutes after cancelling — filing a second `job_runs` row and overwriting `job_config.last_run_status`. `completeJob`/`failJob` now ignore a job that already reached a terminal status and warn instead; the same guard also collapses the double-report from a core function that fails its own job and rethrows into the executor's catch. (2) Nothing interrupts an in-flight HTTP or model call, so cancellation granularity is whatever the poll interval is — for anything doing paid model calls in a loop, check between calls and not just between users.
- **A job log is trimmed from both ends, not just the front.** `addLog` bounds what it keeps (`LIVE_LOG_LIMIT` 500 in memory, `STORED_LOG_LIMIT` 300 persisted into `job_runs`), and both used to be a plain `slice(-n)`. For a job that writes two lines per unit of work that is the wrong half: a 200-title analysis pass produced 400+ entries, so the history dialog opened at "[152/200]" and every line explaining what the run set out to do — how many titles were pending, which retrieval mode, whether anything succeeded early — had been dropped, while 197 identical failures were kept. `jobs/logWindow.ts` keeps a head (`LOG_HEAD_ENTRIES` 30) plus as much tail as the budget allows and inserts **one entry naming how many were dropped**, because a gap the reader cannot see is worse than a shorter log. Pure and pinned (`logWindow.test.ts`, run by `test:schedule`), including the small-budget cases where head + marker + tail must still come to exactly the limit.

## Recommender / embeddings pipeline (order matters)

sync-users → sync-movies/series (media server → DB) → enrichment (TMDB/OMDb fields onto rows) → generate embeddings (`buildCanonicalText` — **includes enriched fields; changing enrichment output means re-embedding**) → generate recommendations (taste vector → pgvector candidates → score: similarity/novelty/rating + taste-profile boosts → diversity selection → AI explanations → `recommendation_*` tables) → outputs (STRM libraries, channels, playlists, collections).

Embedding tables are shared consumers: recommender, `/api/similarity` graph, semantic search, discovery scoring, taste-profile interests. Movies and series are **parallel pipelines** (`recommender/movies/` vs `recommender/series/`) — a fix in one usually needs mirroring in the other. Same for `media/emby/` vs `media/jellyfin/`.

- **The canonical text read the sync's columns and ignored enrichment's, and the job could not re-embed anyway.** Two independent gaps that hid each other. (1) `buildCanonicalText` used `tags` and `awards` — written by `movies/sync.ts` — while `keywords` and `awards_summary`, the enrichment columns added beside them by `0059`, went into no vector at all; `languages`, `collection_name`, `composers` and `cinematographers` likewise. The pairs are easy to confuse and were. **`keywords` was the expensive one**: TMDb keywords are where "film noir" is actually written down (almost no noir has the word in its title or synopsis), so a `semanticSearch` for a *style* had only plot prose to match on — the same failure the country filter was added to work around. Scores are still deliberately out: a bare "82" embeds as noise, and quality already has `calculateRatingScore` plus the Browse filters. (2) Selection was `LEFT JOIN … WHERE e.id IS NULL` — **missing, not stale** — with no hash and no version, while `canonical_text` sat stored on every row since `0007` and was compared to nothing. So changing the builder did nothing to 12.5k existing rows, and the only remedy was `POST /api/settings/ai/embeddings/clear`, which TRUNCATEs movies, series **and episodes** across every dimension table. Five things are load-bearing now. (a) `text_version` (`0138`, on the movie and series families only) makes a builder change cheap to detect; NULL predates it, so the first run after this rebuilds everything once. **Episodes are excluded on purpose** — their canonical text reads no enrichment column, so re-embedding the largest table would buy nothing. (b) The staleness clause compares **`updated_at`, not `created_at`**: `storeEmbeddings` upserts, so `created_at` holds the first write forever and a row would re-qualify on every pass. (c) Because the batch loops read until the selection empties, a row that survives being handled is an **infinite job, not a wasted call** — which was already reachable, since a failed batch is never stored and comes straight back. Both loops now attempt each row at most once per run, and `markEmbeddingsCurrent`/`markSeriesEmbeddingsCurrent` restamp rows whose text turned out unchanged (most enrichment passes touch columns the text does not read, so re-embedding them would buy an identical vector). (d) Counts and selections must share the predicate — `MOVIE_STALE_SQL`/`SERIES_STALE_SQL` — or the progress bar describes a total the loop never reaches. (e) `buildCanonicalText` must be **deterministic**, since the skip-unchanged guard is a string comparison against the stored text; any instability re-embeds the whole library every run and bills for it. `canonicalText.test.ts` pins that. Downstream: a re-embed moves every item vector, so taste profiles (means of item vectors) need `rebuild-taste-profiles` and then a recommendations regenerate.
- **OMDb was asked for `plot=short`, which is the one thing it has that we already had.** The media server syncs a one-paragraph blurb into `overview`; `plot=short` returns roughly the same thing, so `OMDbMovieResponse.Plot` was typed and extracted by nothing. `plot=full` is the *same request, same quota, larger response* and returns IMDb's user-submitted synopsis — several times longer and different in kind, narrating the story rather than pitching it, which is exactly the specificity a concept query matches on. Stored as `plot_full` (`0139`) rather than into `overview`, because `movies/sync.ts` rewrites `overview` from the media server on every pass and would erase it. Three rules. (1) The canonical text uses it **instead of** the overview, never alongside — both tell the same story, and including both weights plot twice against genre, crew and keywords. (2) It is used **only when actually longer**: OMDb falls back to the short blurb when IMDb has no long synopsis, so a non-null value is not evidence of anything. The first implementation got this wrong in the fallback branch (`plotFull || overview` returns a *shorter* plotFull) and `canonicalText.test.ts` caught it. The web's `hasLongerPlot` uses the identical condition on purpose, so the embedded text is the text a reader can see. (3) The 1000-char cap stays — length is not the constraint (8191 tokens) but **dilution** is: a 2,000-word synopsis pulls the vector toward plot minutiae and away from what the film *is*, which costs item-to-item similarity even where it helps query recall. In the UI it is opt-in behind a "Read full synopsis" button in `MediaHero`, collapsed by default and never swapped in silently, because a full IMDb synopsis routinely gives away the ending. Note `0139` also has to **clear `omdb_enriched_at`** — the stamp records that OMDb was asked, not *what for*, so every already-enriched row would keep the gap forever. That is the second such clear (`0137` was the first); a per-source *version* rather than a bare timestamp would make the next one a config change instead of a migration.
- **Two ratings were arriving in responses the enrichment already parsed, and were dropped on the floor** (`0140`). `getMovieEnrichmentData`/`getSeriesEnrichmentData` call `/movie/{id}` and `/tv/{id}` for the collection, crew and production companies — `vote_average`/`vote_count` ride on that same response, so `tmdb_rating`/`tmdb_vote_count` cost **no extra request and no extra quota**. IMDb's is subtler: the detail page already showed a 0–10 score, but from `movies.community_rating`, which the *media server* syncs — for Emby that value **is** the IMDb rating, so it was right by inheritance, with no vote count and its meaning decided by another product. OMDb returns `imdbRating`/`imdbVotes` in the response `extractRatingsData` was already parsing. Four things. (1) **Vote counts are half the point**: 8.2 from 22,000 votes and 8.2 from six are not the same claim, and every score on the card has that ambiguity — these are the two where the count is held, shown on hover. (2) Both parsers are traps. `"N/A"` must become **null, not 0**, or unrated titles sort below genuinely bad ones; and `imdbVotes` is thousands-grouped, where `parseFloat('545,163')` returns **545** — a wrong number that looks entirely plausible on a badge. `ratings.test.ts` pins both. (3) `MediaInfoCard`'s `hasRatings` and every badge guard use `!= null`, because **pg returns NUMERIC as a string**: a stored `0` arrives as `'0.0'` and passes a truthy test, while a real 0 as a number fails one — the same trap the insights panel hit. (4) `0140` deliberately clears **nothing**: `0139` already nulls `omdb_enriched_at` everywhere, and `enrichMovie` calls TMDb and OMDb together on any row it processes, so one pass fills all four columns — but shipping `0140` *without* `0139` in the same deploy would leave every already-enriched row empty forever. Ratings stay **out of the canonical text** for the usual reason: a bare "82" embeds as noise. **TMDB has no awards API** — checked against their documentation index, nothing containing "award", "Oscar" or "nomination"; the awards tab on themoviedb.org is website-only data, so OMDb's `awards_summary` remains the only structured source.

## Auth model

`plugins/auth.ts`: `x-api-key` header (takes precedence) or `aperture_session` cookie. `requireAuth`/`requireAdmin` — **`requireAdmin` has no bypass**; server-side callers that need to act without a logged-in user call the domain function directly (`routes/jobs/startJob.ts` is the one for jobs, used by the setup wizard) rather than replaying an HTTP request through `fastify.inject`. API-key users are forced `provider:'emby'`, `collectionsEnabled:false`.

- **Sessions are bearer tokens, not row ids**: the cookie holds 32 random bytes; `sessions.token_hash` stores only its sha256, and `sessions.id` is unrelated. 30-day absolute lifetime plus a 7-day idle timeout (`last_seen_at`, rewritten at most every 5 min). `is_enabled` is enforced on *both* the login path and every session lookup, and `PUT /api/users/:id` revokes sessions when it disables an account — a disabled user loses access immediately. The `cleanup-auth-state` job sweeps expired/idle rows, deliberately with a 1-day grace margin so the auth plugin stays the only thing that decides a session is dead.
- **Brute-force controls are two-layer, on different axes**: `@fastify/rate-limit` keyed on **IP alone** for `/api/auth/login` (folding the username in widens the keyspace, so a spray rotating usernames would get a fresh bucket per request and never trip it), plus DB-backed per-account lockout in `apps/api/src/lib/loginAttempts.ts` with progressive backoff, which is what covers one account attacked from many IPs. **Only `InvalidCredentialsError` counts toward the lockout** — the providers throw it on 401 and a plain `Error` otherwise, so a media-server outage returns 503 instead of locking out every user who retries.
- **Deployment posture lives in `apps/api/src/config/security.ts`**, not scattered env reads: `DEPLOYMENT_MODE` (`direct` default, or `proxy`/`tunnel`/`cloudflared`), `TRUST_PROXY`, `HOST`, `COOKIE_SECURE` (defaults on in production — *not* derived from `APP_BASE_URL`), `API_DOCS` (`public|admin|off`, admin-only in production), `ALLOW_PASSWORDLESS_LOGIN` (production gate over the `allow_passwordless_login` admin toggle), `SETUP_ALLOW_REMOTE`, `CSP_REPORT_ONLY`. All booleans parse case-insensitively via `envFlag`. `helmetOptions()` and `config/rateLimits.ts` live here too so `security.test.ts` asserts the objects the server actually registers.
- **`TRUST_PROXY` is load-bearing and `=true` is a footgun**: it trusts `X-Forwarded-For` from anyone, so a caller can forge their address to mint rate-limit buckets and look local to the setup guard — pin the proxy (`TRUST_PROXY=172.18.0.1`) instead. Leaving it unset *behind a proxy* is worse: every visitor collapses to the proxy's address, so the login limiter becomes one global bucket and `isTrustedSetupSource` sees the whole internet as local. `DEPLOYMENT_MODE=proxy` supplies a loopback default; an explicit `TRUST_PROXY` always wins.
- **`config/deploymentPosture.ts` is the one source of truth for "is this exposed correctly"** — the boot warnings and `GET /api/settings/deployment` (Settings → System → Deployment) both render its `findings`, so they cannot drift. Findings are stable ids translated under `settingsDeployment.findings.*`; a new one needs `title`/`detail`/`fix` in en or the panel shows a raw key (there is a test for exactly that). Crucially it is **evidence-based, not config-only**: `noteRequest` samples live traffic from the access-log hook, because an instance behind a tunnel with no trusted proxy looks perfectly healthy from config alone — seeing `X-Forwarded-For` while trusting nothing is the only reliable tell.
- **Trusted proxies are editable at runtime** (`config/proxyTrust.ts`, `PATCH /api/settings/deployment`), stored in `system_settings.trusted_proxies`. This works because **Fastify accepts a *function* for `trustProxy` and consults it per request** — the value being passed at construction does *not* freeze the decision. (An earlier reading of `Request.buildRequest` concluded it did, which is why the panel first shipped read-only; `security.test.ts` pins the dynamic behaviour now.) Matching delegates to `proxy-addr`, the same library Fastify uses, so CIDRs behave identically to the static form. `TRUST_PROXY` still wins outright when set — the UI goes read-only — because it must also be available *before any admin exists*, which is the only way the first-run setup guard can be protected behind a tunnel.
- `@fastify/helmet` sets the CSP — `imgSrc` is deliberately wide because TMDB posters load direct from `image.tmdb.org` and `getProxiedImageUrl` only proxies media-server URLs; `styleSrc`/`fontSrc` must keep the Google Fonts hosts that `index.html` pulls; Swagger UI gets a relaxed CSP scoped to `/openapi` because it bootstraps inline. `connect-src 'self'` also fences assistant-ui's cloud path (see the comment at the `useChatRuntime` call site).
- **First-run setup is network-restricted**: a plugin-scoped `onRequest` hook in `routes/setup/index.ts` refuses `/api/setup/*` from non-local addresses until setup completes (admins and `GET /api/setup/status` always pass). Before that hook existed, whoever reached a fresh instance first could configure it and become admin.

## Web conventions

- Provider tree (App.tsx): `I18nextProvider > RtlProviders > BrowserRouter > SetupProvider > AuthProvider`; authed pages additionally get `ViewModeProvider > UserRatingsProvider > WatchingProvider > AssistantDockProvider` + floating `AssistantModal`.
- Route table lives in `apps/web/src/App.tsx`; shell is `components/Layout.tsx` (sidebar items feature-gated by watching/collections flags).
- **A page's title lives in the app bar, not on the page**: at `md`+ the bar's left half was empty (hamburger and wordmark are mobile-only, jobs widget/search/avatar are pinned right) while every page spent ~80px repeating the same words below it. `components/PageHeading.tsx` publishes them through `hooks/PageHeaderProvider` (mounted by `Layout`, above both the bar and the `<Outlet/>`) and renders the familiar block only below `md`, where the bar has no room. Three traps: (1) the outer wrapper **stays in the tree** at every width — most callers sit it beside a toolbar in a `space-between` row, and removing it would leave one child, which flexbox puts at the *start*; (2) `icon` is rendered in the page block only and never published, because the header lives in state and an element prop is a new object every render, so publishing it would loop; (3) only **one** publisher per route — `AdminLayout` deliberately doesn't publish (each admin page does, which is more use than five "Administration"s), since React runs child effects before parent ones and the last writer would be the parent. A page with no `PageHeading` and no `usePageHeader` shows an empty bar; the always-full-viewport surfaces (`/assistant`, `/explore`) call `usePageHeader` directly and skip the block entirely.
- Hooks pattern: `XProvider.tsx` + `x-context.ts` + `useX.ts` triplets in `src/hooks/`.
- **New UI string**: add to `src/i18n/locales/en/translation.json` (en is source of truth), use `t('ns.key')`, then `pnpm i18n:sync` to stamp placeholders into the other 14 locales. RTL locales: ar, he — use logical CSS properties. Server error strings: wrap with `lib/withServerMessageDetail.ts`. Authoritative guide: `src/i18n/CONVENTIONS.md`.
- **Never write the product name in a UI string — write `{{appName}}`.** The instance is renamable (Settings → System → Instance name, stored as `system_settings.app_name`, served by public `GET /api/branding`), and the rename reaches all 15 locales at once because i18next fills the placeholder from `interpolation.defaultVariables`. That is set to the default in `i18n/config.ts` and overwritten by `lib/branding.ts` once the fetch lands — safe to assign late because i18next reads `defaultVariables` off the shared options object *at interpolate time*, not at init; the `changeLanguage` nudge afterwards is only there to re-render what's already on screen. `GET` is deliberately unauthenticated (login and setup render the name before any session). The few spots with no translation to interpolate into — logo `alt` text, `document.title`, the `formatJobName` fallback — call `useAppName()`/`getAppName()` instead; note the job fallback must resolve the name *per call*, since a module-level const would freeze the default before the fetch resolves. **The `<title>` can't wait for that fetch** — a tab (or a bookmark taken right then) would show the default on every cold load — so `plugins/static.ts` stamps the name into the shell on the way out: it reads `apps/web/dist/index.html` once at boot, rewrites the `<title>` element per request, and serves it from both `GET /` and the SPA fallback. That is also why `@fastify/static` is registered with `index: false` — otherwise a directory request would answer off disk and skip the rewrite. Falls back to the default if the DB read throws, so a database outage can't stop the shell booting. Left alone on purpose: `/aperture-libraries` and `/mnt/ApertureLibraries/` are real paths, and `helperApertureLibs` is a key name.
- Client caches to remember when changing API shapes: `WatchingContext` (localStorage, versioned — bump version on shape change), `ViewModeProvider` (localStorage + server prefs).
- **Breakpoints lie inside the main pane**: MUI breakpoints are *window* media queries, but `Layout.tsx` shrinks `<main>` with `marginInlineEnd: dockWidth` when the assistant is docked, and `MediaDetailModal` renders a whole page inside a dialog. A grid keyed on `md`/`lg` therefore keeps its full-desktop column count in a half-width pane (this is what shrank Related Movies to ~110px posters). Size in-pane grids off their container — `gridTemplateColumns: 'repeat(auto-fill, minmax(Npx, 1fr))'`, or MUI 6's `theme.containerQueries` — rather than subtracting `dockWidth` from a breakpoint, which still gets the dialog case wrong.
- **Assistant surfaces**: three containers share `AssistantChatSurface` — the dock (Fab default, md+), the dialog (opt-in via the header toggle, and the fallback below md), and the `/assistant` page. Only the page renders the conversation list inline (`sidebarInline`); the floating pair use the history drawer. The header's expand button routes to `/assistant` carrying `{ conversationId }` in the route state, which `useAssistantChat(active, initialConversationId)` seeds — without it the page would resume whichever conversation was updated last.
- **The sidebar has three states, and `collapsed` is not the one to branch on**: `Layout.tsx` renders one `renderDrawer({ labels, collapsible })` for both drawers. Below `md` it's a temporary overlay, always `DRAWER_WIDTH` and labelled regardless of the rail preference (`collapsible: false` — an overlay you dismiss has nothing to collapse). At `md`+ it's a permanent rail whose paper widens to `DRAWER_WIDTH` on hover **without** the nav Box or `<main>` changing width — the paper is `position: fixed`, so the flyout floats over the page and content never moves. Branch on **`labels`** (`!collapsed || flyout`), never on `collapsed`, or the flyout renders icons. The flyout is gated on `(hover: hover) and (pointer: fine)` so a touch screen gets taps instead, opens instantly on `onFocus` for keyboard users, and is delayed both ways so brushing past doesn't trigger it. Default collapse state follows `lg` until the user toggles once; `sidebarCollapsed` is **absent** from `/api/auth/me/preferences` until then, which is the "has a preference" signal (`hasSidebarPreference`).
- **The welcome guide is route-gated and snoozed, not "first visit"**: `components/WelcomeModal.tsx` explains the recommender only, so `useWelcomeModal` opens it by itself on `/recommendations` alone (`WELCOME_ROUTE`) — the user menu's "How it works" still opens it anywhere. It is a **controlled dialog only**; `Layout.tsx` mounts exactly one, and `onClose` always receives an explicit `WelcomeDismissal` (`session` | `day` | `week` | `never`), never MUI's close event. Three storage keys back that: the pre-existing `aperture-welcome-dismissed` (still the "never" flag, so anyone who already ticked the box stays dismissed), `aperture-welcome-snooze-until` (epoch ms, localStorage) and `aperture-welcome-session-snooze` (sessionStorage, holding the user id — the closest a browser gets to "until I sign in again"). A plain close snoozes for the session; showing the guide on every refresh is what made it feel like nagging.
- **The detail page states each fact once, and the hero is where the duplicates were resolved.** `pages/media-detail` rendered the same information twice in three separate places: genre chips in `MediaHero` *and* an identically-sourced "Genre Analysis" chip row in `MovieInsights`; the star rating in the hero *and* a "Critic Ratings" panel of IMDb/TMDB/RT/Metacritic badges in `MediaInfoCard`, several screens down; and `awards_summary` in its own sidebar card. All three now render once, at the top — the rating line carries every score, the awards sit on the line under it, and director/writer moved up beside them, out of the info card (which is now cast, secondary crew, studios, languages, countries and links). Four things to keep straight. (1) The genre classification comes from `insights.genreAnalysis`, whose two lists **partition the title's genres exactly** — both insights routes filter the item's own `genres` column against the viewer's top-10 watched genres — so styling the hero chips by set membership can never leave one unaccounted for, and the panel keeps only the *counts*. It rides a later request than the media, so chips restyle when it lands and stay neutral for a title no run scored. Colour is explained by per-chip tooltips, since deleting the panel's chips also deleted the only legend. (2) `hasCriticRatings` and `personPath` live in `pages/media-detail/helpers.ts` rather than beside the components: a module exporting both a component and a plain function trips `react-refresh/only-export-components`, and lint runs at `--max-warnings 0`. (3) Every rating guard is `!= null`, never truthiness — pg returns NUMERIC as a string, so a stored `0` arrives as `'0.0'` and passes a truthy test while a genuine numeric 0 fails one; the panel this replaced had one guard of each kind. (4) `MovieInsights` now opens **expanded for both variants** (it was collapsed for a scored-but-not-picked title): a panel whose whole content is an explanation reads as empty when it is shut.
- **Item detail in a dialog**: `components/MediaDetailModal.tsx` renders the *route page* `pages/media-detail` (which now takes optional `id`/`onBack`/`onOpenMedia` instead of only reading `useParams`), hosted by `hooks/MediaDetailModalProvider`. Chat cards call `useMediaDetailModal()`; a **null** opener means "no host mounted, navigate instead" — that's how the docked assistant keeps routing the main pane while the /assistant page and the floating dialog open in place (`AssistantChatSurface` prop `openMediaInModal`). Related titles / insight evidence inside the dialog swap the target rather than route, or they'd move the page under the dialog. `MediaBackdrop`'s `mx/mt: -3` is why the dialog content keeps `p: 3`.

## When you touch X, check Y

- **New/changed core or ui export** → rebuild packages before typecheck; check `packages/core/src/index.ts` barrel (exports won't resolve until added there or to a subpath export in core `package.json`).
- **Schema change** → new `db/migrations/NNNN_*.sql`; check both migration runners; grep for the table name across core (raw SQL is duplicated in many modules).
- **Enrichment fields** → re-embedding may be required (canonical text), similarity `reasons.ts`, gap analysis, top picks all read enriched columns.
- **Series/watching changes** → `watching/tmdbTotals.ts` caches TMDB totals on `series` rows (`tmdb_total_episodes/seasons`, `tmdb_status`); Watching page, upcoming episodes, and MyWatchHistory grids all read them.
- **Media-server calls** → implement in BOTH `media/emby/` and `media/jellyfin/`; interface is `media/MediaServerProvider.ts`.
- **Movie-side recommender/sync fix** → check the series mirror (and vice versa).
- **Renaming/removing an API route** → grep `apps/web/src` for the literal `/api/...` string (no typed client to catch it).
- **Integration client changes** (tmdb/omdb/trakt/mdblist/seerr/justwatch) → they log to `errors/` (`api_errors`) and often have DB caches with TTLs; check retry gating (`shouldAutoRetry`).
- **Job behavior** → schedule comes from DB `job_config`, not `definitions.ts`; progress API is in core.

## Workflow notes

- Work happens directly on `dev` (no feature branches). `main` is a stale upstream mirror; `.github/workflows/sync-dev.yml` force-resets `dev` to `main` on pushes to `main`. Pushing to `origin/dev` triggers the Docker build — don't push without being asked.
- **Never open the live site right after a push.** A push only starts the image build; the running instance changes when the operator manually pulls it. So the browser will be showing the *old* build, and "verified" would be a lie. Browser checks (`claude-in-chrome` against the deployed instance — the local dev server can't be started here) happen only when the operator says the new image is deployed. A push is the end of the turn, not the cue for a screenshot.
- Docker: `docker/Dockerfile` (4-stage; copies built dists + `db/`); compose variants per platform (dev/prod/external-db/windows/unraid/synology/qnap). Runtime data in `data/` (gitignored except `.gitkeep`s); operator i18n overrides mount at `/config/i18n`.
- Docs for humans live in `docs/` (admin guides, feature docs, screenshots).
