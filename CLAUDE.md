# Aperture — Repo Map

Self-hosted media recommendation & watch-tracking app for Emby/Jellyfin. AI recommendations via pgvector embeddings. Integrations: TMDB, OMDb, Trakt, Seerr (Jellyseerr/Overseerr), MDBList, JustWatch, n8n, Tavily, fastCRW (self-hosted search + scrape, `packages/core/src/lib/crw.ts`), LLDAP (optional email import, `packages/core/src/lldap/`).

> **Keep this map current.** Adding/moving/renaming a route, page, core module, or table updates the relevant section here in the same change. Stale entries cause wrong-file edits.

## Repo-wide invariants

These hold everywhere; sections below reference them by name instead of restating them.

- **HNSW / `ef_search`** — pgvector's default `ef_search` is 40, and an HNSW scan never returns more rows than `ef_search`. Any query asking for >40 neighbours, or applying a post-filter (watch status, country, series scope) that pgvector resolves *after* the scan, needs `SET LOCAL hnsw.ef_search = 500` inside a transaction. It must be `SET LOCAL` so it cannot leak onto the pooled connection and change the other vector queries, which are tuned for the default. Without it a filtered `LIMIT 20` comes back nearly empty and the filter looks broken; a bare `LIMIT 400` either returns short or makes the planner drop the index and seq-scan every embedding.
- **NUMERIC arrives as a string** — pg returns NUMERIC as text, so a stored `0` arrives as `'0.0000'` and passes a truthy test, while a genuine numeric `0` fails one. Guard every score/rating column with `!= null`, never truthiness. Also `Number(null)` is **0, not NaN**, so mapping a NULL column through `Number()` silently fabricates a real zero — map NULL to `undefined` instead.
- **Absent ≠ false** — fields added by a migration are absent on older rows, and absent must preserve the pre-migration behaviour. Check `=== true` / `!= null` explicitly. Applies to `ContentItem.watched`, `evidenceSupportsCause`, `sharedIds`, the preference chain, weight shares, and `freeTier`.
- **The web bundle never imports `@aperture/core`** — server code would break it; duplicate tiny helpers instead (see `src/i18n/localeDirection.ts`). Any constant the UI needs (novelty band, threshold decisions) rides in the API response as a *decided* value and is never hardcoded in the bundle, or it drifts the first time core retunes it.
- **Parallel implementations must be mirrored** — `recommender/movies/` vs `recommender/series/`, `media/emby/` vs `media/jellyfin/`, and the two explanation generators. A fix in one usually needs the other. Where they have drifted, this file says so explicitly.
- **Duplicated predicates get split into a pure module with a test** — the recurring bug here is one rule copied into several places that then disagree, and agree only by being wrong identically. `watchedExclusion.ts`, `pending.ts`, `genrePreference.ts`, `logWindow.ts`, `crossMedia.ts`, `jobs/state.ts`, `explanationParsing.ts`, `countryMatch.ts`, `titleMatch.ts` all exist for this reason: pure, no DB, pinned by a test.
- **Never threshold a cosine band blind** — measured bands here are far narrower than they look: twin centroids span 0.898–0.993, `avgNovelty` pins into [0.8, 1.0], normalized dispersion read 0.000 for all 14 profiles, raw neighbour cosines crowd into 0.66–0.83. A measure calibrated on one population is not a measure on another. Measure the distribution before picking a number, and prefer a threshold whose failure is asymmetric toward the safe side.
- **Measure per user before reading an aggregate as a mechanism** — a per-user score averaged *across* users can show a trend that exists in no user. Similarity-by-decade over 9 users read as a clean recency bias (1930s 0.29 → 2020s 0.59, monotonic); per user the gradient *reverses*, each peaking at their own era. Control: a taste vector is equidistant from every decade the user actually watched (one 381-film user spans 0.7542–0.7596 across 50 years), so the embedding has **no** era bias — the population simply leaned recent. Same trap as watch-history Jaccard, where 1–8% pairwise overlap looks like "nobody shares taste" but is exactly what identical taste produces at ~100 watched out of 12.5k.

## Architecture (30 seconds)

pnpm monorepo, ESM everywhere, no ORM (raw SQL via `pg`):

- **`packages/core`** (`@aperture/core`) — ALL domain logic. `tsc` → `dist/`. Subpath exports: `.`, `/config`, `/db`, `/media`, `/recommender`, `/strm`, `/channels`, `/jobs`, `/watching`. Root `src/index.ts` is a giant barrel (~1090 lines).
- **`apps/api`** (`@aperture/api`) — thin Fastify HTTP layer (port 3456): routing, auth, job orchestration. Handlers call core functions; `src/lib/db.ts`, `lib/logger.ts`, `config/env.ts` are pure re-export shims of core.
- **`apps/web`** (`@aperture/web`) — Vite + React 18 SPA (dev port 3457, proxies `/api` → 3456). MUI 6, react-router 7, i18next (15 locales), d3, recharts. No central API client: raw `fetch('/api/...', { credentials: 'include' })` everywhere.
- **`packages/ui`** (`@aperture/ui`) — shared React components (MoviePoster, StarRating, BaseCarousel, RankBadge, StatusCard, TrailerModal, `getProxiedImageUrl`). Web aliases it to `src/` for hot reload; typecheck/build use `dist/`.
- **`db/migrations/`** — numbered SQL (`0001`–`0180`; `0129` is used twice, tolerated since the runner tracks filenames). Postgres + pgvector.

```
pnpm dev                # api + web concurrently (kills stale 3456/3457 first)
pnpm build              # pnpm -r build (topo order)
pnpm typecheck          # builds packages/* FIRST, then pnpm -r typecheck
pnpm lint / validate    # eslint --max-warnings 0 / lint + typecheck
```

**Critical:** apps consume the compiled `dist/` of core/ui. After adding/changing any export in `packages/core` or `packages/ui`, run `pnpm --filter "./packages/*" build` or app typecheck fails with TS2305/TS2307.

## Naming traps (easy to edit the wrong module)

Each entry is the rule. `[F-NNN]` points at the full evidence in [docs/aperture-forensics.md](docs/aperture-forensics.md) — the measurements, the failure as it presented, and the alternatives already tried and rejected. **Read the linked section before changing, reverting, or arguing with a rule**; you do not need it to write correct code. **A new entry goes here as the rule, with its evidence appended to [docs/aperture-forensics.md](docs/aperture-forensics.md) under the next free number.**

- **`discover/` vs `discovery/`** (api routes, mirrored in web/core): `discover` = browse people/studios + TMDB-external detail (`/api/discover/*`); `discovery` = missing-content engine feeding Seerr (`/api/discovery/*`). Unrelated third: `assistant/discovery/` (web-grounded chat candidates), whose grounding is multi-source via `assistant/discovery/sources/` (a `WebSearchSource` registry): Google grounding + Tavily (core `lib/tavily.ts`, `system_settings.tavily_integration`). Sources **run concurrently** (`gatherFromSources` is a `Promise.all` over the registry) and are **combined, never raced** — all their text feeds one structuring pass, so they compose and fall back for one another; first-come-first-served would discard the loser's material. Tavily errors log under the `tavily` provider. **fastCRW is NOT one of these** — it is title analysis only, and appears nowhere in `assistant/`. [F-001](docs/aperture-forensics.md#f-001)
- **A new AI role is a list, not a union.** `AI_FUNCTIONS` (core `lib/ai-capabilities/types.ts`) is the one copy; `AIFunction` derives from it. Roles are *also* a JSON-Schema `enum` on **ten** Fastify routes (`settings/schemas.ts` ×3, `setup/schemas.ts` ×7) that TypeScript cannot check against the union — adding a role means adding it there too, or its settings card silently renders "No models available" for every provider. Runtime guards use `isAIFunction`, never a hand-written `includes()`. Anything enumerating roles must iterate `AI_FUNCTIONS` (omitting one hides the spend dashboard and the pricing summary rather than erroring). **Never add a role to a SQL `CHECK`** — `0144` dropped the old one and `aiFunctionSchemas.test.ts` fails on any later migration whose `CHECK` names 2+ roles. `custom_ai_models_provider_check` deliberately stays (it guards providers, which change when an integration is written). Custom models are keyed `(provider, function_type)`, so they do not carry across roles; `getModel` and `getModelsForFunction` both go through `modelPool`. [F-002](docs/aperture-forensics.md#f-002)
- **Web Search is Google-only and holds two keys.** `getProvidersForFunction('webSearch')` returns just `google`; `AIFunctionCard` renders a label instead of a dropdown when a role has exactly one provider, and auto-corrects an off-list selection. `ProviderConfig.fallbackApiKey` sits alongside `apiKey` because Gemini's free tier is what breaks grounding. **Anything spending grounding quota must go through `withGroundingModel`/`withWebSearchModel`** (core `lib/ai-provider.ts`) or the meter undercounts: it walks `getWebSearchAttempts()`, advances **only** on a quota error, and writes every attempt to `web_search_usage`. Limits and cooldowns in `lib/webSearchQuota.ts`; counters in `lib/webSearchUsage.ts`, day windows anchored to **midnight US/Pacific**. `webCandidates.ts` cannot use the wrapper (its cascade fights the key loop) and meters by hand via `recordWebSearchCall`. An omitted `fallbackApiKey` in PATCH means "leave alone"; only an empty string clears it. [F-003](docs/aperture-forensics.md#f-003)
- **Two "cost" surfaces, only one real**: `CostEstimatorSection` *projects*; `InferenceDashboardSection` *measures*, covers `METERED_PROVIDERS` (OpenRouter and Z.AI — see the metering rule below), and hides itself when no role uses one of them. Capture is in the **provider's `fetch`** (`createOpenRouterUsageFetch(role)`, core `lib/openrouter-usage.ts`), so a new generateText/streamText call site needs no instrumentation — but `role` is baked in at provider-creation and is part of the provider cache key. `feature`/`sessionId`/`userId` ride an AsyncLocalStorage (`lib/inferenceContext.ts`) set in exactly three places: `runJob`, the chat handler, `testProviderConnection`. Unwrapped work records as `unattributed`. Cost is nullable end to end — **never treat a missing cost as zero**; the dashboard reports `pricedCalls` separately. [F-004](docs/aperture-forensics.md#f-004)
- **OpenRouter pricing resolves through its own catalog**, not `PROVIDER_MAP` (`lib/pricing-cache.ts` has no `openrouter` entry and its data file ships zero models). Use `getOpenRouterModelInfo`, **exact id only** — `:free`/`:extended` variants are priced differently. `FunctionPricing.pricingKnown` distinguishes "free" from "unpriceable"; anything rendering money must show unknown as unknown, never $0. [F-005](docs/aperture-forensics.md#f-005)
- **The assistant consumes the recommender's output, not its logic.** Of twelve tools only `getMyRecommendations` touches the pipeline (reads `is_selected` off the newest completed run). `semanticSearch`/`findSimilarContent` are bare pgvector kNN with **no** novelty term, taste boosts, diversity or reserved slots. Each item carries `source` (`ranked`|`twin`|`interest`|`acclaimed`), **derived** from `score_breakdown` by `pickSource` — never pass it through, because that object holds `twinMatch.donorId` and **the model must never receive an identity it could name**. Twin picks carry `sharedTitles` (from the *reader's own* history, so no donor leak), resolved **batched per tool call** via `resolveTwinSharedTitles`. Unknown/absent `source` reads as `ranked`. Nothing calls `ContentItemSchema.parse()`, so extra fields reach the client — `tool-ui/types.ts` mirrors the schema by hand and must be updated alongside it. [F-006](docs/aperture-forensics.md#f-006)
- **`searchMyRecommendations` is the library-scoped personalized search** (`assistant/tools/recommendations.ts`): ANN joined to `recommendation_candidates` for the newest **completed** run, re-ranked by `blendQueryAndTaste`. The join restricts to titles scored for this user *and* applies the watched exclusion for free. Rules: both terms are **min-max normalised over the fetched pool before blending, never raw** (cosine sits in a narrow band — see the cosine invariant); `QUERY_WEIGHT` is 0.6 so the request leads and taste breaks ties; `ANN_POOL_SIZE` (400) is fetched before the join and needs the `ef_search` treatment. **Search results carry no `rank`** — `recommendation_candidates.rank` is the position among everything scored, and `ContentCard` renders any `rank` as a poster RankBadge; only `getMyRecommendations` sets one, from `selected_rank`. (2) It searches **`queryText` — the user's own words** — where the tool searches a `concept` the model paraphrased first, so this section has no paraphrase step to go wrong. (3) **`TASTE_SECTION_QUERY_WEIGHT` is `1 - QUERY_WEIGHT`**, not its own number: the two are one decision about how hard a section leans, and only the `< 0.5` inequality (which is what makes the heading true) is pinned. (4) **Dedupe across all three plus the seed** is load-bearing, not defensive: three directions over one library, so overlap is normal. (5) `TASTE_POOL` (24) is **headroom, not a display count**. (7) `TASTE_MAX` (6) keeps it inside one `enrichCardReasons` batch, so the feature costs one model call. - **A watch can be dated ROUGHLY, and the estimate has to say so.** Rating a title the media server never played now asks *when*, and marks it played with an actual date: `POST /Users/{UserId}/PlayedItems/{Id}` takes an optional `DatePlayed` that Aperture had always omitted. **Emby wants `yyyyMMddHHmmss`, Jellyfin wants ISO 8601** — same path, same parameter, different encoding — so each provider formats its own and there is deliberately no shared helper; neither server rejects a value it cannot parse, it stamps *now* instead, so a formatting mistake silently backdates nothing rather than throwing. `lib/watchDateBands.ts` is the one home for the ladder (pure, pinned). Six rules. (1) **The release date clamps the ladder from below ONLY** — a 1998 film is exactly what someone watches *this month*, so an old title keeps all five rungs and it is new titles that lose options; each band is an interval, its start clamped to `premiere_date`, and an empty interval drops the band. (2) **One surviving band becomes a yes/no, never a silent write** — marking someone’s media server off the back of a rating is not what they asked for; a title released in the future offers nothing and is not prompted. (3) **Midpoint, at 12:00** — midpoint so the error is symmetric and bounded by half the band; midday because `DatePlayed` carries **no timezone** and the docs do not say whether a bare stamp is UTC or server-local, so a ±12h misreading still lands on the right day, and because it keeps invented watches out of the small hours of the heatmap. (4) **`longerAgo` writes a PLACEHOLDER, not a midpoint** — interpolating back to the release date answered *2011* for a 1998 film, a considered-looking estimate of something nobody stated; it writes 1 Jan of two years ago, always past the recency term’s 360-day floor (`max(0.25, 0.5 ** (days/180))`) where every older date weighs identically, which is also why a year picker buys the recommender nothing. (5) **Whole days, never halved milliseconds** — both ends are local midnights, so a span crossing DST is not a whole number of 24h periods and halving the ms lands at 23:30 the previous day in half the world’s timezones; and a midpoint is **never allowed into the future**, since on the 1st of a month "this month" is one day and a future `last_played_at` sorts to the top of the taste history forever. (6) **`watch_history.approximate_played_at` (`0163`) stores the estimate we SENT, not a boolean** — the server’s date later disagreeing with it proves a real play happened, so the marker self-clears; the comparison carries a day of slack because of the timezone ambiguity above, or the first sync would clear every marker. **Counted, never plotted**: approximate rows count as watches everywhere asking *how many* or *what kind*, and are excluded from **every surface with a time axis** — heatmap, busiest day, the 12-month timeline and `historySpan`, plus `watchStatsBreakdown`’s `month`/`day`/`timeOfDay` ([F-102](docs/aperture-forensics.md#f-102)’s chip-and-list rule). Heatmap and busiest-day alone is **not** enough: the timeline buckets by month and a band is month-accurate for only two of its five rungs, and `historySpan` names the month of a viewer’s first play in a caption, so one backfill dated before their real history rewrites their origin story. The excluded count ships as `approximateWatches` and the page states it — a total that exceeds what the charts add up to reads as a bug when unexplained and as a caveat when not. **"I haven’t seen it" is not a sixth rung** — it is not a *when*, and mixing it into a list of times adds a decision to every use; it is the named dismissal, and `user_ratings.not_watched_declared_at` exists now although only the inline prompt reads it, because the batch prompt would otherwise resurface a genuinely unwatched title forever. - **Mean-centred embeddings** (`embedding_centered`, `0154`). Every canonical text shares a register, so a large part of every cosine measures that; subtracting the library mean removes it (measured ndcg@100 20.5% → 31.9%). Five rules. (1) It is a **stored column, not a `- mean` term at each call site**, so a new query cannot forget it. (2) The mean is therefore **never stored or looked up at query time** — a profile built from the centred column is already centred. (3) **No index, deliberately** — the recommender uses a LIMIT above table size, so the planner abandons HNSW anyway. (4) A profile records its own space (`user_taste_profiles.embedding_space`); `resolveEmbeddingSpace` **refuses** (returns null, run finalizes `failed`) rather than falling back, because comparing a raw centroid against centred items is a confident number that means nothing. `buildSpaceFor` and `resolveEmbeddingSpace` are separate functions with a test pinning that anything built now is immediately servable. (5) **`isCenteringReady` is all-or-nothing** and the refresh is ONE statement — a half-filled column silently shrinks the candidate pool, and a batched refresh leaves rows centred against different means. **The interest ANN paths stay raw in both pipelines**, as do `storeEvidence` and the similarity graph: their query vector is a fresh embedding of interest *text*, which nothing centred. A raw profile stays raw until `rebuild-taste-profiles` moves it, which is the entire rollback. (6) **The rows are normalised before the mean is taken and before it is subtracted** — every other vector op here is cosine and magnitude-invariant, but centring is a *subtraction*, where `AVG` skews toward long vectors and a common mean rotates each row by a different amount, yielding wrong **directions** rather than wrong scale. `storeEmbeddings` normalises nothing, so this is load-bearing the moment vectors are not unit-length: for any one model all but one valid dimension is an MRL truncation, and some providers never return unit vectors at **any** width (`pplx-embed-v1-4b` is served int8-quantised and documented as unnormalised at its own native 2560). It is **inert on gemini-embedding-001 at native 3072** (measured norms 0.999930–1.000079) — which is exactly why it looks deletable and must not be deleted. (7) **Centring runs automatically at the end of both embedding jobs** (`centreAfterGeneration`, inside the job because each owns its own progress and calls `completeJob` itself), gated by the pure, pinned `centeringNeeded({ generated, ready, rows, centredRows })`. It was manual-only with nothing chaining it, so any sync that embedded a new film left `embedding_centered` NULL and every centred profile refusing — visible only as staleness, since a failed run leaves the previous completed one live. The gate is load-bearing: both jobs run on a **6-hour interval**, so unconditional would rewrite ~77 MB to identical values four times a day; the `!ready` half is what makes a failed centring self-healing. **A third condition catches rows LEAVING**: every embedding table is `ON DELETE CASCADE` from `movies`/`series`, so a title dropped from the media server takes its vector with it and leaves no NULL — `generated` 0 and `ready` true, while the mean still counts the departed films. The live row count is compared against the count at the last successful centring (`system_settings.embedding_centering_state`, keyed by media type **and model**, written inside `refreshCenteredEmbeddings` so the manual job records it too); an **unknown** previous count reads as needing work. **`refresh-embedding-centering` is manual-only and must stay that way** — it is the remedy for a column that is *populated but wrong* (a bad mean has no NULL to repair and reads as ready), not for routine drift, and scheduling it would both reinstate the timed full-table rewrite the gate exists to prevent and multiply the profile drift below. It never rethrows (the embeddings are good; the next pass retries). One copy in `centering.ts`, not mirrored per pipeline. Episodes have no centred column, so the series job centres series only. `refresh-embedding-centering` stays for a manual sweep. - **A centroid is a sum, and only the sum cares about magnitude.** All 31 `<=>` comparisons are cosine, which is why nothing normalizes on write; the taste vector is the sole place vectors are *summed* — `buildWeightedAverageEmbedding` (`taste-profile/builder.ts`) and its twin `weightedMeanEmbedding` (`clustering.ts`). Summing raw makes a title's influence `weight × ‖v‖`, multiplying `calculateEngagementWeight`'s whole ladder by a per-title factor; the trailing L2 normalize does **not** fix it (it rescales the finished mean). **Inert at a model's native dimension and only there** — 7 of 8 `VALID_EMBEDDING_DIMENSIONS` are MRL truncations, where Google requires manual normalization. `l2Normalize` is exported and **shared** by both paths (was a third copy): `clustering.test.ts` asserts K=1 is **bit**-identical to `buildTasteProfile`, and float multiply is not associative, so both sites must do the same operations in the same order. The guard is a **pair** of tests — scaling an item's vector must not move the centroid, *and* doubling its weight must; the first alone passes if weights are ignored. Costs a `rebuild-taste-profiles`, never a re-embed. [F-037](docs/aperture-forensics.md#f-037)
- **Changing the embeddings model deletes nothing, and the panel has to say so.** Rows are keyed `UNIQUE(<item>_id, model)` per dimension table and **every** read filters `WHERE model = $n`, so a model change starts a new set beside the old one and switching back reuses it — the staleness join carries `AND e.model = $1`, so old rows count as present. Deletion is only ever the two explicit admin routes. `lib/embeddingSets.ts` (`getEmbeddingSetsReport`) is what makes that visible. Six rules. (1) Readiness is measured with **`MOVIE_STALE_SQL`/`SERIES_STALE_SQL` imported, never re-expressed** — a set can be fully populated and still need rebuilding when `CANONICAL_TEXT_VERSION` moves, so a row count is not an answer. (4) **Episode pending is missing-only and reads the setting** — episodes are outside the `text_version` scheme and their tables have no `text_version`/`updated_at`; with generation off, pending is genuinely 0. - **Embedding retrieval mode is reachable through OpenRouter, and this file said the opposite until 2026-08-28.** `input_type` and `dimensions` are both in OpenRouter's embeddings schema, and `@openrouter/ai-sdk-provider`'s `extraBody` is spread verbatim into the request body — so it is a settings argument, not a fork. Measured on one document: for `gemini-embedding-001` the **default output space IS `RETRIEVAL_QUERY`** — `search_query` returns the byte-identical vector to sending nothing, while `semantic_similarity` (**0.860**) and `search_document` (**0.910**) are each a genuinely different space, so every vector this app has ever stored is in the *query* space. Where *no* value moves it — gemini-2 — "ignored" is the only supportable reading. Exactly one path is taken — a prefix-conditioned model is sent no parameter. Only *verified* prefixes ship: Google documents an asymmetric `title: … | text: …` form this app has never measured, so asking for it is a **400**, not a silent fallback. This library's task is symmetric (item↔item, and a taste centroid is a mean of item vectors), so `semantic_similarity` is the mode it wants, and every vector currently stored was embedded without it. **A parameter mode on OpenRouter REQUIRES a pinned upstream.** Measured on 001: `google-vertex` honours `input_type` (cosine 0.841 from unmoded), `google-ai-studio` drops it and returns the unmoded vector — each deterministic alone, a coin flip together, so unpinned it writes a mixture of two spaces into one set. `requiresProviderPin` refuses that combination at the settings route and the Save button, since no later step can repair such a set. The provider rules live inside the function for the same reason (a mode is dropped for a provider that cannot send one, a pin for a provider with no routing), so writer and readers agree structurally instead of because the settings route filtered the config first. - **The embedding set identity is one function, because two modes of one model collide.** Rows are keyed `UNIQUE(<item>_id, model)` and every read filters `WHERE model = $n`, so `${provider}:${model}` built inline in **nineteen places** meant a semantic-mode pass would `ON CONFLICT DO UPDATE` straight over the default-mode set — destroying the control it was meant to be compared against, silently. `lib/embeddingIdentity.ts` is the one home (`embeddingSetId`, pure, pinned). (5) **`finalizeRun` stores the EFFECTIVE weights** — that is what `0147`'s column means, and storing configured ones would leave the panel multiplying numbers that do not reproduce the match. (6) `0150` widens them `NUMERIC(3,2)` → `NUMERIC(6,4)`, because `0.25 × 1.2391` stores as **0.31** at two decimals; **no backfill is possible**, since the gain depends on a candidate pool that no longer exists. `SCORE-DIAG` logs both `weights` and `effectiveWeights`. The match set was a strict subset of the exclusion set, so the map was empty on every run and `similarityScore` was the constant **0.5**: 45.5% of the configured blend contributing **zero** ranking variance, with popularity silently deciding half the order. A candidate is not in the library, so its vector must be **made, not found** — `discover/embeddings.ts` builds a canonical text mirroring `buildCanonicalText`'s section order and labels (six of its nine sections; no studios, cinematographers or keywords, and an overview rather than `plot_full`) and caches it in `discovery_candidate_embeddings` (`0160`) keyed `(media_type, tmdb_id, model)` where **`model` is a set id from `getEmbeddingInvocation().setId`**, so a provider/model/mode change starts a fresh set. Dimension-free `halfvec`, no index, following `0079`/`0086`: it is read by key and scored in JS, never by ANN. Five rules. (1) **The candidate document is systematically thinner than the library's, and that is safe only because discovery RANKS**: every candidate is thin the same way, so the offset is common and cancels — never threshold a discovery similarity against a constant derived from library-to-library distances, and never compare it to a recommender one. (2) **The space is the profile's decision**: `resolveEmbeddingSpace(profileSpace, isCenteringReady)` refuses rather than mixing, and for a centred profile this is the **one** place F-036's "the mean is never looked up at query time" does not hold — a candidate has never been through `refreshCenteredEmbeddings`, so `getLibraryEmbeddingMean` recomputes `AVG(l2_normalize(embedding))` **once per run**, and `centreVector` l2-normalises **before** subtracting (centring is a subtraction, so an unnormalised row is rotated by the wrong amount — a wrong *direction*, not a wrong scale). A refusal costs the taste term, not the run. (3) **Similarity is min-max normalised across the pool**, the same treatment popularity gets, measured **only over candidates that have a vector** so unembeddable titles do not drag the floor down; a missing vector scores a neutral 0.5. (4) **Popularity is normalised WITHIN each source** (`popularityScoresBySource`, pure and pinned) — the field holds TMDb's unbounded metric, a Trakt watcher count, and a hardcoded **0** for `trakt_popular`/`trakt_recommendations`, so pooling them buried the source the code itself calls "most personalized" and hands source score 1.0. (5) **Nothing may call the AI SDK `embed`/`embedMany` directly** (F-093 rule 8): `getEmbeddingInvocation().embedBatch` only, and `embeddingCallSites.test.ts` scans for violations. The cache is pruned beside the pool on the same window, or it becomes the unbounded thing the pool was. **Everything is admin-tunable now** — `discovery_config` in `system_settings` via `discover/config.ts`, `sanitizeDiscoveryConfig` clamping on both read and write (it checks absent **before** coercing, because `Number(null)` is 0 and finite, which clamps a missing knob to its *minimum* instead of restoring its default), surfaced at Admin → Recommendations → Discovery tuning. **An unparsed halfvec is a STRING, and a length check against one silently skips everything.** pg returns `halfvec` as text, so a row annotated `{ embedding: number[] }` is a claim TypeScript cannot check against a driver — the legacy `user_preferences` read handed `maxTasteSimilarity` a ~40,000-character string, whose `.length` never equals 3072, so every taste vector was skipped and every candidate scored a flat neutral. Cast `::text` and parse explicitly, exactly as `getUserTasteClusters` does, and return NONE rather than a vector that failed to parse. It hid because the path was dead: with the candidate map always empty its output was never consumed, so **repairing a dead path exposes every latent bug in the code that fed it** — precisely the code with no coverage. Its sibling: a stale `user_taste_clusters.embedding_model` makes `getUserTasteClusters` discard the cluster, which is F-042's rule (a model change reaches nobody until `rebuild-taste-profiles`) and is NOT fixed by `generate-series-embeddings` reporting zero pending. **That legacy read is now DELETED** ([F-106](docs/aperture-forensics.md#f-106)): it carried no model and no space, so no clusters means no taste term rather than a confident cosine across two spaces. It is kept live by `onMovieWatched` (the rating prompt's path) and by `MediaHero` calling `setMovieWatched` on both Mark Watched and Mark Unwatched — **movies only**, since neither media-server provider defines `markEpisodePlayed`. (9) **Franchises reads `movie.watched` from its own endpoint, not the provider** — that is the figure its progress bar counts, so the ticks and the "3 of 5 watched" line cannot disagree; the franchise SQL moved to `played = true` in the same change, since it had been counting any `watch_history` row. Deliberately unbadged: My Watch History and the stats drill-in (everything there is watched by construction), Home's two rails (recommendations are unwatched by construction, history watched), another user's profile (the set is the *viewer's*), and gap analysis (TMDb rows with no library id). [F-109](docs/aperture-forensics.md#f-109)
- **`user_preferences` is not a recommendation table, and a `DELETE` by user id there is a claim about every feature that has parked a column on it.** One row per user holds *both* Watcher Identities (`taste_synopsis`, `series_taste_synopsis`), the excluded-library list and per-user algorithm settings inside `settings` JSONB, `include_watched`, `dislike_behavior`, preferred/excluded genres, the two blend weights and the two similarity-graph flags. `clearUserRecommendations` deleted the whole row under the comment *"Clear taste profile"*, so **one press of Regenerate on My Recommendations silently reset all of it** — and the `full-reset-movie-recommendations` job did it for every user at once. Nothing expires an identity (there is **no** background refresh job; `getTasteSynopsis` only reads, and its docstring's `refresh_interval_days` claim is false), so a synopsis that vanishes was deleted, and the "it goes after a few days" cadence is the interval between presses. The delete also achieved **nothing it was written for**: the taste profile is `user_taste_profiles`, rebuilt by `getUserTasteProfile` ([F-042](docs/aperture-forensics.md#f-042)), while `taste_embedding`/`series_taste_embedding` on this row are **write-only** since [F-106](docs/aperture-forensics.md#f-106) deleted the last reader. Both movie functions are now the series ones with `'movie'` substituted — `clearUserSeriesRecommendations` was always the correct half of the pair (the mirroring invariant), and the movie side had drifted twice: it deleted preferences, *and* its run delete carried **no `media_type` filter**, so asking for new films emptied the series tab and a job named *full-reset-movie* deleted every series run in the database. Candidates and evidence go with the runs by `ON DELETE CASCADE` (`0013`); the explicit deletes were the second spelling that let the two paths disagree. **Nothing is recoverable** — the synopses were AI-written and stored once. Same file, other direction: `streamTasteSynopsis` stored `fullText` unconditionally, and a stream that finishes clean with no `text-delta` (a reasoning model spending the whole cap on scratchpad, F-030) wrote `''` over a good synopsis, which `getTasteSynopsis` reads as never generated — **an empty generation now throws instead of storing**, which surfaces the failure over SSE and leaves the card rendering the profile it already fetched. [F-110](docs/aperture-forensics.md#f-110)
- **The Watcher Identity is written by the RUN, not by a button, because five things read it.** `taste_synopsis`/`series_taste_synopsis` feed both explanation generators (unshifted to the **top** of the prompt context), the assistant's system prompt (which otherwise substitutes the literal *"No movie taste profile available yet."*), the discovery taste brief ([F-008](docs/aperture-forensics.md#f-008) — with none it returns null and the turn is not personalised at all), AI channel generation and the suggestion chips. All five have a null branch and none of them says anything when it fires, so a viewer who never found the Generate Identity button got worse explanations, a worse assistant and an unpersonalised brief, silently. Three signals said automatic was always the intent: `getTasteSynopsis`'s docstring promised a background job **that was never written**, `CostEstimatorSection` bills `enabledUsers × runsPerWeek` synopsis calls (so the projected spend had a line item for work that never happened), and `refresh_interval_days` existed with nothing riding on it. `lib/tasteSynopsisRefresh.ts` is called at **step 2b of both pipelines** — after the profile is resolved and after the early returns that finalize `failed`, before scoring, so *this* run's explanations use the fresh text and a doomed run pays nothing. **The trigger is the profile moving or the prompt version moving, not a clock**: `user_taste_profiles.auto_updated_at` against the synopsis stamp, so it inherits `isProfileStale`'s pacing and re-describing an unchanged centroid is impossible — plus `<column>_version` (`0176`) against `TASTE_SYNOPSIS_PROMPT_VERSION`, checked first, because a prompt change moves no centroid ([F-129](docs/aperture-forensics.md#f-129)). `synopsisNeedsRefresh` is pure and pinned — **empty counts as missing** (agreeing with `getTasteSynopsis`, whose truthy test is falsy for `''`), **a null `auto_updated_at` is not staleness** (a locked profile would otherwise pay on every run forever), text with no stamp is rewritten, and it is **strictly newer, never `>=`** (the synopsis is written *after* the rebuild that prompted it; verified against an injected `>=`, which fails exactly the tie case). It **fails open in every direction** — unconfigured model, cancel, outage, empty generation — returning an outcome instead of throwing, since a run that produced good picks must not be failed by the prose about them. The unconfigured check happens **before** the generator is called, not inside it: the generator answers an unconfigured model by storing the fallback blurb, which is right for someone watching the card and a wasted write in a background run (since [F-129](docs/aperture-forensics.md#f-129) the blurb stores a NULL version, so it no longer stamps the row current). Cancel is polled once on entry — one short call per user per media type, so the caller's per-user loop is the seam. The button survives as an override (*"that doesn't sound like me, try again"*), and lives on Watch Stats only. [F-111](docs/aperture-forensics.md#f-111)
- **The Watcher Identity is written from a viewing RECORD compared with the library — never a lookup table, never favourites.** It was a genre-to-adjective table keyed on which genres sat in a viewer's top ten (`drama` → "heartwarming", `thriller` → "fast-paced"/"plot-twisting"), plus threshold labels on a favourite rate and a rewatch rate, all over `played OR is_favorite`, with every title banned — so the model could say nothing about one viewer it could not say about everyone, and wrote a horoscope. Measured live: one viewer's "44% favourite rate" was 175 unplayed bookmarks of 183, another held 872 unplayed favourites against 159 played films, and `play_count > 1` is set on unplayed rows (it exceeded one viewer's played count), so neither rate measured what its label claimed. `tasteAnalyzer.ts` reads, `tasteEvidence.ts` (pure, pinned) selects and writes the document, `tasteSynopsisPrompt.ts` instructs, `tasteSynopsisStream.ts` is the one generator for both media types. Eight rules. (1) **PLAYED titles only**, for the identity and the card's stats — a claim made to the viewer's face ([F-114](docs/aperture-forensics.md#f-114)); only the dispersion fallback in `tasteAnalyzer.ts` keeps `WATCH_HISTORY_TASTE_SQL`, being recommender input. (2) **A preference is a skew against the library, never volume**: the viewer's count against the count the label's library share predicts, ranked by a smoothed log2 ratio shrunk by `n/(n+K)` with `n = max(watched, expected)` — the expected count is the evidence for an avoidance, the watched count for an attraction. Both sides go through one `libraryFilter`, and each facet's totals are the titles carrying that facet, so an unkeyworded film does not dilute keyword shares. (3) **Titles and names travel with every pattern**; the prompt's own examples use `[placeholders]`, pinned, because a model imitating a named example writes that director into someone else's identity. Examples are fetched `EXAMPLE_CANDIDATES` (8) deep and each title is spent once across the document — ordered by the viewer's own rating, one 10/10 film otherwise heads every facet. **A TMDb collection counts once in every facet comparison** (`UNIT_EXPRESSION`; three extended editions of one trilogy were a country AND a director preference), the country facet needs five such choices (co-producers and filming locations), and rated titles carry genres and keywords so the model can say what the favourites share. (4) **Nothing about how someone watches unless measured** — no rewatch rate, favourite rate or dispersion label (it reads 0 everywhere); unfinished films and series progress are measured, specials excluded from both halves. **A rated film is never "unfinished"** (the rating is the stronger evidence), and **a show is "stopped" only against the episodes that had aired by the viewer's last play** (`episodes.premiere_date`) — otherwise a season that arrived later reads as abandonment; a show with any undated episode gets neither "stopped" nor "caught up". **Air date is not acquisition date and nothing stores the latter** (`episodes.created_at` is the sync's insert time), so "stopped" also requires a season the viewer STARTED to be left incomplete — a finished season one reads as "finished every season they started", never as quitting. **A facet carried by under half of the library or of the viewer's titles is left out** (`MIN_FACET_COVERAGE`): TV production countries cover 27% of series, and which ones is not random. (5) **Below `MIN_TITLES_FOR_SYNOPSIS` (5 films / 3 shows) a stored identity is CLEARED**, since the old ones described watchlists. (6) **`TASTE_SYNOPSIS_PROMPT_VERSION` is stored beside the text (`0176`) and the gate rewrites anything older or NULL** — bump it when the prompt OR the evidence changes what an identity would say; a fallback blurb stores NULL so a provider failure retries. (7) The skew thresholds and history floors are provisional and err toward fewer claims. (8) **The prompt asks for ANALYSIS, not recitation** (`TASTE_SYNOPSIS_PROMPT_VERSION` 3): version 2 answered the horoscope by banning interpretation — every sentence a title or a number, 180 words, a list of "Patterns" — and the model recited the evidence table back. The figures are the model's, at most two reach the reader, and no ratios; the model may use what it knows about the titles it names; every claim must be specific enough to be false for most viewers. **Read a generated identity before shipping a prompt change** — version 2 passed two live SQL checks and failed the only test that mattered. **An analysis prompt costs thinking**: at `maxOutputTokens` 4000 version 3 reasoned through the whole allowance and wrote nothing, so the ceiling is 16,000 (F-030's), and an empty result logs its `finishReason` and token counts. Open: favourites-as-watchlist still feed the taste vector, the explanation context and the discovery brief; and **a new prompt version reaches only viewers whose scheduled run proceeds**, because the activity gate (step 0b) returns before the refresh (step 2b) in both pipelines. [F-129](docs/aperture-forensics.md#f-129)

- **Who may be NAMED in a watch counter is one function, and the payload is the boundary.** The community strip is anonymous ("6 Watched, 7 Plays"); `lib/watcherVisibility.ts` decides whether a viewer also gets names, and both `watchStats.ts` handlers (movie and series mirror) call it. Five rules. (1) **Names are attached server-side or not at all** — a viewer with no visibility gets **no `watchers` key**, not an empty array and not nulls, so nothing a client does can reveal what it never received. (2) **`WatcherAudience` is a discriminated union, not a boolean**, and its unused `users` branch is deliberate: the planned friends feature changes *this function* and nothing else, and callers are already written against a set of visible people rather than yes/no. Shape any future rule as **"which users may this viewer see watch data for"**, never "who watched this title" — the first is reusable by ratings, badges and recommendations, the second is not. (3) **An assumed session resolves correctly for free**: the auth plugin makes `request.user` the target and puts the real admin on `request.impersonation`, so viewing as a non-admin shows the anonymous version. (4) A series row is per **episode**, so the series query aggregates per user and `favorite` means *has a favorited episode* — the same reading `favoritedEpisodes` uses. (5) The counter and the list will stop agreeing the moment visibility is partial (6 watched, 2 names): keep the aggregate as the true total and treat names as a separate claim, or the number means different things to different viewers. Known and unfixed: `watchPercentage` divides by `COUNT(*) FROM users`, which counts disabled and provider-disabled accounts, so Household Reach reads low. [F-110](docs/aperture-forensics.md#f-110)
- **`users.is_enabled` is derived from the feature switches, by one rule, at every writer.** It decides who can sign in, which sessions and API keys work and who can be viewed as, and it opens the WHERE clause of every per-user job — yet four writers worked it out by hand from Movies and Series alone, and `PUT /api/users/:id` cleared it only when both arrived OFF **in the same request**, while the Users page sends one switch per request. So an account switched off one switch at a time stayed enabled under a row of switches all reading off: still signing in, API keys still working, still getting personal Emby home rows — 7 of 50 accounts on a live instance. `lib/accountEnabled.ts` is the one rule: `isAccountEnabled` for an INSERT, `accountEnabledSql` for an UPDATE, pinned against each other on all 64 rows. Four rules. (1) **Movies, Series, Discover or Collections enables an account** — Discover because Discover-only viewers are a supported population ([F-104](docs/aperture-forensics.md#f-104)) and three live accounts were exactly that, which "Movies or Series" would have switched off; Collections because only a signed-in person can use it. Request depends on Discover and Email only permits notifications, so neither counts alone. (2) **An admin already enabled stays enabled with every switch off** — neither the login route nor the session lookup exempts admins, so deriving the flag made switching off your own recommendations a lockout; it never *enables* an admin, because the user sync imports every Emby admin switched off. (3) **An UPDATE's SET list reads the row as it was before the statement**, so a switch written in the same statement is passed as its bind parameter; the bare column reads the old value and the account follows the switch one save late. (4) An explicit `isEnabled` in the PUT body is still honoured, and the Users page takes `is_enabled` from the response instead of computing it from two switches — which is what hid the drift until a reload. The page states it as its own column, **`{{appName}} access`**, beside **`{{provider}} account`**: it used to be only a faint green row tint next to a chip reading "Status: Active" that describes the media-server account (`Policy.IsDisabled`, read live, set in Emby's dashboard), and the two read as one. `0174` re-derived existing rows. [F-127](docs/aperture-forensics.md#f-127)
- **A feature permission is a CAPABILITY, decided in one module from the session.** `apps/api/src/lib/permissions.ts` (`can`, `requireCapability`, `refusalFor`, `discoverRequestSql`; pure, pinned). Before it, `discover_enabled` was **seventeen** inline `SELECT discover_enabled FROM users WHERE id = $1`, `can_manage_watch_history` a private async helper, `collections_enabled` one bare expression and `email_notifications_allowed` a column test — three spellings of one question, a query per request for a value the session had already loaded, and nothing pinned. Six rules. (1) **Flags ride on `SessionUser`**, so a check costs nothing and one query decides a request’s permissions; a flag added there must be selected in `USER_COLUMNS` and mapped in `toSessionUser`, or every capability reading it silently answers "not granted". (2) **Admin override is declared per capability, never assumed** — Collections and watch-history management bypass, **Discover deliberately does not** (an admin with Discover off has always been refused there), and the test asserts the bypass *set*, so a careless `adminOverride: true` fails it. (3) **`discover:request` requires `discover`, enforced at the READ and at the WRITE** — the rule lived only in `pages/Users.tsx`, so `PUT /api/users/:id {"discoverRequestEnabled": true}` granted working Seerr request rights to an account with Discover switched off. `discoverRequestSql` follows `accountEnabledSql`’s mechanism exactly (an UPDATE’s SET list reads the row as it was *before* the statement, so a column the statement also writes is passed its bind parameter, or the dependency holds one save late); `0181` re-derives existing rows, as `0174` did for `is_enabled`. (4) **The refusal text is per capability** — every string already existed at the call site being replaced and is the only part of this a user sees; `refusalFor` returns a **copy**, since the rule table is shared. (5) **A target-scoped permission reads the row** (`PERMISSION_COLUMNS` + `toPermissionSubject`): `email_notifications_allowed` belongs to the account being *edited*, and an admin must respect it rather than grant it by being an admin. Watch-history management looks identical and is the opposite — `requireSelfOrAdmin` runs first, so the caller is the same question minus a query. (6) **Movies and Series are NOT capabilities** — nothing in the HTTP layer reads them, and a capability nothing enforces is a promise the module cannot keep. Open, and named rather than fixed: API keys carry the account’s **admin** rights (`collections_enabled` is forced false, which shows the concern was noticed and dropped); there is no audit trail for a permission change; `max_parental_rating` is applied in the recommender, channels and discovery but not in browse, search, similarity or the assistant; and the sidebar gates only `collections` and `watching`, so Discover and My Requests are shown to viewers who will get a 403. [F-132](docs/aperture-forensics.md#f-132)
- **`provider_disabled` refuses at three doors, and the fourth clears it.** Every per-user job gates on it — both recommender pipelines, both STRM writers, discovery, `twinAffinity`, `rebuildAllTasteProfiles`, `homeSections` — and `strm/cleanup.ts` treats it as grounds to **delete** that viewer’s generated library, yet the auth plugin never selected it, so a viewer disabled on the media server kept a working session for up to 30 days and working API keys indefinitely. The session lookup, `validateApiKey` and the assumption lookup all refuse now; the **login route sets it false**, which is load-bearing rather than tidy — authenticating against the media server is positive evidence the account is not disabled there, and without it a wrong flag is a lockout with no way back but the next user sync. The flag mirrors Emby’s `Policy.IsDisabled` and the sync clears it when an account returns, so **the session rows are NOT deleted** (unlike the `is_enabled` case): refusing the lookup already ends access at once, and signing everyone out over a media server that was briefly answering wrong is the expensive direction of that mistake. The assumption row **is** deleted, being a one-hour lease an admin can start again. Note it means *disabled in Emby*, never *deleted from Emby* — nothing marks the latter ([F-126](docs/aperture-forensics.md#f-126)). [F-132](docs/aperture-forensics.md#f-132)
- **An API key is a SCOPED credential, not the account.** `packages/core/src/apiKeyScopes.ts` (`read`, `write`, `admin`; pure, pinned) plus `api_keys.scopes` (`0182`). A key used to carry `is_admin` straight onto the request, so one minted for a shell script could purge the database and read provider credentials — with none of a session’s limits (no idle window, no lifetime, nothing revoking it when an admin is demoted). Seven rules. (1) **A scope NARROWS, never widens** — `admin` on a non-admin’s key grants nothing; anything that could *add* authority would be a second permission system racing the first. (2) **`read` is implied and is a real member**, or the empty array means "everything" by accident. (3) **Unrecognised is DROPPED at the read and REFUSED at the write** — right for a value already stored, wrong for one somebody is asking for, since storing less than was asked for hands back a key that looks granted and is not; deliberately **no SQL `CHECK`** ([F-002](docs/aperture-forensics.md#f-002)’s rule about a vocabulary in two places). (4) **Existing keys were backfilled to the full set** — they are wired into somebody’s Home Assistant, and silently narrowing a running integration is worse than making the authority visible and narrowable; **new** keys are `read` alone. (5) **`isAdmin` is narrowed at the DOOR, not in `requireAdmin`** — it is read in ~30 places (self-or-admin checks, admin branches of list routes, capability overrides), so guarding only the admin-only *routes* leaves a read-only key reading every account through a handler it may call. (6) **The `write` guard is one hook over every route**, present and future, sharing `lib/requestWrites.ts` with the read-only assumed session — the method rule and both its correction lists (batch lookups that are POSTs, the Trakt OAuth GETs that write) live there now, and `impersonation.ts` keeps only its exit routes. (7) **A refusal names its kind** (`API_KEY_READ_ONLY` beside `IMPERSONATION_READ_ONLY`): a script that suddenly 403s needs to know the key is narrowed, not that the account lost a permission. Four queries shared one row type and spelled the column list out by hand — now `API_KEY_COLUMNS_FOR(alias)`, because a missed `scopes` arrives `undefined` and normalizes to the default, so the key silently loses authority it was granted. [F-133](docs/aperture-forensics.md#f-133)
- **Every route declares who may call it, and a scan enforces it.** `apps/api/src/routes/routeGuards.test.ts` fails on a registration with no `preHandler` that is not allowlisted with a reason (verified against an injected violation). **There were 31.** Most were correctly public — health probes, login, the branding and locale list the login page renders before any session, and the whole `/api/setup/*` plugin (fenced by its own `onRequest` hook) — and finding that out required reading all 31. Five were not: `GET /api/settings/media-server` (server name, id, public URL), `/api/genres`, **`/api/media/images/*`** (an unauthenticated proxy for ANY media-server image path using the admin API key, including `/Users/{id}/Images/Primary`), and both avatar routes (a 200 confirms an account exists; the first’s "public contexts" comment had no such caller, the second has no caller at all). All five take `requireAuth` now — same-origin `<img>` carries the cookie, so nothing in the bundle changed. **Eight more checked `request.user` INSIDE the handler**, which is why an inline check deliberately does not satisfy the scan: it is invisible to any audit of the route table, each had picked its own error body, and the ninth forgets. Four rules. (1) **The point is the review, not the count** — it claims every unguarded route was looked at once by someone who wrote down why. (2) **The head-finder stops at the handler**, so a `preHandler` on a route nested in a handler body cannot answer for its parent. (3) **The handler is found by its opening `async (`, never by balancing parens** — generics, object literals and template strings sit in between, and a counter that got one wrong would scan the wrong span silently; a shape it misses trips the floor assertions instead. (4) **A stale allowlist entry FAILS** — a renamed route comes back unguarded and is reported, but the list would still read as reviewed. It checks that a guard is *declared*, never that it is the *right* one. [F-133](docs/aperture-forensics.md#f-133)
- **Every permission change is recorded, and the ROW is diffed rather than the request.** `packages/core/src/permissionAudit.ts` + `0183` (`permission_changes`). Nothing wrote down a single change to the ten permission booleans or to a key’s scopes, and every cause looks identical from outside: an admin unticked a switch, the user sync saw `Policy.IsDisabled` flip, a **derived** column followed a switch that WAS ticked ([F-132](docs/aperture-forensics.md#f-132)), or a key was narrowed. Five rules. (1) **Before/after snapshots, never the request body** — a recorder fed the request reports that Discover was unticked and misses that request rights went with it, which is the class of change nobody remembers making and therefore the one this exists for. (2) **Only real changes are stored**, or the scheduled user sync grows the table with the clock instead of with events; nothing prunes and nothing needs to. (3) **A creation records GRANTS only** — an import with everything off granted nothing. (4) **It never fails the write**: the change already happened, so every path swallows and logs. (5) **No FK on `subject_id`** (the audit must outlive the account) and `ON DELETE SET NULL` on the actor (deleting an admin must not erase what they did); labels are stored beside the ids so a deleted subject stays readable. **A database trigger was the first choice and cannot know the ACTOR** — Postgres has no request context and a session GUC needs every write inside an explicit transaction on a pinned connection, which pooled autocommit `query()` is not — so `permissionAuditCallSites.test.ts` covers the drift instead (verified against an injected unrecorded write; it keeps **two copies of the column list on purpose**, since a scan that imported the list it checks would agree with itself, and it lives in core because it scans both packages and an api-side test reaching into `packages/core/src` breaks core’s `rootDir`). Its first run found two real things: `setUserAiExplanationOverride` was audited at its route and now records itself with a **required** actor, and two allowlist entries were stale — which the test refuses, because a renamed route comes back unguarded while the list still reads as reviewed. The login writer records **before** the `is_enabled` refusal: a refused login still cleared `provider_disabled`. [F-134](docs/aperture-forensics.md#f-134)
- **The client is told the ANSWERS, never the rules.** `capabilitiesFor` ships decided booleans on `/api/auth/check`, `/me` and `/login`; `useCapability` reads them and has deliberately **no fallback logic**, because working a capability out from the user’s flags is how the bundle comes to hold a second copy of a rule the API then disagrees with ([F-132](docs/aperture-forensics.md#f-132)). Four rules. (1) They ride on **`/auth/check`**, the call the client boots from — on `/me` alone the first paint gates on nothing. (2) **Absent reads as false**, so a client built before a capability existed hides the feature rather than linking to a 403. (3) During an assumption they are the **target’s**, which is the point. (4) The sidebar gated on `watching` (an instance switch) and on `isAdmin || collectionsEnabled` — the admin-override half of a rule whose other half lives in core — while **Discover carried no gate at all**, so every viewer got a link to a page answering 403. **My Requests is deliberately NOT gated on `discover:request`**: its Issues tab is reachable by anyone who can report a problem ([F-107](docs/aperture-forensics.md#f-107)), and hiding it would strand issues already filed. Same change: `Users.tsx`’s six near-identical toggle handlers became one `togglePermission(user, key)`, and **`applySavedRow` takes the whole row from the response** rather than the value it sent — load-bearing, since two of those columns are derived and a page applying what it sent is wrong about the ones that moved with it until a reload ([F-127](docs/aperture-forensics.md#f-127)). The AI-explanation toggle stays separate: different endpoint. [F-134](docs/aperture-forensics.md#f-134)

## Jobs system (how background work runs)

1. Job catalog: `apps/api/src/routes/jobs/definitions.ts` (static list; **crons there can drift — DB `job_config` via core `getAllJobConfigs()` is authoritative**).
2. Execution: `apps/api/src/routes/jobs/executor.ts` — one `switch` mapping job name → core function. Adding a job = core function + executor case + definitions entry (+ default `job_config` row if scheduled) **+ an entry in `apps/web/src/pages/jobs/constants.tsx`** and **+ an entry in core's `JOB_SCHEDULE_DEFAULTS`**.
3. Scheduling: `apps/api/src/lib/scheduler.ts` (node-cron; executor injected via `setJobExecutor` in `routes/jobs/index.ts`, which also guards against double-runs).
4. Progress: in-memory + SSE, lives in **core** `jobs/progress.ts` (`withProgress`, `subscribeToJob`); run history in `job_runs`.
5. Shared mutable state: `routes/jobs/state.ts` `activeJobs` Map is also imported by `gap-analysis` and setup, which call `runJob` directly (bypassing jobs HTTP routes).

- **The job registry is `jobDefinitions`, not core.** `getValidJobNames()` is **deleted** — it returned the keys of a *seed schedule* map, so four jobs correctly wired everywhere else still answered 404 on `/api/jobs/:name/config`, and the dialog looked normal until Save. Core cannot import the API app, so no build can see that kind of divergence. The map is now `JOB_SCHEDULE_DEFAULTS` and is only a **default cadence**, but its keys still matter: **the scheduler builds its task list from `getAllJobConfigs()`, which merges DB rows with this map and never reads `definitions.ts`'s `cron` field**, so a scheduled job absent from both is silently never scheduled. `getJobConfig` **no longer returns null** — a job with neither a row nor a default reads as manual-only. `jobDefaults.test.ts` fails on a registered job with no seed, a seed naming a dead job, and a `manualOnly` job seeded with a real cadence; it imports core through `dist`, so it only sees source changes **after a build**. [F-076](docs/aperture-forensics.md#f-076)
- **A weekly schedule can name several days, and only one reader may resolve them.** `0149` adds `schedule_days_of_week INTEGER[]`, backfilled from the scalar. **`resolveScheduleDays` is the one reader**, used by both `scheduleToCron` and `formatSchedule` — otherwise the scheduler runs on days the admin's own summary does not name. The scalar is still *written* (earliest selected day) purely so a rollback reads a sane schedule rather than a NULL meaning Sunday. **Biweekly is truncated to one day** by `normalizeScheduleDays` at the write layer, since two firings in one week are 3–4 days apart and the second is always dropped — picking Mon+Thu would quietly mean "every other Monday". Out-of-range days are **dropped, not clamped**, and the route rejects them. `ScheduleTable`'s `computeNextRun` duplicates the resolver's fallback order by hand (web-never-imports-core invariant). [F-077](docs/aperture-forensics.md#f-077)
- **`JOB_CATEGORIES` is an allowlist, and a job missing from it has no UI at all.** `apps/web/src/pages/jobs/constants.tsx` maps job name → category and `JobCategoryList` filters on it, so an otherwise perfectly registered job gets **no card** — meaning no Run button and, worse, **no Cancel button**. The Schedule tab lists everything the API returns and therefore hides the omission: the job looks present, is runnable from there, and cannot be stopped. A new job needs a `JOB_CATEGORIES` entry plus `JOB_ICONS` and `JOB_COLORS`; a new *category* needs `title`/`description` under `admin.jobsPage.categories.*`. [F-078](docs/aperture-forensics.md#f-078)
- **A job that never calls `createJobProgress(jobId, …)` has no progress record, and every progress API then no-ops in silence.** Every function in `jobs/progress.ts` opens with `activeJobs.get(jobId)` and returns when absent — correct (a finished job is evicted after five minutes) but completely quiet. Missing that one line produces **every** symptom at once and no error: empty bar and log pane, no `job_runs` row (because `completeJob` returns before `saveJobRun`), and `isJobCancelled` reducing to `undefined?.status === 'cancelled'`, i.e. **always false**, so Stop cannot work however diligently the work polls it. **The executor is not a generic wrapper** — only cases that call `createJobProgress` get progress, and those same cases must call `completeJob` (skipping it when cancelled, since `cancelJob` already filed the row). `setJobStep`'s `itemsTotal` may be left 0 and filled by the first `updateJobProgress`. `addLog` **mirrors to the container logger**. The silent early returns now warn once per job id. [F-079](docs/aperture-forensics.md#f-079)
- **Cancelling is cooperative, and the terminal state is a one-way door.** `cancelJob` only sets `status='cancelled'` and writes the `job_runs` row; work stops solely because the core function polls `isJobCancelled(jobId)` — which `enrichment/`, `mdblist/`, `studioLogos.ts`, `backupService.ts`, `explanationRefresh.ts` and all four recommendation loops do, and everything else does not. `analysis/job.ts` cancels too but will **not** appear in a grep for `isJobCancelled`: it takes an injected `shouldCancel` supplied at the executor case. Two consequences: a job that does not poll runs to completion after being cancelled and used to **flip its own status back** (the record sits in `activeJobs` for five more minutes), so `completeJob`/`failJob` now ignore a job already in a terminal status; and nothing interrupts an in-flight HTTP or model call, so for anything doing paid model calls in a loop, **check between calls, not just between users**. [F-080](docs/aperture-forensics.md#f-080)
- **A cancelled job that keeps running is not the bug; letting a second one start beside it is.** All three claim sites asked `getJobProgress(id)?.status === 'running'`, and a *cancelled* job is not running — so the check passed for precisely the case it existed to stop, and nine users were scored twice in 13 minutes. **Membership in `activeJobs` is the correct test**, since the entry is cleared by `runJob`'s `finally` — when the work exits, not when someone asks it to. `decideClaim` is one pure function in `routes/jobs/state.ts`, pinned by `state.test.ts`. The cancel handler no longer `delete`s the entry, so a cancelled job holds its slot while winding down — which makes the **409 message load-bearing** ("was cancelled and is still winding down" is a different fact from "is already running"). **Releasing must be identity-checked** (`releaseJob`), because a zombie exits *after* its replacement has claimed the name. The escape hatch is **eviction, not force**: a terminal record is dropped after five minutes and `decideClaim` admits a claim when the holder has no record. **The 409 must be visible** — `handleRunJob` was `if (response.ok)` with no `else`, so a rejected start showed nothing, and a Run button that silently does nothing is what sends an operator to `docker stop`. [F-081](docs/aperture-forensics.md#f-081)
- **A per-run item cap is declared on the job and stored on its schedule row.** `JobDefinition.runLimit` (`{ default, min, max, unit }`) says a job works through at most N items per run and that N is the operator's; `job_config.max_items_per_run` (`0177`) holds the choice, NULL meaning the default. `routes/jobs/runLimit.ts` is the one pair of decisions (pure, pinned): `runLimitError` refuses a number for a job that declares no limit and anything out of range (**refused, never clamped**), and `resolveRunLimit` reads an unset **or no-longer-valid** stored value as the default. The executor resolves it per run, so it applies to manual runs too; the list route ships the resolved `runLimit.value` so the card cannot state a different cap from the one the run uses. Only `generate-title-analysis` declares one (default `DEFAULT_MAX_TITLES_PER_RUN`). It is schedulable but **seeded manual** — each title is paid retrieval and inference, so a cadence is opted into. **`setJobConfig` is a partial update**: a PATCH naming no `scheduleType` keeps the whole current schedule (row, or the seed it is already running on) and a missing `isEnabled` keeps the current one. It used to fill a missing type with `'daily'` and every time field with null, so the Schedule tab's enable switch — which sends `isEnabled` alone — turned any job it touched into "daily at midnight". `maxItemsPerRun` undefined leaves the cap alone; null clears it.
- **A streamed model call needs a STALL ceiling, and the abort signal alone does not end the caller's wait.** A title analysis run sat on one title for **8h45m** and could not be stopped: `streamText` was passed no `abortSignal`, the OpenRouter fetch carries none of its own, and streaming had removed the ceiling that used to apply by accident (a non-streaming call gets no headers until the model finishes, so Node's 300s `headersTimeout` ended a wedged call; an SSE response sends headers at once). Cancellation is polled **between titles**, so Stop set a status the stuck title never read, and `runJob`'s slot is held until the work exits. `lib/streamStall.ts` (`startStreamStallGuard`, pure, pinned) is the one home. Six rules. (1) **A stall window, never a wall-clock cap** — a cap cannot tell slow from hung, which is why `LOCAL_INFERENCE_TIMEOUT_MS` is an hour; `WRITE_STALL_MS` is 10 minutes against measured healthy calls of 46–102s, with a 1-hour deadline as a backstop only. (2) **The caller RACES `guard.aborted`; awaiting the read bundle is not enough.** Measured on `ai@5.0.118`: after an abort the socket closes but `await stream.text` **never settles** and `onAbort` never fires, while `for await (fullStream)` throws — so the analysis writer (which reads the promise bundle) needs the race and the Watcher Identity (which consumes `fullStream`) does not. (3) **A partial answer is never read** — it would hand `findResponseProblem` a truncated document and file a stall as an unusable RESPONSE, the one outcome that does not rotate ([F-066](docs/aperture-forensics.md#f-066)); `abortOutcome` maps stall/deadline to a rotating `error` and cancellation to `cancelled`, and the title writes no row either way. (4) **`shouldCancel` rides on the guard**, which is what gives Stop reach into an in-flight request; a poll that throws is ignored. (5) **Activity is a timestamp read on an interval**, not a timer per chunk (a delta arrives per token), and reasoning deltas count. (6) The LM Studio branch always accepted a `signal` and **nothing passed one**. Still uncovered: the assistant chat's two `streamText` calls (one request, not a job slot) and the grounding path's `generateText` (bounded by Node's 300s, but Stop cannot interrupt it). [F-131](docs/aperture-forensics.md#f-131)
- **A job log is trimmed from both ends.** `addLog` bounds what it keeps (`LIVE_LOG_LIMIT` 500 in memory, `STORED_LOG_LIMIT` 300 persisted), and a plain `slice(-n)` keeps the wrong half: a 200-title pass opened at "[152/200]" with every line explaining what the run set out to do already dropped, while 197 identical failures were kept. `jobs/logWindow.ts` keeps a head (`LOG_HEAD_ENTRIES` 30) plus as much tail as the budget allows and inserts **one entry naming how many were dropped**. Pure and pinned (`logWindow.test.ts`), including the small-budget cases where head + marker + tail must total exactly the limit. **The marker's count must be cumulative**: `condenseLogs` runs on *every* append past the limit, so recomputing from the list in front of it — a list already holding its own marker — reported "2 earlier entries not kept" for a job that had discarded thousands. The count rides in `data.elided` and a later pass adds to it; detection is on that field, never on the message text, which is prose. A stored log's figure is `limit − head − tail` and describes the **buffer**, not the run — do not read it as a total. [F-082](docs/aperture-forensics.md#f-082), [F-094](docs/aperture-forensics.md#f-094)

## Recommender / embeddings pipeline (order matters)

sync-users → sync-movies/series (media server → DB) → enrichment (TMDB/OMDb fields onto rows) → generate embeddings (`buildCanonicalText` — **includes enriched fields; changing enrichment output means re-embedding**) → generate recommendations (taste vector → refresh the Watcher Identity if that vector or its prompt version moved → pgvector candidates → score: similarity/novelty/rating + taste-profile boosts → MMR selection → AI explanations → `recommendation_*` tables) → outputs (STRM libraries, channels, playlists, collections).

Embedding tables are shared consumers: recommender, `/api/similarity` graph, semantic search, discovery scoring, taste-profile interests. Movies and series are **parallel pipelines** (`recommender/movies/` vs `recommender/series/`) — see the mirroring invariant.

- **A canonical-text change reaches existing rows only via `CANONICAL_TEXT_VERSION`.** Selection was once `LEFT JOIN … WHERE e.id IS NULL` (**missing, not stale**), so editing the builder did nothing to 12.5k rows and the only remedy was a TRUNCATE of every dimension table. `text_version` (`0138`, movie and series families only — **episodes excluded on purpose**, their text reads no enrichment column) makes a builder change cheap to detect; NULL predates it. Five rules: the staleness clause compares **`updated_at`, not `created_at`** (`storeEmbeddings` upserts, so `created_at` holds the first write forever); a row that survives being handled is an **infinite job**, so both loops attempt each row at most once per run and `markEmbeddingsCurrent` restamps rows whose text turned out unchanged; counts and selections must share the predicate (`MOVIE_STALE_SQL`/`SERIES_STALE_SQL`) or the bar describes a total the loop never reaches; and `buildCanonicalText` must be **deterministic**, since the skip-unchanged guard is a string comparison (pinned by `canonicalText.test.ts`). A re-embed moves every item vector, so it costs `rebuild-taste-profiles` and then a regenerate. [F-083](docs/aperture-forensics.md#f-083)
- **The canonical text is nationality-heavy by construction — do not add more proper nouns.** Of fifteen fields, **six were nationality-coded** (director, studio, cinematographer, composer, cast, country) against three describing what a title is *like* (genres, plot, keywords), so the vector partly works as a nationality detector. Three fields were removed: **content rating** ("NR" tracks age and non-US origin, not the work), **awards** (same rule that keeps scores out, and award prose clusters award films together regardless of subject), and **composers** — but **not cinematographers**, since the below-the-line argument holds for photography as a style signal and not for a single composer credit appearing on two or three titles. `MAX_KEYWORDS` deliberately **stays at 18** (coverage is uneven, so raising it trades one dilution for another). This reduces rather than removes the effect — five nationality-coded fields remain. **The plot-widening this entry credits as the bigger lever never happened**: `plot_full` is the blurb on a real library, so proper nouns are ~a quarter of the median document, not ~2%, and these three removals carry the whole load alone. [F-084](docs/aperture-forensics.md#f-084), [F-089](docs/aperture-forensics.md#f-089)
- **`plot_full` is OMDb's `plot=full`, and it replaces the overview in the vector rather than joining it.** Same request and quota as `plot=short` (which returns roughly what the media server already syncs into `overview`), but it is IMDb's user-submitted synopsis — longer and different in kind. Stored as its own column (`0139`) because `movies/sync.ts` rewrites `overview` every pass. Three rules: use it **instead of** the overview, never alongside, or plot weighs twice against genre/crew/keywords; use it **only when actually longer** (OMDb falls back to the blurb, so non-null proves nothing — the naive `plotFull || overview` returns a *shorter* value and `canonicalText.test.ts` caught it); and the cap is **4000 chars** (`PLOT_CHARS`) — 1000 kept only the setup, the most interchangeable part of any story, while uncapped makes cosine partly measure *"does this title have an IMDb synopsis"*. In the UI it is opt-in behind "Read full synopsis" (spoilers). `0139` also **clears `omdb_enriched_at`**, since the stamp records that OMDb was asked, not what for. **Measured since: on this library `plot=full` is the blurb** — 99.7% populated, but p50 431 chars, 0.75% over 2,000, none over 5,000 — so the cap is nearly never reached and proper nouns are ~a quarter of the median 905-char document rather than the ~2% F-084 assumes. Trimming is exhausted (cast 3, studios 2, cinematographers 2, keywords 18); a wider plot source is the only lever left, and every candidate reintroduces the coverage asymmetry the cap bounds. [F-085](docs/aperture-forensics.md#f-085), [F-089](docs/aperture-forensics.md#f-089)
- **`tmdb_rating`/`tmdb_vote_count` and `imdb_rating`/`imdb_vote_count` cost no extra request** (`0140`) — they ride on responses enrichment already fetches and parses. **Vote counts are half the point**: 8.2 from 22,000 votes and 8.2 from six are not the same claim. Both parsers are traps: `"N/A"` must become **null, not 0**, or unrated titles sort below genuinely bad ones; and `imdbVotes` is thousands-grouped, where `parseFloat('545,163')` returns **545** (pinned by `ratings.test.ts`). Every badge guard uses `!= null` (NUMERIC invariant). Ratings stay **out of the canonical text** — a bare "82" embeds as noise. **TMDB has no awards API**, so OMDb's `awards_summary` remains the only structured source. [F-086](docs/aperture-forensics.md#f-086)
- **Ratings refresh is a separate module and job, because metadata and ratings want opposite selection rules.** `needsEnrichmentSql` has **no TTL** — right for a plot or a cast list, wrong for a rating, and one shared predicate let the field that never changes set policy for the field that changes weekly. The error is **biased, not random**: a new release's rating starts high and decays as the vote base widens, so a frozen copy systematically *overrates* recent films, and rating is a quarter of the blend. Emby is not an independent second opinion (its rating-sync plugin reads OMDb and MDBList). Six things (`ratings/`, `0148`, job `refresh-ratings`): the IMDb source is a **bulk file, not an API** (`title.ratings.tsv.gz`, 8.2 MB, daily, no key) so **one request covers all ~12.5k titles**; `RATING_SOURCE_IDS` is **the one copy** and the job's step count derives from it (a hand-written number is the second copy that stops matching); `imdb_ratings_refreshed_at` is stamped on **every row we looked for, not only the ones we found**, since a title with no votes is absent from the file entirely; **OMDb still writes those columns but only while that stamp is NULL** (conditional rather than deleted, because the source is opt-in on licence grounds, and the clobber it prevents is latent until the next stamp clear); and `parseRatingsLine` is pure and pinned (`imdbDataset.test.ts`) — the `wanted` set is checked **first** (rejecting ~99% of 1.5M lines and disposing of the header for free), `indexOf` rather than `split`, and `Number()` with an explicit empty-string guard since **`Number('')` is 0, not NaN**. [F-087](docs/aperture-forensics.md#f-087)
## Auth model

`plugins/auth.ts`: `x-api-key` header (takes precedence) or `aperture_session` cookie. `requireAuth`/`requireAdmin` — **`requireAdmin` has no bypass**; server-side callers that need to act without a logged-in user call the domain function directly (`routes/jobs/startJob.ts` is the one for jobs, used by the setup wizard) rather than replaying an HTTP request through `fastify.inject`. API-key users are forced `provider:'emby'`, `collectionsEnabled:false`, and carry the account’s other permission flags — but only the rights their **scopes** allow (see the API key rule above; a key without `admin` has `isAdmin` false whatever the account is, and one without `write` is refused every writing request). **Feature permissions are not checked here** — `requireAuth`/`requireAdmin` answer *is there a user* and *is it an admin*; everything per-feature goes through `lib/permissions.ts` (see the capability rule above), composed as `preHandler: [requireAuth, requireCapability('discover')]`.

- **Sessions are bearer tokens, not row ids**: the cookie holds 32 random bytes; `sessions.token_hash` stores only its sha256, and `sessions.id` is unrelated. 30-day absolute lifetime plus a 7-day idle timeout (`last_seen_at`, rewritten at most every 5 min). `is_enabled` is enforced on *both* the login path and every session lookup, and `PUT /api/users/:id` revokes sessions when it disables an account — a disabled user loses access immediately. The `cleanup-auth-state` job sweeps expired/idle rows, deliberately with a 1-day grace margin so the auth plugin stays the only thing that decides a session is dead.
- **Account assumption ("view as user") layers a second cookie, it never swaps the session.** `aperture_impersonation` sits *beside* `aperture_session`, backed by `impersonation_sessions` (`0159`, one-hour lease, `ON DELETE CASCADE` from `sessions(id)`). The auth plugin resolves the session, then makes `request.user` the **target** — every handler downstream is unchanged — and puts the real admin on `request.impersonation`. The admin's own credential is never touched, so leaving is a delete of one row and one cookie rather than a re-mint of a token the DB only stores a hash of. **An assumed session is read-only**: `impersonationBlocksRequest` (`lib/impersonation.ts`, pure, pinned) refuses every unsafe method except the two that *end* it (`/api/auth/impersonate/stop`, `/api/auth/logout`) plus two POSTs that are only lookups (`/api/favorites/status/bulk`, `/api/seerr/status/batch`). **The method rule has two named exceptions in the other direction**, because two GETs write: `/api/trakt/auth-url` mints an OAuth state bound to the *current* user and `/api/trakt/callback` redeems it into their token store, so an assumption could otherwise link the admin's Trakt account to someone else's — a cross-account data flow outliving the assumption. `getUserSettings` was a third such path (a getter that INSERTed a defaults row) and is now a pure read; **a getter that writes defeats this guard silently**, so audit the call graph, not the handler list. Nothing writes to the target: no session row, no `last_login_at`, no `updated_at`. The exit lives in `Layout`'s AppBar so it is on every authenticated page structurally; its height rides in `--aperture-chrome-top`, which four layout calculations read. [F-103](docs/aperture-forensics.md#f-103)
- **Brute-force controls are two-layer, on different axes**: `@fastify/rate-limit` keyed on **IP alone** for `/api/auth/login` (folding the username in widens the keyspace, so a spray rotating usernames would get a fresh bucket per request and never trip it), plus DB-backed per-account lockout in `apps/api/src/lib/loginAttempts.ts` with progressive backoff, which is what covers one account attacked from many IPs. **Only `InvalidCredentialsError` counts toward the lockout** — the providers throw it on 401 and a plain `Error` otherwise, so a media-server outage returns 503 instead of locking out every user who retries.
- **Deployment posture lives in `apps/api/src/config/security.ts`**, not scattered env reads: `DEPLOYMENT_MODE` (`direct` default, or `proxy`/`tunnel`/`cloudflared`), `TRUST_PROXY`, `HOST`, `COOKIE_SECURE` (defaults on in production — *not* derived from `APP_BASE_URL`), `API_DOCS` (`public|admin|off`, admin-only in production), `ALLOW_PASSWORDLESS_LOGIN` (production gate over the `allow_passwordless_login` admin toggle), `SETUP_ALLOW_REMOTE`, `CSP_REPORT_ONLY`. All booleans parse case-insensitively via `envFlag`. `helmetOptions()` and `config/rateLimits.ts` live here too so `security.test.ts` asserts the objects the server actually registers.
- **`TRUST_PROXY` is load-bearing and `=true` is a footgun**: it trusts `X-Forwarded-For` from anyone, so a caller can forge their address to mint rate-limit buckets and look local to the setup guard — pin the proxy (`TRUST_PROXY=172.18.0.1`) instead. Leaving it unset *behind a proxy* is worse: every visitor collapses to the proxy's address, so the login limiter becomes one global bucket and `isTrustedSetupSource` sees the whole internet as local. `DEPLOYMENT_MODE=proxy` supplies a loopback default; an explicit `TRUST_PROXY` always wins.
- **`config/deploymentPosture.ts` is the one source of truth for "is this exposed correctly"** — the boot warnings and `GET /api/settings/deployment` (Settings → System → Deployment) both render its `findings`, so they cannot drift. Findings are stable ids translated under `settingsDeployment.findings.*`; a new one needs `title`/`detail`/`fix` in en or the panel shows a raw key (there is a test for exactly that). Crucially it is **evidence-based, not config-only**: `noteRequest` samples live traffic from the access-log hook, because an instance behind a tunnel with no trusted proxy looks perfectly healthy from config alone — seeing `X-Forwarded-For` while trusting nothing is the only reliable tell.
- **Trusted proxies are editable at runtime** (`config/proxyTrust.ts`, `PATCH /api/settings/deployment`), stored in `system_settings.trusted_proxies`. This works because **Fastify accepts a *function* for `trustProxy` and consults it per request** — the value being passed at construction does *not* freeze the decision. (An earlier reading of `Request.buildRequest` concluded it did, which is why the panel first shipped read-only; `security.test.ts` pins the dynamic behaviour now.) Matching delegates to `proxy-addr`, the same library Fastify uses, so CIDRs behave identically to the static form. `TRUST_PROXY` still wins outright when set — the UI goes read-only — because it must also be available *before any admin exists*, which is the only way the first-run setup guard can be protected behind a tunnel.
- `@fastify/helmet` sets the CSP — `imgSrc` is deliberately wide because TMDB posters load direct from `image.tmdb.org` and `getProxiedImageUrl` only proxies media-server URLs; `styleSrc`/`fontSrc` must keep the Google Fonts hosts that `index.html` pulls; Swagger UI gets a relaxed CSP scoped to `/openapi` because it bootstraps inline. `connect-src 'self'` also fences assistant-ui's cloud path (see the comment at the `useChatRuntime` call site). `referrerPolicy` is `no-referrer` and stays that way — the YouTube trailer frame overrides it per-element rather than the policy being loosened for the whole site (see the Error 153 rule above).
- **First-run setup is network-restricted**: a plugin-scoped `onRequest` hook in `routes/setup/index.ts` refuses `/api/setup/*` from non-local addresses until setup completes (admins and `GET /api/setup/status` always pass). Before that hook existed, whoever reached a fresh instance first could configure it and become admin.

## Web conventions

- Provider tree (App.tsx): `I18nextProvider > RtlProviders > BrowserRouter > SetupProvider > AuthProvider`; authed pages additionally get `ViewModeProvider > UserRatingsProvider > WatchingProvider > AssistantDockProvider` + floating `AssistantModal`.
- Route table lives in `apps/web/src/App.tsx`; shell is `components/Layout.tsx` (sidebar items feature-gated by watching/collections flags).
- **The admin console is generated from one registry, and that is what stops it drifting.** `pages/admin/nav/registry.ts` is pure data (no JSX, no React) listing 8 groups and 42 entries; `elements.tsx` holds the icon and the `lazy` component for each, keyed by the same id; `routes.tsx` builds the `<Route>` table from it; `search.ts` builds the palette index from it. Adding a section means an entry **and** an element — omit the entry and the section gets no route at all, which is the opposite of the `JOB_CATEGORIES` failure where a missing key leaves a job present-but-crippled. Seven things. (1) Depth is capped at **two** (group → leaf) permanently; a group past ~12 leaves splits rather than growing a third tier — three stacked scrollable tab strips is what this replaced. (2) `registry.test.ts` runs under `node --import tsx --test` (`pnpm --filter @aperture/web test`, the web package's first test runner) and pins: unique ids and paths, exactly one index route, entry↔element parity, every i18n key resolving in `en`, **every barrel export in `settings/components/index.ts` having a home**, every legacy redirect target existing, and **every declared field anchor existing as an `id` in a section**. (3) Search has three tiers — sections free from the registry, ~33 `fields` opted in with anchors, and **every job** — and matches translated titles/blurbs **plus untranslated `aliases` written in the registry rather than in `translation.json`**, so `omdb` and `pgvector` keep working in all 15 locales. **The jobs tier is not optional the way fields are**: 28 jobs are the largest set of named, runnable things in the console, and unindexed they sent every job name to a settings page that merely mentioned the word — `sync movies` reached Libraries, `rebuild taste profiles` reached a slider labelled "Borrowed from a taste twin", `studio logos` reached **nothing**, and `full reset recommendations` put the destructive database purge on top. They are read from `pages/jobs/registry.ts`, the same array the page renders, which is why that module was split out of `constants.tsx` (JSX icons) — a search index built from a second list would drift, and the failure mode is a job that is findable but has no card. **A `#job-…` link must also open the tab holding it**: the page unmounts inactive `TabPanel`s, so a global job's anchor did not exist and the scroll silently did nothing; `jobTabIndex` derives the tab from the same three arrays. **The result floor is relative, never absolute** — only results matching as many query tokens as the best result survive, which took `api key` from 15 rows to 2 while never turning "few results" into "none". Hyphens tokenise like whitespace so a kebab id pasted from a log searches as its words. **The query is tokenised and scored per word, never matched whole.** Matching the whole string looks reasonable — settings names are often two words — but nobody types a label verbatim; they name the area and the thing, and those words sit in *different* indexed strings. `ai embedding model`, `novelty weight`, `backup database` and `trusted proxy` each returned **zero**. So each entry's haystack also carries its **group label** (weight 40) and each field's carries its **parent section title** (45) — that is what makes "novelty weight" reach a slider labelled "Genre Discovery". Ranking is **tokens matched first, score second**, so a result answering the whole phrase beats one scoring higher on part of it, and a stray word degrades to the best partial match instead of nothing. Pinned by `search.test.ts` against the real registry and the real English strings. (4) The palette is ⌘⇧K, separate from `GlobalSearch`'s ⌘K, because content results arrive from a debounced API call and these are local and instant. **Which palette a keystroke belongs to is decided once, by `lib/searchShortcut.ts`, and neither listener may decide for itself.** Both listen on `window`, and `preventDefault()` does not stop a sibling listener on the same target — so the only thing separating them was a case comparison on a letter (`e.key === 'k'` here, either case there). **Letter case is not a signal of Shift**: with Caps Lock on, Caps and Shift cancel and ⌘⇧K arrives as lowercase `'k'`, both matched, and both palettes opened stacked (reproduced in a browser). `shiftKey` is the only field that answers it. Two smaller rules inside the resolver: **Ctrl+Alt is AltGr**, which types a character, so it is not a shortcut; and a non-Latin layout (`'л'`, `'ק'`) falls back to `e.code === 'KeyK'` — but **only** as a fallback, since matching `code` first would give a Dvorak typist's Ctrl+V the palette. Pinned by `searchShortcut.test.ts`, which also scans `apps/web/src` for anything comparing the K key by hand (verified to fail on an injected violation). (5) `MediaTypeCard` in `RecommendationConfigSection` renders **twice**, so its anchors are namespaced by an `idPrefix` prop (`rec-movie-*`/`rec-series-*`) — a bare id would be duplicated and every jump link would land on the movie copy. (6) Old addresses (`/admin/settings?tab=…`, `/admin/users`, `/admin/jobs`, `/admin/translations`, `/admin/gaps`) redirect via the **frozen** `legacyRoutes.ts`; it never grows. (7) Admin lives in the **app bar** (`AdminMenuButton`, admin-only, left of the avatar), not the sidebar. `RunningJobsWidget` stays beside it deliberately — it is a live progress bar and self-hides at rest, so a count badge could not replace it. **Every row in its popper is a link into the job** (`jobConsoleLink`, the one spelling of that address, shared with the palette and pinned against it) — a progress bar that reports a job is failing and offers no way to read its log is where an admin goes hunting through the console by hand. The destination opens the job's **tab and its logs**, via `expandLogs`, which is idempotent on purpose: `toggleLogs` would close the logs of anyone who already had them open, including on a second click of the same link, which is the natural thing to try when the first appeared to do nothing. A job absent from `JOB_CATEGORIES` has no card, so it links to the page rather than a dead anchor. **The widget names a job in the progressive tense and the page does not** ("Syncing Movies" vs "Sync Movies") — that is deliberate, but only 12 of 29 jobs have such a string, so the fallback is **the page's own name**, never a second title-caser: that drift is how one job read "Sync Lldap Emails" here and "Sync LLDAP Emails" on its card. Two keys under `runningJobs.jobNames` (`generate-embeddings`, `generate-recommendations`) name jobs that do not exist and are dead; renaming them would strand their 14 translations, so they are left for a copy pass. (8) **A precondition is declared once, on the entry.** `gate` is read by the route *and* the nav column (dimmed with a reason, never disabled — the old tab was unclickable, so the only way to learn what it needed was to hover it); `GATE_TOOLTIP_KEYS` is a `Record<AdminGate, …>` so a new gate without an explanation is a type error. Only a **pass** is cached: configuring TMDB is one of the things you come here to do, and caching the negative would leave the section refusing until a reload. (9) **`hooks/activeJobs.ts` is the one poll of `/api/jobs/active`** — the app bar widget and the nav column's Jobs badge both read it, reference-counted, and an in-flight response is dropped if the last subscriber left (it would otherwise refill the cache the cleanup just emptied). (10) The hash-scroll effect keys on **`location.key`**, not just path and hash: searching for the same field twice changes neither, and keying on those alone made the second search do nothing. (11) **The nav rail is capped, not fixed, and the cap only works because of the flex chain.** The chain is `maxHeight: calc(100vh - 112px)` + `flexDirection: column` on the Paper, then `flex: 1; minHeight: 0` on both the wrapper and the scrolling list. **`minHeight: 0` is load-bearing**: a flex item defaults to `min-height: auto` and refuses to shrink below its content, so `overflowY: auto` never engages. It first shipped with `height: 100%` on the child of a `maxHeight`-only parent, which resolves to `auto` and overflowed silently; the fix at the time was a *definite* `height`, which was wrong in the other direction and stayed wrong for a release — measured, a collapsed 676px column sat in a 788px box with 112px of dead space, and an expanded 1461px one sat in the same 788px box behind a scrollbar, because the height never moved at all. **The real cause of the scrollbar was not the height but the expansion**: `expanded` was a *list* and nothing ever removed from it, so browsing accumulated open groups until forty rows were in a viewport-height box — while the component's own docstring claimed only the current group was open. One group at a time (`AdminGroupId | null`) removes the inner scrollbar in seven of eight groups; the effect keys on the active **entry** as well as the group, or someone who collapsed the group they are standing in and then jumped elsewhere inside it arrives with the selected row hidden. **Integrations is at eleven entries and is the one group that still scrolls on a short screen — it is the next to split**, per the registry's own two-level rule. (12) **The content pane has an error boundary** (`AdminErrorBoundary`, reset on path change). Every destination is one lazy component in one outlet, so without it a single section throwing unmounts the sidebar, the app bar and the nav column together — a white screen naming nothing. It also carries the reload prompt for the other failure lazy routes introduce: hashed chunk filenames plus image-swap deploys mean a tab left open across a deploy asks for a file the new build does not serve. (13) **An `id` written one line below an opening tag is a JSX child, not a prop.** React renders it as literal text, the element never gets the attribute, and TypeScript, eslint and a source-text search for the anchor all pass — the only tell is `id=rec-movie-max-candidates` printed on the page. `registry.test.ts` throws on that shape specifically, because it is the one way a promised anchor can pass every other check and still not exist. (14) The subtree ends in a **catch-all redirect** — an unmapped `/admin/*` still matches the shell, so without it the frame renders around an empty outlet, which is a blank page rather than a wrong one.
- **User settings has three tabs, and `?tab=profile` is an alias rather than a dead link.** `USER_SETTINGS_TAB_KEYS` (`pages/UserSettings/tabHelpers.ts`) is `watcher, algorithm, preferences`; the index is a **position in a JSX list**, so a key that does not round-trip sends one tab's address to another tab's panel — pinned by `tabHelpers.test.ts`. Profile was deleted because everything on it but one card was a **read-only echo of the account menu header** (avatar, username, display name, media server, role, every field disabled under a caption saying they are synced from the media server). The exception is the **email address and notification opt-in**, the only place a viewer can set their own address, which moved to Preferences as `EmailNotificationsCard` — so the legacy alias points `profile` at **preferences**, not at the default, or an old bookmark lands somewhere sharing nothing with what it asked for. Its state deliberately **stays in the parent** rather than becoming self-contained like its Preferences siblings: the whole card is gated on `emailNotificationsAllowed`, an admin-granted flag arriving on the same GET as the values, and **the Grid item is gated with it** — a card returning null still occupies its column, so an ungranted viewer would get a hole rather than a shorter grid. The account menu lost its Profile row in the same change (`userSettingsMenuItems`, whose `tab` field is typed against the key list, so a stale entry is a compile error rather than a 404). Seven `userSettings.*` strings were orphaned by the deletion and pruned from all 15 locales; the locale files round-trip byte-identically through `JSON.stringify(obj, null, 2)`, which is what makes a scripted prune safe there. [F-112](docs/aperture-forensics.md#f-112)
- **A page's title lives in the app bar, not on the page**: at `md`+ the bar's left half was empty (hamburger and wordmark are mobile-only, jobs widget/search/avatar are pinned right) while every page spent ~80px repeating the same words below it. `components/PageHeading.tsx` publishes them through `hooks/PageHeaderProvider` (mounted by `Layout`, above both the bar and the `<Outlet/>`) and renders the familiar block only below `md`, where the bar has no room. Three traps: (1) the outer wrapper **stays in the tree** at every width — most callers sit it beside a toolbar in a `space-between` row, and removing it would leave one child, which flexbox puts at the *start*; (2) `icon` is rendered in the page block only and never published, because the header lives in state and an element prop is a new object every render, so publishing it would loop; (3) only **one** publisher per route — `AdminShell` publishes each section's registry title, *except* for the five entries flagged `ownsHeading` (Overview, Users, Jobs, Translations, Gap analysis), which were pages before they were leaves and still announce themselves. The shell expresses "don't publish" by **not mounting** its `AdminHeaderPublisher`, never by publishing an empty title: React runs child effects before parent ones, so a parent publishing `''` blanks the bar the child just filled in. A page with no `PageHeading` and no `usePageHeader` shows an empty bar; the always-full-viewport surfaces (`/assistant`, `/explore`) call `usePageHeader` directly and skip the block entirely.
- Hooks pattern: `XProvider.tsx` + `x-context.ts` + `useX.ts` triplets in `src/hooks/`.
- **New UI string**: add to `src/i18n/locales/en/translation.json` (en is source of truth), use `t('ns.key')`, then `pnpm i18n:sync` to stamp placeholders into the other 14 locales. RTL locales: ar, he — use logical CSS properties. Server error strings: wrap with `lib/withServerMessageDetail.ts`. Authoritative guide: `src/i18n/CONVENTIONS.md`.
- **Never write the product name in a UI string — write `{{appName}}`.** The instance is renamable (Settings → System → Instance name, stored as `system_settings.app_name`, served by public `GET /api/branding`), and the rename reaches all 15 locales at once because i18next fills the placeholder from `interpolation.defaultVariables`. That is set to the default in `i18n/config.ts` and overwritten by `lib/branding.ts` once the fetch lands — safe to assign late because i18next reads `defaultVariables` off the shared options object *at interpolate time*, not at init; the `changeLanguage` nudge afterwards is only there to re-render what's already on screen. `GET` is deliberately unauthenticated (login and setup render the name before any session). The few spots with no translation to interpolate into — logo `alt` text, `document.title`, the `formatJobName` fallback — call `useAppName()`/`getAppName()` instead; note the job fallback must resolve the name *per call*, since a module-level const would freeze the default before the fetch resolves. **The `<title>` can't wait for that fetch** — a tab (or a bookmark taken right then) would show the default on every cold load — so `plugins/static.ts` stamps the name into the shell on the way out: it reads `apps/web/dist/index.html` once at boot, rewrites the `<title>` element per request, and serves it from both `GET /` and the SPA fallback. That is also why `@fastify/static` is registered with `index: false` — otherwise a directory request would answer off disk and skip the rewrite. Falls back to the default if the DB read throws, so a database outage can't stop the shell booting. Left alone on purpose: `/aperture-libraries` and `/mnt/ApertureLibraries/` are real paths, and `helperApertureLibs` is a key name.
- Client caches to remember when changing API shapes: `WatchingContext` (localStorage, versioned — bump version on shape change), `ViewModeProvider` (localStorage + server prefs).
- **Breakpoints lie inside the main pane**: MUI breakpoints are *window* media queries, but `Layout.tsx` shrinks `<main>` with `marginInlineEnd: dockWidth` when the assistant is docked, and `MediaDetailModal` renders a whole page inside a dialog. A grid keyed on `md`/`lg` therefore keeps its full-desktop column count in a half-width pane (this is what shrank Related Movies to ~110px posters). Size in-pane grids off their container — `gridTemplateColumns: 'repeat(auto-fill, minmax(Npx, 1fr))'`, or MUI 6's `theme.containerQueries` — rather than subtracting `dockWidth` from a breakpoint, which still gets the dialog case wrong. **Corollary measured on the deployed app: `lg` (1200px) is often never reached** — a real pane came in at **1040px**, so a tile strip keyed `sm={4} lg={3}` rendered three-up with an orphan row and an `lg={6}` pair stacked instead of pairing. Start a wide arrangement at **`md`**; nothing in a build or a typecheck can see this.
- **Chat text is scaled, and it takes two mechanisms because one cannot reach both halves.** `CHAT_TEXT_SCALE` (1.1, `components/assistant/density.ts`) is the one number. `Typography variant="caption"` resolves to a rem value off the **root** font size, so a font-size on the thread's own box cannot touch it — `Thread` mounts a nested theme (`scaleChatTypography`, which reads each variant off the outer theme and multiplies, so it cannot drift from `theme.ts`). Markdown prose declares nothing and inherits, so the viewport carries a `fontSize` for it instead. They cannot compound: a rem variant ignores its parent, and inherited text has no variant. A hardcoded px size in the chat goes through `chatText()`. **Override the variants, never `typography.fontSize`**: `createTheme(outer, overrides)` merges its extra args *after* building, so an explicit `caption: { fontSize }` lands on top — whereas moving the coef (`typography.fontSize`, which is what scales MUI's defaults) is silently defeated, since the outer theme's already-built variant objects are merged over the recomputed ones. Measured, not reasoned: every text variant ×1.1, headings and `textTransform` untouched. The theme is mounted on `Thread`, not on the surface, because the surface also hosts `MediaDetailModalProvider` and a media page is not chat text. **`CAPTION_CHAR_PX` in `ContentCard` travels with the scale** — it converts a character budget to a line clamp, so left behind it hands every list card a line of synopsis it has no room for. Scaling is text only; avatars, posters, icons and padding are geometry and stay put.
- **Assistant surfaces**: three containers share `AssistantChatSurface` — the dock (Fab default, md+), the dialog (opt-in via the header toggle, and the fallback below md), and the `/assistant` page. Only the page renders the conversation list inline (`sidebarInline`); the floating pair use the history drawer. The header's expand button routes to `/assistant` carrying `{ conversationId }` in the route state, which `useAssistantChat(active, initialConversationId)` seeds — without it the page would resume whichever conversation was updated last.
- **The sidebar has three states, and `collapsed` is not the one to branch on**: `Layout.tsx` renders one `renderDrawer({ labels, collapsible })` for both drawers. Below `md` it's a temporary overlay, always `DRAWER_WIDTH` and labelled regardless of the rail preference (`collapsible: false` — an overlay you dismiss has nothing to collapse). At `md`+ it's a permanent rail whose paper widens to `DRAWER_WIDTH` on hover **without** the nav Box or `<main>` changing width — the paper is `position: fixed`, so the flyout floats over the page and content never moves. Branch on **`labels`** (`!collapsed || flyout`), never on `collapsed`, or the flyout renders icons. The flyout is gated on `(hover: hover) and (pointer: fine)` so a touch screen gets taps instead, opens instantly on `onFocus` for keyboard users, and is delayed both ways so brushing past doesn't trigger it. Default collapse state follows `lg` until the user toggles once; `sidebarCollapsed` is **absent** from `/api/auth/me/preferences` until then, which is the "has a preference" signal (`hasSidebarPreference`).
- **The welcome guide is route-gated and snoozed, not "first visit"**: `components/WelcomeModal.tsx` explains the recommender only, so `useWelcomeModal` opens it by itself on `/recommendations` alone (`WELCOME_ROUTE`) — the user menu's "How it works" still opens it anywhere. It is a **controlled dialog only**; `Layout.tsx` mounts exactly one, and `onClose` always receives an explicit `WelcomeDismissal` (`session` | `day` | `week` | `never`), never MUI's close event. Three storage keys back that: the pre-existing `aperture-welcome-dismissed` (still the "never" flag, so anyone who already ticked the box stays dismissed), `aperture-welcome-snooze-until` (epoch ms, localStorage) and `aperture-welcome-session-snooze` (sessionStorage, holding the user id — the closest a browser gets to "until I sign in again"). A plain close snoozes for the session; showing the guide on every refresh is what made it feel like nagging.
- **The detail page states each fact once, and the hero is where the duplicates were resolved.** `pages/media-detail` rendered the same information twice in three separate places: genre chips in `MediaHero` *and* an identically-sourced "Genre Analysis" chip row in `MovieInsights`; the star rating in the hero *and* a "Critic Ratings" panel of IMDb/TMDB/RT/Metacritic badges in `MediaInfoCard`, several screens down; and `awards_summary` in its own sidebar card. All three now render once, at the top — the rating line carries every score, the awards sit on the line under it, and director/writer moved up beside them, out of the info card (which is now cast, secondary crew, studios, languages, countries and links). Four things to keep straight. (1) The genre classification comes from `insights.genreAnalysis`, whose two lists **partition the title's genres exactly** — both insights routes filter the item's own `genres` column against the viewer's top-10 watched genres — so styling the hero chips by set membership can never leave one unaccounted for, and the panel keeps only the *counts*. It rides a later request than the media, so chips restyle when it lands and stay neutral for a title no run scored. Colour is explained by per-chip tooltips, since deleting the panel's chips also deleted the only legend. (2) `hasCriticRatings` and `personPath` live in `pages/media-detail/helpers.ts` rather than beside the components: a module exporting both a component and a plain function trips `react-refresh/only-export-components`, and lint runs at `--max-warnings 0`. (3) Every rating guard is `!= null`, never truthiness — pg returns NUMERIC as a string, so a stored `0` arrives as `'0.0'` and passes a truthy test while a genuine numeric 0 fails one; the panel this replaced had one guard of each kind. (4) `MovieInsights` now opens **expanded for both variants** (it was collapsed for a scored-but-not-picked title): a panel whose whole content is an explanation reads as empty when it is shut.
- **Item detail in a dialog**: `components/MediaDetailModal.tsx` renders the *route page* `pages/media-detail` (which now takes optional `id`/`onBack`/`onOpenMedia` instead of only reading `useParams`), hosted by `hooks/MediaDetailModalProvider`. Chat cards call `useMediaDetailModal()`; a **null** opener means "no host mounted, navigate instead" — that's how the docked assistant keeps routing the main pane while the /assistant page and the floating dialog open in place (`AssistantChatSurface` prop `openMediaInModal`). Related titles / insight evidence inside the dialog swap the target rather than route, or they'd move the page under the dialog. `MediaBackdrop`'s `mx/mt: -3` is why the dialog content keeps `p: 3`.

## When you touch X, check Y

- **New/changed core or ui export** → rebuild packages before typecheck; check `packages/core/src/index.ts` barrel (exports won't resolve until added there or to a subpath export in core `package.json`).
- **Schema change** → new `db/migrations/NNNN_*.sql`; check both migration runners; grep for the table name across core (raw SQL is duplicated in many modules).
- **Enrichment fields** → re-embedding may be required (canonical text), similarity `reasons.ts`, gap analysis, top picks all read enriched columns.
- **Series/watching changes** → `watching/tmdbTotals.ts` caches TMDB totals on `series` rows (`tmdb_total_episodes/seasons`, `tmdb_status`); Watching page, upcoming episodes, and MyWatchHistory grids all read them.
- **Media-server calls** → implement in BOTH `media/emby/` and `media/jellyfin/`; interface is `media/MediaServerProvider.ts`.
- **Anything reading media-server `Tags`** → pass them through `withoutManagedTags` (`media/managedTags.ts`); an `aperture:` tag that reaches `movies.tags`/`series.tags` is embedded as a theme.
- **Writing `users.is_enabled`** → go through `apps/api/src/lib/accountEnabled.ts`; never derive it from the request body.
- **Gating a route on a per-user feature flag** → add a capability to `apps/api/src/lib/permissions.ts` and use `requireCapability`/`can`; never `SELECT <flag> FROM users` in a handler.
- **Adding a permission flag to `SessionUser`** → select it in `USER_COLUMNS` (`plugins/auth.ts`) and map it in `toSessionUser`, and add it to `API_KEY_USER_COLUMNS` in `packages/core/src/apiKeys.ts`; a missed one reads as "not granted" only after signing in.
- **Adding a route** → give it a `preHandler`, or add it to `routeGuards.test.ts`’s allowlist with a reason; the test fails either way until you choose.
- **Deciding whether a request writes** (a read-only guard of any kind) → `apps/api/src/lib/requestWrites.ts`; never re-derive it from the method.
- **Writing a permission column** → record it (`auditUserPermissions`, with `readUserPermissions` for the before snapshot); `permissionAuditCallSites.test.ts` fails until you do, or until the file is allowlisted with a reason.
- **Gating anything in the web bundle on a permission** → `useCapability(...)` off `/api/auth/check`; never re-derive it from `user.*` flags.
- **Movie-side recommender/sync fix** → check the series mirror (and vice versa).
- **New/moved admin section** → add an entry to `pages/admin/nav/registry.ts` **and** an element to `elements.tsx`; run `pnpm --filter @aperture/web test`, which fails until the section has a home.
- **Renaming/removing an API route** → grep `apps/web/src` for the literal `/api/...` string (no typed client to catch it).
- **Integration client changes** (tmdb/omdb/trakt/mdblist/seerr/justwatch) → they log to `errors/` (`api_errors`) and often have DB caches with TTLs; check retry gating (`shouldAutoRetry`).
- **Job behavior** → schedule comes from DB `job_config`, not `definitions.ts`; progress API is in core.

## Workflow notes

- Work happens directly on `dev` (no feature branches). `main` is a stale upstream mirror; `.github/workflows/sync-dev.yml` force-resets `dev` to `main` on pushes to `main`. Pushing to `origin/dev` triggers the Docker build — don't push without being asked.
- **Never open the live site right after a push.** A push only starts the image build; the running instance changes when the operator manually pulls it. So the browser will be showing the *old* build, and "verified" would be a lie. Browser checks (`claude-in-chrome` against the deployed instance — the local dev server can't be started here) happen only when the operator says the new image is deployed. A push is the end of the turn, not the cue for a screenshot.
- Docker: `docker/Dockerfile` (4-stage; copies built dists + `db/`); compose variants per platform (dev/prod/external-db/windows/unraid/synology/qnap). Runtime data in `data/` (gitignored except `.gitkeep`s); operator i18n overrides mount at `/config/i18n`.
- Docs for humans live in `docs/` (admin guides, feature docs, screenshots).
