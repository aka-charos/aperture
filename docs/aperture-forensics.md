# Aperture — Forensics

Evidence behind the trap rules in `CLAUDE.md`. Each `F-NNN` here is the full record for the
matching `[F-NNN]` pointer in CLAUDE.md's "Naming traps" section: the measured numbers, the
failure as it actually presented, the alternatives that were tried and rejected, and the
reasoning that produced the rule.

**When to read one.** The rule in CLAUDE.md is enough to stay out of the trap. Open the
matching section here when you are about to change, revert, or argue with one of those rules —
that is what the evidence is for. Reading it is never required to write correct code.

**When to write one.** A new trap entry in CLAUDE.md gets its rule inline and its evidence
here, under the next free number.


## F-001

**`discover/` vs `discovery/`**

**`discover/` vs `discovery/`** (both in api routes and mirrored in web/core): `discover` = browse people/studios + TMDB-external detail (`/api/discover/*`); `discovery` = missing-content suggestion engine feeding Seerr requests (`/api/discovery/*`). There is also `assistant/discovery/` (web-grounded chat candidates) — unrelated. Its web grounding is **multi-source** via `assistant/discovery/sources/` (a `WebSearchSource` registry): Google grounding (Gemini `google_search`) + Tavily (core `lib/tavily.ts`, config in `system_settings.tavily_integration`, `/api/settings/tavily`). Sources compose (combined into one structuring pass) and fall back for one another; Tavily errors log under the `tavily` provider in `api_errors`.

## F-002

**A new AI role is a list, not a union — `AI_FUNCTIONS` (core `lib/ai-capabilities/types.ts`) is the one copy, and `AIFunction` is derived from it.**

**A new AI role is a list, not a union — `AI_FUNCTIONS` (core `lib/ai-capabilities/types.ts`) is the one copy, and `AIFunction` is derived from it.** The roles are also a JSON-Schema `enum` on **ten** Fastify routes (`settings/schemas.ts` ×3, `setup/schemas.ts` ×7), and TypeScript cannot check a hand-written copy of a union against the union. `titleAnalysis` shipped present in the type, in every handler and on the settings card while missing from all ten, so `GET /api/settings/ai/providers|models?function=titleAnalysis` answered **400** — and the card reads a 400 as `data.models || []`, which renders as **"No models available", for every provider**, with the "+ Add custom model" escape hatch rejected by the same rule. The role looked fully configurable and could not be configured at all. Three more copies were runtime `if (!['embeddings', …].includes(fn))` guards (two in `setup/handlers/ai.ts`, one in `settings/handlers/aiConfig.ts`), now `isAIFunction`. Two further places *omitted* a role rather than rejecting it, which is the quieter failure: `getOpenRouterRoles` (`routes/inference/`), where `configured: roles.length > 0` hides the entire measured-spend dashboard — so a library-wide analysis job billed to OpenRouter would have reported nothing — and the pricing summary behind the Cost Estimator. Both iterate `AI_FUNCTIONS` now, and `aiFunctionSchemas.test.ts` walks both schema modules structurally and fails on any role enum that is not the shared list. **The sixth copy was in SQL, where no build could ever see it**: migration `0089` put `CHECK (function_type IN ('embeddings','chat','textGeneration','exploration'))` on `custom_ai_models` and nothing revisited it, so the database rejected *both* later roles from the day they existed. `webSearch` never surfaced it because Google is not a custom-model provider and no request could reach the insert; `titleAnalysis` broke the only path that role has, since it points at a local or OpenRouter model and those catalogs ship zero built-ins — the dialog validated the model, reported "Model validated successfully!", then took a bare **500** from the constraint with the real cause visible only in the container log. `0144` **drops** it rather than extending it, because a sixth copy would drift exactly as the first five did; the guards that replace it are both derived (the route schema enum, plus `isAIFunction` inside `addCustomModel`), and `aiFunctionSchemas.test.ts` now also fails on any migration after `0144` whose `CHECK` names two or more roles. The `custom_ai_models_provider_check` constraint is deliberately left in place: same shape, but it guards a set that changes when an integration is written rather than when a role is named, and it has been maintained (`0090`, `0092`). Two things are deliberately **not** shared. Custom models are keyed `(provider, function_type)`, so an LM Studio or OpenRouter model added under Text Generation does not appear under Title Analysis — the three catalogs shipping zero built-ins (`openai-compatible`, `openrouter`, `huggingface`) need one added per role, which is the normal flow and not the bug above. And `getModel` read `textGenerationModels` only while `getModelsForFunction` fell back to `chatModels` — only Ollama publishes the former, so any cloud model picked for a writing role looked *unknown* when looked up again, losing its display name and its catalog price; both go through `modelPool` now.

## F-003

**The Web Search role is Google-only, and the settings card knows it**

**The Web Search role is Google-only, and the settings card knows it**: `getProvidersForFunction('webSearch')` returns just `google`, and `AIFunctionCard` renders a **label instead of a dropdown whenever a role offers exactly one provider** (it also auto-corrects a selection that isn't on the list, which is what stopped an unconfigured card sitting on the OpenAI default). The role holds **two** keys — `ProviderConfig.fallbackApiKey` alongside `apiKey` — because Gemini's free tier is what usually breaks grounding. Anything spending that quota must go through **`withWebSearchModel`** (core `lib/ai-provider.ts`): it walks `getWebSearchAttempts()` (primary, then fallback, keys parked by a recent 429 last), moves to the next key **only** on a quota error, and writes every attempt to `web_search_usage`. Free-tier limits, `429 RESOURCE_EXHAUSTED` classification (per-minute vs per-day) and the in-memory cooldowns live in `lib/webSearchQuota.ts`; the DB counters and the `/api/settings/ai/web-search/usage` summary in `lib/webSearchUsage.ts` — day windows are anchored to **midnight US/Pacific** and filtered by model, because that is how Google's RPD works. Call sites: `assistant/discovery/sources/googleGrounding.ts` and core `channels/webExpand.ts` use the wrapper; `assistant/discovery/webCandidates.ts` can't (its strict→lenient→text cascade would fight the key loop) so it meters by hand via `recordWebSearchCall` — **a new consumer that skips both will silently undercount the meter**. The fallback key is not in `ai_provider_credentials` (that store is per provider, shared across roles), so the PATCH handler treats an omitted `fallbackApiKey` as "leave it alone" and only an empty string clears it.

## F-004

**Two different "cost" surfaces, and only one of them is real**

**Two different "cost" surfaces, and only one of them is real**: `CostEstimatorSection` *projects* spend (published per-million prices × assumed call volumes); `InferenceDashboardSection` *measures* it. The measured one is OpenRouter-only because OpenRouter is the only provider that returns spent credits on every response, and it hides itself when no role uses OpenRouter. Capture happens in the **provider's `fetch`**, not at call sites: `createProviderInstance(config, role)` hands OpenRouter a `createOpenRouterUsageFetch(role)` (core `lib/openrouter-usage.ts`) that tees the response, reads `usage` out of the JSON body or the last SSE chunk, and writes `llm_inference_calls`. So **a new generateText/streamText call site needs no instrumentation at all** — but note the `role` is baked in at provider-creation time and is therefore part of the provider cache key. Everything else (`feature`, `sessionId`, `userId`) rides an AsyncLocalStorage (`lib/inferenceContext.ts`) established in exactly three places: `runJob` in `jobs/executor.ts` (tags `job:<name>`, which is what attributes nearly all background inference), the chat handler (`assistant.chat` + conversation id — it wraps `createUIMessageStream`, which invokes `execute` **synchronously**, so the scope covers the whole turn), and `testProviderConnection`. Unwrapped work still records, just as `unattributed`. Cost is nullable end to end and sums skip nulls, so the dashboard reports `pricedCalls` separately — never treat a missing cost as zero.

## F-005

**The estimator read $0.00 for every OpenRouter setup**

**The estimator read $0.00 for every OpenRouter setup**: `PROVIDER_MAP` in `lib/pricing-cache.ts` has no `openrouter` entry *and* `ai-capabilities/data/openrouter.json` ships zero models (they're all user-entered), so `findModelPricing` returned null and the fallback `model?.inputCostPerMillion ?? 0` produced a confident zero. Fixed by resolving OpenRouter through its own catalog (`getOpenRouterModelInfo`, exact id only — `:free`/`:extended` variants are priced differently). `FunctionPricing.pricingKnown` now distinguishes "free" from "nobody could price this"; anything rendering money from it must show the unknown case as unknown, not as $0.

## F-006

**The assistant consumes the recommender's output, not its logic.**

**The assistant consumes the recommender's output, not its logic.** Of its twelve tools exactly one touches the pipeline — `getMyRecommendations` (`assistant/tools/recommendations.ts`), which reads `is_selected = true` off the newest completed run, so twin and interest fillers do appear in chat. Everything else is a different engine: `semanticSearch`/`findSimilarContent` are bare pgvector kNN over the same embedding tables with **no** novelty term, taste-profile boosts, diversity selection or reserved slots, and the discovery tools are web-grounded. So a niche request answered in chat is served by exactly the mechanism the taste-twin feature exists to compensate for. Each recommendation item now carries `source` (`ranked` | `twin` | `interest`), **derived** from `score_breakdown` by `pickSource` rather than passed through it, because that object also holds `twinMatch.donorId` and the model must never receive an identity it could name; the enum plus a rule in the tool description is the whole fact it needs. A twin pick also carries `sharedTitles` — the same overlap the insights panel renders, resolved through the same `lib/twinShared.ts` the insights routes use. Those are titles from the **reader's own history**, so naming them leaks nothing about the donor, and they are what lets chat explain a borrowed pick concretely rather than gesturing at "someone with similar taste". Resolution is **batched per tool call** (`resolveTwinSharedTitles`), not per item — the tool returns up to 50 picks and a per-item lookup would put 50 round trips inside one chat turn. Unknown or absent markers read as `ranked`, which is what makes pre-slot runs behave. Nothing calls `ContentItemSchema.parse()`, so extra fields survive to the client — `tool-ui/types.ts` mirrors the schema by hand and has to be updated alongside it.

## F-007

**Chat's personalized search reuses the pipeline's output instead of re-implementing it.**

**Chat's personalized search reuses the pipeline's output instead of re-implementing it.** `searchMyRecommendations` (`assistant/tools/recommendations.ts`) is the answer to "chat is bad at recommending": ANN over the embedding table for the request, joined to `recommendation_candidates` for the newest **completed** run, then re-ranked by `blendQueryAndTaste`. That join is doing three jobs at once — it restricts to titles the recommender scored *for this user*, and because the pool is by construction what they have **not** seen, it applies the pipeline's watched exclusion for free. Three things are load-bearing. (1) **Both terms are min-max normalised over the fetched pool before blending, never used raw** — cosine here sits in the same narrow high band that made centroid similarity useless for twins, so a raw weighted sum would let `final_score`'s wider spread decide everything; `tasteBlend.test.ts` pins that a compressed term still moves the ranking, and that a flat term contributes 0 rather than NaN. (2) `QUERY_WEIGHT` is 0.6 — the request leads, taste breaks ties, because a ranking that puts general taste first answers a question the user didn't ask. (3) `ANN_POOL_SIZE` (400) is fetched before the join, since watched titles drop out of it — and it is paired with `SET LOCAL hnsw.ef_search = 500` inside a transaction, because **pgvector's default `ef_search` is 40 and nothing else in this repo raises it**: an HNSW scan never returns more rows than `ef_search`, so a bare `LIMIT 400` either comes back short or makes the planner drop the index and sequentially scan every embedding. Any new query asking for more than 40 neighbours needs the same treatment, and it must be `SET LOCAL` so it cannot leak onto the pooled connection and change the other vector queries, which are tuned for the default. A new tool also needs its `TOOL_PHASES` entry (`helpers/status.ts`) and a line in `prompts/rules/tools.ts`. Two things this got wrong on the first pass, both user-visible within a day. (1) It passed `recommendation_candidates.rank` as the card's `rank`, and `ContentCard` renders any `rank` as a **RankBadge on the poster** — but that column is the position among *everything the run scored*, so the first two cards read "2012" and "449" as though they were match positions. Search results carry no rank now (`semanticSearch` omits it too); only `getMyRecommendations` sets one, from `selected_rank`. (2) The tool shipped with **no `reason`**, and the prompt rule made it the default for "find me something" — which diverted open requests off the web-discovery path, the only thing that writes per-card reasons, so cards lost their "why". It now calls `enrichCardReasons` like discovery does, and the rule was walked back: **discovery stays primary for open recommendation requests**, and this is the library-scoped answer plus discovery's in-library fallback (replacing `getTopRated`, which sorts by raw rating and knows nothing about the user). `DISCOVERY_PROMPT` now makes the follow-up call **mandatory below 8 resolved cards**, not merely permitted: the old rule was a `MAY` plus a fallback that only fired at *zero*, so a French-noir turn resolving **5 of 19** web candidates satisfied neither branch and the model — having already produced an answer — declined the option. The two tools fail in opposite directions, which is the whole point: `findCandidatesInLibrary` is capped by *the intersection of what the web names and what this library holds*, while `searchMyRecommendations` searches the library itself, so a thin resolve is precisely when recall is missing. A threshold rather than "always" because a healthy turn (9 of 20) would otherwise pad a good answer with weaker picks and spend another embedding + ANN + enrichment call.

## F-008

**The taste brief personalises SELECTION, never RETRIEVAL — and an instruction saying so was not enough.**

**The taste brief personalises SELECTION, never RETRIEVAL — and an instruction saying so was not enough.** `prompts/context/user.ts` puts both taste synopses and the last ten watches in the chat prompt, but the discovery pipeline's model calls are *separate* and see only the user's message — so "find me something arthouse" searched the web for exactly that, with no idea who was asking. `discovery/tasteBrief.ts` builds a short profile that `discoveryResolve` fetches and hands to `gatherWebCandidates`, which applies it in the **structuring pass** (`webCandidates.ts` `viewerBlock`, prefixed to `structurePrompt`). That call has no search tool: the titles it may return are exactly the ones the sources already retrieved, so a profile there can reorder and tie-break but cannot bend what was looked up. Four rules. (1) **The profile must never reach a search call.** It did, in the first version — two channels, task instructions plus profile in `system`, the question alone as the user message, and an explicit *"do NOT search for the titles in it"* rule. Measured on the live instance, the request "suggest me french film noir movies based on my history" produced **twelve** search queries, every one of them `French film noir` + a descriptor of the user's favourite Lynch film (`surreal`, `dreamlike`, `fragmented narrative`, `puzzles`, `non-linear`, `ambiguous endings`), one naming *Inland Empire* outright — against 6 grounding sources, where a clean "series like Twin Peaks" turn on the same build got 9 from 4 queries. A system message is still context and `google_search` draws on all of it; worse, the user's own *"based on my history"* reads as permission, so the rule loses exactly when personalisation is wanted. `WebSearchSource.gather` therefore takes **only the query** and `WebSearchContext` is deleted — the boundary is the type signature, not a sentence in a prompt. (2) The precedence line stays in the new location: unstated, personalisation quietly overrides the question and "a good horror film" starts returning arthouse dramas. It may order candidates, never add, drop or re-justify them. (3) **Tavily deliberately ignores it** — it is a search API, not a model, and pasting profile prose into a keyword query degrades results; a new source must make the same call for itself. What Tavily *does* get is a **reasoning cue appended to the request**, because its `answer` is LLM-written from the retrieved results and there is no separate answer prompt — one string serves both retrieval and synthesis. That matters because the structuring pass omits any title arriving without a real "why", and bare snippets are exactly what a plain query returns: **Tavily can supply half the grounding text and none of the candidates**, and every log line looks identical either way (nothing tracks per-candidate provenance — to test, disable the Web Search role and see whether Tavily alone still yields a healthy `candidateCount`). Hence also `include_answer: 'advanced'` rather than a bare `true` (credits are charged on `search_depth`, so the longer answer is free), and the answer gets **its own char budget** — `maxContentChars` is a per-*snippet* cap and applying it to the answer meant lowering it to trim snippet bloat destroyed the only reasoned part of the response, removing it entirely at the 100-char floor. Fails soft to null, which restores the previous un-personalized behaviour. (4) The titles it carries are **signature** ones (favorite → play count → recency, mirroring `recommender/movies/taste.ts`, gated on `WATCH_HISTORY_TASTE_SQL`; both inlined because neither is exported from a core barrel) and it **groups by title**, because a `watch_history` row is an *episode* — the ten most recent rows on the live instance held `Silo` four times, so the old `last_played_at DESC` list could name one show six times. **Establishing the brief's influence took two attempts, and the first inference was wrong**: a "like Meshes of the Afternoon" request issued twelve grounding queries, six of them `«Title» + seed + "comparison"`, matching the six-entry list in count — but five of those titles appear in *no* watch history on the instance, so the model was working from its own knowledge, and the `(1932 film)` suffix was Wikipedia's disambiguator rather than this file's `Title (Year)`. The French-noir turn above is the real proof, because *Inland Empire* appears nowhere in the request and the call carried no conversation history. `personalized: true` in the `web-candidates` log now means only that a brief was **built and will be applied at structuring** — it says nothing about retrieval, which no longer receives it. Note also that a longer query list costs **no extra quota**: Gemini's free tier limits requests per day, so twelve queries inside one grounded call meter identically to six — a bad title list costs relevance and context, never spend. **Open, and measured: the empty-text retry is not metered.** `recordWebSearchCall` fires once per *key attempt* in `withWebSearchModel` ([ai-provider.ts:623](packages/core/src/lib/ai-provider.ts:623)), but `googleGrounding`'s `PASS1_MAX_ATTEMPTS` loop sits **inside** that attempt, so a grounding call that returns empty and retries makes two requests Google counts and writes one row to `web_search_usage`. Seen live: "suggest me french noir movies **based on my watched history**" returned zero queries and zero text on attempt 1 — a soft refusal at the deictic phrase, absorbed silently — then produced twelve queries on attempt 2. Fixing it is not just a counter: the retried request succeeded at HTTP level and returned nothing, which is neither `ok` nor `rate_limited` nor `error`, so it likely wants a new status rather than being folded into an existing one.

## F-009

**The intent router decides whether the web search exists at all, and it**

**The intent router decides whether the web search exists at all, and its axis is the *answer*, not the wording.** `helpers/routeIntent.ts` classifies each turn `discovery` or `library`, and `findCandidatesInLibrary` — the only tool that searches the web or writes card `reason`s — is added *only* on discovery turns (`handlers/chat.ts`). So a misroute is not a degraded answer, it is a different engine, and nothing downstream can recover it. The taxonomy originally read *any* reference to the user's collection as a library question, which sent **"suggest film noir movies based on my history"** to `library`: the user asked for personalized recommendations and got thirty films they had already watched. The rule now is that a request for titles to watch is `discovery` **even when personalized**, because the discovery path *is* the personalized one — `discovery/tasteBrief.ts` feeds the profile into the grounding call, so "based on my history" says how to aim the search, not what kind of answer to give; `library` means the answer is *facts about their collection* (history listing, counts, ratings, do-I-own-X, what to resume). Four things are load-bearing. (1) There are **two layers, and only one is appealable**: `prefilterIntent` (pure, exported, pinned by `routeIntent.test.ts`) decides with no LLM at all, so a bad match there is final — which is why `RECOMMENDATION_HINTS` is checked first and wins outright, and why `LIBRARY_HINTS` no longer matches bare taste statements (`i like|i love|i watch`), which used to let "I like noir, what's good" hard-route away from the web. (2) **Ambiguity resolves toward discovery** because a discovery turn suppresses only three list builders (`DISCOVERY_SUPPRESSED_TOOLS`) and keeps history/ratings/stats, while a library turn has no web tool — discovery is nearly the superset. (3) The **error** path still falls back to `library`, deliberately: a routing failure is not a routing doubt, and `DISCOVERY_PROMPT` orders a web search that a counting question doesn't want. (4) A library-routed model reaching for `getWatchHistory` produces watched titles **even with `excludeWatched` on**, since it is in `EXEMPT_TOOLS` — and because every tool returning `items` renders as cards, a lookup the model intended as context becomes the visible answer. That last one is a design gap, not a bug: there is no way to call a tool privately.

## F-010

**The chat can query watch history by content, not just by recency — `getWatchHistory` alone could not, and that produced confident false negatives.**

**The chat can query watch history by content, not just by recency — `getWatchHistory` alone could not, and that produced confident false negatives.** Its entire input schema is `type` + `limit` (`tools/history.ts`), ordered `last_played_at DESC`: no genre, era, country, director or concept, and `limit` is unclamped, so "more rows" was never the fix. Meanwhile `searchContent`/`semanticSearch` search the **library** and touched `watch_history` only to *exclude*, and `ContentItem` had no watched marker — so "list me the french film noir movies I watched" asked for an intersection the model could compute from nothing but a 50-row recency sample, and it answered *"you haven't watched any"*, three times, twice with the unwatched filter off. Three pieces fix it, all small because the machinery existed. (1) **`watchStatus: 'all' | 'watched' | 'unwatched'`** on both search tools (`watchStatusCondition` in `tools/search.ts`) — the `NOT IN` half was already written in three places; this adds the `IN` half. On the semantic path it must run inside a transaction with `SET LOCAL hnsw.ef_search = 500`: pgvector post-filters a WHERE predicate and an HNSW scan never yields more rows than `ef_search` (default 40), so a filtered `LIMIT 20` comes back nearly empty and the filter looks broken. (2) **`ContentItem.watched`**, stamped by `annotateWatchedItems` (one round trip per result page, `helpers/unwatched.ts`). It is **absent when not looked up**, which is not the same as false — the card branches on `=== true`, and the schema description tells the model the same. (3) `withUnwatchedFilter` skips a call whose `input.watchStatus === 'watched'`: same reasoning as `EXEMPT_TOOLS` but decided **per call**, since one tool now serves both kinds of request. Only `'watched'` overrides — `'all'` is the model's default, not a user intent. Also added a `country` filter (see the next entry — the `language` filter added alongside it was a mistake and is gone), and fixed `director`/`tag`, which used `$n ILIKE ANY(directors)` — backwards, since in `a ILIKE b` the *right* side is the pattern, so it asked whether the literal string `%Nolan%` matches the pattern `Christopher Nolan` and matched nothing. They now use `directors::text ILIKE $n`, the form `actor`/`studio` always used.

## F-011

**"French film noir" was inexpressible, and the tool surface hid that behind three separate silent zeroes.**

**"French film noir" was inexpressible, and the tool surface hid that behind three separate silent zeroes.** Asked to list them, the chat ran ten `searchContent` calls, every one returning 0 rows, then exhausted `stopWhen: stepCountIs(5)` and ended the turn with **no prose at all** — the user saw five "No results found" strips and a semantic carousel of Kurosawa and Turkish prison drama. Three compounding causes, none visible from the logs (which record tool names and result counts but not arguments). (1) **`languages` is populated for 88 of 12,584 movies — 0.7%.** It is written in exactly two places, both in `enrichment/index.ts`, both from OMDb's `Language` field; no media-server sync path touches it. `production_countries` by contrast is 99.4% populated (`movies/sync.ts` writes it from Emby's `ProductionLocations`) and holds **1,688** French films. The `language` filter shipped with the description *"use for 'French films' etc."*, which routed the one phrasing that mattered at the one column that is empty — so the filter is now **deleted**, not documented around: a parameter that works on an OMDb-enriched instance and silently returns nothing everywhere else is worse than an absent one. (2) **`query` matches literal text in `title`/`overview`**, but the prompt rule said *"French film noir" → country: "France" + query or genre for the noir part*. Almost no noir has "noir" written in its title or synopsis and there is no Film Noir genre, so both branches of that instruction returned zero. The rule now routes style→`semanticSearch(concept)` and fact→filters, and `query`'s own description says outright that it is not a concept search. (3) **`semanticSearch` had no `country`**, so the only tool that understands "film noir" as a *style* could not be scoped to France — which is why it answered with *Stray Dog*. It takes `country` now, through the same `hasPostFilter` → `SET LOCAL hnsw.ef_search = 500` path the watch-status filter uses, since a country predicate post-filters the ANN scan identically. The remaining trap is the demonym: `production_countries` stores *"France"* while a user says *"French"*, and `'{France,Italy}' ILIKE '%French%'` is **false** — a prompt can ask the model to say "France" but a rule that must win against the user's own wording every turn is not a fix, so `helpers/countryMatch.ts` maps ~120 nationalities to the stored name. Its values are deliberately **substrings rather than exact names** so one entry covers the variants: `United States` matches "United States of America", `Germany` matches "West Germany", `Czech` matches Czech Republic / Czechia / Czechoslovakia. Unknown input passes through unchanged. The reason the turn produced *nothing at all* rather than a bad answer was separate, and is the next entry.

## F-012

**A step is a model round trip, and the last one was always wasted.**

**A step is a model round trip, and the last one was always wasted.** `stopWhen: stepCountIs(MAX_STEPS)` in `handlers/chat.ts` is consulted **only after a step that called tools**, so the final step's results are fetched, streamed to the client as cards, and then never sent back to the model — the loop ends with nobody left to read them. A turn that spent every step searching therefore ended with **no prose at all** (five "No results found" strips and silence), because tool results reach the UI through `renderToolResult` independently of the model composing anything from them. Three consequences. (1) The effective tool budget was always `MAX_STEPS - 1`, since results from the last step cannot influence output; `prepareStep: ({ stepNumber }) => stepNumber === MAX_STEPS - 1 ? { toolChoice: 'none' } : undefined` therefore costs **no retrieval** — it repurposes a step that was already dead into the one that writes the answer. `stepNumber` is 0-indexed (`stepNumber: steps.length` in the SDK). (2) Raising `MAX_STEPS` does **not** cost tokens on healthy turns — a two-step turn pays for two steps whatever the ceiling — but each step resends the entire system prompt *plus all accumulated tool results*, so late steps are much more expensive than early ones and the cost grows superlinearly within a turn. Raising it alone also fixes nothing: a model looping on failing searches burns 10 as easily as 5. The guard is what makes a higher ceiling safe, because a turn can no longer end without prose. (3) Hitting the guard logs `warn` "Step budget exhausted" — reaching it means every search was spent, which is a signal about the *tools*, not the model, and it was previously invisible.

## F-013

**A carousel heading can assert a claim the retrieval cannot support.**

**A carousel heading can assert a claim the retrieval cannot support.** `semanticSearch` is bare kNN with no distance floor — it returns its k nearest however far away they are — and it titled them *Movies matching "{{concept}}"* over *Found {{count}} titles matching your search*. For a query with no good match in the library that is the UI vouching for results it has no basis to vouch for. The strings now say *Movies closest to "…"* / *The {{count}} nearest titles in your library*: same rows, a claim that is true. A **distance cutoff was deliberately not added** — this repo has twice measured a cosine band far too narrow to threshold blind (twin centroids spanning 0.898–0.993, `avgNovelty` pinned in [0.8, 1.0]), so the query→item distribution has to be measured before any number is picked. Note also the separate case the headings cannot fix: on a broad tool call the cards are *honest but are not the answer* — a request for French drama answered by `searchContent(genre: "Drama", watchStatus: "watched")` renders 50 dramas of every nationality under prose naming nine French ones. That is what `format: 'brief'` plus an explicit display call would solve, and it costs a step the budget above does not have.

## F-014

**The enrichment job could not tell "already done" from "never asked", and that froze OMDb out of an entire library.**

**The enrichment job could not tell "already done" from "never asked", and that froze OMDb out of an entire library.** `enrichment_version` (migration `0068`) records which *schema* version was current when a row was touched — **not which sources answered**. `enrichMovie`/`enrichSeries` stamp it and `enriched_at` on every pass, whether OMDb ran, was disabled, held no key, was skipped for a missing `imdb_id`, errored, or found nothing; the selection then reads `WHERE enriched_at IS NULL OR COALESCE(enrichment_version, 0) < $current` and excludes that row **forever**. So a library enriched before OMDb was configured is stamped complete, and adding the key afterwards does nothing at all. Measured live: `movies.languages` populated for **88 of 12,584** rows (0.7%), with `rt_critic_score`, `metacritic_score` and `awards_summary` equally bare — while `getEnrichmentVersionStatus` reported **zero outdated**, because by its own definition they were. Four things are load-bearing. (1) The fix is `omdb_enriched_at` (migration `0136`), stamped only when the call was **attempted and did not throw**. "Not found" counts as attempted — OMDb genuinely has no entry for some titles and retrying them every pass would never end — while an error does not, so a transient outage retries next run. That distinction needs the discriminated `OmdbOutcome`, since `data: null` alone cannot express it. (2) The predicate is now **one function**, `enrichment/pending.ts`'s `needsEnrichmentSql`, split out of `index.ts` so it is testable without a database (same reason as `watchedExclusion.ts`). It previously lived in four places — two counts and two selections — which agreed only by being wrong identically, and that is exactly why nothing looked broken: the progress counter said nothing was pending and the selection returned nothing, in perfect agreement. Keep them on the shared builder or a count that drifts from the selection makes a run appear to stall or finish early. (3) The OMDb clause is **conditional on OMDb being usable**, and the guard matters in the other direction too: with OMDb off nothing could ever satisfy it, so every row would stay permanently pending and each pass would re-run TMDb across the whole library without the job ever reaching "nothing to do". (4) `0136`'s backfill reads evidence from `awards_summary`/`languages` **only** — `rt_critic_score`/`metacritic_score` are written by `mdblist/enrichment.ts` as well, and `production_countries` by `movies/sync.ts` on every sync, so none of those prove OMDb ran. Two consequences worth remembering: `clearEnrichmentData` clears the new column too but is **still called by nothing** (no route, no job, no button — the only enrichment "clear" in the API is `clear-interrupted`, which clears a stuck *run record*), and the cost of a backfill is set by the OMDb tier, since `omdb/client.ts` throttles to 10 req/sec against a 1,000/day free cap versus 40 on patron — the same job is a two-week trickle or a single pass depending on the key.

## F-015

**"Attempted and did not throw" was the wrong boundary, because the OMDb client never threw.**

**"Attempted and did not throw" was the wrong boundary, because the OMDb client never threw.** The first thing the fixed job did on the live instance was fail every request with `HTTP 401` and log every title as `OMDb: not found` — stamping the whole library complete again, one migration after `0136` unstamped it. `omdbRequest` returned `null` for a non-OK response *exactly* as it does for a genuine "Movie not found!", so `OmdbOutcome` read a transport failure as an answer. Five things came out of fixing it, and the last is the one that bites. (1) **A null return now means "OMDb has no entry" and nothing else**; every other outcome throws `OmdbRequestError`. The classification is pure and pinned in `omdb/failures.ts` — same split-for-testability as `pending.ts`. (2) **OMDb answers 401 for both an invalid key and an exhausted daily quota**, and only the JSON body separates them; the client read `response.status` and returned before touching it, so the logs could say nothing but "HTTP 401" for two faults with opposite fixes. `errors/omdb.ts` had *already* recorded this in a comment and defined both body patterns — the client just never called `parseApiError`, which is also why OMDb was the one integration whose outages never reached the API Errors page. `testOMDbConnection` had the same hole and returned `API returned status 401`, from the one button whose entire job is to say what is wrong. (3) OMDb also returns auth and quota errors as **HTTP 200 with `Response: "False"`**, so the old "False means not found" branch retired rows on the strength of a reply saying the key was invalid; `isNotFoundBody` is a closed list and anything unrecognised is a failure. (4) A bad key is a fact about the *account*, so the client **latches** it for ten minutes rather than making one doomed round trip per library item (a full pass of `OMDB ✗ … (HTTP 401)` is what this looked like). It expires because the fix is often activating the existing key at omdbapi.com, which changes nothing the code can observe. Keys are `.trim()`ed on write and read — a pasted newline reaches OMDb as a different string while looking perfect in the settings field. (5) **`enrichMetadata`'s `while (true)` loops only exit when the pending selection empties, so not stamping a failed row spins them forever** — and over-stamping was what had been holding that together. Both loops now attempt each row at most once per run (`attemptedMovieIds`/`attemptedSeriesIds`); the rows stay pending for the *next* run, which is the entire point of not stamping them. Any future "leave it pending" outcome needs the same guard. Migration `0137` clears stamps carrying no OMDb evidence, the inverse of `0136`'s test and deliberately over-broad: it also clears genuine not-founds, because an extra request is cheap and a wrongly retired row is permanent.

## F-016

**A library row has three names, and the assistant used to know only one.**

**A library row has three names, and the assistant used to know only one.** `movies`/`series` carry `title`, `original_title` and `sort_title`; on the live instance **12,563 of 12,584 films have an original title and 3,739 (30%) differ from the title** — *Elevator To The Gallows* is stored beside *Ascenseur Pour L'échafaud*. The ingest was never the problem: `MOVIE_LIST_FIELDS`/`SERIES_LIST_FIELDS` request `OriginalTitle` and `SortName`, both Emby and Jellyfin mappers read them, `movies/sync.ts` writes them on insert **and** both update paths, and `0060` already trigram-indexes `original_title`. Every *reader* compared `title` alone. Three distinct failures came out of that, and the fuzzy one was the least damaging: (1) `resolveCandidates` Tier 3 searched `title` only; (2) **`idMatchValid` threw away correct ID hits** — an exact `imdb_id` match was rejected because the row's English title had no overlap with the candidate's French one, so tiers 1 and 2 were defeated too; (3) `normalizeTitle` stripped `[^a-z0-9]`, which **deletes** accented letters rather than folding them, so `"L'échafaud"` → `l chafaud` while `"L'echafaud"` → `l echafaud` — the same film failing to match itself. All title comparison now goes through `helpers/titleMatch.ts` (NFD + combining-mark strip, plus a ligature map for `æ ø ß ł đ þ` which have no decomposition), which also replaced **three** identical copies of the normalizer in `resolveCandidates`, `webCandidates` and `discoveryResolve` — they must agree, or a title survives dedupe and then fails to match. The SQL half is `anyTitleMatchesSql`/`titleMatchRankSql`: all three columns, wrapped in `unaccent()` (migration `0134`; safe because `0060` already creates `pg_trgm`, so contrib is present) so an unaccented source string still finds the accented row. Localized title outranks original outranks sort — the name on the poster must win. Applied to all five lookups: Tier 3, `getContentDetails` ×2, the `findSimilarItems` seed ×2, and `searchContent`'s text filter. Two things to keep in mind: `unaccent()` is STABLE, so it **costs the trigram index** and falls back to a seq scan (milliseconds at 12.5k rows, inside a tool call taking tens of seconds — `0134` records the IMMUTABLE-wrapper recipe if the library grows), and a non-Latin title normalizes to **empty**, which `titlesOverlap` deliberately treats as *no match* while `idMatchValid` treats as *trust the id* — the two callers want opposite defaults, so the helper stays out of it.

## F-017

**A tool call can now be private: `format: 'cards' | 'brief'`.**

**A tool call can now be private: `format: 'cards' | 'brief'`.** Every tool result carrying `items` renders as a wall of posters, so a model calling a tool to *inform itself* made a lookup the visible answer — most starkly when it fetched fifty recent plays, found no French noir among them, and announced none had been watched with fifty unrelated posters underneath. `brief` (on `getWatchHistory`, `getUserRatings`, `searchContent`, `semanticSearch`) returns `{ id, brief, count }` and **no `items` key at all**. That omission is the whole mechanism: `Thread.tsx`'s `renderToolResult` dispatches on shape (`carousels` → `items` → `contentId` → `people` → `movieCount` → `studios`) and falls through to `return null`, so there is **no client change and both renderers agree for free** — a brief result must never accidentally carry one of those keys. It is also far cheaper: a `ContentItem` hauls a poster URL, synopsis, director and action hrefs that a lookup never uses. Only the model can know why it is calling, which is why this is an input rather than a per-tool flag — `getWatchHistory` is genuinely the answer to "what have I watched" and genuinely context before a recommendation. The search tools build their brief **after** `annotateWatchedItems`, so a private lookup can answer "have they seen these?", which is the main reason to make one; they also keep a `yearById` map because `ContentItem` folds the year into `subtitle`. `FORMAT_PARAM_DESCRIPTION` and `briefResult` live in `tools/utils.ts`, and there is a matching rule in `prompts/rules/tools.ts` — a new lookup-prone tool needs both.

## F-018

**Episode embeddings had no reader for their entire existence, and now have exactly one.**

**Episode embeddings had no reader for their entire existence, and now have exactly one.** `episode_embeddings_*` is the largest embedding table on any real library — one row per episode against one per show, measured live at **16,591 rows / 535 MB against 987 series / 33 MB** — and `generateMissingSeriesEmbeddings` filled it unconditionally via `includeEpisodes = true`, a default parameter no caller ever passed. Nothing read it. `getEpisodeEmbedding` and `getSeriesEpisodeEmbeddings` (the latter commented *"for computing series taste from episodes"*) were exported through three barrels and called by nothing; every other reference was a count, a `DELETE` or a `TRUNCATE`. So every new episode bought an embedding call for an index with no consumer. Note the fear that motivates aggregating them is unfounded in the other direction too: **nothing pools episode vectors into the series vector**, so a 20-season show and a 6-episode miniseries contribute exactly one vector each — `buildSeriesCanonicalText` describes the show and its only trace of episodes is the literal string `"5 seasons, 62 episodes"`. Where episode *count* could have skewed things is the taste profile, and that was already handled: `calculateEngagementWeight` uses `log10(episode count)` precisely so a 400-episode show cannot outvote five finished miniseries. The reader is now `searchEpisodes` (`assistant/tools/episodes.ts`), which is the **only** tool that knows what happens inside an episode — "the one where they get stuck in the desert" is unanswerable from the series index however good it is. Six things are load-bearing. (1) **`ContentItem.id` is the EPISODE id**, because `ContentCarousel` keys React on it and two episodes of one show would collide; navigation travels separately as `episode.seriesId`, which `ContentCard` prefers when present. No `'episode'` member was added to the `type` enum on purpose — type drives watched lookups and detail routes throughout the client, and a third value would need handling in every one of them to fix a problem the extra field already solves. `tool-ui/types.ts` mirrors it by hand, as always. (2) The tool is in **`EXEMPT_TOOLS`**: an episode id matches neither a movie nor a series, so `withUnwatchedFilter` is a silent no-op on it — and it *should* be, since "which episode of X was the desert one" is asked about a show the user has by definition been watching, so filtering on the parent would empty the answer. Episode-level watch status is a tool parameter instead. (3) Any post-filter needs `SET LOCAL hnsw.ef_search = 500`, and **series scoping is the worst case in the repo** — one show is a fraction of a percent of the episode index, so at the default 40 the filter returns nothing and looks broken. (4) The subtitle puts the **year first** because `ContentCard`'s `splitMeta` only lifts a leading four-digit segment into the title parens; any other order silently drops it into the meta line. (5) `createEpisodeTools` returns `Promise<ToolSet>` and reads the setting **itself**, mirroring `createN8nTools` — a conditional spread at the call site instead made every tool `T | undefined` in the merged object and broke `onStepFinish`'s typing. (6) Generation is governed by `system_settings.episode_embeddings_enabled` (**default on**, Settings → AI Config → Episode Embeddings), and with it off the tool is absent rather than empty, so the model says it cannot search episode content instead of reporting a confident false negative. Disabling and deleting are **separate actions** (`PATCH` vs `POST /api/settings/ai/embeddings/episodes/clear`): the first is free to reverse, the second costs a re-embed of every episode. Episodes remain excluded from the `text_version` staleness scheme, so their selection is still missing-only.

## F-019

**Version identity is a fork problem, and there were five disagreeing strings.**

**Version identity is a fork problem, and there were five disagreeing strings.** `routes/api.ts` said `0.1.0`, `routes/health` said `0.7.8`, two OpenAPI examples said `0.7.8`, and `apps/api/package.json` said `0.7.8` — nothing read anything else. `config/version.ts` is now the only source. It exposes **two fields rather than one string**, deliberately: `APP_VERSION` is the upstream lineage this fork tracks (dgruhin-hrizn/aperture) and `APP_BUILD` is the fork build. Joining them forces a SemVer question with no good answer — `0.7.8-mod.412` is a *pre-release* and sorts **below** plain `0.7.8`, which is backwards for something that is 0.7.8 plus work, while the semantically-correct `0.7.8+mod.412` uses a `+` that is **illegal in a Docker tag**. Keeping them apart sidesteps it; `fullVersion()` still joins with `-` for single-string surfaces, where the mis-sort costs nothing because nothing resolves ranges against this app. Both come from Docker build args set by CI: `APP_BUILD` is `mod.<commits>.g<shortsha>` (`git describe` shape — count for a monotonic build number, SHA so a history rewrite can't create a collision). **`fetch-depth: 0` on both build jobs is load-bearing** — `actions/checkout` defaults to depth 1, which would make `git rev-list --count` return 1 and every build `mod.1`. Outside CI the args are empty and the code falls back to `dev`, so a hand-built image never claims to be a release. The `ARG`s sit in the runtime stage, after the build stages, so bumping a version does not invalidate their layer cache.

## F-030

**A reasoning model spends the explanation's token budget on thinking, and one truncated character used to discard the whole batch.**

**A reasoning model spends the explanation's token budget on thinking, and one truncated character used to discard the whole batch.** Both generators ask for ten explanations as one JSON object, and a `JSON.parse` failure replaced *all ten* with `generateFallbackExplanation` — a template so plausible ("Based on your enjoyment of X, this Drama shares similar qualities you'll likely appreciate") that the page reads as a model that has quietly got worse rather than one that never spoke. Measured live on DeepSeek V4 Flash: three parse errors of the form *"Unterminated string in JSON at position 3068"*, with `llm_inference_calls` showing `completion_tokens` pinned at exactly **3000** on those calls and `reasoning_tokens` of 2079 and 2283 — leaving ~700–900 tokens for ten explanations that need ~1,200. (1) `shared/explanationParsing.ts` is now the one home for both the numbers and the reading; the two generators held **identical private copies** of `getExplanationBatchSize`, which is exactly how one could have been raised without the other. (2) The large-context ceiling is **16000**, not a number close to the observed sum: `maxTokens` is a cap, not a reservation, so headroom is free on a healthy call and is the whole answer on a bad one. The Groq/Ollama tiers are deliberately **not** raised — theirs are bounded by the model's whole context window, so a bigger output budget trades this bug for a worse one. (3) `parseExplanationResponse` tries strict JSON first and salvages entry-by-entry only when that fails, keeping every finished explanation and skipping the half-written one a truncation ends on; it handles the reversed key order and decodes escapes, so a `\"noir\"` doesn't terminate an entry early. **The first version of that salvage was a regex, and it produced a second and worse incident — see the next entry.** (4) **`finishReason === 'length'` is the direct tell** and is logged whenever the strict reader rejected the response; token counts are deliberately *not* repeated in that log, since `llm_inference_calls` already records them with the reasoning split. (5) A degraded batch is no longer silent — it used to be indistinguishable from success.

## F-031

**Recovering from a broken response is inference, and inference that reaches the page has to be a whole sentence.**

**Recovering from a broken response is inference, and inference that reaches the page has to be a whole sentence.** The salvage above shipped and immediately caused a worse failure than the one it fixed: every explanation on the detail page became a sentence fragment — *"If"*, *"Given how much you loved the quiet human connection of"* — while the job logged `generated: 20` and no warning at all. Three things combined. (a) The model writes film titles in bare double quotes **because the prompt does**, on every line (`"${m.title}"`, `"${e.title}"`), and does not escape them, so the document is not valid JSON and salvage has to read it. (b) The salvage pattern's string body `(?:[^"\\]|\\.)*"` stops at the first unescaped quote, so `...the moral murk of "Parasite", this...` matched up to the quote before the title and stored the lead-in as a finished explanation. (c) The caller's only check was `byIndex.size < movies.length` — ten fragments is not a short batch, so nothing warned. **Measured on the affected run**, and the numbers are worth keeping because they show the failure is per *response* rather than per explanation: `selected_rank` 1–10 were fragments of 2–107 characters containing **no** double quote at all, 11–20 were 414–483 characters and every one contained quotes. The split falls exactly on the batch boundary (`batchSize` 10) — one document failed to parse and had every quote-carrying entry cut at its first title, the next parsed strictly and kept everything. So "titles in quotes render fine" and "titles in quotes broke it" are the same fact seen from either side of a batch, which is why this looked intermittent and unrelated to quoting. Across every stored run on the instance exactly one batch was affected. Four rules now. (1) **Where a string ends is decided by structure, not by the first quote**: `isValueEnd` accepts a quote only when what follows is `}`/`]`, a comma introducing the next `"key":`, or nothing at all. A bare `"\s*[,}\]]` lookahead is *not* enough and fails on the commonest phrasing there is — in `I loved "Heat", but colder` the quote after Heat is followed by a comma. (2) **Anything salvaged must still read as a finished sentence** (`looksComplete`: 40 chars and terminal punctuation, closing quotes allowed after it). This applies to the salvage path **only** — a strict parse returns exactly what the model wrote, so a terse explanation there is its judgement and not a reading error. The guard is what covers the genuinely ambiguous case, where a response ends right after a quoted title and the final quote is equally plausibly a terminator or a title close. (3) **`describeExplanationBatch` is shared** by both generators, because the condition that let this through was duplicated and the whole point of the module is that the two cannot drift; it reports any response the strict reader rejected, not merely a short one, and puts `finishReason === 'length'` first because that is a cause rather than a symptom. (4) The prompt now says not to write double quotes in the explanation text — worth doing at the source, but it is a request, so the reader holds regardless. `explanationParsing.test.ts` pins the exact live shapes.

## F-032

**Explanations can be re-run alone, without re-scoring anything**

**Explanations can be re-run alone, without re-scoring anything** (`recommender/explanationRefresh.ts`, job `refresh-recommendation-explanations`, `POST /api/recommendations/:userId/explanations`). The picks, scores, diversity selection and evidence are already stored; the explanation is a separate text-generation call on top, and it is the *only* part of the pipeline that depends on which writing model is configured — so rewriting a paragraph used to mean regenerating everything, minutes of work for a different set of picks. Four things are load-bearing. (1) It targets the **newest `status='completed'` run** per user per media type, the same resolution every reader uses. That is not just tidiness: `thinSupersededCandidates` strips non-selected rows from every *other* run, so an older one holds only its ~20 picks. (2) That mattered because `normalizedSimilarity` used to be unstored, leaving `buildRunSimilarityScale` to recompute it from the run's own pool — and against a *thinned* run the scale came from the top slice of the distribution, whose mean is nothing like the pool's. Migration `0141` stores it, so that path now only runs for older rows (`resolveNormalizedSimilarity` prefers the column and treats NULL as "predates 0141", never as zero); the newest-completed-run rule stands on its own merits regardless. (3) `score_breakdown` is where `interestText` and the twin flag are recovered from, so a reserved-slot pick is still explained by the interest or the kindred viewer rather than by a similarity ranking that did not choose it — and the donor id stays in the column, only the flag travels. (4) Every score column is read through a `Number.parseFloat` helper, because **pg returns NUMERIC as a string** and `'0.0000'` is truthy. The AI-explanation setting gates it per user exactly as it gates the pipelines. (5) It is **cancellable**, which for a job of this shape is not optional — it is minutes long and every step is a paid model call. `isJobCancelled` is polled once per user × media type *and* between batches inside both generators (the optional `shouldCancel` argument on `generateExplanations`/`generateSeriesExplanations`, which the pipelines don't pass since they have no job id there), so the worst case is one in-flight request rather than one whole user. A cancelled run stores the explanations it already paid for and leaves the rest on their previous text, and it deliberately **does not call `completeJob`** — `cancelJob` has already written the `job_runs` row.

## F-033

**"Favorited" and "watched" are three different questions, not two**

**"Favorited" and "watched" are three different questions, not two** (`recommender/watchedExclusion.ts`): `WATCH_HISTORY_TASTE_SQL` (`played OR is_favorite`) answers *what shaped your taste*; `WATCH_HISTORY_EXCLUDABLE_SQL` (`played OR ≥5% progress`) answers *have you seen it* and is shared with `discover/filter.ts` and the STRM safety net — **never fold `is_favorite` into it**, or a bookmarked title silently becomes unrequestable in Seerr. The third question, *should we recommend it*, is the recommender-only `getExpandedFavoritedMovie|SeriesIds`, unioned into `excludeIds` in both pipelines' `!includeWatched` branch: a favorite is already found, so offering it back spends one of ~20 discovery slots on the user's own bookmark. Series favorites are recorded per **episode**, so the series helper means "has a favorited episode" — a show favorited on the server with nothing played leaves no `watch_history` rows and needs no exclusion. `watchedExclusion.test.ts` pins the split. **The two exclusions now happen at different stages, and the stage is the whole point.** `excludeIds` is enforced at *retrieval* — watched titles are never fetched, scored or stored, which is right when a viewer has thousands of them. `selectionExcludeIds` holds favorites and is enforced at *selection*: the title is retrieved, scored and stored like any other and is simply never picked. Both pipelines build a `selectableCandidates` list for this and hand it to **every** selector — diversity selection and all three slot fillers — while `storeCandidates` still receives the full pool. Excluding favorites at retrieval meant a hearted film had no `recommendation_candidates` row, so the insights route answered `isRecommended: false` and `MovieInsights` returned null: marking a film as one you cared about silently deleted its match / discovery / quality bars at the next run. Favorites number tens, not thousands, so scoring them is cheap — which is exactly why watched titles stay excluded at retrieval. Disliked titles are still retrieval-excluded and have the same latent problem. Consequence worth remembering: because a favorite is taste input *and* (before this) a candidate, `storeEvidence`/`storeSeriesEvidence` used to match a pick against **itself** at cosine 1.0 and burn one of its three evidence slots — the LATERAL joins now carry an explicit `<> sel.selected_*_id`, which matters beyond the UI because `explanations.ts` feeds those same rows to the model under "use this data, don't invent connections".

## F-034

**A genre weight measured volume, not preference, and the library was never the denominator.**

**A genre weight measured volume, not preference, and the library was never the denominator.** `calculateGenreWeight` (`taste-profile/franchise.ts`) scored a genre by its engagement relative to the average across the viewer's *other* genres, with no reference at all to what the collection holds — so in a comedy-heavy library comedy reads as beloved on volume alone, and a viewer who has taken every one of the eleven noirs on the shelf reads as indifferent to noir. Measured on the live instance against one viewer's 1,561 films: comedy is everywhere in their raw counts (96 comedy-crimes, 183 comedy-dramas) while their availability-adjusted selection rate for it is **0.76** — they choose it *less* often than it is offered. Their real preferences are crime 1.88, thriller 1.52, mystery 1.42, biography 1.33, against family 0.39, music 0.48, horror 0.54. A 2.5-fold spread between what the old measure reported and what the viewer does, on the input feeding the preference nudge. The base term is now `(watched_in_genre / watched_total) ÷ (available_in_genre / available_total)`, in `taste-profile/genrePreference.ts` (pure, split out for the same reason as `watchedExclusion.ts` and `pending.ts`). Five things are load-bearing. (1) **The denominator must be the same population the numerator counted** — `getLibraryGenreCounts` takes the viewer's excluded-library ids, because `detectMovieGenres` already filters by them, and a viewer who hides the horror library would otherwise read as horror-averse purely because the numerator lost those rows while the denominator kept them. (2) **The arithmetic is in log2 space**: a ratio is multiplicative, so "twice as often" and "half as often" must be equal and opposite deviations, which a linear map gets wrong at both ends. (3) **Shrinkage toward neutral by `n/(n+10)`** does two jobs with one constant — it damps a thin history *and* a thin library section, which look identical from inside the function: both are a confident ratio computed from almost nothing. Nine of twenty noirs is a ratio near 4 and still only nine films. (4) The band is **[0.7, 1.3], exactly the 0.6 width the old formula's [0.8, 1.4] produced** (asymmetric there for no stated reason). Correcting *what* is measured must not quietly change *how hard* genre preference pushes, or neither change can be evaluated; the ±0.3 rating and +0.2 favourite adjustments on top are untouched for the same reason. Rebalancing the three against each other is a separate decision needing its own evidence. (5) A ratio that cannot be computed returns **null, and null maps to exactly 1.0** — "we cannot tell" and "they are indifferent" are different claims, but by the time it reaches a score they must be indistinguishable, or an unmeasurable genre gets penalised for being unmeasurable. `detectAndUpdateGenres` **bails without writing** when the library has no genre-bearing titles rather than flattening every stored weight to neutral; the old weights stay and the next rebuild retries. Note the numerator still counts *every* `watch_history` row rather than gating on `WATCH_HISTORY_TASTE_SQL` like the rest of the recommender, so an abandoned title counts as genre evidence — deliberately left alone here, since changing the gate and the denominator in one pass would confound both. `genrePreference.test.ts` pins the band width, the log symmetry, the shrinkage and the live ordering.

## F-035

**Genre reaches the score three times, and two of those are marginal approximations of what the embedding already does.**

**Genre reaches the score three times, and two of those are marginal approximations of what the embedding already does.** `calculateGenreNoveltyScore` rewards genres the viewer watches *less* (peaked at half-unfamiliar); the genre affinity above rewards genres they watch *more*; and `buildCanonicalText` writes the genre list into the embedded text, so the taste vector — 50% of the blend at default weights, more in practice — already separates a crime-drama from a crime-comedy. The first two both take a plain **arithmetic mean over the title's own genres** (`familiaritySum / itemGenres.length`, `totalWeight / count`) and neither has any notion of genre co-occurrence. **Measured, so it does not have to be argued again**: across 68 genre pairs with ≥15 films in a 1,561-film history, the interaction — observed pair rate against what the library's own co-occurrence plus each genre's marginal preference predicts — clusters at 1.0, and the highest-volume pairs are dead neutral (Action+Adventure 1.00, Action+Drama 1.01, Drama+Thriller 0.98). **Do not build a joint genre model**; it is worth 1–2 points on a term worth about six. What the residual *does* show is a shape error: two strongly-preferred genres together under-deliver (crime+thriller 0.75 at prefs 1.88×1.52, mystery+thriller 0.72) while two avoided genres over-deliver (family+fantasy 2.29 at 0.39×0.59, horror+sci-fi 1.67). Saturation at the top, compensation at the bottom — exactly the error a *linear mean* makes, so the fix is to compress the averaged affinity toward neutral, not to add structure. The naive lift `P(A∧B)÷P(A)P(B)` computed *within* watched titles is **not** the measure and will mislead: it reports how genres co-occur in cinema (animated musicals exist), not what anyone prefers.

## F-036

**Mean-centred embeddings, and the one rule that makes them safe.**

**Mean-centred embeddings, and the one rule that makes them safe.** Every canonical text describes a film, in one template, in one register, so all ~12,589 vectors share a direction and a large part of every cosine measures it -- raw neighbour cosines on the live library crowd into **0.66-0.83**, putting an excellent match ~0.13 from a poor one. Subtracting the library mean removes it. Measured by `evaluate-recommender` over 33 qualifying viewers: **ndcg@100 20.5% -> 31.9%**, recall@100 11.2% -> 20.6%, median percentile 86.6% -> 91.1%, winning in all three history-size buckets and for 25 of 33 viewers, with the biggest gains on the viewers raw served *worst* (67.7->93.6, 83.5->97.6, 54.0->72.7); five lose 1-4 points. (2) **It is a stored column (`embedding_centered`, migration 0154), not a `- mean` term at each call site.** Centring is a property of the whole library, so making it ingestion-time means a new query cannot forget it -- the exact failure shape this file records three times over (the AI role enum copied into ten schemas, the enrichment predicate copied into four places, the two centroid paths that disagreed about normalisation). It also means **the mean is never stored or looked up at query time**: the taste centroid is BUILT FROM these vectors, so a profile built from the centred column is already centred and needs no mean to be compared against it. **No index on the column, deliberately** -- the recommender uses a LIMIT above table size, which makes the planner abandon HNSW anyway. (3) **A profile is built once and read later, so it records its own space** (`user_taste_profiles.embedding_space`). Comparing a raw centroid against centred items is not a degraded ranking, it is a cosine between two different origins: a confident number that means nothing, which would read as the recommender mysteriously getting worse. `resolveEmbeddingSpace` is the one reader and it **refuses** (returns null, the run finalizes `failed`) rather than falling back when a centred profile meets an unusable column. (4) **The safety property is that a raw profile stays raw even once centring is available.** Filling the column changes nothing until `rebuild-taste-profiles` deliberately moves a user -- so the migration and the backfill are inert, the rollout is stepwise, and rebuilding profiles from the raw column is the entire rollback. `buildSpaceFor` (build) and `resolveEmbeddingSpace` (read) are separate functions with a test pinning that anything built now is immediately servable, because a drift between them would strand a user with no recommendations at all. (5) **`isCenteringReady` is all-or-nothing** and the refresh is ONE statement: a half-filled column silently shrinks the candidate pool (NULL rows drop out of an `ORDER BY ... LIMIT`), and a batched refresh would leave rows centred against different means -- every row non-NULL, readiness reporting true, and the vectors disagreeing about where the origin is. (6) **The interest ANN paths stay raw on purpose, in both pipelines.** Their query vector is a fresh embedding of interest *text*, which nothing centred; both sides raw is internally consistent, and centring the text side would need the query-time mean this whole design avoids. Same for `storeEvidence` and the similarity graph -- and note the measurement supports that scope: on the live neighbour dumps, centring barely changes item-to-item *ordering* (Oppenheimer, Dune 2 and Poor Things return identical top-3s) and mainly widens the spread, so the gain was concentrated in the centroid path all along.

## F-037

**A centroid is a sum, not a comparison, and only the sum cares whether a vector is unit-length.**

**A centroid is a sum, not a comparison, and only the sum cares whether a vector is unit-length.** Every one of the 31 vector comparisons in this repo uses pgvector's `<=>`, which is cosine and therefore magnitude-invariant, so an unnormalized embedding costs them nothing — which is exactly why nothing ever normalized on write. The taste vector is the one place that *adds* vectors: `buildWeightedAverageEmbedding` (`taste-profile/builder.ts`) and its deliberate twin `weightedMeanEmbedding` (`clustering.ts`) both summed **raw** embeddings, making a title's influence `weight × ‖v‖` rather than `weight` — so `calculateEngagementWeight`'s whole ladder (log10 episode count, the completion bands, favourite ×1.5, the 180-day half-life) was multiplied by an uncontrolled per-title factor. The trailing L2 normalize does **not** fix that: it rescales the finished mean, long after the relative contributions are decided. Four things worth keeping. (1) **This is inert at a model's native dimension and only there.** `gemini-embedding-001` returns unit vectors at 3072, which is what this instance runs, so the fix corrected nothing that was live here. It stops being inert the moment the dimension is not native — Google's documentation says outright that *"you must manually normalize non-3072 dimensions"*, and **seven of the eight entries in `VALID_EMBEDDING_DIMENSIONS` are truncations**, so the correctness of the taste vector rested entirely on which one an operator happened to pick. MRL truncation also makes the norm depend on how much of *that text's* energy landed in the kept dimensions, so the distortion is per-title rather than a constant. (2) **The two centroid paths already disagreed**: the K≥2 path has always fed `l2Normalize`'d vectors to spherical k-means (the `UnitItem` construction), so at a truncated dimension one viewer's taste was computed under one rule at K=1 and another at K≥2 — and `chooseK` compared a raw-mean fallback against unit-based clusters to decide between them. `l2Normalize` is now exported and **shared**, rather than a third copy of the formula. (3) The shared primitive is not tidiness — `clustering.test.ts` asserts K=1 is **bit**-identical to `buildTasteProfile`, and float multiply is not associative, so `unit[i] * weight` and `raw[i] * (weight / norm)` are different numbers; the two call sites must perform the same operations in the same order. (4) The guard is a **pair** of tests: scaling an item's vector must not move the centroid, *and* doubling its weight must — the first alone is satisfied by ignoring weights altogether. Costs a `rebuild-taste-profiles`, never a re-embed.

## F-038

**Embedding task type IS reachable through OpenRouter. This entry previously said it was not, and that was wrong.**

**CORRECTED 2026-08-28.** The original entry read: *"the `openrouter` provider does not [support it]: `OpenRouterEmbeddingSettings` carries only `user` and provider-routing preferences, and OpenRouter's embeddings endpoint is OpenAI-shaped … with nowhere for a Google-native field to live — no `dimensions` either. So reaching `SEMANTIC_SIMILARITY` means pointing the embeddings role at the **`google` provider directly**."* Every clause after the first is false, and the entry cost real time: it was read, believed, and used to rule out a whole class of explanation for why an A/B between two embedding models came out the way it did. **An entry in this file asserting that a door is locked is worth checking against the installed package before it is relied on.**

**What is actually true.** OpenRouter's `POST /api/v1/embeddings` documents an `input_type` field (typed `string`, examples `search_query` / `search_document`, no enum) and a `dimensions` integer. `@openrouter/ai-sdk-provider@1.5.4` reaches both: `OpenRouterEmbeddingSettings` extends `OpenRouterSharedSettings`, which carries `extraBody?: Record<string, unknown>`, and `doEmbed` builds its request as `{ model, input, user, provider, ...config.extraBody, ...settings.extraBody }` — spread verbatim into the outgoing JSON. So an OpenAI-shaped extra is a settings argument, not a fork.

**Measured, on one canonical film document, same text each time** (probe run by the operator against the live endpoint):

| Model | default vs `search_query` | default vs `search_document` | default vs `semantic_similarity` |
|---|---|---|---|
| `google/gemini-embedding-001` | identical (cosine 1.0, max diff 0.0) | identical | **cosine 0.867021, max diff 0.0535** |
| `google/gemini-embedding-2` | cosine 0.9357 | cosine 0.9842 | **identical (max diff 0.0)** |

Two readings. First, `input_type` is honoured — a max coordinate difference of 0.053 is a different space, not float noise or nondeterminism. Second — and this was **misread on the first pass** — 001's default is the retrieval space with `semantic_similarity` the outlier, while for gemini-2 `input_type` is simply a **no-op**. A byte-identical result is evidence the parameter was *ignored*; it was read instead as evidence that the default *is* the semantic space, which is the same identity pattern that had just been correctly read as "ignored" for 001's two retrieval values. The parsimonious reading was available and the flattering one was taken. So "the default" is not a stable thing to reason about across models, and neither is "sending nothing is safe".

This matters because **this library's task is symmetric**. Film document against film document (evidence lookup, Explore graph, related titles, MMR redundancy), and a taste centroid that is a weighted mean of item vectors — still item space. Query→item search is the minority path. `SEMANTIC_SIMILARITY` is the mode built for exactly that, and every vector this instance holds was embedded without it.

**What this does NOT overturn.** The Gemini-001-vs-Qwen result stands: Gemini won on ndcg@20 (10.7 vs 8.1), rec@20 (5.1 vs 3.7) and 23 of 33 viewers (exact two-tailed *p* = 0.0351). What changes is the *label* on it — that was **default-mode Gemini against unprompted Qwen**, not either model in the configuration this task calls for. Neither was measured at its best. See [F-093](#f-093) for what the mode is now wired to, and the collision that had to be fixed before the comparison could even be run.

**Google direct is still an option and still works differently.** `@ai-sdk/google@2.0.52` takes `providerOptions.google.taskType` with the full native enum (`SEMANTIC_SIMILARITY`, `CLASSIFICATION`, `CLUSTERING`, `RETRIEVAL_DOCUMENT`, `RETRIEVAL_QUERY`, `QUESTION_ANSWERING`, `FACT_VERIFICATION`, `CODE_RETRIEVAL_QUERY`) plus `outputDimensionality`. Note the shape difference that shows up in the code: Google's rides **per call**, OpenRouter's is baked into the **model instance** — which is why `getEmbeddingInvocation` hands back a model *and* `providerOptions` together rather than just a model.

**The two original traps were right and still apply.** (1) **Task types are different vector spaces**, so every call site must agree — and there are **six**, not the four this entry claimed: the library `embedMany` (movies and series), `embedText()`, `semanticSearch`'s query, the custom-interest re-embed, and the assistant's three tool embed sites through one `ToolContext`. (2) A mode change is **invisible to the staleness predicate** — the canonical text is unchanged, so `markEmbeddingsCurrent` would restamp rather than re-embed. That second trap is now handled structurally rather than by a `CANONICAL_TEXT_VERSION` bump: the mode rides in the *set identity*, so a mode change starts a new set that is empty and therefore entirely pending, exactly as a model change does.

**`dimensions` is deliberately NOT plumbed**, though it is equally reachable. Seven of the eight `VALID_EMBEDDING_DIMENSIONS` are MRL truncations, and truncating requires re-normalising (F-036, F-037) — `storeEmbeddings` normalises nothing. A dimensions knob without that renormalisation is a footgun that produces plausible, wrong vectors. Neither planned experiment needs it: gemini-embedding-001 is 3072 native and gemini-embedding-2's recommended top size is also 3072.

**Gemini-2's semantic mode is a TEXT PREFIX, and OpenRouter is a faithful pipe.** A second probe embedded the same canonical document four ways — Google's native API and OpenRouter, each bare and each prefixed with Google's documented `task: sentence similarity | query: `:

| | vs Google bare | sha256 |
|---|---|---|
| Google, bare | — | `2d136b29…` |
| **OpenRouter, bare** | **identical, cosine 1.0** | `2d136b29…` |
| Google, prefixed | cosine **0.8106**, max diff 0.166 | `a4a61c43…` |
| **OpenRouter, prefixed** | cosine **0.8106** | `a4a61c43…` |

Two conclusions, both load-bearing. **OpenRouter is not degrading anything** — byte-for-byte identical to Google's own API on both inputs, which retires the "is the proxy the problem" question for good. And **the prefix is a far larger transformation than any `input_type` value**: 0.811 against the bare document, versus 0.867 for 001's `semantic_similarity` and 0.948–0.984 among gemini-2's `input_type` values. Large enough to reorder nearest neighbours and move every user centroid.

So `input_type: semantic_similarity` on gemini-2 does nothing, and the earlier "its default IS the semantic space" reading was wrong. Gemini-2 dropped `task_type` and moved task conditioning into the prompt, exactly as Google documents; OpenRouter's generic label has nothing to map onto.

**The consequence for this app is an architectural constraint, not a setting.** A prefix changes the *text*, so it must be applied to every document in a set and to anything compared against them — never a mix. One index of half-prefixed films, or a centroid built from bare vectors and compared against prefixed candidates, produces a confident ranking of two different spaces. That is the same failure `resolveEmbeddingSpace` refuses for raw-vs-centred (F-036), and it must be enforced the same way: the prefix rides in the **set identity**, so a prefix change starts a new, empty, fully-pending set rather than contaminating an existing one — and it therefore needs no `CANONICAL_TEXT_VERSION` bump.

**Mean-centring is already per set** (`refreshCenteredEmbeddings` computes `AVG(l2_normalize(embedding))` under `WHERE model = $1`), so each set gets a mean from its own rows with nothing extra to build.

**A prefixed set may legitimately score WORSE on the holdout metrics.** `metrics.ts` is a guard rail, not a target (F-057): it can only reward more of what a viewer already engaged with, so a space that improves cinephile kinship — the actual reason to want it — can lose on ndcg while being the better recommender. That is what the seed neighbour dumps are the PRIMARY instrument for, and why `evaluation_seed_titles` being populated with discriminating titles matters before this comparison rather than after.

**OpenRouter now ships built-in embedding models, and only embedding models.** It is a `CUSTOM_MODEL_PROVIDERS` member — no built-in chat, text-generation or exploration entries, because that catalog is thousands of models that turn over weekly and a curated list would date on contact. Embeddings are the exception: the whole OpenRouter embedding catalog is a handful, and shipping none of them meant an operator had to hand-register a model before the feature worked at all. Three are listed (`google/gemini-embedding-2`, `google/gemini-embedding-001`, `qwen/qwen3-embedding-8b`), each carrying the measured mode behaviour from the table above in its description. Four rules, pinned by `embeddingCatalog.test.ts`. (1) The declared **`embeddingDimensions` picks the table** — `getCurrentEmbeddingDimensions` reads it to choose `embeddings_<n>`, so editing a number migrates nothing and instead points every read at a different table, which presents as a library that lost its vectors rather than as an error. The two models with rows on disk are pinned to the dimensions those rows are in. (2) Entries carry **no static price**: `pricing-cache.ts` has no `openrouter` table (F-005), so a number written here would be the only source and would drift; `getModelsForFunctionWithCustom` enriches built-ins from the live cached catalog instead — the same fetch the custom branch already makes. Without that enrichment, promoting a model from custom to built-in would have LOST its price, since only the custom path looked it up. (3) The merge **dedupes by id, built-in winning** — anyone running this fork before the promotion had registered these by hand, so the picker would otherwise offer the same model twice with one row tagged "Custom model"; built-in wins because that is already the precedence in `getCurrentEmbeddingDimensions`, and keeping the custom row would let a dropdown entry advertise a dimension the resolver would not use. (4) `gemini-embedding-2` is listed at **3072**, not one of its smaller Matryoshka sizes, so a comparison against 001 measures the model rather than truncation.

## F-039

**Series engagement weighting lives in two places and must agree**

**Series engagement weighting lives in two places and must agree**: `taste-profile/builder.ts` `calculateEngagementWeight` (log10 episode count × completion × favorites × rating × 180-day recency half-life) feeds the taste vector *and* the clusters — the primary retrieval path; `series/pipeline.ts` `getSeriesWatchHistory` has its own simpler weight feeding only the fallback single centroid. Both now call the shared **`completionMultiplier`** (exported from the `taste-profile` barrel): `>0.9 → 1.5`, `>0.5 → 1.2`, `≥0.25 → 1.0`, `≥0.1 → 0.4`, else `0.25`. The sub-1.0 bands are the point — bonuses alone left forty abandoned shows outvoting five finished ones ~2.5:1, because people sample far more than they finish. **The denominator is `series.total_episodes` (what the media server holds), never `tmdb_total_episodes`** — a user who owns one season of five and watched it finished everything available and must not be penalised for content they don't have; the 0.25–0.5 band stays neutral for the same reason (season two arrived and they never noticed). `engagement.test.ts` pins the bands and the 9:1 ratio.

## F-040

**What counts as a watched episode was three different things**

**What counts as a watched episode was three different things**: the sync stores episode rows for played ∪ in-progress (`position > 0`) ∪ favorited-unplayed (`media/emby/series.ts`), so an episode quit after 30 seconds used to inflate both `episodeCount` and `completionRate` for exactly the shows the user bounced off. Both builder queries now gate on `WATCH_HISTORY_TASTE_SQL`, matching `series/pipeline.ts`, `genreFamiliarity.ts` and `eraDiagnostics.ts`.

## F-041

**Favoriting a show marks the Series item, not its episodes, so it produ**

**Favoriting a *show* marks the Series item, not its episodes**, so it produces no `watch_history` rows anywhere. Series-level favorites reach the taste profile through `user_watching_series` (the bidirectional mirror maintained by `watching/favoriteSync.ts`) via `getFavoritedSeriesWithoutHistory`, appended inside builder's `getSeriesWatchHistory` and de-duped by a `NOT EXISTS`. **That mirror only refreshes while the Watching feature is enabled** — with it off the table goes stale and flagged shows silently stop contributing. Same table is unioned into `getExpandedFavoritedSeriesIds` so a flagged show isn't recommended back.

## F-042

**Changing how taste is calculated does not reach anyone until their profile goes stale.**

**Changing how taste is calculated does not reach anyone until their profile goes stale.** `getUserTasteProfile` only rebuilds when `isProfileStale` says the profile has aged past its own `refresh_interval_days` (30 by default), so after shipping a change to `builder.ts` — the engagement ladder, which rows feed the vector, clustering — most users keep scoring against the old maths, and the logs say `✅ Using stored taste profile` rather than anything that looks wrong. **The full-reset recommendation jobs do not help**: they clear `recommendation_*` and regenerate, reading whatever profile already exists. The sweep is the manual **`rebuild-taste-profiles`** job (core `taste-profile/rebuildAll.ts`), which is the per-user Settings button applied instance-wide. It honours `is_locked` (an admin job must not overwrite a profile its owner pinned; the per-user endpoint passes `skipLockCheck: true` because there the caller owns it), and detects a no-op build by comparing `auto_updated_at` across the call, since `getUserTasteProfile` returns the *stale* profile rather than null when a build yields nothing.

## F-043

**"Generate recommendations" and "Full reset" run the same pipeline; only the wipe differs.**

**"Generate recommendations" and "Full reset" run the same pipeline; only the wipe differs.** `clearAndRebuildAllRecommendations` is `clearAllRecommendations()` plus the same per-user loop `generateRecommendationsForAllUsers` runs — neither was ever incremental, and the description "rebuilds from scratch" describes both. (The reset also selects on `is_enabled` alone, so it regenerates for users who have that media type *disabled*.) The scheduled job opts into `recommender/activityGate.ts` via `skipIfUnchanged`, the **only** caller that does: a manual regenerate means someone asked for work. **That sentence was true of the intent and false of the code for as long as the gate existed.** `skipIfUnchanged: true` was hardcoded inside `generateRecommendationsForAllUsers`, and the executor makes no distinction between the scheduler and the Jobs console — so pressing **Run** skipped every user whose inputs had not moved, and since a skip writes no run row, the operator got a green tick and no change. `runJob` now takes a `JobTrigger` (`apps/api/src/routes/jobs/executor.ts`) that defaults to `'manual'` at every entry point, and only the `setJobExecutor` callback in `routes/jobs/index.ts` — the single scheduled path — passes `'scheduled'`. The default direction is the safety property: a caller that forgets gets the work done rather than silently getting nothing. **This matters most after a deploy**, because a code change is not one of the gate's signals: when `0141` shipped columns that only a fresh run could fill, pressing Run was the obvious remedy and was the one thing that could not work — every user was skipped, and the only ungated path was the full reset. Three more things are load-bearing. (1) **A skip writes no run row at all** — `/api/recommendations` serves the newest `status='completed'` run, so an empty one blanks the page; that is why `runId` is now `string | null`. (2) The **watch-history sync moved above** the gate and the run record, or the gate would judge people on data it was about to refresh. (3) The catalogue signal is a **count against `newCandidateThreshold`, not a timestamp**, because `MAX(movies.created_at)` is global — one new film would regenerate all eighteen users and the gate would never fire. Never gate on `movies.updated_at`: the sync rewrites every row every few hours. `maxRunAgeDays` is the backstop for inputs nobody enumerated, and every failure path regenerates, so a bug here can only cost compute. `activityGate.test.ts` pins the comparison directions.

## F-045

## F-046

## F-049

**Taste twins are behavioural, and the embedding version of the same idea does not work here.**

**Taste twins are behavioural, and the embedding version of the same idea does not work here.** A "twin" is another viewer whose watch history overlaps a user's far more than chance; a bounded few of their titles earn reserved slots (`recommender/twinAffinity.ts` for the SQL, `recommender/shared/twinSlots.ts` for the pure maths, wired into both pipelines beside the interest slots). The obvious implementation — cosine between `user_taste_profiles.embedding` centroids — was measured and rejected: across all 153 pairs on the live instance those cosines span **0.898–0.993**, with unrelated viewers above 0.95, because a centroid is the mean of ≤150 item vectors that already sit in a narrow cone (`clustering.ts` records item→own-centroid distance 0.238–0.254 for *every* user). Compression is the arithmetic working, not a defect, so there is nothing to "fix" in profile generation — and note there is no profile *text* to rewrite either; the column is a weighted mean of item embeddings. Mean-centring against the population centroid does reopen the range (top-25 spread 0.578→0.305 vs 0.993→0.928 raw), which is a live option for a secondary signal but is not what ships. Five things are load-bearing:
  1. **Donors ≠ recipients.** Only `is_enabled AND movies|series_enabled AND NOT provider_disabled` may *receive*, but anyone with watch history is valid *evidence* — most users on this instance have recommendations switched off during testing, and the single strongest pair (333 shared titles, ~2× the next real pair) has a donor among them. Collapsing the two populations deletes that relationship.
  2. **The idf denominator counts everyone with history**, not just recipients. Rarity is better estimated with more observers; narrowing it only loses precision.
  3. **idf ranks *pairs* and must never rank *titles*.** A shared title necessarily has ≥2 viewers so its idf varies, which is why affinity discriminates well. An unwatched candidate almost always has exactly one viewer — 46 of 48 sampled — so every candidate ties at `ln(N/1)` and ordering by it is arbitrary. Fillers are therefore ordered by the pipeline's own `finalScore`; the twin decides what is *eligible*, the ranking decides what is *good*. Same pinning pathology as `avgNovelty` in [0.8, 1.0] and normalized dispersion reading 0.000 for all 14 profiles — a measure calibrated on one population is not a measure on another.
  4. **The bar is derived per run, never stored**: `median + k·MAD` over every pair. Absolute affinities are uninterpretable (the strongest real pair scored 0.198 against a body of 0.03–0.09, because most of anyone's watch mass is on titles nobody else touched), and enabling viewers changes N, which shifts every idf. Raw MAD, no 1.4826 factor — the distribution is right-skewed and pretending otherwise would be false precision. Zero spread returns null rather than the median, which would admit half the population.
  5. **Both knobs are in `SCORING_FIELDS`.** `{movie,series}_twin_threshold_k` (1–4, default 2.0) and `_twin_max_slots` (0–10, default 4, 0 disables — there is no separate toggle) are admin-editable at Settings → AI Config → Algorithm → Taste Twins. Omit either from `SCORING_FIELDS` and editing it would not bump `scoring_updated_at`, so the activity gate would see no change and the new value would sit unused until `max_run_age_days` fired.
  Slots come *out of* `selectedCount` and are computed against `selectedCount − reservedInterestSlots`, so the two slot features can never over-reserve (pinned by a sweep in `twinSlots.test.ts`). Explanations get the same treatment interest picks do — a `fromTasteTwin` flag, a prompt line, a `CRITICAL:` rule and a non-AI fallback — because a twin pick is precisely the item similarity did *not* choose, and without it the model invents a watch-history justification. **Copy never names the donor**: `score_breakdown.twinMatch` stores `donorId` and the panel says "someone here whose taste closely overlaps yours". Known blind spot: the activity gate cannot see twin-driven change, so a user whose own history is unchanged but whose twin watched fifty new films is skipped until `maxRunAgeDays`.

## F-050

**`selectedCount` is a budget, and every spender must be visible.**

**`selectedCount` is a budget, and every spender must be visible.** Three things draw from it: top-ranked picks, interest slots and twin slots. Both slot features shipped with an admin ceiling *and* a hardcoded `*_SLOT_SHARE` of 0.2 sitting underneath it, so a ceiling of 4 against a 10-item list silently produced 2 and the settings page gave no hint why. Both shares are now deleted: `computeReservedInterestSlots(selectedCount, interestCount, maxSlots)` and `computeReservedTwinSlots(remaining, twinCount, maxSlots)` are bounded only by things an admin can see — what exists (interests written, twins that cleared the bar), the configured ceiling, and the list length. Four consequences. (1) **`{movie,series}_interest_max_slots`** (migration 0133, default 3) had to exist, because making twins honest while interests stayed two hidden constants would just move the surprise; it is in `SCORING_FIELDS` alongside the twin columns. (2) Removing `INTEREST_SLOT_SHARE` **raises** interest slots on short lists — at `selectedCount` 10 the old share capped them at 2 and the setting now delivers 3. (4) The UI enforces the budget in the *controls* — each slider's max is `selectedCount` minus the other's value, lowering Recs Per User clamps both, and a readout shows the ranked/interests/twins split live. ## F-051

**The evidence carousel had no distance floor, so "the best available" and "a good match" rendered identically.**

**The evidence carousel had no distance floor, so "the best available" and "a good match" rendered identically.** `storeEvidence` runs a LATERAL kNN restricted to titles the viewer has already watched and keeps the three nearest, with **no minimum similarity** -- correct as a query (the panel wants the closest things in their history) and a false claim once captioned *"Why We Think You will Like This / Based on your history with similar movies"*. Measured live on 12,589 movies (gemini-embedding-001 @3072, raw cosine): the panel offered **Metropolis -> A Clockwork Orange 0.67 / Das Boot 0.67** and **Dancer in the Dark -> In A Better World 0.694 / Fargo 0.694**. Those are real near-neighbours -- library-wide they rank about 8th-11th of 12,589 -- but the same library answers **Woman in the Moon 0.767 / Die Nibelungen 0.724** and **Breaking the Waves 0.756 / Dogville 0.738** once it can reach past that viewer history, so what the panel showed was a pool limitation presented as a reason. Four things. (1) The fix is a threshold and the threshold is **measured, not guessed**: everything a person recognised as correct sits at 0.75+ (Stalker->Solaris 0.788, Poor Things->Kinds of Kindness 0.814, Dune 2->Dune 0.829), both complaints sit at 0.69 and below, and rank 10 of the whole library lands at 0.68-0.72. `EVIDENCE_CAUSAL_MIN_COSINE` is **0.72**. This repo has twice been burned thresholding a compressed cosine band blind (twin centroids 0.898-0.993, `avgNovelty` pinned in [0.8,1.0]), so what makes a provisional number shippable here is that **the failure is asymmetric and the safe side is up**: set too high, the same three titles still appear under *"Closest in your library"* and merely stop being called the cause; set too low, the panel asserts something false. It also governs one heading -- no score, no ranking, no pick depends on it. (2) It is a **raw** cosine and is tied to the embedding that produced it. Mean-centring roughly doubles the spread (Poor Things->Kinds of Kindness is 0.814 against 0.682 at rank 10 raw, and 0.563 against 0.264 centred), so if centred vectors ever back this lookup the constant is measured against the wrong distribution and must be re-derived, not carried over. (3) The API sends a **decided boolean** (`evidenceSupportsCause`), never the threshold, for the same reason `scoreScales.novelty` ships its bounds: the web bundle never imports `@aperture/core`. **Absent reads as permitted** (`=== false`, not `!`), so runs predating the field keep the heading they shipped with, exactly as the preference chain and weight shares do. (4) The **prose says the same thing**, or the fix would only move the lie into the paragraph above the posters: `evidenceHeading` takes a third **required** argument (a default is a decision a caller can forget, and the two generators exist to stop drifting), and a distant ranked pick reuses `EVIDENCE_HEADING_RESERVED` rather than adding a third label -- *"context only, NOT why this was picked"* is already the claim, and `buildSlotRules` is written against exactly two headings.

## F-052

**The insights panel holds two kinds of "evidence" and only one of them is a reason.**

**The insights panel holds two kinds of "evidence" and only one of them is a reason.** `recommendation_evidence` (written by `storeEvidence`) is a LATERAL kNN run *after* selection: the pick's three nearest neighbours in the reader's own history by embedding cosine. For a ranked pick that is a fair account of why it is there. For a **reserved-slot** pick it is not — the ranking is exactly what did not choose it — so labelling it "Why We Think You'll Like This / Based on your history with similar movies" asserted a cause that was false, directly under a banner saying the scores did not put the film in the list. `MovieInsights.tsx` now switches that heading to a non-causal one (`closestInLibrary*`) whenever `scoreBreakdown` carries `twinMatch` **or** `interestMatch`; same rows, different claim. **A score of 0 and a score never taken are different, and NUMERIC-as-string hid that.** `diversityScore` is measured relative to what is already selected, so it only exists for candidates `applyDiversityAndSelect` actually walked — never for the thousands scored but not picked, and never for reserved-slot fillers, which are appended after it returns. ## F-055

**The insights panel printed four numbers on three different scales and claimed they were one calculation.**

**The insights panel printed four numbers on three different scales and claimed they were one calculation.** Under the heading *"How We Calculated Your Match"*, a live pick read **Taste Match 78 / Discovery 72 / Quality 85** beneath a headline of **90** — which no weighted average of those three can produce, since a weighted average cannot exceed its largest input. (2) **`applyPreferenceAdjustment` overwrote `finalScore` in place**, moving it by up to half the remaining headroom, so even a correctly-scaled similarity left an unexplained gap; `baseScore` is captured before the nudge in both pipelines and the panel renders *blended → preferences ± → match* as an explicit chain, shown only when the column is non-null. Also: the Discovery bar is filled against `[NOVELTY_ALIEN_FLOOR, NOVELTY_PEAK]` rather than 0–100, because that curve is peaked rather than a fraction and floors near 0.47, so drawn raw the *lowest possible* discovery score looks like a half-full bar. Storing `normalized_similarity` also retires the fragility documented under `explanationRefresh`: `buildRunSimilarityScale` now only runs for pre-0141 rows. **`0141` made the arithmetic correct and still left it uncheckable, which took a live complaint to notice.** A card reading **Taste Match 75 / Discovery 76 / Quality 28** under a headline of **63** closes exactly — at 0.50/0.25/0.25 it is 63.5 — but nothing on the page stated the weights, so the obvious reading is an average, which gives 60, and the panel looked broken for being right. ## F-056

**A 20% diversity weight was behaving as a hard sort, because nothing put it on the same scale as what it competed with.**

**A 20% diversity weight was behaving as a hard sort, because nothing put it on the same scale as what it competed with.** The old selector (`shared/selection.ts`, now deleted) blended `finalScore` against `1 − (genres already covered / genres on this title)`, with "covered" a plain `Set.has` — so one Drama closed Drama for the rest of the list, and after five picks the term was effectively bimodal: 0 for almost everything, 1 for anything carrying a rare genre. The scales then decided everything. Measured off the insights panel live, `finalScore` runs **0.905 at rank 1 to 0.82 at rank 200 — a spread of 0.08** across the entire realistic contender set, against a diversity term spanning the full 0–1; at `w = 0.2` that is 0.064 of relevance against **0.20** of diversity. The arithmetic is exact: an uncovered-genre title wins whenever `b > B − 0.25`, i.e. thousands of them, so once a genre was covered nothing sharing it could be picked again while any unrepresented genre remained — genre coverage first, match second. And because genre coverage is a property of the **library** rather than of a person, that is also a large part of why picks overlapped so heavily between users. Replaced by **`shared/mmr.ts`**: `(1 − w)·relevance − w·gain·max sim(d, selected)`, the standard MMR the old code was approximating. Four things are load-bearing. (1) **`gain` = relevance spread / redundancy spread**, measured over the shortlist before selection starts — the same `effectiveBlendWeights` correction, applied one layer up where it had never been applied and where the mismatch was far worse; clamped `[0.25, 40]`, and 1 when either spread is unmeasurable. (2) It reranks a **shortlist** (`mmrPoolSize`, 15 per slot, floor 150) rather than the whole scored pool, which is what stops a rank-3000 title taking a slot and also what keeps the embedding fetch to a few hundred vectors instead of the library. (3) **`variety` is measured against the FINISHED list**, not incrementally — scored as it goes, the top pick reads 1.0 every time for having had nothing to differ from, which is the same confident non-measurement as the old "Variety 0%". (4) A title with no embedding answers **0 redundancy** and competes on relevance alone; excluding it would drop a good pick over a missing row. Series **network diversity is gone** with the genre term: a series' canonical text already carries its network, so same-service shows sit closer in embedding space and the penalty catches it without a second hand-weighted axis. This also removes one of the three places genre entered the score — genre spread still emerges, since same-genre titles are close in the vector space, it is just no longer a separate vote. Both selectors are async now (they fetch the shortlist's vectors); `mmr.test.ts` pins the live-shaped regression — at `w = 0.2` the leader must still lead and nothing beyond rank 60 of 300 may be reached.

## F-057

**There is now a way to tell whether a retrieval change helped, and it is deliberately two instruments.**

**There is now a way to tell whether a retrieval change helped, and it is deliberately two instruments.** `core/src/evaluation/`, job **`evaluate-recommender`** (manual-only, reads only, writes nothing). **`neighbours.ts` is PRIMARY**: a title's ten nearest neighbours, raw and mean-centred side by side, with **country in a column** — six of the fifteen `buildCanonicalText` fields are nationality-coded proper nouns (director, studio, cinematographer, composer, cast, country) against three that describe what a film is like, so a nationality detector shows up immediately; `countryConcentration` turns that into a number to compare against the country's share of the catalogue. Someone who knows twenty films judges a change from this in a minute. **`metrics.ts` is a GUARD RAIL, never a target** — every metric here can only reward more of what someone already engaged with, so novelty and diversity score worse on them *correctly*, and tuning to maximise one builds precisely the recommender nobody wants. Five things are load-bearing. (1) **Relevance is graded, not asserted**, because no label here is trustworthy: `WATCH_HISTORY_EXCLUDABLE_SQL` counts ≥5% progress as watched, and an Emby favourite is a bookmark as often as a verdict (this file already says so under `watchedExclusion`). A title bailed on scores **0** and contributes nothing; a rewatch or a finished-and-marked title scores **1**; a bookmark scores 0.3. `SKEPTICAL_RELEVANCE_WEIGHTS` re-runs the same evaluation barely believing favourites — **a conclusion that flips between the two weightings is an artifact and gets thrown away**, which is a robustness check the graded labels buy for free. (2) The holdout is a **per-viewer count, never a shared cutoff date**: a date gives a heavy watcher sixty-five answers and a sporadic one six, so the pooled result measures heavy users and anyone sporadic drops out of the sample entirely. Most-recent rather than random, because random leaks — hide one film of a twenty-film binge and finding it is near-duplicate lookup. (3) Aggregation is **macro, one vote per viewer**, and the per-viewer rows are always printed; this instance has twice been misled by an average that described nobody. Results are also bucketed by history size, because a change can help thin profiles and hurt thick ones and the aggregate would read that as a loss. (4) **Random and rating-only baselines run through the same harness** — a metric with no baseline is uninterpretable, and "does any of this beat sorting by IMDb score" is the question worth being able to answer. (5) Scope is **retrieval only**, on purpose: every open question is about retrieval, and the full pipeline is neither side-effect free nor injectable. `loadLibraryMatrix` holds the whole table in one normalised `Float32Array` (~77 MB at 1536 dims) so ranking is pure arithmetic; `meanCenter` carries **the mean it subtracted**, because a query centred with the mean of an already-centred matrix lands in a different space and still returns a confident ranking.

## F-058

**A weighted average assumes its terms are comparable, and novelty was competing on a track 37% as wide.**

**A weighted average assumes its terms are comparable, and novelty was competing on a track 37% as wide.** Influence is **weight share × realized spread**, so a term confined to a narrow output band hands most of its configured weight back before any data is involved. `calculateGenreNoveltyScore` output into [0.47, 0.84] — the values the old branch-based implementation produced, held deliberately so that replacing branches with a curve stayed a change about *what* novelty measures — while similarity (post-`normalizeSimilarity`) and `calculateRatingScore` both use the whole range. Measured across nine users on the live instance via the `SCORE-DIAG` log: novelty's p10–p90 spread ran **0.133–0.289** against similarity's steady **0.577** and rating's steady **0.46**, so a novelty weight configured at 8.1% delivered between **2.1% and 4.5%** of the actual movement depending on the viewer. Four things. (1) The band is now the full **[0,1]**, and the stretch preserves the curve's **proportions exactly** — the familiar floor still sits (0.57−0.47)/(0.84−0.47) = 0.27 of the way from the alien floor to the peak, pinned by `novelty.test.ts`, so this is a scale change and not a redesign of what novelty rewards. (2) It also retires a **display** problem: a bar that could never read below 47% nor above 84% needed a `scale 47–84%` caption to be intelligible at all, and the panel now suppresses that caption whenever the band is the full range (the check stays rather than the caption being deleted, because the scale rides in from core's constants and a retune could narrow it again). (3) **The spreads say which term deserves which instrument, and they are not the same.** Rating's 0.46 is identical for every user, so its shortfall is purely structural and a *fixed* gain is the right correction; novelty's varies **2.2×** between users, so a fixed stretch scales everyone by the same factor and leaves that unfairness intact — the residual wants a *bounded adaptive* gain, and only novelty earns one. Similarity is already pool-adaptive and correct; do not touch it. (4) Do **not** blanket z-score all three. Similarity's compression is an artifact of the embedding cone plus ANN returning its nearest slice; novelty's and rating's are often real information — a pool where every candidate is a crime-thriller genuinely has no genre variation to report, and amplifying it lets noise decide, which is the same pinning pathology as twin centroids spanning 0.898–0.993. Correct the structural under-use; stay conservative about the genuine compression. Note also an old comment here claimed *"the fall is deliberately shallower than the rise"*, which never matched either implementation: the legacy branches put `tooNovel` a flat 0.1 **below** `allFamiliar` at every input, so the alien end was always penalised harder. Consequence to remember: a stored `novelty_score` from a run made before this is on the old scale, so its bar fills differently until the next regenerate — the number shown is right either way.

## F-059

**The spread correction goes on the WEIGHT, not on the component — and that choice is what keeps "Quality 82%" meaning IMDb 8.2.**

**The spread correction goes on the WEIGHT, not on the component — and that choice is what keeps "Quality 82%" meaning IMDb 8.2.** `effectiveBlendWeights` (`shared/scoring.ts`) multiplies each configured weight by a gain for how much of the range its term actually uses, so influence tracks the slider instead of the term's shape. The two directions are mathematically identical — `w/spread × value` orders exactly as `w × value/spread` — but only this one leaves the numbers on screen alone, and the panel's numbers are exact, checkable claims that exist because a previous round of this made them so. Six things. (1) **`TARGET_COMPONENT_SPREAD` (0.57) is not a tuning knob and not an average of the three**: `normalizeSimilarity` produces it by construction — tanh(z/2) over a roughly normal z lands p10–p90 near 0.57 whatever the pool holds, measured 0.546–0.577 across nine live users — so similarity is the term already on scale and the other two are corrected **onto** it. It therefore never gets a gain itself; a second correction would double-count `normalizeSimilarity`. (2) **Rating gets a fixed gain, novelty a per-run one, and the measurement is what decides which.** Rating's spread was 0.46 for eight of nine users and 0.44 for the ninth — a constant shortfall wants a constant (`0.57/0.46` = 1.239). Novelty's varied **2.2×** between users on identical settings, so a constant would leave that unfairness exactly where it was. (3) **The novelty gain is clamped to [0.7, 1.5]**, and the clamp is a guard rail rather than a mechanism: against real pools the wanted gains land in [0.73, 1.58], so it binds on one user and only just. What it guards is the perverse direction — a pool with almost no novelty signal would otherwise divide by a tiny spread and hand the ranking to noise. A spread of zero returns gain **1.0**, not infinity. (4) **Two passes, not one**, in both scorers: the gain is a property of the pool, so every candidate needs a novelty score before any candidate can have a final one. The similarity scale already worked this way. `scoreCandidates`/`scoreSeriesCandidates` therefore return `{ candidates, weights }` rather than an array. (5) **`finalizeRun` stores the EFFECTIVE weights**, which is not a repurposing — 0147's column means "what this run blended with", and that is now the corrected value. Feeding it the configured weights instead would leave the panel multiplying numbers that do not reproduce the match, which is the precise fault 0147 was written to fix. Migration `0150` widens them `NUMERIC(3,2)` → `NUMERIC(6,4)`, because `0.25 × 1.2391` stores as **0.31** at two decimal places and three such roundings miss the arithmetic by up to half a percent. **No backfill is possible**: the gain depends on the novelty spread of a candidate pool that no longer exists. (6) The `SCORE-DIAG` log now carries **both** `weights` (configured) and `effectiveWeights`, and `influence` is computed from the effective ones — computed from the configured ones it would describe a blend that did not happen. Measured effect at the live 70.4 / 8.1 / 21.4: realised influence was **77.8 / 3.3 / 18.9** before, and lands within a percentage point of the configured shares after (pinned by `novelty.test.ts`, which also pins that the clamped case still improves).

## F-060

**Re-normalising similarity inside the selection band was simulated on live data and rejected: renormalise one term of three and it takes the whole ranking.**

**Re-normalising similarity inside the selection band was simulated on live data and rejected: renormalise one term of three and it takes the whole ranking.** The premise is real — `normalizeSimilarity` calibrates spread over the *whole* candidate pool, but selection happens among the few hundred nearest, where similarity's realised spread collapses to **0.028** (measured p10–p90 across the current top 50, against a pool-wide 0.57). The obvious fix is to z-score similarity against the top-N band instead. Simulated in SQL from stored `similarity_score`/`novelty_score`/`rating_score` and the per-run weights from `0147`, at N = 200/500/2000, it decompresses exactly as intended — spread ×19.1 / ×14.9 / ×6.4 — and that is the problem. **Novelty and rating are not re-normalised, so they keep their pool-wide spread inside a band where similarity now has the full tanh range**, and realised influence goes to **93.6 / 2.2 / 4.3** at N=200 against a configured **70.4 / 8.1 / 21.4**. Quality stops filtering: 10–13 of every user's 20 picks change, and for one live user *Blade Runner 2049*, *Interstellar*, *The Prestige*, *Dunkirk*, *Mad Max: Fury Road* and *Knives Out* leave, replaced by *Renfield*, *Underwater*, *Men in Black: International*, *Hotel Artemis* and *Extraction 2* — the dense mass of generic titles that sit nearest a centroid once nothing else can outvote proximity. The compression is therefore **left alone**, consistent with the rule above about not blanket z-scoring: it is partly an artifact of the embedding cone and partly the ANN honestly reporting that the top 500 really are all about equally close. The only sound version would re-normalise **all three** terms onto one target spread computed over the same band — `TARGET_COMPONENT_SPREAD` applied to the selection band rather than the pool — which is a different and larger change, unmeasured, and not worth attempting without first showing the top-band ordering is actually wrong rather than merely flat.

## F-061

**The explanation model was given a pairing and asked to supply a reason, with nothing to build one from.**

**The explanation model was given a pairing and asked to supply a reason, with nothing to build one from.** The prompt carried the pick's title, year, genres and 250 characters of its own synopsis, plus the **bare titles** of its three nearest neighbours in the viewer's history — no synopsis for those three, no themes, no crew. So "both are Korean masterpieces about the poor infiltrating the lives of the wealthy" was entirely the model's pretrained knowledge of two famous films; the pipeline contributed only the fact that they were close in vector space. Fine for canonical cinema, silently unfounded for anything obscure, and the one remaining instruction shaping the prose was *"Create excitement"*. Six changes, mirrored in both generators. (1) **Evidence rows now carry `overview`**, and the pick's own plot budget rose 250→600 (`shared/explanationPrompt.ts`, shared for the same reason `explanationParsing.ts` is — the two generators are near-duplicates and drifting constants would be invisible). `plot_full` is deliberately **not** used despite being longer and more specific: it is IMDb's synopsis, which routinely gives away the ending — the web UI hides it behind a button for exactly that reason — and handing it to a model instructed not to spoil is a rule that only has to fail once. (2) **`keywords` and `directors` reach the prompt**, keywords being where a style is actually written down (almost no noir has "noir" in its title or synopsis, and there is no Film Noir genre — the same gap that forced a country filter onto the assistant's search tools). (3) **The raw cosine percentages on each evidence line are gone.** They sit in a band a few points wide, so 74 versus 69 reads as a meaningful grade while carrying almost nothing, and the only thing a model can do with such a number is repeat it. Order is the usable part and is preserved, labelled *nearest first*. (4) A **no-invention rule**: obscure titles are expected, work only from the data given, and state no awards, reception, festival history or production trivia that is not in it. (5) *"Create excitement"* became *"be specific rather than superlative"* — naming what two films share is both more persuasive and checkable. (6) `clip()` replaced `substring(n) + '...'`, which appended an ellipsis unconditionally: a complete synopsis presented as though it trailed off is an invitation to continue it, which is the exact failure the rest of this is trying to reduce. Also note `getUserTasteContext` in both generators counted **every** `watch_history` row, including titles abandoned after two minutes, so a genre someone kept bouncing off could be presented as a favourite; both queries are now gated on `WATCH_HISTORY_TASTE_SQL` like everything else in the recommender.

## F-062

**The evidence lookup searched 1.4% of a real viewer's history.**

**The evidence lookup searched 1.4% of a real viewer's history.** Both pipelines handed `storeEvidence` the *same* list they built the taste vector from — `recentWatchLimit`, default **50**, favourites-first. That is right for a centroid (a weighted mean whose tail contributes almost nothing) and wrong for a nearest-neighbour lookup: for a viewer with 3,510 watched films, whatever genuinely sat closest to a pick was usually not in the candidate set at all, and the three titles shown under *"based on your history with similar movies"* were the nearest among a handful of favourites — which the explanation model, instructed to use exactly those and invent nothing, then reasoned from. Both pipelines now fetch a separate pool at `EVIDENCE_HISTORY_LIMIT` (5000, `shared/evidencePool.ts`). The limit exists only to bound the `uuid[]`, not because more history is worse — for this lookup it is strictly better — and ordering is still favourites-first so a viewer past the cap loses their least-engaged tail. **Do not "simplify" it by joining `watch_history` inside the LATERAL**: an explicit id list keeps the planner on a filtered scan, whereas a join predicate beside `ORDER BY embedding <=> …` is exactly the shape that lets it pick the HNSW index and post-filter, and an HNSW scan never returns more rows than `ef_search` (default 40) — watched titles are a small fraction of the index, so the `LIMIT 3` would come back empty and the evidence would silently vanish.

## F-063

**One grounding role, and the free tier is far smaller than the docs imply — and the model ceiling is not the ceiling that stops you.**

**One grounding role, and the free tier is far smaller than the docs imply — and the model ceiling is not the ceiling that stops you.** `webSearch` (assistant discovery, plus `channels/webExpand.ts`) is the only role that spends Google grounded search. `titleAnalysis` was the second until it moved to self-hosted retrieval — see the next entry — so this machinery now serves one consumer, and stays role-parameterised only because a self-hosted grounding source is planned for discovery too. **The measured numbers matter more than the design**, and they were transcribed from a live free-tier account's AI Studio rate-limit page on 2026-08-17 into `FREE_TIER_MODEL_LIMITS` / `FREE_TIER_GROUNDING_RPD` (`webSearchQuota.ts`). Read together they say something neither says alone. **Search grounding is a separate quota from the model's own, charged per model *family*, and on the free tier the whole Gemini 3.x family gets `0`** — the page lists four search-grounding buckets (Default, Gemini 2, Gemini 2.5, Gemini 3 → 1,500 / 1,500 / 1,500 / **0** per day) against per-model *map* grounding, which is what identifies them as family buckets. So `gemini-3.5-flash-lite` has **500 requests/day and cannot ground at all**, while `gemini-2.5-flash` grounds inside a 1,500/day allowance it can never reach because the *model* caps it at **20/day, 5 RPM**. Twenty grounded turns a day, and only from a 2.x model. That combination is nastier than it looks, because `gemini-2.5-flash-lite` is **no longer offered to new Google projects**: a fresh project can select 3.x, which is useless for grounding, and 2.5 Flash Lite, which it cannot have. `google.json`'s model descriptions carry this per model — the 3.5 Flash Lite entry used to recommend itself for Web Search, which was exactly backwards. It is also what makes `ProviderConfig.fallbackApiKeys` load-bearing rather than a nicety: a second key from a second **Google project** turns 20 into 40, since keys inside one project share quota. Slots are `primary`/`fallback`/`fallback2`… (the legacy scalar `fallbackApiKey` is still read, never written), dedupe drops a fallback repeating the primary, and cooldowns key on **role + slot**. **Anything spending grounding quota must go through `withGroundingModel` or the meter undercounts.** **The table shipped, was deleted, and came back gated — the gate is the whole point.** The first one claimed `rpd: 1000` for flash-lite where the account enforces 20, drawing a 1.2%-full green bar at 60% of the real day; it was deleted because Google has *withdrawn* the published per-model table and the numbers genuinely differ per account **and per tier**, so one operator's figures are wrong for everyone else. Two things make a table safe now. It applies **only when the operator ticks "These keys are on the free tier"** (`ProviderConfig.freeTier`, read through `isFreeTierConfig` — absent means free, only an explicit `false` opts out, and it is stored only when false); untick it and the meter shows bare counts, because a paid project's real budget is many times the free one and a bar claiming otherwise reads as full on a day that has barely started. And it is **subordinate to observation**: `resolveModelLimits` lays anything Google's own 429 disclosed over the defaults **field by field**, so a wrong default can only survive until the account contradicts it, and `source` (`observed`/`freeTier`/`mixed`) rides to the panel so the line under the bars says which it is showing. Observed limits apply **whatever the checkbox says** — a paid tier has limits too, just larger — so unticking withdraws an assumption, it does not blind the meter. Nothing throttles on any of this: key rotation and cooldowns are driven by real 429s. Traps pinned by `webSearchQuota.test.ts`: a **token** quota also reads as PerMinute, so without the token check a 250,000 TPM ceiling lands on the requests-per-minute bar; a **grounding** refusal is also a per-day request limit, so without `limitIsGrounding` a 1,500/day search allowance lands on a bar measuring a 20/day model (the ordinary quota ids and Gemini model ids contain neither "grounding" nor "search", which is what keeps the guard from firing on them); an **unattributed** limit is dropped rather than guessed at; `groundingRpd: 0` is a **real answer** and must be tested with `!= null`, never truthily, or "none" renders as "unknown"; the family prefix match takes the **longest** hit, so `gemini-2.5-*` is not read as plain `gemini-2` when the two buckets diverge; keys are restricted to models `google.json` can actually offer, since Google is not a custom-model provider and an id nobody can pick is an id nobody can check; and `getFreeTierLimits` returns a **copy**, because callers hand it straight into an API response. The observed store is in memory like the cooldowns — losing it costs a gauge until the next 429, whereas persisting risks showing a stale limit after a tier upgrade. Note also the grounding allowance is charged against the whole family across every consumer of that Google project, and nothing here meters it separately, which is why the panel states it as a caption rather than drawing a fill level for a budget it does not count. One open problem remains: the empty-text retry inside `googleGrounding`'s `PASS1_MAX_ATTEMPTS` loop sits *inside* one key attempt, so it makes two requests Google counts while writing one `web_search_usage` row.

## F-064

**Title analysis is title-scoped; the recommendation explanation is user-scoped; merging them would poison the explanation.**

**Title analysis is title-scoped; the recommendation explanation is user-scoped; merging them would poison the explanation.** `analysis/` writes a critic-informed account of *the work* — how it was made, what its makers were attempting, what tradition it sits in, what critics disagree about — cached in `title_analysis` forever and shared by every user. **Where its sources come from is a setting, not a fact** (`analysis/mode.ts`, Settings → Integrations → Retrieval). `crw` — the default — retrieves BEFORE the model is called: `lib/crw.ts` posts to fastCRW's `/v1/search` with `scrapeOptions`, which runs a SearXNG metasearch *and* fetches each hit as clean markdown in one call, and the `titleAnalysis` role — an ordinary writing role, typically a local LM Studio model via `openai-compatible` — writes from that text. That replaced a grounded Gemini call for two reasons. Cost: at a measured 20 grounded requests/day the library was ~2 years of work per key (13,576 titles), where self-hosted is bounded by GPU time — roughly 1–3 min/title, so weeks. And **honesty**, which matters more: this prompt used to be made *entirely* of outside knowledge, the one thing the explanation prompt forbids, and one prompt could not hold both rules. Now it can, because the outside knowledge is *in* the prompt and "use only the sources" is checkable rather than hopeful. The alternative is `grounding`: a Gemini model searches for itself, which is better retrieval and no infrastructure but is metered per day per Google project — a few dozen titles, not a library — and it is Google-only, since no other provider grounds natively (`checkModeReadiness` refuses the combination rather than letting a model produce confident unsourced prose about every film). **`title_analysis.retrieval_mode` records which one wrote each row**, so the two are comparable on a real library instead of arguable: `SELECT retrieval_mode, model, count(*), count(analysis) FROM title_analysis GROUP BY 1,2`. `POST /api/analysis/:type/:id?force=true` re-runs a cached title and is **admin-only** — it is the only way to run both modes over the same title, and also the only way to spend unboundedly by holding a button. It is reachable **from the panel itself** — a *Re-run this analysis* control under a rule, shown to admins over any row that already exists — because a comparison that needs `curl` is a comparison nobody runs, and because it is the only route a **declined** row has: an ordinary POST is answered from storage, and a decline is stored on purpose. The same admin check ships `provenance` beside the text (model, retrieval mode, source count, retrieved chars, prompt version, timestamp). That is what makes the re-run worth having: those columns exist so the modes can be compared after the fact, and without them on screen a before-and-after compares nothing. Withheld from non-admins because it describes our infrastructure rather than the film. Because grounding mode spends the same quota Web Search does, `titleAnalysis` stays in `isGroundingRole` for key handling and out of the credential-donor loop even though it usually points at a local model: a setting whose safety depends on another setting is not a safe setting. Twenty-one things are load-bearing. (1) **Questions, not a directive.** "Analyse this film" makes a model comply at a fixed register and find meditations on grief in an action programmer; specific questions with no answers produce short output instead — measured by hand, *Love Actually* returned ~250 words and *Dancer in the Dark* ~900, both correct. The register rule is explicit for the same reason: the failure is not analysing a genre film, it is analysing one *as if it were Tarkovsky*. Reception figures ride along as **calibration, marked not to be quoted back**, which stops a Criterion essay about a Metacritic 46. (2) **Prompt order is subject → documents → task/rules**, so the last thing the model reads is ours and not a scraped page. Retrieved markdown is untrusted text entering a prompt whose output is stored forever and shown to every user; the fence says so outright, but the structural defences (fixed output shape, closed question set, instructions last) are what carry it. (3) **`sourceFloor.ts` gained a signal grounding could not give it.** It sees real domains now, which catches the failure that only appears with in-house search: for an obscure title a metasearch returns IMDb, JustWatch and "where to watch" SEO — plenty of characters, zero criticism, and a count-based floor reads that as healthy. `LISTING_DOMAINS` is deliberately short and excludes Wikipedia, RT, Metacritic and Letterboxd (all carry writing), and the rule fires only when **every** substantive source is a listing. Every threshold still errs toward keeping, because a decline is **stored** and retires the title until `ANALYSIS_PROMPT_VERSION` moves. (4) **`budget.ts` is the new hard limit.** Google compressed the web server-side; CRW hands back whole articles, and 6 × 12,000 chars is ~18k tokens. Allocation is water-filling (a short document is never cut to reserve room a long one will not get) and documents are **dropped whole rather than shredded** — fragments are worse input *and* they lie to the floor, which counts sources. `clip` reserves the truncation marker inside the limit; appending it after slicing overshot the budget, which a test caught. (5) **`analyseTitle` throws on anything that might be systemic and only stores a decline it believes.** Zero results, or results carrying zero text, **throw** — a working metasearch finds something for nearly any released title, so nothing at all is far likelier to mean SearXNG's upstream engines are throttling or serving CAPTCHAs, and an afternoon of that would otherwise write permanent declines across the library. Sources that are present but *thin* do reach the floor, because there the web genuinely answered and answered poorly. (6) **A row existing means the attempt happened; its contents say what came of it.** `analysis IS NULL` is a decline, no row at all is "never asked or failed in transport". `prompt_version` makes improving the prompt a config change rather than the migration `0137` and `0139` both had to be — it is at **5** now, and every bump re-analyses the whole library, so it is only for changes that would make a stored row wrong or unusable. (7) The job attempts **each row at most once per run** (`attempted` set), or the loop reading until the pending selection empties spins forever on the very failures step 5 leaves pending — the shape that made `enrichMetadata` non-terminating. Cancellation is polled **between titles**. (8) `sourceBudgetChars` lives on the **CRW settings card** although it is really a property of the model's context window, because an operator tunes retrieval volume and how much the model can swallow as one decision. (9) The commonest setup mistake is the **base URL**: fastCRW ships its own compose project, so it sits on a different Docker network and `http://crw:3000` will not resolve — the published host port (`host.docker.internal:3000`) is what works. Test runs a real one-result search rather than a health ping, because the documented footgun (bare container, no search sidecar) passes a health check. (10) **A search that is blocked answers `200 {results: []}`, and three things now read that correctly.** Measured live against the `crw-camofox` fork (Camofox/Firefox driving Google directly, no SearXNG): a first-boot browser profile on a datacenter address was handed Google's `/sorry/index` interstitial, and the call came back a well-formed empty success — indistinguishable from "the web has nothing on this title". So `CrwSearchResponse` carries **`warnings`** (`readCrwWarnings`, which reads the plural list inside `data` *and* the singular scalar beside it — engine-level failures and partial scrape failures have different shapes and neither implies the other); `crwSearch` logs them at **warn**, since they arrive on a 200 and nothing else in the pipeline would ever mention them; both of `retrieveSources`' throws repeat them, because those are the lines an operator actually reads in a job log. And `describeTestOutcome` makes **zero results a FAILED connection test** — the probe query is banal by design, so an empty answer cannot mean "hard question", and the old *"Connected. Search returned 0 result(s)."* rendered a green tick over a retrieval service that could not retrieve. It is pure, so the decision is testable without stubbing `fetch` (`lib/crw.test.ts`, run by `test:analysis`). (11) **The timeout default is set by a number the service prints at boot, not by taste.** CRW's ladder is HTTP → LightPanda → heavy browser, and with `auto_extend_deadline_for_ladder` on (its shipped default) one page reaching the heavy tier gets the whole ladder: a stock deployment logs `deadline_ms_default=15000 ladder_min_ms=82500 effective_default_ms=82500`, and search runs *before* any of that. The old 90s default sat under the worst case with the search leg unaccounted for, and a timeout **throws — which writes no row**, so the title silently stays pending and the work is lost rather than retried loudly. Now 180s. Note most of that 82.5s is fixed per-tier overhead (`2 × 28s`), so lowering the heavy tier's own budget buys far less than it looks like it should. (12) **`checkModeReadiness` was called only by the settings page, to draw a badge — so it described the configuration without governing it, and a guard nothing calls is a comment.** Measured live: retrieval left on `grounding` while the role pointed at an OpenRouter model, which cannot ground. Every call logged `webSearchQueries: 0, groundingChunks: 0`, the model wrote 8,023 characters from its own memory, `sourceFloor` correctly judged that unsupported — and the **decline was stored**, retiring the title until `ANALYSIS_PROMPT_VERSION` moves. Roughly one title a minute, permanently, from a search that never happened, with CRW's log idle throughout. Two fixes, both needed: the check now runs inside **`analyseTitle`** (the choke point every path goes through, including the detail-page button) *and* as a pre-flight in `generateTitleAnalyses`, because discovering it per title would spend the whole budget on identical failures. And the branches were **asymmetric** — `retrieveSources` throws when the metasearch returns nothing, while the grounding branch happily wrote from zero chunks; zero chunks now throws too, so both modes leave the title pending instead of recording "the web has little on this film" on the strength of a search that did not occur. (d) **`testCrwConnection` walks the same cascade and names the engine that answered**, because a button testing one engine while the job tries three lies in both directions — green while every real run fails over, or red while the job is fine on a fallback. Three changes, and the reframe matters more than the reorder. The order is now work → tradition → dispute → intent → circumstances, so anyone who stops halfway has read the half worth reading. The opening question was **reframed rather than moved**: "what is formally or technically distinctive about how it was made" reliably returns hardware because that is a literal answer to it, where asking what the work is doing and how its choices serve that makes technique the evidence instead of the subject. ## F-065

**A failed AI call was unreadable, and the message shown for it blamed the wrong half of the job.**

**A failed AI call was unreadable, and the message shown for it blamed the wrong half of the job.** `APICallError` declares `url` and `requestBodyValues` **before** `statusCode` and `responseBody`, and pino's error serializer copies enumerable own properties in declaration order — so `logger.warn({ err })` wrote the entire ~16 KB analysis prompt ahead of the only two fields that say what went wrong. Measured live: the same unusable line was pasted three times before anyone noticed the answer was already inside it — `code: 404, provider_name: "Nvidia", raw: ""`, i.e. OpenRouter's *sole* free endpoint for that model had been deranked (`status: -2` on `GET /api/v1/models/:slug/endpoints`, against `0` for healthy), so there was nothing to route to and `isRetryable: false` was correct. **`describeAiError` (core `lib/aiErrors.ts`) is what gets logged now**: status, retryability, the model id lifted out of the body, the provider URL, and the response body clipped to 400 chars — with the request body **deliberately dropped**, since it is what made the line unreadable, is reconstructible from the title being processed, and is the one field that could carry user content into a log. It unwraps `RetryError` explicitly, because the SDK's backoff wraps the real failure in an error whose own message says only that retries were exhausted — reading the top of the chain would lose the status on exactly the calls that tried hardest. Applied at the analysis writer (the only frame that knows the model and attempt), the analysis route, and `recordLlmError`, which had the identical defect for chat prompts. **`isProviderError` is a separate field from `status`, and that distinction is the user-visible half**: a dropped connection is a provider failure carrying no status, so a caller must not infer "not the model" from a missing one. The analysis route's 503 used to read *"This is usually the daily search quota; it resets overnight"* unconditionally — wrong for a model failure, and a leftover from grounding mode, since the default retrieval mode is self-hosted and **has no daily search quota at all**. An operator was told to wait until morning for an endpoint its provider had withdrawn permanently. The two halves now get separate messages and the status rides along, because 401/403 is a key, 429 is a rate limit, 404 means the provider no longer serves that model, and 5xx is theirs to fix. Worth knowing when picking a free model for `titleAnalysis`: a `:free` variant usually has exactly **one** upstream endpoint and therefore no fallback, so `/models/:slug/endpoints` is the fastest way to tell a withdrawn model from a broken config.

## F-066

**A free-tier model has two failure modes that no retry can reach, and `titleAnalysis` now answers both — a spare MODEL list and a minimum spacing between calls.**

**A free-tier model has two failure modes that no retry can reach, and `titleAnalysis` now answers both — a spare MODEL list and a minimum spacing between calls.** They are separate settings because they answer different questions, and conflating them is what made `fallbackApiKeys` look like it should have covered this: **a spare key answers "this account is out of quota", a spare model answers "this model is gone"**, and the measured failure was the second — a `:free` OpenRouter model whose sole upstream endpoint its provider deranked, returning 404 with an empty body and `isRetryable: false` on every call, for which no key and no amount of waiting is a fix. Both live on the role's `ProviderConfig` (JSON in `system_settings.ai_config`, so no migration) and are offered by **one card only**, gated on `AIFunctionCard`'s `supportsFallbackModels`: `analysis/generate.ts` is the only consumer that walks either, and a setting no consumer reads is worse than an absent one. Seven things are load-bearing. (1) **`fallbackModels` carries a provider per entry**, so a cloud role can fall back to a local server and survive the *provider* being down rather than only the model; credentials are resolved per provider from the shared store at attempt time, because storing a key beside a spare model would make it a second home for a credential. (2) **The attempts are all constructed up front** (`getTitleAnalysisModelAttempts`), not lazily — a fallback whose provider has no credentials is a configuration mistake, and discovering it at the moment the primary dies, halfway through a library pass, is the worst possible time; a fallback that cannot even be built is skipped with a warning rather than taking the primary down with it. (3) **What rotates**: any provider failure (429, 5xx, a withdrawn endpoint's 404, a dropped connection — i.e. `describeAiError`'s `isProviderError`), *and* an answer that breaks the output contract once that model has spent its `MAX_WRITE_ATTEMPTS`, since "cannot follow the format" is a fact about the model and has already cost one library pass. (4) **A truncation deliberately does NOT rotate.** It names a *setting* — the output ceiling — which every model would hit identically, so rotating would spend a second model to reproduce the same result and then report the second model's name, sending the operator after the wrong thing; the thrown message says which number to change and where instead. (5) **Pacing is ONE stored number, `callSpacingSeconds`, with the checkbox derived from `> 0`** rather than a flag stored beside it — two places holding one answer is the shape of nearly every bug in this file. It is **absent-means-off**, the exact opposite of `freeTier`, and the asymmetry is the point: `freeTier` only chooses a denominator for a meter, so reading its absence as "free" is safe, whereas this one *delays real work* and an absent-means-on reading would silently start pacing every already-configured role, local models included. (6) The gate (`lib/callPacing.ts`) is a **reservation, not a last-call timestamp**: two callers arriving in the same millisecond — the on-demand button during a batch run — would both read the same timestamp, wait the same amount and fire together, which is pacing that does nothing precisely when two things are running. It is keyed on the **provider**, because the limit belongs to the account: falling back from one OpenRouter free model to another keeps waiting, falling back to a local server does not. It sits immediately before **every** request including the write retries, since a retry is a request the provider counts. Cancellation is polled *inside* the wait — a minute-long cool-off that ignores Stop is a button that does not work — and the wait is announced to the job console before it is served, or a silent minute inside a run whose other steps are also minutes long reads as a wedged job, which is how the last failure storm started. A backwards clock is detected by comparing against the reading that *issued* the reservation, which is exact, rather than by capping the wait, which would collapse a legitimate queue. (7) **Grounding mode paces but does not rotate models**, deliberately: its model choice is already constrained to Google's grounding-capable ones and its characteristic failure is a spent daily quota, which `withGroundingModel` answers by rotating *keys* — a second model on the same exhausted project fails identically.

## F-067

**A per-user score averaged ACROSS users can show a trend that exists in no user.**

**A per-user score averaged ACROSS users can show a trend that exists in no user.** Similarity-by-decade averaged over 9 users read as a clean recency bias (1930s 0.29 → 2020s 0.59, monotonic); per user the gradient *reverses* — a 1995-taste viewer scores pre-1980 films 0.502 vs 0.488 for 2015+, a 2018-taste viewer 0.283 vs 0.647. Each peaks at their own era; the population simply leaned recent. Control: each user's taste vector is equidistant from every decade of films they actually watched (one user with 381 films spans 0.7542–0.7596 across 50 years), so the embedding has **no** era bias. Same trap as watch-history Jaccard, where 1–8% pairwise overlap looks like "nobody shares taste" but is exactly what identical taste produces at ~100 watched out of 12.5k. Cross-user pick overlap tracks taste-year proximity (adjacent-era users share 9–10 of 20, users 25 years apart share 0) and is the system working. **Measure per user before reading an aggregate as a mechanism.**

## F-068

**maxCandidates cannot usefully exceed the table it queries.**

**maxCandidates cannot usefully exceed the table it queries.** Retrieval is one `ORDER BY embedding <=> $1 LIMIT n` over *one* embedding table, so n above the row count returns no more titles — it just stops the planner using the HNSW index and buys an exact sequential scan. Both sliders shipped above their tables (16K vs 12,584 movies; 50K vs ~1k series, set on the false belief that series retrieval is episode-level — `series_embeddings` is one vector per show, and `episode_embeddings`' only reader anywhere is the assistant's `searchEpisodes`). The web slider's max is now the live count from `getLibraryItemCounts()`, the PATCH handlers cap it, and both syncs call `clampMaxCandidatesToLibrary()`. That clamp writes `UPDATE` **directly** rather than through `updateConfigFor`: `maxCandidates` is in `SCORING_FIELDS`, so the normal setter would bump `scoring_updated_at` and the activity gate would regenerate every user for a change that cannot alter a single pick. It only ever lowers — a library that grew leaves the admin's number alone.

## F-069

**A vote count is a sound GATE and a worthless SCORE — and the direction is counterintuitive, so measure before "fixing" this again.**

**A vote count is a sound GATE and a worthless SCORE — and the direction is counterintuitive, so measure before "fixing" this again.** `calculateRatingScore(rating)` takes one argument and never sees `imdb_vote_count` (99.9% populated, `community_rating` tracks `imdb_rating` at r=0.996). The obvious fix — Bayesian shrinkage toward the library mean — was measured and is **backwards here**: thin-voted titles average **5.95** against a library mean of **6.52**, so shrinking would *raise* 2,294 obscure poorly-rated films, and only 8 films rated ≥8.0 sit under 1,000 votes at all. Vote count in this library correlates *positively* with rating (<500 votes → 5.95; 50k+ → 6.89), so as a score term it is a popularity proxy. As an *eligibility* test it is exactly right, which is what `isAcclaimed` uses it for. Same shape as idf in `twinAffinity.ts`: sound for ranking pairs, arbitrary for ranking titles.

## F-070

**Acclaimed slots are the third claimant on `selectedCount`**

**Acclaimed slots are the third claimant on `selectedCount`** (`shared/acclaimedSlots.ts`, migration `0152`, **default 0 = off**). Why a slot and not a weight: *Shawshank* (9.3) scored 0.640 similarity against *All Quiet* (7.8) at 0.895; rating correctly favoured Shawshank 0.930 to 0.760 and still lost, because similarity outvotes rating ~5:1. Solving for the flip gives **`w_rating > 0.60`** — rating would have to be over half the blend, applied to every pick, to rescue a handful. Three rules. (1) Fillers are ordered by the viewer's own `finalScore`, **never by rating** — an acclaim-ordered list hands every user the same titles, which is the failure this feature was built to answer, so the gate decides *eligible* and the ranking decides *good for this viewer*. (2) It is measured **last**, against `selectedCount − interests − twins`, so the three features can never over-reserve (swept in `acclaimedSlots.test.ts`). (3) It needs its own explanation flag (`fromAcclaimed`), a `CRITICAL:` prompt rule and a non-AI fallback in **both** generators, plus `acclaimedMatch` in `MovieInsights`' `fromReservedSlot` and a fourth `pickSource` value — otherwise the model explains a title the ranking rejected as a taste match, and the panel captions a similarity lookup as the reason it is there.

## F-071

**The preference nudge is a setting now, not a constant.**

**The preference nudge is a setting now, not a constant.** `applyPreferenceAdjustment` moves a blended score toward 1.0 (or down toward 0) by a share of the *remaining* gap, scaled by franchise/genre/interest affinity. That share was a hardcoded `MAX_PREFERENCE_HEADROOM = 0.5` — half the distance to a perfect match, easily enough to reorder a list, and the only input to `final_score` an admin could neither see nor change. Worse after `0141`, which made the *effect* visible on the insights panel ("blended → preferences → match") while its cause stayed invisible. It is now `{movie,series}_preference_strength` (migration `0153`, default 0.50 = previous behaviour, 0 disables) and is in `SCORING_FIELDS`. Three things. (1) The parameter defaults to the old constant, so an un-passed call is byte-identical — pinned by `preferenceStrength.test.ts`. (2) A negative or non-finite value is **clamped, never trusted**: a negative share would invert the nudge and push loved titles *down*, which is worse than ignoring the setting. (3) `discover/scorer.ts` deliberately does **not** pass it — discovery has its own config, and an admin tuning recommendations must not silently change what gets requested from Seerr. The panel deliberately gains no "strength" caption: the delta it renders is stored per run and therefore always true, whereas labelling it with today's config is exactly the fault `0147` fixed for the blend weights, and would need the value stored on `recommendation_runs` first.

## F-072

**A weighted mean can only say "more like this", so a disliked title must weigh 0 — and the scale is 1-10, not "1-10 or 1-5".**

**A weighted mean can only say "more like this", so a disliked title must weigh 0 — and the scale is 1-10, not "1-10 or 1-5".** `user_ratings.rating` carries `CHECK (rating >= 1 AND rating <= 10)` (migration `0053`), so nothing needs to detect the scale. `calculateEngagementWeight` tried anyway — `item.rating > 5 ? item.rating / 10 : item.rating / 5` — which cannot work, since a 3 is either "good out of 5" or "bad out of 10" and the value does not say which. The resulting curve was **non-monotonic**: 1→0.65, 4→1.10, **5→1.25 (the maximum, tied with 10/10 and ahead of a 9)**, 6→0.95, 10→1.25. The legacy `movies/taste.ts` path had the milder version of the same fault, giving a 1-3 title weight **0.2** under a comment saying it "shouldn't shape recommendations much" — but 0.2 still shapes them *toward* what the viewer disliked, and then everything near that centroid scores higher. Both now drop the item entirely (`isDislikedRating`, `recommender/ratingBands.ts`, shared because the two builders **and** `getDislikedMovieIds` all encode the bands). `calculateEngagementWeight` returns 0 and **both** consumers filter `weight > 0` before use — `buildTasteProfile` and `buildTasteClusters` — since the total-weight-of-zero check inside `buildWeightedAverageEmbedding` is a guard, not a filter, and clustering would otherwise still place a centroid on a disliked point. Pushing the centroid *away* is deliberately **not** attempted: a negative weight in a weighted mean yields a vector that need not lie near the data at all, and cosine against it is uninterpretable. The real mirror of a taste twin is also unbuildable — non-overlap is not anti-correlation, and watch-history Jaccard measured **0-11.5% across all 171 pairs**, so "low overlap" describes every pair on the instance. An item-level dislike *penalty* at scoring time is the buildable version, and unlike a twin it needs no reserved slot, because a demotion never has to win against a dense score.

## F-074

**"Show cross-media connections" was a filter that could never match, and the shape of that mistake is worth remembering.**

**"Show cross-media connections" was a filter that could never match, and the shape of that mistake is worth remembering.** The Explore switch fed `crossMedia` to `/api/similarity/graph/:source`, whose only use of it was `if (!includeCrossMedia && conn.item.type !== centerItem.type) continue` — but the connections came from `getSimilarMovies`/`getSimilarSeries`, single-table kNN that `JOIN movies`/`JOIN series` and stamp `type` as a literal. A movie center could only ever produce movie connections, so the predicate was never true: the toggle read as broken because it *was* a no-op, and the only visible effect was the refetch its dependency change triggered (graph tears down, force simulation restarts, everything appears to vanish and come back). A guard against a case the query cannot produce is not a feature, and nothing typed can catch it. Four things now. (1) **Both functions take `includeCrossMedia` and query the other table with the same vector.** That is sound because `getActiveEmbeddingTableName` derives both suffixes from one `getCurrentEmbeddingDimensions()` call, so `embeddings_N` and `series_embeddings_N` hold vectors from the same model in the same space; no re-embedding and no second model call is involved. (2) **Merging is by reserved slots, not by a shared `ORDER BY`** (`similarity/crossMedia.ts`, pure and pinned by `crossMedia.test.ts`). The two canonical-text builders differ systematically — a series text carries a network and the literal `"5 seasons, 62 episodes"`, a movie text carries a collection — so film↔film and film↔series distances are two populations, and a plain top-N lets whichever sits higher take every slot. (3) **The reservation has to be applied twice**, once inside `getSimilarMovies`/`getSimilarSeries` and again in `getGraphForSource`, because the graph draws only `connectionsPerNode` (3) of the 6 it fetches and its own re-sort by similarity would drop the cross-media entries the first reservation admitted. Its dedupe was also moved *before* selection — skipping an already-drawn edge mid-loop used to spend a slot on nothing. (4) **The switch is disabled outside the Browse views**, since semantic search and the focused rabbit-hole graph come from endpoints that never receive the flag (`getSimilarWithDepth` is still same-media only: its watched filter, bubble analysis and BFS are all keyed to one media type). `crossMediaNodeCount` is logged on every graph build precisely so a silent return to zero is visible.

## F-077

**A weekly schedule can name several days, and only one reader may resolve them.**

**A weekly schedule can name several days, and only one reader may resolve them.** `schedule_day_of_week` held a single integer while the cron field it feeds has always accepted a list, so "Tuesdays and Fridays" was inexpressible. `0149` adds `schedule_days_of_week INTEGER[]` and backfills from the scalar. ## F-079

**A job that never calls `createJobProgress(jobId, …)` has no progress record, and every progress API then no-ops in silence.**

**A job that never calls `createJobProgress(jobId, …)` has no progress record, and every progress API then no-ops in silence.** `jobs/progress.ts` keeps an in-memory `activeJobs` map, and *every* function there opens with `activeJobs.get(jobId)` and returns when it is absent — correct (a finished job is evicted after five minutes and late calls must not resurrect it) but completely quiet. `generate-title-analysis` was registered perfectly everywhere else — `definitions.ts`, the executor switch, `JOB_CATEGORIES` — and missed this one line, which produced **every** symptom at once and no error anywhere: `updateJobProgress` and `addLog` did nothing, so the card showed an empty bar and an empty log pane; `completeJob` returned *before* `saveJobRun`, so no `job_runs` row was ever written and the history dialog read "No run history found for this job"; and `isJobCancelled` reduced to `undefined?.status === 'cancelled'`, which is **always false**, so Stop could not work however diligently the work polled it. ## F-080

**Cancelling is cooperative, and the terminal state is now a one-way door.**

**Cancelling is cooperative, and the terminal state is now a one-way door.** `cancelJob` only sets `status='cancelled'` and writes the `job_runs` row; the work stops solely because the core function polls `isJobCancelled(jobId)` — which `enrichment/`, `mdblist/`, `studioLogos.ts`, `backupService.ts`, `explanationRefresh.ts` and (since the incident in the next bullet) all four recommendation loops do, and everything else does not. Note `analysis/job.ts` cancels too but will not turn up in a grep for `isJobCancelled`: it takes an injected `shouldCancel`, which the executor supplies at the case (executor.ts:317) — the same shape the recommendation pipelines now use to reach inside a single user. Two consequences. (1) A job that does not poll keeps running to completion after being cancelled, and used to then call `completeJob` and **flip its own status back** — the record still sits in `activeJobs` for five minutes after cancelling — filing a second `job_runs` row and overwriting `job_config.last_run_status`. `completeJob`/`failJob` now ignore a job that already reached a terminal status and warn instead; the same guard also collapses the double-report from a core function that fails its own job and rethrows into the executor's catch. (2) Nothing interrupts an in-flight HTTP or model call, so cancellation granularity is whatever the poll interval is — for anything doing paid model calls in a loop, check between calls and not just between users.

## F-081

**A cancelled job that keeps running is not the bug; letting a second one start beside it is.**

**A cancelled job that keeps running is not the bug; letting a second one start beside it is.** Measured live on 2026-08-21: `generate-movie-recommendations` was cancelled 46 seconds in, kept running because that loop polled nothing, and a replacement was admitted at 23:35:14 — **nine users scored twice, 18 runs in 13 minutes**, double the explanation spend, with `job_runs` holding three rows because the zombie's `completeJob` hit the terminal-status guard and filed nothing. The forensics are only recoverable because `0147` stores per-run weights: dividing each user's logged influence by its spread recovers the exact blend, which showed the novelty weight moving from 1% to 8% *between* 23:34:37 and 23:35:15, i.e. an admin changed a slider while both loops were mid-flight. Four things. (1) **The guard was keyed on the right map and the wrong question.** All three claim sites — the Run button, the scheduler, gap analysis — asked `getJobProgress(id)?.status === 'running'`, and a *cancelled* job is not running, so the check passed for precisely the case it existed to stop. Membership in `activeJobs` is the correct test, since the entry is cleared by `runJob`'s `finally` — i.e. when the work actually exits, not when someone asked it to. `decideClaim` is now one pure function in `routes/jobs/state.ts`, pinned by `state.test.ts`, for the same reason as `watchedExclusion.ts` and `pending.ts`: the bug was a predicate, and a predicate nothing can test is how it survived three copies. (2) **The cancel handler used to `activeJobs.delete(name)` immediately**, which is what opened the door; it no longer does, so a cancelled job holds its slot until it stops. That makes the 409 message load-bearing — "was cancelled and is still winding down" is a different fact from "is already running", and without the distinction the console looks broken. (3) **Releasing must be identity-checked** (`releaseJob`): a zombie exits *after* its replacement has claimed the name, so the old unconditional delete in both `executor.ts` and the scheduler wrapper would have opened the guard on a live run — turning one double-run into two. (4) The escape hatch is **eviction, not force**: `progress.ts` drops a record five minutes after any terminal status, and `decideClaim` admits a claim when the holder has no record, so a job that hung or never polls frees its slot after five minutes rather than needing a container restart. A force-release button would let an operator recreate this bug on demand. Both recommendation pipelines now poll between users **and** pass `shouldCancel` down to `generateExplanations`, which already accepted one and was never given it — that is the seam where Stop saves money, since explanations are the only paid part of a run. A cancelled loop also skips `completeJob` and no longer logs "🎉 All users processed successfully". **The 409 has to be visible or the whole guard backfires**: `handleRunJob` in `pages/jobs/hooks/useJobsData.ts` was `if (response.ok)` with no `else`, and its `catch` only fires on network errors — so a rejected start showed nothing at all. That was survivable while the guard was released eagerly (a 409 after cancelling was impossible); now it is the *expected* answer for as long as the work takes to wind down, and a Run button that silently does nothing is exactly what sends an operator to `docker stop`, which is how the double-run started. Both it and `handleCancelJob` now surface the server's own wording, which is the entire value of having worded it.

**A job log is trimmed from both ends, not just the front.**

**A job log is trimmed from both ends, not just the front.** `addLog` bounds what it keeps (`LIVE_LOG_LIMIT` 500 in memory, `STORED_LOG_LIMIT` 300 persisted into `job_runs`), and both used to be a plain `slice(-n)`. ## F-083

**The canonical text read the sync's columns and ignored enrichment's, and the job could not re-embed anyway.**

**The canonical text read the sync's columns and ignored enrichment's, and the job could not re-embed anyway.** Two independent gaps that hid each other. (1) `buildCanonicalText` used `tags` and `awards` — written by `movies/sync.ts` — while `keywords` and `awards_summary`, the enrichment columns added beside them by `0059`, went into no vector at all; `languages`, `collection_name`, `composers` and `cinematographers` likewise. ## F-084

**The canonical text said nationality six times by accident, and embedded the first act of every long film.**

**The canonical text said nationality six times by accident, and embedded the first act of every long film.** Fifteen fields go in; **six were proper nouns tied to a country** — director, studio, cinematographer, composer, cast, `From {country}` — against **three** describing what a title is actually like (genres, plot, keywords). An embedding has no idea those are six separate facts: it sees one document dense with German-morphology tokens and another the same, which is why the three "closest titles in your library" for *Metropolis* came back **A Clockwork Orange / Das Boot / Cloud Atlas at 67 / 67 / 66** — two German productions and a German co-production, tied to the decimal. The evidence query is exact and the pool is the viewer's whole history (`EVIDENCE_HISTORY_LIMIT`), so that was not a lookup bug; the vector really is partly a nationality detector. Three fields removed. **Content rating**: "NR" means nobody submitted it to the MPAA, which tracks age and non-US origin rather than the work, and as a literal shared string it makes an era-and-nationality detector out of every old or foreign title — anything real in R vs PG is already in genres and keywords. **Awards**: the same rule that has always kept *scores* out, since quality has its own blend term — and worse, awards prose hands every awarded title the tokens "Won"/"Oscars"/"nominations", so award films cluster with award films regardless of subject. **Composers**, but **not cinematographers**: the below-the-line argument (a Deakins photograph or a Greenwood score identifies a film) holds for perhaps fifty people, and for the other ~10,000 crew names in a real library a credit appears on two or three titles and contributes nothing to similarity except nationality — photography survives that as a style signal, a single composer credit does not. `MAX_KEYWORDS` deliberately **stays at 18**: keyword coverage is uneven across the library, so raising it trades one dilution for another. Two things to keep in mind. The remaining five nationality-coded fields are still there, so this reduces the effect rather than removing it — the bigger lever was widening the plot, which takes the proper nouns from ~8% of a document to ~2% without deleting anything. And **`CANONICAL_TEXT_VERSION` is what makes any of this reach existing rows** (1 → 2 here); a builder change with no bump is invisible to the staleness predicate, and the bump costs the full cascade: re-embed → `rebuild-taste-profiles` → regenerate recommendations.

## F-085

**OMDb was asked for `plot=short`, which is the one thing it has that we already had.**

> **Corrected by [F-089](#f-089).** Measured on the live library, `plot=full` returns the blurb rather than IMDb's synopsis — 99.7% populated but **p50 431 characters, 0.75% above 2,000, none above 5,000** — so the 5,000–15,000 character synopsis this entry assumes never arrives, `PLOT_CHARS` is nearly never reached, and the plot-widening F-084 credits for cutting proper-noun density did not land. The reasoning below is sound and the guards it describes still earn their place; only the premise about what OMDb returns was wrong.

**OMDb was asked for `plot=short`, which is the one thing it has that we already had.** The media server syncs a one-paragraph blurb into `overview`; `plot=short` returns roughly the same thing, so `OMDbMovieResponse.Plot` was typed and extracted by nothing. `plot=full` is the *same request, same quota, larger response* and returns IMDb's user-submitted synopsis — several times longer and different in kind, narrating the story rather than pitching it, which is exactly the specificity a concept query matches on. Stored as `plot_full` (`0139`) rather than into `overview`, because `movies/sync.ts` rewrites `overview` from the media server on every pass and would erase it. Three rules. (1) The canonical text uses it **instead of** the overview, never alongside — both tell the same story, and including both weights plot twice against genre, crew and keywords. (2) It is used **only when actually longer**: OMDb falls back to the short blurb when IMDb has no long synopsis, so a non-null value is not evidence of anything. The first implementation got this wrong in the fallback branch (`plotFull || overview` returns a *shorter* plotFull) and `canonicalText.test.ts` caught it. The web's `hasLongerPlot` uses the identical condition on purpose, so the embedded text is the text a reader can see. (3) The cap is **4000 characters** (`PLOT_CHARS`, shared by both builders), and both halves of that are deliberate. It was 1000, and `substring(0, 1000)` keeps the **first** thousand — for a real IMDb synopsis, the setup, which is the most interchangeable part of any story, so long-plot films were being made to look *more* alike; it also largely cancelled this feature, since a real synopsis runs 5,000–15,000 characters and keeping the first 10% keeps the part most like the blurb we already had. Removing the cap is the opposite error: `plot_full` exists only where OMDb had one, so uncapped a 12,000-character document is ~95% plot while a 250-character overview is ~30% plot and 70% metadata — not comparable, and cosine starts partly measuring *"does this title have an IMDb synopsis"*, the same coverage-asymmetry argument that keeps analysis prose out of the vector entirely. 4000 reaches the turn and the ending for almost every synopsis while keeping every document inside one order of magnitude of every other. In the UI it is opt-in behind a "Read full synopsis" button in `MediaHero`, collapsed by default and never swapped in silently, because a full IMDb synopsis routinely gives away the ending. Note `0139` also has to **clear `omdb_enriched_at`** — the stamp records that OMDb was asked, not *what for*, so every already-enriched row would keep the gap forever. That is the second such clear (`0137` was the first); a per-source *version* rather than a bare timestamp would make the next one a config change instead of a migration.

## F-087

**Enrichment fetches a rating once and never looks again, and that is not a small error.**

**Enrichment fetches a rating once and never looks again, and that is not a small error.** `needsEnrichmentSql` selects a row that has never been enriched, or whose `enrichment_version` is behind, or that OMDb was never asked about — **there is no TTL anywhere**. That is exactly right for metadata, which does not move: a plot, a cast list, a country of production are written once and stay correct. It is wrong for a rating, and putting both behind one predicate let the field that never changes set the policy for the field that changes weekly. Measured live on *The Drama* (tt33071426), all on the same day: our stored copy and **OMDb itself** both read 7.2 / **81,611** votes, the NFO on disk read 7.1 / 108,798, and **IMDb's own dataset read 7.1 / 112,851** — OMDb was 31,240 votes (28%) behind and had not moved in five days, so a TTL that re-asked OMDb would have spent the quota re-fetching the same number. Note the error is **biased, not random**: a new release's rating starts high on early-adopter enthusiasm and decays as the vote base widens, so a frozen copy systematically *overrates* recent films — and the rating score is a quarter of the blend at default weights. Note also that Emby is not an independent second opinion; the rating-sync plugin that keeps `community_rating` fresh reads OMDb and MDBList, so it carries the same stale number by a longer road. Six things about the fix (`ratings/`, migration `0148`, job `refresh-ratings`). (1) **It is a separate module and a separate job, not a flag on enrichment** — the whole point is that the two kinds of data want opposite selection rules, and a shared predicate is how they got confused in the first place. (2) The IMDb source is a **bulk file, not an API**: `title.ratings.tsv.gz` is 8.2 MB gzipped, refreshed daily, no key and no rate limit, so **one request covers all ~12.5k titles** and the source needs no TTL, no age-weighting and no budget. The per-title equivalent on OMDb's free tier is 1,000 calls/day, i.e. a thirteen-day trickle that can never keep up with the rows that actually move. Its cost is a **licence** (personal/non-commercial) rather than a quota, which is why every source is **opt-in** (`system_settings.ratings_refresh`, Settings → Integrations → Ratings Refresh) and why nothing-enabled logs and exits rather than failing. (3) `RATING_SOURCE_IDS` is **the one copy** — the config shape, defaults, sanitizer, PUT body schema and the job's step count are all derived from it. The step count especially: the executor sizes the progress record before the job reads its own config, and a hand-written number there is the second copy that stops matching and leaves the bar finishing at 50%. (4) `imdb_ratings_refreshed_at` is stamped on **every row we looked for, not only the ones we found**, because a title with no votes yet is absent from the file entirely — without that there is no way to tell "IMDb has nothing for this" from "the job never ran". Same principle as `omdb_enriched_at`: what is recorded is that the source was *asked*. The miss-stamping pass is skipped on cancellation, since rows past the break were never actually looked for. (5) **OMDb still writes those two columns, but only while `imdb_ratings_refreshed_at IS NULL`.** Conditional rather than deleted because the source is opt-in — an instance that declines the licence would otherwise have no IMDb rating at all — and the guard means switching the source off later *freezes* the values rather than reverting them. The clobber it prevents is **latent**: rows are normally selected once and never again, so nothing collides today; it fires at the next `enrichment_version` bump or stamp clear (`0137` and `0139` both did this), arriving attached to a migration about something else. (6) `parseRatingsLine` is pure and pinned (`imdbDataset.test.ts`) for the usual reason, and three of its details are load-bearing: the `wanted` set is checked **first**, immediately after the id is isolated, because it rejects ~99% of 1.5M lines and also disposes of the header row for free; `indexOf` rather than `split('	')`, which would allocate an array per line; and `Number()` rather than `parseFloat`, which accepts trailing garbage — with an explicit empty-string guard, since `Number('')` is **0, not NaN**, and a truncated line would otherwise store a real 0.0 rating.

## F-088

**The admin could not see what embeddings the instance already held, so every model change looked like a full re-embed.**

**The admin could not see what embeddings the instance already held, so every model change looked like a full re-embed.** The storage model is already correct and has been for a long time: rows are keyed `UNIQUE(<item>_id, model)` inside a per-dimension table (`0078`, `0091`), writes are `ON CONFLICT (<item>_id, model) DO UPDATE`, and **all 31 read paths filter `WHERE model = $n`** — verified across the recommender's candidate retrieval, `storeEvidence`'s LATERAL, the similarity graph, the series pipeline and `centering.ts`. So changing the embeddings model starts a *new* set beside the old one, deletes nothing, and switching back reuses what is already stored: the staleness join is `LEFT JOIN embeddings_N e ON e.movie_id = m.id AND e.model = $1`, so the old rows count as present and only genuinely new or genuinely stale titles are regenerated. Deletion happens **only** through two explicit admin routes. None of that was visible anywhere. `EmbeddingSetsManager` existed but returned `null` unless `sets.length > 1` **and** an inactive set existed — it appeared only *after* the switch it was meant to inform, which is exactly backwards, and it never showed the active set at all, so straight after a change every row read as inactive and the set the instance was actually using appeared nowhere. Seven things about the fix (`lib/embeddingSets.ts`, `getEmbeddingSetsReport`). (1) **Readiness is measured with the job's own predicate, not a row count.** `MOVIE_STALE_SQL`/`SERIES_STALE_SQL` are imported rather than re-expressed, because a set can be fully populated and still need rebuilding when `CANONICAL_TEXT_VERSION` moves or titles were re-enriched — a count matching the library size answers a different question from the one the admin is asking. A second copy of the predicate here would drift and the panel would promise ready for a set the job then rebuilds from scratch. (2) **`decideStatus` is pure, exported and pinned** (`embeddingSets.test.ts`), and its null case is the one that matters: an unmeasured set is `unknown`, **never `ready`**. The failure is asymmetric — reporting unknown as ready tells someone a switch is free when it may cost a full library re-embed, while the other direction merely asks them to look. `empty` outranks the null check, because a set with no rows needs no measurement and "nothing stored" is more use than "unknown" for the model an admin just selected. (3) The totals are the **embeddable** population, mirroring the job's `library_config` branch — an instance with disabled libraries would otherwise show coverage against titles the job will never touch, and read as permanently incomplete. (4) **Episode pending is missing-only and reads the setting**: episodes are outside the `text_version` scheme by design (`0138` — their canonical text touches no enrichment column) and their tables have no `text_version`/`updated_at` to test; with generation off the job produces none, so pending for them is genuinely 0 rather than the whole 16.5k table. (5) The listing is keyed on **(model, dimension)**, not model alone. Dimensions resolve through `getCurrentEmbeddingDimensions`, which reads a *custom* model's configured value — edit that after embedding and one model name owns rows in two tables, which merged would report a dimension wrong for half its rows. `DELETE …/sets/:model` takes an optional `dimensions` querystring for the same reason, declared in the schema so Fastify coerces it (an undeclared query param arrives as a string and matches no dimension). (6) **The status ships as a decided value**, never a threshold — the web bundle never imports core, so a rule encoded in the UI drifts the first time this changes. The panel also carries the post-switch job sequence, because the step everyone misses is `rebuild-taste-profiles`: moving every item vector does not move a stored centroid, `getUserTasteProfile` rebuilds only when `isProfileStale` says so, and until then the run compares new item vectors against an old-space profile for up to `refresh_interval_days` (30). `refresh-embedding-centering` has to precede it, since `buildTasteProfile` records which space it was built in. (7) **A set carries two dates, and they are not equally trustworthy.** `firstGeneratedAt` is `MIN(created_at)`, which is solid: `created_at` survives `ON CONFLICT DO UPDATE`, so it genuinely dates the set rather than the last thing to touch it. `lastGeneratedAt` is `MAX(updated_at)` for the movie and series families and `MAX(created_at)` for episodes, which have no `updated_at` — `0138` added it to those two families only, and added it as `NOT NULL DEFAULT NOW()`, so **a row not rewritten since that migration reports the migration's own timestamp** rather than its true write date. That is a floor, not a lie, but it means an old untouched set can look more recently written than it is; the first date has no such gap, which is why the UI shows a single date only when the two agree and a range otherwise. The range is also the honest shape for a live set — new arrivals are embedded into it as they sync, so "generated" was never one moment.

## F-089

**`plot=full` returns the blurb on this library, and the plot-widening F-084 credits never happened.**

**`plot=full` returns the blurb on this library, and the plot-widening F-084 credits never happened.** [F-085](#f-085) is built on the premise that OMDb's `plot=full` returns IMDb's user-submitted synopsis — "several times longer and different in kind", running 5,000–15,000 characters — and [F-084](#f-084) leans on that in turn, closing with the claim that the real answer to the vector's nationality density "was widening the plot, which takes the proper nouns from ~8% of a document to ~2%". Measured on the live instance, neither holds. **Coverage is not the problem**: `plot_full` is populated for **12,547 of 12,589** films (99.7%). Length is. `SELECT percentile_disc(...) WITHIN GROUP (ORDER BY length(plot_full))` returns **p50 431, p90 921, p99 1,925, max 4,947**, with **94 films (0.75%) above 2,000 characters and none at all above 5,000**. Against an `overview` averaging 330 characters, `plot_full` averages **512** and is longer at all for **7,302 films (58%)** — so what the feature actually delivers at the median is roughly a hundred extra characters of blurb, not a synopsis. Four consequences. (1) **`PLOT_CHARS = 4000` is very nearly inert.** It can bind only on films between 4,000 and 4,947 characters, a subset of those 94; the 1000 → 4000 raise did real work for the ~10–12% sitting above 1,000, which is worth having and is not what the entry credits it with. The cap itself is **not wrong** — the coverage-asymmetry reasoning behind it stands and would bite immediately if a wider source arrived — it is simply not reached. (2) **F-084's nationality mitigation rests on a denominator that does not exist.** A median canonical text is ~905 characters (`avg(length(canonical_text))` over `embeddings_3072`; max 4,407): roughly 430 of synopsis, ~220 of concept vocabulary (genres, themes, 18 keywords) and ~210 of proper nouns and nationality markers (title, director, 3 actors, 2 studios, 2 cinematographers, country, language, collection). That is **about a quarter of the median vector, not 2%** — so the three field removals in F-084 are carrying the whole load alone, and the *Metropolis* result that prompted them was never fully answered. (3) **Trimming the numerator is close to exhausted.** `buildCanonicalText` already caps cast at 3, studios at 2, cinematographers at 2 and keywords at 18; there is almost nothing left to cut that is not real signal, which leaves **widening the denominator as the only remaining lever**. (4) **What F-085 got right is unaffected and must not be undone in the process**: storing `plot_full` in its own column still matters, since `movies/sync.ts` rewrites `overview` on every pass; and the "only when actually longer" guard is doing *measurable* work rather than defending a hypothetical — it correctly rejects OMDb's fallback for **42%** of the library. This is a separate entry rather than an edit to F-085 because the premise was reasonable when written and the record of what was believed is the point of this file. Open: every source that would actually supply a 5,000–15,000 character narrated plot is external — Wikipedia plot sections via the fastCRW integration `analysis/` already uses, or the title-analysis prose F-085 rules out — and each one reintroduces the coverage asymmetry the cap exists to bound, so a plot source is a design problem with a coverage floor, not a column swap. `countryConcentration` in the `evaluate-recommender` neighbour dump is the instrument that would show whether any of it worked; measure before and after.

## F-090

**Centring is the one place a subtraction meets vectors nobody normalised, and it fails silently on the safest-looking configuration.**

**Centring is the one place a subtraction meets vectors nobody normalised, and it fails silently on the safest-looking configuration.** All 31 vector comparisons in this repo use `<=>`, which is cosine and therefore magnitude-invariant, so a non-unit stored vector has never cost any read path anything and no reader has ever had to care. `refreshCenteredEmbeddings` is the exception, and it is easy to miss because it does not look like one: it is a **subtraction**, and it fails twice over on rows of differing norm. `AVG` weights each row by its magnitude, so a long vector drags the library mean toward itself; and subtracting a fixed mean from rows of differing magnitude moves each by a different *proportion of itself*, so the results differ in **direction**, not merely in scale. Cosine cannot recover from that — the centred column becomes a confident set of wrong angles, and since [F-036](#f-036) makes centring worth **ndcg@100 20.5% → 31.9%**, corrupting it is expensive in exactly the place the gain came from. `storeEmbeddings` normalises nothing; it stores what the provider returned. Four things. (1) **It is currently inert, and measurably so** — norms over `embeddings_3072` on the live instance span **0.999930 to 1.000079 around an average of exactly 1.000000**, which is halfvec rounding of a vector that was unit-length when written. `gemini-embedding-001` at its native 3072 returns unit vectors, so `l2_normalize` here is the identity far below halfvec precision. **That inertness is the trap**: the call looks like dead code, and the configuration that proves it harmless is the one configuration where it does nothing. Do not delete it. (2) **It is a latent defect on the current schema, not a new requirement.** Seven of the eight `VALID_EMBEDDING_DIMENSIONS` are MRL truncations, where the norm depends on how much of that text's energy landed in the kept dimensions — Google's own documentation requires manual normalisation below 3072 — so an operator can already select a broken configuration today. Other providers return non-unit vectors at *every* dimension: Qwen3-Embedding's reference usage applies `F.normalize` after pooling and leaves it to the caller. (3) **This is the same argument `buildWeightedAverageEmbedding` already makes** for unit-normalising each item before summing ([F-037](#f-037)). That was the first place vectors are added rather than compared; this was the second, and it was missed for the same reason — the read paths are all cosine, so nothing downstream complains. Any future code that **sums or subtracts** these vectors is the third case and needs the same treatment; comparing them does not. (4) **Normalising here rather than in `storeEmbeddings` is deliberate.** This job is idempotent and re-run on demand, so the fix repairs existing rows with no re-embed; writing normalised vectors instead would leave old and new rows in different states until a full pass, and would discard what the provider actually returned — the only ground truth available when a model is behaving oddly. Still one statement, so F-036's all-or-nothing property is untouched. `l2_normalize` needs pgvector 0.7.0, which this schema already requires (`0024` and `0078` use halfvec, `0091` uses `binary_quantize`).

## F-091

**Centring was a manual job nothing chained, so every routine sync quietly armed a refusal.**

**Centring was a manual job nothing chained, so every routine sync quietly armed a refusal.** `refresh-embedding-centering` was `scheduleType: 'manual'` and `refreshCenteredEmbeddings` had exactly one caller — its own executor case. Meanwhile `generate-movie-embeddings` and `generate-series-embeddings` run on a **six-hour interval**. So the routine path was: new film syncs → gets embedded → lands with `embedding` filled and `embedding_centered` **NULL** → `isCenteringReady` flips false → and every viewer on a centred profile hits [F-036](#f-036)'s refusal row and finalizes `failed` with *"Taste profile space does not match available embeddings"*. Nothing was broken, nothing was misconfigured, and no amount of reading the recommender would find it — the trigger was a film arriving. The saving grace is the one already designed in: readers resolve the newest `status='completed'` run, so a refusal leaves the previous good run live and the page does not blank ([F-046](#f-046)). It degrades into staleness rather than absence, which is exactly why it could sit there unnoticed. Both jobs now call `centreAfterGeneration` before `completeJob`. Four things. (1) **Inside the job, not after it in the executor** — both embedding functions own their own progress record and call `completeJob` themselves, so centring afterwards would run against a job already reported finished, outside both the progress bar and the recorded duration. Each job gained a step for it (the series count is `shouldEmbedEpisodes ? 5 : 4`, since its whole bar already depends on episode scope). (2) **It is gated, and the gate is not gold-plating.** Rewriting the column is a full-table UPDATE — ~77 MB for 12,589 movies at 3072 halfvec — against jobs that fire four times a day and usually find nothing, so unconditional would mean rewriting the table to byte-identical values for the autovacuum churn and WAL volume of a real change. `centeringNeeded(generated, ready)` is pure, exported and pinned: **new vectors** (which land NULL *and* move the mean the rest of the column was centred against), or **an unready column**, which repairs an interrupted refresh — and is what makes a failed centring self-healing, since the next scheduled pass simply sees it unready and retries. (3) **It never rethrows.** The embeddings are written and good by that point, so failing the job would report the wrong thing; the error is logged loudly and the `!ready` condition collects it next pass. (4) **One copy, in `centering.ts`.** The movie and series pipelines are mirrored by design, but this is error handling rather than pipeline logic, and a drifting copy fails silently — one media type stops being servable for centred profiles while the other keeps working. Episodes have no centred column (`0154` covers the movie and series families only), so the series job passes `seriesGenerated` and centres series alone. `refresh-embedding-centering` stays for a manual sweep. Still unmodelled, and second-order rather than first: `embedding_space` records that a profile is centred, not *which mean* it was centred against, so re-centring after new arrivals shifts every item vector slightly while stored profiles reflect the old mean. Fifty new films against 12,589 move it very little and everything moves together, so relative geometry barely changes and the 30-day profile refresh sweeps it up — but it is real drift, and the space tag guarantees less than it appears to.

## F-092

**The harness could only ever measure the model already in use, and read its neighbours off the one seed population where every model agrees.**

**The harness could only ever measure the model already in use, and read its neighbours off the one seed population where every model agrees.** Two independent gaps, both of which made `evaluate-recommender` unable to answer the question it exists for. (1) **`loadLibraryMatrix` resolved the model and the table for itself**, so comparing two models meant flipping the active configuration between runs -- which also flips which set `refreshCenteredEmbeddings` writes, so the two things you most want held still both moved at once. It now takes an optional `{ modelId, dimensions }`. Both fields are required because **the dimension names the table**: rows are keyed `(item, model)` inside a per-dimension table, so a model change leaves the previous set intact ([F-088](#f-088)) -- the storage property that makes an A/B possible without a re-embed, which nothing could reach. `runEvaluation` still measures one set and now reports which; the executor enumerates every set with rows, so an operator runs the job unchanged and gets a table per model. The matrix carries its own `modelId` for the same reason it already carries `centered`: two sets are indistinguishable by inspection, and a report that cannot name what it measured is not a comparison. **The confound to check before reading anything is `poolSize`** -- `loadLibraryMatrix` deliberately applies no library filter so the pool is stable, but a set the embedding job never finished is genuinely smaller, and both `medianPercentile` and a deep-cutoff ndcg read BETTER on a smaller pool, so a half-embedded model wins. The executor warns when sets disagree. `canonical_text` is stored per row, so the sibling confound is checkable rather than avoidable: join the two sets and assert the texts are identical, or you are comparing texts and not models. (2) **Seeds were unreachable.** `seedTitles` existed on `EvaluationOptions` and the executor never passed it, so the dump always ran on `popularSeedIds` -- the same unreachable-parameter shape as the deleted `getValidJobNames` ([F-076](#f-076)), sitting on the instrument this module's own header calls PRIMARY. It is not a cosmetic default: popularity selects canonical, heavily-written-about films, which is precisely where two embedding models agree, while the seeds that discriminate are the obscure, the stylistic and the non-English -- all three structurally excluded. Seeds now come from `system_settings.evaluation_seed_titles`, newline-separated because a film title may contain a comma. Three details. `resolveSeedIds` wraps both title columns in `unaccent()` (`0134`), because a non-English title is one of the seeds worth stressing a model on and nobody types "Ascenseur pour l'échafaud" with the accent -- STABLE, so it costs the trigram index, irrelevant for a handful of seeds once per run. A seed that resolves to a real film but has **no vector in this set** is now logged rather than silently filtered, because that is exactly the case that matters when two sets are compared: a seed present in one dump and absent from the other reads as the models disagreeing. And zero usable seeds logs why instead of returning quietly, which would delete the primary instrument from the report and look like it merely had nothing to say.

## F-093

**Two modes of one model collide on the set identity, and the second pass silently destroys the first.**

Embedding rows are keyed `UNIQUE(<item>_id, model)` inside a per-dimension table and every read filters `WHERE model = $n`, so that one string is the whole boundary between one population of vectors and another. It was built inline as `${provider}:${model}` in **nineteen places across five files** (`ai-provider.ts`, both `recommender/*/embeddings.ts`, `settings/handlers/aiConfig.ts`, `settings/handlers/recommendations.ts`) — the duplicated-predicate shape this repo keeps paying for, and here it was load-bearing rather than merely untidy.

**The failure it would have caused.** Once [F-038](#f-038) established that `input_type: semantic_similarity` is a real, distinct space, the obvious next move is to embed the library in it and compare against the existing default-mode set. With the identity built from provider and model alone, both are `openrouter:google/gemini-embedding-001`, both land in `embeddings_3072`, and the second pass `ON CONFLICT DO UPDATE`s straight over the first. The A/B destroys its own control, the sets panel shows one row where it should show two, and `getEmbeddingSetsReport` cannot see that anything happened. Nothing errors. Note `google/gemini-embedding-2` does **not** collide — its model id differs — which is exactly the kind of asymmetry that makes this look like it works right up until it does not.

**The fix is one pure module**, `lib/embeddingIdentity.ts`, pinned by `embeddingIdentity.test.ts`. Seven things matter.

1. **The absent case must be byte-identical to the legacy string.** Every row already on disk was written as `provider:model`. Any decoration at all — a trailing separator, a `~none`, a normalised case — makes the entire existing library invisible to the staleness join and to the recommender's `WHERE model = $n`, presenting as a library that lost its embeddings overnight. Three separate tests cover this: undefined, explicitly-undefined, and blank/whitespace (a cleared settings field arrives as `''`, not `undefined`).

2. **The separator is `~`, not `#` or `:`.** `:` and `/` are both already *inside* model ids (`google/gemini-embedding-001`; OpenRouter's `:free` and `:extended` variants), so neither can delimit. `#` fails differently and worse: the set id is a URL path segment in `DELETE /api/settings/ai/embeddings/sets/:model`, so the one caller that forgets `encodeURIComponent` has everything after the `#` silently dropped — quietly addressing the semantic set's id to the default set and deleting the wrong vectors. `~` is unreserved in RFC 3986 and survives a raw path intact.

3. **An unrecognised mode is dropped, never forwarded.** OpenRouter's `input_type` is an unconstrained string, so a typo would be accepted, ignored by the provider, and then stored in an identity claiming a mode the vectors were never embedded in. Dropping falls back to the default space, which is where everything already lives — the asymmetric-failure choice.

4. **A provider that cannot carry a mode may not store one.** Only `openrouter` (via `extraBody`) and `google` (via `providerOptions.taskType`) can send one. The settings route **rejects** the combination with a 400 rather than storing it, and `getEmbeddingInvocation` warns and drops if it meets one anyway.

5. **The model and the identity are handed out together.** `getEmbeddingModelInstance` is **replaced** by `getEmbeddingInvocation`, returning `{ model, providerOptions, setId, inputType }`. Not a wrapper — replaced, so every call site is a compile error until it is looked at. That is how the two API call sites outside `packages/core` were found (`assistant/handlers/chat.ts`, `settings/handlers/tasteProfile.ts`), neither of which appeared in a grep scoped to core. `embedMovies` previously fetched the model while `storeEmbeddings` separately re-read the config to build the identity — two `getFunctionConfig` calls, so an admin saving the AI card mid-pass could file half a batch under an identity naming a space it was not embedded in.

6. **The id travels on the row, not alongside the batch.** `EmbeddingResult.setId` is stamped where the vector is produced, and the three `storeEmbeddings` writers pass `embeddings.map(e => e.setId)` rather than `Array(n).fill(modelName)`. There is no second place for it to be decided.

7. **The assistant's `ToolContext` collapsed from two fields to one.** It carried `embeddingModel` *and* `embeddingModelId`, resolved by two separate calls, and three tools embed a query then filter on the id. A query embedded through one configuration and filtered against another id still returns a confident ranking of the wrong population. Now one `embedding: EmbeddingInvocation`.

**Nothing parses a set id in the data path** — `embeddingSets.ts` treats it as opaque throughout, which is why a suffix could be added without touching it. `describeEmbeddingSetId` exists for display only, and the web panel mirrors it by hand (web-never-imports-core); a drift there costs a label, never a query.

**One door to the embedding SDK, because a prefix transforms the input rather than the request.** A mode delivered as a parameter is either sent or not; a mode delivered as a *text prefix* means the caller has to change what it embeds, and a call site that embeds raw text produces a vector with the right width, a unit norm and plausible neighbours, sitting in a different space from every row beside it. Nothing downstream can detect that, and TypeScript will not help — an unused `prepareText` is not an error.

The count is the argument. There were **eleven** `embed`/`embedMany` call sites across core and the API: both library passes, episodes, `embedText`, the similarity graph's query, three assistant tools, two settings handlers and the global search route. `routes/search/index.ts` was **missed twice** while enumerating them by hand, in a session specifically counting them. A convention would not have survived that.

So `getEmbeddingInvocation` returns `embedOne` / `embedBatch`, which apply the prefix internally, and `embeddingCallSites.test.ts` scans `packages/core/src` and `apps/api/src` for any direct SDK call outside `ai-provider.ts`. Two properties make that test worth having rather than decorative: it asserts the walk actually reached the tree (a silently-empty scan would pass forever, including a check that it reached the file that was missed by hand), and it was **verified to fail** by injecting a violation and confirming it reported the right file and line before being removed.

`testProviderConnection` is inside the gateway file and legitimately embeds the literal `'test'` unconditioned — it is checking reachability, not producing a stored vector.

**Two defects surfaced while enumerating those sites, both in `routes/search/index.ts`.** Its `getQueryEmbedding` built its own OpenAI client from `getEmbeddingModel()` — the *legacy* bare model name in `system_settings.embedding_model` — plus `getOpenAIApiKey()`. On any instance not using OpenAI that returns null, so semantic search was silently off and the route quietly degraded to text and trigram matching; on an instance that did have an OpenAI key while embedding its library with something else, it would have scored OpenAI query vectors against Gemini item vectors. And its ANN join carried **no `WHERE e.model` filter** — harmless while a dimension table holds one set, actively wrong the moment a second lands beside it, which is exactly what the set-identity work above enables. `similarity/index.ts` filters on `model` in all eight of its queries; this route was the only outlier.

**Cost of switching the mode**, which the settings card states in an inline warning: it starts a new set beside the old one, so the library keeps answering from the current space until embeddings → centring → **`rebuild-taste-profiles`** → recommendations have all run. Moving item vectors does not move a stored centroid, and `isProfileStale` will not notice for up to 30 days (F-088).
