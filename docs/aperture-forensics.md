# Aperture — Forensics

Evidence behind the trap rules in `CLAUDE.md`. Each `F-NNN` is the record for the matching
`[F-NNN]` pointer there: what was measured, how the failure presented, which alternatives were
rejected, and why.

**When to read one.** The CLAUDE.md rule is enough to write correct code. Open the entry when
you are about to change, revert or argue with that rule.

**When to write one.** A new trap gets its rule in CLAUDE.md and its evidence here, under the
next free number.

**What never goes in here.** This repository is public. Record mechanisms, not the deployment
they were measured on: no usernames, account or viewer counts, per-person watch histories or
picks, library sizes, hostnames, addresses, database row or run ids, or anything that
identifies an instance or a person. Say "measured on a production library" and give the
*shape* of the result (a ratio, a band, "a minority of viewers") rather than the raw count. Keep
each entry short: the rule, the evidence that justifies it, and what was rejected.


## F-001

**`discover/` vs `discovery/`.** `discover` = browse people/studios + TMDb-external detail (`/api/discover/*`); `discovery` = missing-content engine feeding Seerr (`/api/discovery/*`). `assistant/discovery/` is a third, unrelated thing (web-grounded chat candidates) whose grounding is a `WebSearchSource` registry: Google grounding + Tavily (`lib/tavily.ts`, `system_settings.tavily_integration`). Sources are combined into one structuring pass so they compose and fall back for one another; Tavily errors log under the `tavily` provider.

## F-002

**A new AI role is a list, not a union.** `AI_FUNCTIONS` is the one copy and `AIFunction` derives from it, but roles were also a JSON-Schema `enum` on ten Fastify routes that TypeScript cannot check. `titleAnalysis` shipped in the type and every handler but missing from all ten enums, so `GET /api/settings/ai/providers|models?function=titleAnalysis` answered 400, which the card rendered as "No models available" for every provider — and the "+ Add custom model" path was rejected by the same rule.

Other copies found: three runtime `includes()` guards (now `isAIFunction`); two places that *omitted* a role rather than rejecting it — `getOpenRouterRoles` (hid the measured-spend dashboard) and the pricing summary — both now iterate `AI_FUNCTIONS`. `aiFunctionSchemas.test.ts` walks the schema modules structurally.

The sixth copy was in SQL: `0089` put a `CHECK` on `custom_ai_models.function_type` naming four roles, so the database rejected both later roles. It surfaced only when `titleAnalysis` pointed at a custom LM Studio/OpenRouter model — the dialog validated, then the insert took a bare 500. `0144` drops the constraint instead of extending it; the test also fails on any later migration whose `CHECK` names two or more roles. `custom_ai_models_provider_check` stays: it guards providers, which change when an integration is written.

Not shared, deliberately: custom models are keyed `(provider, function_type)`, so one added under Text Generation does not appear under Title Analysis. Separately fixed: `getModel` read only `textGenerationModels` while `getModelsForFunction` fell back to `chatModels`, so a cloud model picked for a writing role lost its display name and price on lookup; both go through `modelPool`.

## F-003

**Web Search is Google-only and holds two keys.** `getProvidersForFunction('webSearch')` returns `google`; `AIFunctionCard` renders a label when a role has exactly one provider and auto-corrects an off-list selection (which is what stopped an unconfigured card sitting on the OpenAI default). `ProviderConfig.fallbackApiKey` exists because Gemini's free tier is what usually breaks grounding.

Anything spending grounding quota goes through `withWebSearchModel`: it walks `getWebSearchAttempts()` (primary, fallback, 429-parked keys last), advances only on a quota error, and writes every attempt to `web_search_usage`. Limits, 429 classification and cooldowns: `lib/webSearchQuota.ts`; counters: `lib/webSearchUsage.ts`, with day windows anchored to midnight US/Pacific because that is how Google's RPD resets. `webCandidates.ts` cannot use the wrapper (its strict→lenient→text cascade would fight the key loop) and meters by hand with `recordWebSearchCall`. A consumer that does neither silently undercounts. The fallback key is not in the per-provider credential store, so the PATCH handler treats an omitted `fallbackApiKey` as "leave alone" and only `''` clears it.

## F-004

**Two cost surfaces, one real.** `CostEstimatorSection` projects (price × assumed volume); `InferenceDashboardSection` measures. Capture happens in the provider's `fetch` (`createOpenRouterUsageFetch(role)`), which tees the response and reads `usage` from the JSON body or the last SSE chunk — so a new `generateText`/`streamText` call site needs no instrumentation, but `role` is fixed at provider creation and is part of the provider cache key. `feature`/`sessionId`/`userId` ride an AsyncLocalStorage set in exactly three places: `runJob` (tags `job:<name>`), the chat handler (wraps `createUIMessageStream`, whose `execute` runs synchronously, so the scope covers the turn), and `testProviderConnection`. Unwrapped work records as `unattributed`. Cost is nullable end to end; the dashboard reports `pricedCalls` separately. Never treat a missing cost as zero.

## F-005

**The estimator read $0.00 for every OpenRouter setup.** `PROVIDER_MAP` has no `openrouter` entry and `openrouter.json` ships zero models, so `findModelPricing` returned null and `?? 0` produced a confident zero. Fixed by resolving through OpenRouter's own catalog (`getOpenRouterModelInfo`, exact id only — `:free`/`:extended` are priced differently). `FunctionPricing.pricingKnown` separates "free" from "unpriceable"; render unknown as unknown.

## F-006

**The assistant consumes the recommender's output, not its logic.** Of twelve tools only `getMyRecommendations` touches the pipeline (reads `is_selected` off the newest completed run, so reserved-slot fillers do appear). `semanticSearch`/`findSimilarContent` are bare kNN with no novelty, boosts, diversity or slots — so a niche chat request is served by exactly the mechanism taste twins exist to compensate for.

Each item carries `source`, **derived** by `pickSource` from `score_breakdown` rather than passed through, because that object holds `twinMatch.donorId` and the model must never receive an identity it could name. Twin picks carry `sharedTitles` from the reader's own history (no donor leak), resolved batched per tool call — the tool returns up to 50 picks, and per-item lookups would put 50 round trips in one turn. Unknown `source` reads as `ranked`. Nothing calls `ContentItemSchema.parse()`, so `tool-ui/types.ts` mirrors the schema by hand.

## F-007

**Chat's personalized search reuses the pipeline's output.** `searchMyRecommendations`: ANN for the request, joined to `recommendation_candidates` of the newest completed run, re-ranked by `blendQueryAndTaste`. The join restricts to titles scored for this user and, since that pool is unwatched by construction, applies the watched exclusion for free.

Load-bearing: (1) both terms min-max normalised over the fetched pool — raw cosine sits in a narrow high band and `final_score`'s wider spread would decide everything (`tasteBlend.test.ts` pins that a compressed term still moves the ranking and a flat one contributes 0, not NaN); (2) `QUERY_WEIGHT` 0.6, so the request leads; (3) `ANN_POOL_SIZE` 400 fetched before the join, with `SET LOCAL hnsw.ef_search = 500` (the `ef_search` invariant originated here).

Two first-pass mistakes, both visible within a day: it passed `recommendation_candidates.rank` as the card `rank`, which `ContentCard` renders as a poster RankBadge — so cards read "2012" and "449" (positions among everything scored); and it shipped with no `reason` while the prompt made it the default for "find me something", diverting open requests away from web discovery, the only path writing reasons. It now calls `enrichCardReasons`, and discovery stays primary. The "call it below 8 resolved cards" rule that followed was later replaced by code ([F-120](#f-120)): a French-noir turn resolved about a quarter of its web candidates and the model, already holding an answer, declined an optional follow-up.

## F-008

**The taste brief personalises selection, never retrieval — and a prompt rule saying so was not enough.** The discovery pipeline's model calls saw only the user's message, so "find me something arthouse" searched with no idea who was asking. `discovery/tasteBrief.ts` builds a profile applied only in the structuring pass (`webCandidates.ts` `viewerBlock`), which has no search tool: it can reorder and tie-break but not change what was looked up.

(1) **The profile must never reach a search call.** The first version put it in `system` with an explicit "do NOT search for the titles in it" rule. Measured: "suggest me french film noir movies based on my history" produced twelve grounding queries, every one "French film noir" plus a descriptor of the user's favourite film, one naming it outright — the user's own "based on my history" reads as permission, so the rule loses exactly when personalisation is wanted. `WebSearchSource.gather` now takes only the query and `WebSearchContext` is deleted: the boundary is the type signature. (2) A precedence line stays: unstated, personalisation overrides the question and "a good horror film" returns arthouse dramas. (3) Tavily ignores the brief (keyword API) but gets a reasoning cue appended, because its `answer` is LLM-written and there is no separate answer prompt; the structuring pass drops any title without a real "why", so plain snippets can supply grounding text and zero candidates. Hence `include_answer: 'advanced'` (credits are charged on `search_depth`, so it is free) and a separate char budget — `maxContentChars` is a per-snippet cap, and applying it to the answer destroyed the only reasoned part. (4) Titles are signature ones, grouped by title because a `watch_history` row is an episode (one show can otherwise fill most of a ten-row list).

A first attempt to prove the brief's influence was wrong: a "like Meshes of the Afternoon" turn issued six title-comparison queries matching the brief's length, but those titles were in no watch history — the model was using its own knowledge. `personalized: true` in the log means only that a brief was built for structuring. Twelve queries in one grounded call meter as one request, so a bad query list costs relevance, not quota.

**Retries inside one key attempt must meter themselves.** `googleGrounding`'s `PASS1_MAX_ATTEMPTS` loop sat inside one `withGroundingModel` attempt, so an empty first response (a soft refusal at "based on my watched history", then twelve queries on the retry) made two billed requests and one usage row. The retried request *succeeded with nothing*, which is neither `ok`, `rate_limited` nor `error`, so `WebSearchCallStatus` gained `empty` (`0135` is a `COMMENT` only; enforcement is in the type, since a `CHECK` is what [F-002](#f-002) was about). All three hand-metered sites were audited: `googleGrounding`, `analysis/generate.ts` (same shape around `MAX_WRITE_ATTEMPTS`) and `webCandidates.ts` (meters each cascade pass on success and failure).

## F-009

**The intent router decides whether a web search exists, and its axis is the answer, not the wording.** `findCandidatesInLibrary` — the only tool that searches the web or writes card reasons — is added only on `discovery` turns, so a misroute is a different engine. The old taxonomy read any reference to the user's collection as `library`, so "suggest film noir based on my history" returned thirty films already watched. Now a request for titles to watch is `discovery` even when personalized; `library` means facts about the collection.

(1) `prefilterIntent` decides with no LLM, so a match there is final: `RECOMMENDATION_HINTS` is checked first and wins, and `LIBRARY_HINTS` no longer matches bare taste statements ("I like noir, what's good" used to hard-route away from the web). (2) Ambiguity resolves to discovery, which suppresses only three list builders and is nearly the superset. (3) The error path falls back to `library` deliberately — a failure is not a doubt, and `DISCOVERY_PROMPT` orders a web search a counting question does not want. (4) A library-routed `getWatchHistory` call returns watched titles even with `excludeWatched` on (it is in `EXEMPT_TOOLS`), and any `items` result renders as cards — so a lookup meant as context becomes the visible answer. Fixed later by `format: 'brief'` ([F-017](#f-017)).

## F-010

**Watch history was queryable only by recency, which produced confident false negatives.** `getWatchHistory` takes `type` + `limit`; the search tools touched `watch_history` only to exclude. "List the french film noir I watched" was answered "you haven't watched any" three times. Fix: (1) `watchStatus: 'all'|'watched'|'unwatched'` on both search tools, with the `ef_search` treatment on the semantic path (a filtered `LIMIT 20` otherwise returns nearly empty); (2) `ContentItem.watched` stamped by `annotateWatchedItems`, absent when not looked up, and the card branches on `=== true`; (3) `withUnwatchedFilter` skips a call whose `watchStatus === 'watched'`, per call — `'all'` is the model's default, not a user intent.

Also fixed: `director`/`tag` used `$n ILIKE ANY(directors)`, which is backwards (the right side of `ILIKE` is the pattern), so it asked whether `%Nolan%` matches the pattern `Christopher Nolan` and matched nothing. Now `directors::text ILIKE $n`, as `actor`/`studio` always were.

## F-011

**"French film noir" was inexpressible, behind three silent zeroes.** The chat ran ten `searchContent` calls returning 0 rows, exhausted its step budget and ended with no prose ([F-012](#f-012)).

(1) `languages` was populated for under 1% of movies (OMDb-only, written in two places in `enrichment/index.ts`) while `production_countries` was ~99% populated from the media-server sync. The `language` filter's description said "use for 'French films'", routing the key phrasing at the empty column; it is **deleted** rather than documented — a filter that works only on OMDb-enriched instances is worse than none. (2) `query` matches literal `title`/`overview` text; almost no noir says "noir" and there is no Film Noir genre, so the prompt's "country + query for the noir part" returned zero both ways. Now style → `semanticSearch(concept)`, fact → filters. (3) `semanticSearch` had no `country`, so the only tool understanding noir as a style could not be scoped to France. It has one now, via the same `ef_search` path.

The demonym trap: the column stores "France", users say "French", and `'{France}' ILIKE '%French%'` is false. A prompt rule that must beat the user's own wording every turn is not a fix, so `helpers/countryMatch.ts` maps ~120 nationalities. Values are substrings so one entry covers variants (`Germany` ⊂ "West Germany", `Czech` ⊂ Czechia/Czechoslovakia); unknown input passes through.

## F-012

**The last step was always wasted.** `stopWhen: stepCountIs(MAX_STEPS)` is checked only after a step that called tools, so the final step's results reach the UI as cards and never reach the model. A turn that spent every step searching ended with no prose. `prepareStep` forcing `toolChoice: 'none'` on the last step (`stepNumber` is 0-indexed) therefore costs no retrieval — that step was already dead. Raising `MAX_STEPS` costs nothing on healthy turns, but each step resends the system prompt plus all accumulated tool results, so cost grows superlinearly within a turn; and raising it alone fixes nothing, since a model looping on failing searches burns 10 steps as easily as 5. Hitting the guard logs `warn` "Step budget exhausted" — a signal about the tools.

## F-013

**A heading can assert what retrieval cannot support.** `semanticSearch` has no distance floor, yet headed results *Movies matching "…"*. Now *Movies closest to "…"* / *The {{count}} nearest titles in your library*: same rows, a true claim. A cutoff was deliberately not added — cosine bands here have repeatedly proven too narrow to threshold blind (see the cosine invariant). Separately unfixed: on a broad call the cards are honest but not the answer (fifty dramas of every nationality under prose naming nine French ones); `format: 'brief'` plus an explicit display call fixes it at the cost of a step.

## F-014

**Enrichment could not tell "already done" from "never asked".** `enrichment_version` (`0068`) records the schema version current when a row was touched, not which sources answered; every pass stamped it whether OMDb ran, was disabled, had no key, errored or found nothing, and the selection then excluded the row forever. A library enriched before OMDb was configured stayed stamped complete: measured, `languages`, `rt_critic_score`, `metacritic_score` and `awards_summary` were almost entirely empty while `getEnrichmentVersionStatus` reported zero outdated.

(1) `omdb_enriched_at` (`0136`) is stamped only when OMDb was attempted and did not throw. "Not found" counts (retrying forever would never end); an error does not (an outage retries). That needs the discriminated `OmdbOutcome`. (2) The predicate is one function, `enrichment/pending.ts` `needsEnrichmentSql`; it had lived in four places (two counts, two selections) that agreed by being wrong identically, which is why nothing looked broken. (3) The OMDb clause applies only when OMDb is usable, or every row stays pending and each pass re-runs TMDb across the library. (4) `0136`'s backfill trusts only `awards_summary`/`languages` as proof OMDb ran — the other columns have other writers. `clearEnrichmentData` is called by nothing. Backfill cost is set by the OMDb tier (10 req/s against 1,000/day free vs 40 on patron: weeks vs one pass).

## F-015

**"Attempted and did not throw" was the wrong boundary because the OMDb client never threw.** The fixed job's first run failed every request with 401 and logged each as "not found", restamping the library complete. `omdbRequest` returned `null` for any non-OK response, exactly as for "Movie not found!".

(1) Null now means "OMDb has no entry" and nothing else; everything else throws `OmdbRequestError`, classified purely in `omdb/failures.ts`. (2) OMDb answers 401 for both an invalid key and an exhausted quota, and only the body separates them; `errors/omdb.ts` already defined both patterns but the client never called `parseApiError` (so OMDb outages never reached API Errors). `testOMDbConnection` had the same hole. (3) OMDb also returns auth/quota errors as HTTP 200 with `Response: "False"`, so `isNotFoundBody` is a closed list. (4) A bad key latches for ten minutes rather than one doomed request per item; it expires because the usual fix (activating the key) is invisible to code. Keys are trimmed on write and read — a pasted newline looks perfect in the field. (5) `enrichMetadata`'s `while (true)` loops exit only when the pending selection empties, so an unstamped failure spins forever; over-stamping had been holding that together. Both loops now attempt each row once per run (`attemptedMovieIds`/`attemptedSeriesIds`). `0137` clears stamps with no OMDb evidence, deliberately over-broad: an extra request is cheap, a wrongly retired row is permanent.

## F-016

**A library row has three names; the assistant knew one.** `title`, `original_title`, `sort_title` — measured, nearly every film has an original title and about 30% differ from the title (*Elevator To The Gallows* / *Ascenseur Pour L'échafaud*). Ingest was fine; every reader compared `title` alone. Three failures: `resolveCandidates` Tier 3 searched `title` only; `idMatchValid` rejected a correct `imdb_id` hit because the English title shared no words with the French candidate; and `normalizeTitle` stripped `[^a-z0-9]`, which deletes accented letters, so "L'échafaud" and "L'echafaud" normalised differently — a film failing to match itself.

`helpers/titleMatch.ts` (NFD + combining-mark strip + a ligature map for `æ ø ß ł đ þ`, which have no decomposition) replaced three identical copies that must agree or a title survives dedupe and then fails to match. SQL half: `anyTitleMatchesSql`/`titleMatchRankSql`, all three columns in `unaccent()` (`0134`), localized > original > sort. `unaccent()` is STABLE, so it costs the trigram index (a seq scan measured in milliseconds on a five-figure library; `0134` records the IMMUTABLE-wrapper recipe for larger ones). A non-Latin title normalises to empty: `titlesOverlap` treats that as no match, `idMatchValid` as trust-the-id.

## F-017

**`format: 'cards' | 'brief'` makes a tool call private.** Every `items` result renders as posters, so a lookup meant as context became the answer — most starkly fifty recent plays shown under "you haven't watched any". `brief` returns `{ id, brief, count }` with no `items` key; `renderToolResult` dispatches on shape and returns null, so there is no client change and both renderers agree for free. It is also much cheaper than full `ContentItem`s. It is an input because only the model knows why it is calling. Search tools build the brief after `annotateWatchedItems` (so a private lookup can answer "have they seen these?") and keep a `yearById` map since year is folded into `subtitle`.

## F-018

**Episode embeddings had no reader, and now have exactly one.** The episode table is the largest embedding table on a real library (measured at roughly 15× the series table's size) and was filled unconditionally via a default parameter no caller passed, while two exported readers were called by nothing. Nothing pools episode vectors into the series vector either: a 20-season show and a miniseries contribute one vector each (`calculateEngagementWeight` already uses `log10(episode count)` for the taste side).

`searchEpisodes` is the only tool that knows what happens inside an episode. (1) `ContentItem.id` is the episode id (React keys otherwise collide); navigation travels as `episode.seriesId`. No `'episode'` type — type drives watched lookups and routes everywhere. (2) In `EXEMPT_TOOLS`: an episode id matches nothing, and filtering on the parent would empty an answer about a show the user is watching. (3) Series scoping is the worst `ef_search` case in the repo — one show is a fraction of a percent of the index. (4) Subtitle puts the year first because `splitMeta` only lifts a leading four-digit segment. (5) `createEpisodeTools` returns `Promise<ToolSet>` and reads the setting itself; a conditional spread made every tool `T | undefined` and broke `onStepFinish`'s typing. (6) `episode_embeddings_enabled` defaults on; off means the tool is absent, so the model says it cannot search rather than reporting a false negative. Disable and delete are separate actions.

## F-019

**Five disagreeing version strings.** `config/version.ts` is now the only source, with two fields: `APP_VERSION` (upstream lineage) and `APP_BUILD` (fork build, `mod.<commits>.g<shortsha>`). Joined, `0.7.8-mod.412` is a pre-release that sorts below `0.7.8`, and `+mod.412` is illegal in a Docker tag. `fullVersion()` joins with `-` for single-string surfaces, where nothing resolves ranges. `fetch-depth: 0` is load-bearing (depth 1 makes every build `mod.1`). Outside CI it falls back to `dev`. The `ARG`s sit in the runtime stage so a bump does not invalidate build cache.

## F-020

**Suggestion chips read every `is_selected` row a user ever had** — no status, media type or newest-run bound — so a chip could name a film from a run superseded weeks earlier (pruning keeps selected rows on old runs by design). Now the newest completed movie run, ordered by `selected_rank`: rank is what the page shows, and `final_score` buries reserved-slot picks by construction.

## F-021

**Tool results are post-processed.** `withUnwatchedFilter` (on when the request carries `x-exclude-watched`) strips watched items from any `items`/`carousels[].items`. Tools reporting what the user *has* watched go in `EXEMPT_TOOLS` or they come back empty.

## F-022

**Chat status line.** The turn runs inside `createUIMessageStream`'s `execute` so each phase can emit a transient `data-status` part. `withStatusEvents` is the third tool wrapper; a new tool needs a `TOOL_PHASES` entry. Phases are i18n key fragments; web-facing phase wording stays ambiguous. assistant-ui renders `data-*` parts as null, so they are caught in `onData` and passed through a module store. `toUIMessageStream` needs `sendStart: false` (a second `start` opens a second message) and its own `onError`, or mid-stream failures lose the coded `AI_ERROR:` text.

## F-023

**Two renderers must agree, and the first fix made them agree wrongly.** Live turns come from the runtime, reloaded ones are drawn from the DB, which stored text and tool calls in separate columns and drew text first. The first fix (`OrderedMessageParts`) hoisted text above tools in the live renderer too, in DOM order. The indices must come from `useAssistantState`, never `useMessage`: assistant-ui has two independent external stores, `PartByIndex` resolves against the api store, and reading from the legacy one tore mid-stream, threw `tapLookupResources: Resource not found`, and — with no error boundary anywhere — unmounted the whole SPA. `ThreadErrorBoundary` now contains it. `ThreadScrollControls` scrolls the answer start to the top once per turn unless the reader scrolled away; rows are tagged `data-aperture-answer`, and an empty row is `display:none` so the lookup skips zero-height boxes. Hoisting was itself later reversed ([F-100](#f-100)).

## F-024

**Chat cards remember the request.** `withRequestContext` (fourth wrapper, outermost) stamps `latestUserText` onto every `items` container as `request`; it persists in `tool_invocations`. The "create playlist from these" dialog posts `chatContext: { request, reasons }`, switching `PlaylistTextMode` to `'chat'`. Optional end to end — the Explore dialog posts without it and stays `'graph'`. Both routes also take `userNotes`, orthogonal to mode.

## F-025

**Channel generation is two-phase.** `preview` builds and writes nothing; `generate` with `{ itemIds }` pushes exactly the approved set; a bodyless `generate` is the scheduler path. `preview` is not cheap: `generateChannelPickReasons` makes one text call per 8 non-seed picks. It fails open (no model → no notes) and excludes seeds.

## F-026

**A channel description is media-server metadata** (the playlist/collection Overview). Generate passes it every time; `syncChannelDescription` pushes it alone on edit, so editing a description never rewrites the item list. An empty description leaves the server's overview alone. Renaming still orphans the old Box Set/playlist (lookup is by name).

## F-027

**One dialog, two i18n namespaces.** `PlaylistDialog.tsx` edits playlists and collections; `pages/collections/` renders it with `i18nNamespace="collections"` and every label goes through `pt(key)`. A new string goes in both near-duplicate blocks or one surface renders a raw key.

## F-028

**Every sparkle button offers "build on what I wrote".** All five text-generation routes take optional `userNotes`, sent only for "build on", omitted for "start fresh" (which is what lets a re-roll escape its last answer). `buildUserNotesBlock` puts it at the head of the prompt and `hasUserNotes` adds the rule against overwriting it. The button becomes a menu only when its box is non-empty.

## F-029

**One AI-explanation setting, three surfaces.** `getEffectiveAiExplanationSetting` (global → admin grant → user) gates generation in both pipelines, the NFO `<plot>` credit line, and whether insights returns `aiExplanation`. Before, every run paid for explanations whose only consumer was a column the app never selected. Turning it back on does not backfill. Insights resolves the target user's setting, not the viewing admin's. The credit line's brand comes from `getAppName()` (was a hardcoded name contradicting renamed instances). Pinned by `strm/nfo.test.ts`.

## F-030

**A reasoning model spends the explanation budget on thinking, and one truncated character discarded ten explanations.** Both generators ask for ten explanations in one JSON object; a parse failure replaced all ten with a template plausible enough that the page read as a model quietly getting worse. Measured on a reasoning model: parse errors "Unterminated string in JSON", with `completion_tokens` pinned exactly at the 3000 cap and 2,000+ of them reasoning, leaving too little for ten explanations. Reasoning varied from zero to over two thousand tokens between consecutive calls, hence the intermittency.

(1) `shared/explanationParsing.ts` holds the batch size and the reader; the generators had identical private copies. (2) Large-context ceiling 16000 — a cap, not a reservation, so headroom is free. Groq/Ollama tiers are not raised; theirs are bounded by the context window. (3) `parseExplanationResponse` tries strict JSON, then salvages entry by entry (the first salvage was a regex and caused [F-031](#f-031)). (4) `finishReason === 'length'` is the direct tell and is logged when the strict reader rejects; token counts stay in `llm_inference_calls`. (5) A degraded batch is no longer silent.

## F-031

**Salvaged text must still be a finished sentence.** The regex salvage made every explanation on a page a fragment ("If", "Given how much you loved the quiet human connection of") while the job logged success. The prompt writes titles in bare double quotes and the model does not escape them; the salvage string body stopped at the first unescaped quote, storing the lead-in before a title; and the only check was the batch count. Measured on the affected run: ranks 1–10 were short fragments containing no quote, 11–20 were full-length and all contained quotes — the split falls on the batch boundary, so one response failed strict parsing and had every quoted entry cut, the next parsed cleanly. "Quoted titles render fine" and "quoted titles broke it" are the same fact from either side of a batch.

(1) `isValueEnd` accepts a closing quote only before `}`/`]`, a comma introducing the next `"key":`, or end of input — a bare `"\s*[,}\]]` lookahead fails on `I loved "Heat", but colder`. (2) `looksComplete` (40 chars + terminal punctuation) applies to salvage only; a strict parse is the model's judgement. (3) `describeExplanationBatch` is shared and reports any strict rejection, `finishReason === 'length'` first. (4) The prompt asks for no double quotes — a request; the reader holds regardless. Pinned with the live shapes.

## F-032

**Explanations can be re-run without re-scoring** (job `refresh-recommendation-explanations`). They are the only pipeline stage depending on the writing model, so a rewrite used to cost a full regenerate and a different set of picks. (1) Targets the newest completed run per user per media type — other runs are thinned to their picks. ## F-033

## F-034

**A genre weight measured volume, not preference.** `calculateGenreWeight` scored a genre against the viewer's other genres with no reference to what the library holds, so in a comedy-heavy library comedy read as beloved on volume alone and a viewer who had taken every noir on the shelf read as indifferent. Now `(watched_in_genre / watched_total) ÷ (available_in_genre / available_total)` in `taste-profile/genrePreference.ts`. (1) The denominator must be the population the numerator counted — excluded libraries are excluded from both, or hiding the horror library reads as horror-aversion. (2) Log2 space, so "twice" and "half" are equal and opposite. (3) Shrink toward neutral by `n/(n+10)`: a thin history and a thin library section look identical from inside the function. (4) Band [0.7, 1.3], the same 0.6 width the old [0.8, 1.4] had — correcting *what* is measured must not change *how hard* it pushes, or neither change can be evaluated. (5) An uncomputable ratio returns null → exactly 1.0. `detectAndUpdateGenres` bails without writing when the library has no genre-bearing titles. ## F-035

**Genre reaches the score three times; two are marginal.** Novelty rewards less-watched genres, affinity rewards more-watched, and the canonical text already embeds the genre list. Both explicit terms are an arithmetic mean over the title's genres with no co-occurrence model. Measured across several dozen genre pairs in a large real history, the pair interaction (observed rate against what library co-occurrence plus marginal preferences predict) clusters at 1.0, and the highest-volume pairs are neutral. **Do not build a joint genre model** — it is worth 1–2 points on a term worth about six. The residual is a shape error: two preferred genres together under-deliver, two avoided genres over-deliver — saturation at the top, compensation at the bottom, which is what a linear mean does. The fix is compressing the averaged affinity toward neutral. The naive within-history lift `P(A∧B)÷P(A)P(B)` measures how genres co-occur in cinema, not preference.

## F-036

**Mean-centred embeddings.** Every canonical text shares one template and register, so all vectors share a direction: raw neighbour cosines crowd into roughly 0.66–0.83. ## F-038

**Corrected 2026-08-28.** The original entry claimed OpenRouter's embeddings endpoint had nowhere to put a task mode and no `dimensions`, so reaching `SEMANTIC_SIMILARITY` required the native `google` provider. Every clause after the first was false, and it was believed long enough to rule out a class of explanation for an A/B result. **An entry here claiming a door is locked is worth checking against the installed package.**

**What is true.** OpenRouter documents `input_type` (free string) and `dimensions`. `@openrouter/ai-sdk-provider`'s `extraBody` is spread verbatim into the request body, so both are a settings argument, not a fork. Google native takes `providerOptions.google.taskType` (full enum) plus `outputDimensionality`, **per call**; OpenRouter's is baked into the **model instance** — hence `getEmbeddingInvocation` returns a model *and* options.

**Measured on one document** (cosine against sending nothing):

| Model | `search_query` | `search_document` | `semantic_similarity` |
|---|---|---|---|
| `gemini-embedding-001` | identical | ≈0.91 (initially misrecorded as identical) | ≈0.86 |
| `gemini-embedding-2` | ≈0.94 | ≈0.98 | identical |

Reading: 001's default *is* its query space; for gemini-2 `semantic_similarity` is **ignored**. The first pass read gemini-2's identity as "the default is already semantic" — the same pattern it had just correctly read as "ignored" for 001. The parsimonious reading was available and the flattering one was taken.

**`input_type` on 001 through OpenRouter is a coin flip.** Five identical requests: default stable, `semantic_similarity` returned two distinct vectors (one identical to the default), though the field was on the wire every time. Pinning explained it: `google-vertex` honours the field (cosine ≈0.84), `google-ai-studio` drops it; each is deterministic, the router picks either, and both agree on the unmoded vector (which is what keeps existing unmoded sets safe). A full pass would write an undetectable mixture of two spaces into one set — every row the right width and unit norm. The field is undocumented, so neither upstream is wrong. `provider.only` takes the base slug (`google-vertex`), not the region tag the endpoints API reports; a tag 404s with a helpful list.

**How it was nearly misdiagnosed twice.** Single-sample comparisons first suggested a document-length effect, then a call-order/caching effect (reversing order flipped two documents in opposite directions). Only repeating one request five times showed a coin flip. **One call per configuration cannot separate "these differ" from "this endpoint is nondeterministic"; repeat before interpreting.**

**gemini-2's mode is a text prefix** (`task: sentence similarity | query: `), measured at cosine ≈0.81 from bare text and byte-identical between OpenRouter and Google's native API on both bare and prefixed input — OpenRouter is a faithful pipe. Because the prefix changes the text, no router or cache can collapse it, and both variants were byte-stable. It must apply to every document in a set and everything compared against it, so the prefix rides in the set identity (a change starts an empty set; no `CANONICAL_TEXT_VERSION` bump). Centring is already per set.

**Still true from the original.** Modes are different spaces, so all six call sites must agree (library `embedMany` ×2, `embedText()`, `semanticSearch`'s query, the interest re-embed, the assistant's `ToolContext`), and a mode change is invisible to the staleness predicate — now handled by the set identity. `dimensions` is deliberately not plumbed: truncations need renormalisation `storeEmbeddings` does not do ([F-097](#f-097) refines why). An earlier Gemini-001-vs-Qwen comparison (Gemini ahead on ndcg@20 and on a clear majority of viewers, p≈0.035) still stands but compared default-mode Gemini against unprompted Qwen. A prefixed set may legitimately score worse on holdout metrics, which only reward more of the same ([F-057](#f-057)); the neighbour dumps are the primary instrument.

**OpenRouter ships built-in embedding models only** (its chat catalog is thousands of models; embeddings are a handful, and shipping none meant hand-registering one before the feature worked). Pinned by `embeddingCatalog.test.ts`: (1) `embeddingDimensions` picks the table, so editing it points every read elsewhere and the library looks emptied; (2) no static price — `getModelsForFunctionWithCustom` enriches from the live catalog (without that, promoting a custom model to built-in would have lost its price); (3) dedupe by id, built-in winning, matching `getCurrentEmbeddingDimensions`; (4) gemini-2 listed at 3072 so comparisons measure the model, not truncation.

(3) Rating's shortfall was identical for everyone (fixed gain is right); novelty's varied about 2.2× between viewers (wants a bounded adaptive gain); similarity is already pool-adaptive — leave it. (4) Do not z-score all three: similarity's compression is an artifact of the embedding cone, but a pool of crime-thrillers genuinely has no genre variation, and amplifying it lets noise decide. An old comment claimed the curve's fall was shallower than its rise; the legacy branches always penalised the alien end harder. Stored `novelty_score` values from before this are on the old scale.

## F-059

**The spread correction goes on the weight, not the component** — which keeps "Quality 82%" meaning IMDb 8.2. `effectiveBlendWeights` multiplies each weight by a gain for how much range its term uses; `w/spread × value` and `w × value/spread` order identically, but only this leaves displayed numbers alone.

(1) `TARGET_COMPONENT_SPREAD` 0.57 is not a knob: `normalizeSimilarity`'s tanh(z/2) lands p10–p90 near 0.57 on any roughly normal pool (measured 0.546–0.577), so similarity is the reference and never gets a gain. (2) Rating's spread was ~0.46 for nearly every viewer → fixed gain 0.57/0.46 = 1.239; novelty varied ~2.2× → per-run gain. (3) Novelty gain clamped [0.7, 1.5] as a guard rail (real pools wanted ~0.73–1.58, so it barely binds); zero spread → 1.0. (4) Two passes in both scorers; they return `{ candidates, weights }`. (5) `finalizeRun` stores the effective weights, or the panel multiplies numbers that do not reproduce the match. `0150` widens the columns to `NUMERIC(6,4)` — `0.25 × 1.2391` stored as 0.31. Not backfillable. (6) `SCORE-DIAG` logs both. Realised influence moved from roughly 78/3/19 against a configured 70/8/21 to within a point of configured.

## F-060

**Re-normalising similarity inside the selection band was simulated and rejected.** The premise is real: similarity's spread across the top 50 collapses to ~0.03 against a pool-wide 0.57. Simulated in SQL from stored components at N = 200/500/2000, it decompresses as intended (×19 / ×15 / ×6) — and that is the problem: novelty and rating keep their pool-wide spread, so similarity takes the ranking (realised influence ~94/2/4 against configured ~70/8/21). Quality stops filtering and half or more of each viewer's picks change, well-regarded titles replaced by the dense mass of generic titles nearest any centroid once nothing can outvote proximity. Leave the compression; it partly reflects that the top few hundred really are about equally close. The only sound version renormalises all three over the same band — larger, unmeasured, and not worth attempting without first showing the top-band ordering is wrong rather than flat.

## F-061

**The explanation model was given a pairing and nothing to build a reason from**: title, year, genres, 250 chars of synopsis, and the bare titles of three neighbours. Any specific connection was pretrained knowledge — fine for canonical cinema, unfounded otherwise — and the only style instruction was "Create excitement". ## F-062

**The evidence lookup searched about 1% of a large history.** Both pipelines passed `storeEvidence` the same 50-title favourites-first list the centroid was built from — right for a mean, wrong for nearest-neighbour: for a viewer with thousands of films the true nearest title was usually not in the set, and the model then reasoned from whatever was. ## F-063

## F-064

**Title analysis is title-scoped; recommendation explanations are user-scoped; merging them would poison the explanation.** `analysis/` writes a critic-informed account of the work, cached in `title_analysis` and shared by every user. Retrieval mode is a setting (`analysis/mode.ts`): `crw` (default) retrieves before the model is called via fastCRW `/v1/search` + `scrapeOptions` (metasearch plus markdown fetch in one call) and the `titleAnalysis` role writes from that; `grounding` has a Gemini model search for itself, metered per Google project (a few dozen titles a day, not a library) and Google-only. Self-hosted retrieval replaced grounding for cost (at 20 grounded requests/day a library is years of work per key) and for honesty: the old prompt was made entirely of outside knowledge, which the explanation prompt forbids; with sources in the prompt, "use only the sources" is checkable. `title_analysis.retrieval_mode` records which mode wrote each row. `?force=true` is admin-only and reachable from the panel (a comparison needing `curl` is never run; it is also a declined row's only route); admins also see `provenance` (model, mode, sources, chars, prompt version). `titleAnalysis` stays in `isGroundingRole` for key handling even when local — a setting whose safety depends on another setting is not safe.

What is load-bearing, grouped:

- **Prompt shape.** Questions, not a directive: "analyse this film" finds meditations on grief in an action programmer; specific questions let a slight film get a short answer (measured roughly 250 vs 900 words on two very different films). Reception figures are calibration, marked not to be quoted. Order is subject → documents → task/rules, since scraped markdown is untrusted and the output is stored for everyone. The question list is the article's structure whether meant or not: live answers came back one paragraph per question in order, so version 4's technique-first order made readers cross an equipment list and logistics before anything about what the work does. Order became work → tradition → dispute → intent → circumstances, and the first question was reframed from "what is technically distinctive" (which returns hardware) to what the work is doing and how its choices serve it. Rules added: questions are what to cover, not a form; a sentence-level discipline (three-or-four-sentence paragraphs were met with 150-word semicolon chains); no empty gestures; name whoever the sources name. `CIRCUMSTANCES_QUESTION` (shared by both media types) exists because a case where every production fact was retrieved and none used showed nothing asked for it; it names its test (did this shape the work) and then needed a negative list (budgets, schedules, crew counts, dates) within one pass, when that same case flipped to mostly logistics. The query swapped `review` for `production history`.
- **Retrieval honesty.** `sourceFloor.ts` sees real domains, catching the in-house failure where an obscure title returns only listing/SEO pages (fires only when every substantive source is a listing; Wikipedia, RT, Metacritic and Letterboxd are not listings). `budget.ts` water-fills a character budget and drops documents whole rather than shredding them (fragments are worse input and lie to the floor, which counts sources); `clip` reserves the marker inside the limit. Zero results or zero text **throw** — a working metasearch finds something for nearly any title, so nothing usually means blocked engines, and an afternoon of that would write permanent declines. Thin-but-present sources reach the floor. A row existing means an attempt happened; `analysis IS NULL` is a decline; no row is never-asked or failed-in-transport. `prompt_version` makes prompt changes a config bump, and every bump re-analyses the library.
- **Blocked search looks like an empty answer.** Measured against the `crw-camofox` fork, a first-boot browser profile on a datacenter address got Google's `/sorry/index` interstitial and CRW answered `200 {results: []}`. `readCrwWarnings` reads both warning shapes; `crwSearch` logs them at warn; `retrieveSources`' throws repeat them; `describeTestOutcome` makes zero results a **failed** connection test (the probe query is banal, so empty cannot mean "hard"). Search engines are a cascade (`CrwConfig.searchEngines`, default `google, duckduckgo, bing`) because CRW resolves engines per request and has no config for it; each entry is its own request (several engines in one call are run sequentially and unioned — N× latency on every title). `sanitizeSearchEngines` never returns empty, since empty means Google alone. `crwEngines.ts` parks an engine after 5 consecutive empty answers across different titles for 30 minutes, moving it to the back but never dropping it. `testCrwConnection` walks the same cascade and names the engine that answered.
- **Guards must run where the work runs.** `checkModeReadiness` was called only by the settings page to draw a badge. Measured: retrieval on `grounding` with the role on an OpenRouter model (cannot ground) produced zero grounding chunks, the model wrote from memory, the floor rejected it — and the decline was stored, about one title a minute. The check now runs inside `analyseTitle` and as a job pre-flight, and zero grounding chunks throws like zero search results. `0145` deleted the rows already written.
- **Output contract.** The first real pass stored a free model's thinking ("Here's a thinking process:…") as the analysis, cut off mid-sentence; the three "successes" were all nearly identical lengths just under a 2,000-token ceiling — uniformity no real answer has. Three guards missed it: `finishReason` was never read, `parseAnalysisResponse` fell back to the raw string when the `SOURCES:` line was missing, and the floor only measures "too short". The first fix (reject anything without the closing line) was wrong — it turned a class of capable models into permanent failures, and the role is deliberately a free choice of model. What ships is an opening delimiter (`ANALYSIS_BEGIN_MARKER`): (a) the last occurrence before the closing line wins, so quoting the instruction while reasoning is harmless; (b) only `<think>`-delimited reasoning is stripped — guessing where a prose preamble ends is the salvage regex that caused [F-031](#f-031); (c) missing marker/grade or `finishReason === 'length'` throws rather than declining; (d) up to 3 write attempts; (e) streaming is irrelevant to this. `maxOutputTokens` was a hidden 2,000 near a real long answer's length; it is now `analysisMaxOutputTokens` (default 8,000, 0 = none) beside `sourceBudgetChars` — a length request is editorial, a token cap is a guillotine, so the cap belongs far above any real answer.
- **Job behaviour.** Each row is attempted at most once per run (else the drain loop spins on its own failures). The current title is reported before it starts (a counter moving every few minutes looks wedged). `shouldCancel` is polled after retrieval and before inference, throwing `AnalysisCancelledError`. `CONSECUTIVE_FAILURE_LIMIT` 5: with retrieval stopped mid-run, the whole per-run budget failed in seconds, logged near-identical traces and reported success; now it aborts as a failed job, counting any failure since the storms are indistinguishable from inside the loop.
- **Staleness reaches the page.** Only the batch job asked `ANALYSIS_PROMPT_VERSION`, and stale rows queue behind every never-analysed title. `isAnalysisStale` sits beside its SQL twin in `pending.ts` (both strictly-below, pinned); the route sends `stale`, not the version number; `POST` regenerates a stale row. No admin gate: the button shows only over a stale analysis and a rewrite makes it current. A stored decline is never re-asked.
- **Setup and display.** fastCRW runs in its own compose project, so `http://crw:3000` does not resolve — the published host port does. Test runs a real search, since a bare container passes a health check. The timeout default comes from CRW's own boot log (`effective_default_ms=82500` with ladder extension on; search runs before that), so 90s was below the worst case and a timeout loses the title silently — now 180s. Output formatting: "continuous prose" produced one 900-word block at 200+ chars per line; paragraphs of three or four sentences, an `84ch` measure, a source rail beside the text with no breakpoint (the page also renders in a dialog and beside the dock). Models separate sentences with single newlines, so `pre-wrap` rendered an article as a list; only blank lines split. Sources now carry `url` and render as links only when present (grounding rows have none — its citation URLs are short-lived redirects). The heading is Film/Series Analysis; the standing spoiler disclaimer went, since the question set is pre-viewing by construction.

## F-065

## F-066

**Two free-tier failures no retry can reach**: a spare key answers "this account is out of quota", a spare model answers "this model is gone" (the measured failure: a deranked `:free` model 404ing on every call). Both on the role's `ProviderConfig`, offered only by the `titleAnalysis` card since `analysis/generate.ts` is the only consumer.

## F-067

**A per-user score averaged across users can show a trend that exists in no user.** Similarity-by-decade averaged across viewers read as a clean, monotonic recency bias; per viewer the gradient reversed — each peaked at their own era, and the population simply leaned recent. ## F-084

**The canonical text said nationality six times.** Of fifteen fields, six were country-linked proper nouns (director, studio, cinematographer, composer, cast, country) against three describing what a title is like. ## F-090

**Centring is where a subtraction meets vectors nobody normalised.** Cosine reads are magnitude-invariant, so non-unit vectors never hurt them. `refreshCenteredEmbeddings` subtracts: `AVG` weights rows by magnitude, and subtracting one mean from rows of differing norm changes their **directions**, not just scale — a confident column of wrong angles, in exactly the place [F-036](#f-036)'s gain came from. Rows are now L2-normalised before averaging and before subtracting. (1) Inert on `gemini-embedding-001` at native 3072 (measured norms 0.99993–1.00008, halfvec rounding of unit vectors) — which is why it looks deletable and must not be deleted. (2) Live wherever a provider returns non-unit vectors (MRL truncations on some models; Qwen3's reference usage leaves normalisation to the caller). (3) Same argument as [F-037](#f-037); any future code that sums or subtracts these vectors is the third case. (4) Done here, not in `storeEmbeddings`: the job is idempotent, repairs existing rows without a re-embed, and keeps the provider's raw output as ground truth. Still one statement. Needs pgvector ≥ 0.7.0, already required.

## F-091

**Centring was a manual job nothing chained, so every routine sync armed a refusal.** Embedding jobs run every six hours; a new film landed with `embedding_centered` NULL, `isCenteringReady` flipped false, and every centred profile finalised `failed`. It hid because readers use the newest completed run, so it degraded into staleness. Both jobs now call `centreAfterGeneration` before `completeJob`. (1) Inside the job, which owns its progress and duration. (2) Gated, because the rewrite is a full-table UPDATE (tens of MB) against jobs that usually find nothing: `centeringNeeded` fires on new vectors or an unready column (which makes an interrupted refresh self-healing). (3) Never rethrows — the embeddings are good. (4) One copy in `centering.ts`. Episodes have no centred column. Unmodelled drift: `embedding_space` records that a profile is centred, not against which mean; re-centring shifts items slightly under stored profiles until their refresh.

**The manual job** is now for a column that is populated but wrong (a bad mean reads as ready), not routine drift. Scheduling it would reinstate the timed full-table rewrite the gate prevents and multiply the profile drift above.

## F-093

**The embedding set identity is one function because two modes of one model collide.** The identity (`provider:model`) was built inline in nineteen places. With [F-038](#f-038) showing a mode is a distinct space, embedding the library in a second mode would `ON CONFLICT DO UPDATE` straight over the default set — the A/B destroying its own control, silently. `lib/embeddingIdentity.ts`, pinned:

1. No mode yields the byte-identical legacy string (tested for undefined, explicit undefined, and `''`), or the existing library vanishes from every read.
2. Separator `~`: `:` and `/` appear in model ids, and `#` would be truncated by any caller forgetting `encodeURIComponent` on the delete route — addressing the wrong set for deletion.
3. An unrecognised mode is dropped (OpenRouter accepts any string, which would store an identity claiming a space nothing was embedded in).
4. A provider that cannot send a mode may not store one (settings route 400s).
5. `getEmbeddingModelInstance` is **replaced** by `getEmbeddingInvocation` (`{ model, providerOptions, setId, inputType }`), so every call site became a compile error — which is how two sites outside core were found. The old path read config twice per batch, so a mid-pass save could file half a batch under the wrong identity.
6. The id travels on each row (`EmbeddingResult.setId`).
7. The assistant's `ToolContext` holds one `embedding` bundle, not a model and an id resolved separately.

Nothing in the data path parses a set id; `describeEmbeddingSetId` is display-only.

There were eleven `embed`/`embedMany` sites and one (`routes/search/index.ts`) was missed twice by hand while counting them. `embedOne`/`embedBatch` apply the prefix, and `embeddingCallSites.test.ts` scans core and api for direct SDK calls (it asserts the walk reached the tree, and was verified against an injected violation). `testProviderConnection` legitimately embeds a bare string. That search route also built query vectors from the legacy OpenAI-only path (so semantic search was silently off on non-OpenAI instances, or scored OpenAI queries against another model's items) and had no `WHERE e.model` on its ANN join. Switching the mode costs embeddings → centring → `rebuild-taste-profiles` → recommendations.

The lever already existed on the installed packages — `providerOptions.google.thinkingConfig.thinkingLevel` and `providerOptions.openrouter.reasoning.effort` — and nothing used it. **The first version shipped a fixed vocabulary and was wrong three ways.** It defined `minimal|low|medium|high` over an allowlist of two providers. Measured on OpenRouter's live catalogue (2026-09-01): of ~420 models, ~120 do not reason, ~140 reason with no effort parameter, and ~150 publish `reasoning.supported_efforts`, drawing on **21 distinct vocabularies** over seven words, with no model offering all seven. Anthropic's take `max` and reject `minimal`; OpenAI's take `xhigh` and `none`. A fixed union offers words the model rejects (a 400 on a batch job), hides words it accepts (`none`, the strongest form of what the feature is for), and cannot grow. Native Google was worse: `thinkingLevel` is Gemini 3.x only (2.5 uses `thinkingBudget`, a token count; 1.5 has none), so three of the catalogue's seven models would have 400'd.

**Rebuilt so the vocabulary is data.** `supported_efforts` rides in the cached OpenRouter capabilities (`CACHE_VERSION` 2→3) and is stamped on by `getModelsForFunctionWithCustom` (the only path that works, since OpenRouter chat models are user-entered). Native Google declares `reasoningMechanism: "thinkingLevel"` per model. The dropdown, the settings route and the request builder all call the same function. Rules: (1) absent sends nothing — every existing role builds a byte-identical request; (2) absent `reasoningMechanism` means the model takes none (the discipline [F-097](#f-097) retrofitted); (3) nothing is rounded — an unlisted effort is refused and the provider default stands, erring toward more thinking (visible cost) rather than less (untraceable quality); (4) `KNOWN_REASONING_EFFORTS` is display order and labels, never a filter; (5) roles are an allowlist (`textGeneration`, `titleAnalysis`; chat excluded — interactive, and thinking is often the point); (6) the `providerOptions` key must be the provider id or the SDK silently ignores it — `MECHANISM_PROVIDER` is a table and a test asserts the sole key; (7) the analysis writer resolves per attempt against provider and model; (8) validated at save and at send, and the dropdown re-adds an off-list stored value so a MUI Select cannot blank it.

`@openrouter/ai-sdk-provider`'s `effort: 'high'|'medium'|'low'` type is a stale annotation — `doGenerate` spreads `providerOptions.openrouter` verbatim — while `@ai-sdk/google`'s `thinkingLevel` is a real `z.enum` that throws locally. The router pseudo-models (`openrouter/auto`, `/free`, `/auto-beta`) declare `reasoning_effort` in `supported_parameters` with no `reasoning` object, correctly, which is why `supported_parameters` is not the field to read.

**Measured** (`scripts/probe-reasoning-effort.mjs`, `google/gemini-3.5-flash`, two runs per level): `minimal` 0/0 reasoning tokens, `low` ~766, `medium` ~975, `high` ~1500, no effort ~990 (≈ the catalogue's `default_effort: medium`), invented control word **400**. So the vocabulary is a real capability read, the level is honoured, and `minimal` reaches zero scratchpad. The repeat matters at the top (`high` varied by 53 between its own runs). Per model only: another model may accept a level and ignore it. **The probe's default scope is a priced decision** — its first version swept three vendors (~35 paid generations) to re-derive what the free catalogue says; it now probes the model a role is actually configured with, extremes only, six calls, and refuses to run when no role is on OpenRouter. `thinkingBudget` for Gemini 2.5 is not built: mapping a word to a token count is an unmeasured number.

## F-103

**Account assumption is a second cookie, never a swapped session, and it is read-only because a method rule is the only promise that holds for handlers not yet written.** An `aperture_impersonation` cookie sits beside `aperture_session`, backed by `impersonation_sessions` (`0159`: admin user, admin session, target, one-hour expiry). The auth plugin resolves the session, then sets `request.user` to the target (every handler works unchanged) and `request.impersonation` to the admin.

**Swapping the session cannot be undone**: `sessions.token_hash` stores only a digest, so the admin's token is unrecoverable once overwritten, and exiting would mean minting a login the admin never performed, with a failure mode that strands them in the target's session. Layered, stopping deletes one row and one cookie, and a failed stop leaves them where they were (`stopImpersonation` reloads in a `finally`).

**Nothing writes to the target.** No session row, no `last_login_at`/`updated_at`. Ordinary browsing writes constantly (view modes, conversations, ratings, job starts), and auditing each is a snapshot, not a rule, so `impersonationBlocksRequest` (pure, pinned) refuses every unsafe method. Exempt: the two routes that END it (`/impersonate/stop`, `/logout`); `POST /api/auth/impersonate` is not exempt, so assumptions cannot chain. Two POSTs that are pure reads (`/favorites/status/bulk`, `/seerr/status/batch`) are allowed in a separate set, since blocking them made the assumed view render wrongly. Four checks run every request: still an admin, grant presented by the session that created it, not lapsed, target still enabled. `ON DELETE CASCADE` from `sessions(id)`; the cleanup job deletes lapsed grants on the exact deadline (the plugin already refuses them). Failures are asymmetric: a session-lookup error leaves the grant alone; a grant-lookup error leaves the admin as themselves — wrongly yourself is recoverable, wrongly someone else is not.

The exit lives in `Layout`'s AppBar, so no page can omit it; fallbacks are logout, the one-hour lease, and the admin's untouched cookie (hence the minutes-remaining display). The banner is a fixed 44px published as `--aperture-chrome-top`, read by four layout calculations. Crossing the boundary is a full reload in both directions: three localStorage caches are not namespaced by user, and resetting providers in place risks showing the admin their own data under another name (the keys live in `lib/clientCaches.ts`). Assuming another admin is allowed (it grants nothing new).

**What the security audit changed.** A transitive sweep (handler → core → SQL) found two GETs that write. `GET /api/trakt/auth-url` binds an OAuth state to the current (target) user and the unauthenticated `callback` redeems it into that user's token store — so an admin could attach their own Trakt account to the target's, outliving the assumption; both are in `BLOCKED_GETS`, the callback even when its state might name the admin (that failure costs a retry). `getUserSettings` INSERTed a defaults row when absent, on every page load; it is a pure read now and the two writers insert first. **A getter that writes defeats a method guard silently; find them by tracing the call graph, not reading handlers.** Also: a non-admin presenting a grant no longer deletes it (clearing its own cookie suffices); the stale-cookie clear is scoped to `/api/`. `impersonation.test.ts` boots Fastify and asserts an `onRequest` reply stops the handler — if an upgrade relaxed that, the guard would be advisory. Cleared: registration order, CSRF (`SameSite=Lax`, strict CORS origin), path mangling (exact-match sets fail closed), no method-override plugin, the grant is useless without the admin cookie. Accepted: an assumed session can read the target's assistant conversations; the audit trail is stdout only; instance caches still warm on GETs; neither cookie uses `__Host-`.

## F-104

**Discovery's taste half, its ratings and its pool** (audit of `discover/`, `routes/discovery/` and `generate-discovery-suggestions`, 2026-09-03).

**The similarity term was unreachable.** `scoreCandidates` built its vector map by joining `movies`/`series` on `tmdb_id` — for candidates `filterCandidates` had already removed *because* they are in those tables. The match set was a strict subset of the exclusion set, so the map was always empty and `similarityScore` the constant 0.5, at all three call sites. `scorer.test.ts` passed because it called `maxTasteSimilarity` with hand-built vectors; nothing tested that the pipeline supplied one. Configured share vs share of ranking variance: taste 45.5% → 0%, popularity 27.3% → 50%, recency 18.2% → 33.3%, source 9.1% → 16.7%. The `minSimilarity` filter was inert.

**Popularity mixed three scales**: TMDb's unbounded metric, a Trakt watcher count, and a hardcoded 0 for two Trakt sources — so the sources the code calls most personalised scored zero on the term carrying half the ranking. No personalised pick could outrank a merely popular one.

**Ratings were fetched and discarded, then overwritten.** (1) Trakt candidates are built with `voteAverage: 0`; `enrichBasicData` fetched TMDb details (which carry votes) for every candidate but returned only poster/backdrop/language/overview, and only the top-150 full enrichment copied votes — so a Trakt title showed a rating iff it ranked top-150 for that viewer. Now carried through, and the selection gained `|| !c.voteCount` so clobbered rows heal. (2) The pool upsert used `COALESCE($n, vote_average)`, and COALESCE guards NULL only, so Trakt's literal 0 overwrote good ratings (and popularity). Fixed with `NULLIF(…, 0)` on insert and conflict.

**Repaired in the same pass**: cancellation polled between media types, users and enrichment batches; the pool is pruned and read with `maxPoolCandidates`/`poolMaxAgeDays` (the prune's interval parameter needed an explicit `::int`); two ~200-line near-identical pipelines collapsed into one that always reads the pool (with an empty-pool seed); the store is one transaction chunked at 200 rows (a crash had left half-populated pages presented as complete); pool enrichment is cached (UPDATE-only, and an empty cast is not marked enriched, which would freeze a blank card); O(n²) normalisation and `Math.max(...spread)` removed; the per-candidate SELECT-then-write became chunked `ON CONFLICT` with per-batch dedupe; the franchise nudge compared canonical franchise names against TMDb collection names and never fired for movies (`franchiseKeys` expands both sides); recency's `1 − age/10` cliff made every title over ten years score 0 while an unknown year got 0.5 — now a 12-year half-life, unknown scored as old; dead columns written, dead exports deleted, `hasDiscoverySources` actually checks the TMDb key; a request Seerr declined stayed `submitted` and suppressed its title forever, so `reconcile-discovery-requests` (daily, before suggestions; `resolveRequestStatus` pure — availability outranks request state, pending never walks backwards, rows stranded 24h without a Seerr id are written off); `/expand` used a laxer vote floor than the list it merged into; the refresh route is guarded per user and media type.

**Resolved: embed the candidates.** The shared pool means a candidate is embedded once per instance, not per user per run. `discovery_candidate_embeddings` (`0160`), keyed `(media_type, tmdb_id, model)` with `model` = the set id, dimension-free `halfvec`, no index (read by key, scored in JS), `text_hash` so a pre-enrichment vector is superseded. The candidate document mirrors `buildCanonicalText`'s order and labels but fills six of nine sections, so candidates sit systematically further from the centroid — fatal for a threshold, harmless for a ranking, because the offset is common. Never threshold a discovery similarity against a library-derived constant. For a centred profile this is the one exception to [F-036](#f-036)'s "mean never looked up at query time": `getLibraryEmbeddingMean` recomputes `AVG(l2_normalize(embedding))` once per run and `centreVector` normalises before subtracting. Similarity is min-max normalised over candidates that have a vector (missing = neutral 0.5); popularity within each source (`popularityScoresBySource`), where a flat source resolves to 0.5, "no signal" rather than "unpopular". The two had to land together: fixing popularity alone would have handed more weight to the term standing in for taste.

Shipped alongside: `discovery_config` in `system_settings` (Admin → Recommendations → Discovery tuning; one blob, no per-media split), with `sanitizeDiscoveryConfig` on read and write — it checks absent before coercing, since `Number(null)` is 0 and finite and would clamp a missing knob to its minimum (its own test caught it). Every field has a literal `id=` because `registry.test.ts` scans source for promised anchors. Refresh answers 202 and the page polls the `discovery_runs` row; `refreshInFlight` is released in the background promise's `finally`; the client poll is bounded.

**The first live run exposed two chained faults.** One viewer's series taste term came back flat. (1) Their `user_taste_clusters.embedding_model` named the previous model, so clusters were discarded and the code fell back to the legacy `user_preferences` vector — as designed ([F-042](#f-042): a model change reaches nobody until `rebuild-taste-profiles`). (2) That fallback selected a `halfvec` column bare and annotated it `number[]`; pg returns halfvec as a string, so `maxTasteSimilarity` compared a ~40,000-character string's length against 3072 and skipped every vector. It hid because the dead similarity map meant its output was never consumed: **fixing a dead path exposes every latent bug in the code that fed it**, and those are exactly the untested ones. Fixed: `::text` + explicit parse (a failed parse returns none), a loop instead of `Math.min(...)` (the admin slider now allows arrays large enough to throw `RangeError`), and a `Taste similarity measured` line with `compared` and the **raw** min/max. **A diagnostic that reports the size of an input is not a diagnostic** — log the output of the step that can fail. (The legacy fallback was later deleted, [F-106](#f-106).)

**Anything that scores a taste profile must be able to maintain it.** After the parse fix every viewer compared successfully but split cleanly in two by raw spread — about 0.23 wide for centred profiles and about 0.04 for raw ones, a perfect correlation with `embedding_space`. Not centring readiness, not locks: the raw profiles were weeks older. `rebuildAllTasteProfiles` gated on the recommendation flags while `getDiscoveryEnabledUsers` gated on `discover_enabled`, so discover-only viewers were scored by a profile no job refreshed; the stranded viewers were exactly the narrow rows. Both halves required: the WHERE gains `OR discover_enabled`, and the per-user `mediaTypes` gains `|| user.discover_enabled` — or the gate admits them and rebuilds nothing, reporting success. Any future reader of `user_taste_profiles`/`user_taste_clusters` joins this gate. Only a per-viewer log made it findable; an instance average would have hidden a bimodal split.

**Confirmed after deploy**: the stranded viewers' spreads grew five- to sevenfold and the narrow population vanished (all rows ~0.16–0.29); already-centred viewers were unchanged to four decimals, so the rebuild repaired without disturbing. Series spreads sit consistently below movie spreads because the series library is an order of magnitude smaller — a size effect, not a series defect. This reproduces [F-036](#f-036)'s centring gain accidentally in both directions on a population it was never measured against.

**Discovery was the only per-user loop not gating on `provider_disabled`**, spending TMDb and embedding calls and holding Seerr request rights for viewers the server no longer has. Guarded in the job **and** the refresh route (the auth plugin then ignored the flag, so a dropped viewer could still press Refresh). Read routes are untouched — the guard is about spending, not hiding rows already paid for.

## F-105

**Requesting without leaving Aperture.** Built 2026-09-04 against Seerr v3.4.1 source and the Overseerr OpenAPI spec.

**Everything Aperture submitted was filed by the admin.** Seerr's `checkUser` resolves an API-key request to user id 1 unless `X-API-User` names another user. `POST /request` also takes a body `userId`; `POST /issue` only since v3.4.0; `POST /issue/:id/comment` never (hardcodes `req.user`). Pinned by `requestOptions.test.ts`. `PersonDetail` requests still record as `discovery`, a separate judgement.

## F-106

**One column, several units — the second pass over Discover.** Three of five further faults were one defect: `discovery_pool.popularity` held TMDb's unbounded metric, a Trakt watcher count and a hardcoded 0, with the unit recorded nowhere. [F-104](#f-104) treated that in the scorer while the same ambiguity still decided which rows exist and which fields survive a merge.

**The merge threw away what the pool knew.** `mergeWithPool` pushed a personalised candidate whole and skipped the pool row. A `trakt_recommendations` candidate has `voteAverage: 0`, no poster, no genres (Trakt's payload carries none), so it discarded a pool row with the real rating, poster, genres and cached cast — on the source with `sourceScore` 1.0 — and lost `isEnriched`/`poolId`, re-paying TMDb calls. Now `discover/merge.ts` (no runtime imports, pinned) merges field by field. `NULLIF` fixed what the pool stores and `enrichBasicData` what it enriches; **a fix at one end of a pipeline does not travel to the other**. `updatePoolEnrichmentBatch` was a third place: it cached cast and crew while dropping the rating, poster, genres and language from the same response, so the gap never healed.

**Unit and label were maintained independently.** Per-source normalisation used `sources[1]`, maintained by `ARRAY(SELECT DISTINCT unnest(...))` (no guaranteed order), while `popularity` was COALESCE'd from whichever source last supplied one. Measured, the same source set appeared in both orders, and a small fraction of movies listed a Trakt source first while carrying a TMDb-scaled number — normalised inside a tiny group instead of the TMDb one, so a title that should have scored ≈0.006 scored 1.00 on a term carrying 27% of the blend. F-104's per-source fix created that exposure. `0162` adds `popularity_source`, written in the same expression as `popularity` and NULL whenever it is; the backfill is provable (every pool row listed `tmdb_discover`, the only global source supplying a number). Ordering the `DISTINCT` would only make the wrong answer deterministic, so `sources` is appended to rather than rebuilt — `sources[1]` also decides `calculateSourceScore`, which could otherwise change between runs.

**The same column decided who survived the cap.** `getPoolCandidates` truncated by `popularity DESC NULLS LAST`, so a pool past `maxPoolCandidates` dropped Trakt-only rows first and then the least globally popular — the niche title that best matches one viewer, before it could be scored. The cap is a resource bound for an in-memory list, not a quality judgement. Now `ORDER BY updated_at DESC, tmdb_id ASC` (a unit every row shares; the tiebreak makes truncation deterministic). Inert when measured (pool well under the cap) and changed anyway: the trigger is an admin raising `poolMaxAgeDays`, by which time nobody remembers the column's three units.

**The fallback nobody maintained.** `getUserTasteVectors` fell back to `user_preferences.taste_embedding`, which `rebuild-taste-profiles` never writes, which carries no model and no space — `getProfileEmbeddingSpace` read the space from another table and applied it to this vector. A same-width model change passes the width guard and yields a confident cosine between two spaces: what `resolveEmbeddingSpace` refuses, reached around it. Deleted: no clusters at the active model means no taste term (neutral 0.5) and a warn naming `rebuild-taste-profiles`.

**A normalised measure cannot report on its own normalisation.** The console line read `similarityScore` after min-max, so it printed "0.00–1.00" on every non-flat run; the narrow band that started the investigation would have looked the same. `scoreCandidates` returns `{ candidates, taste }` and the console reports raw min/max plus `compared` against the candidate count.

**Once per run means once per job.** The library mean (an `AVG` over the whole embedding table) and a count were recomputed per user per media type — dozens of full-table aggregations a night for one vector. Now cached per (media type, set id) and cleared explicitly at run start, not by TTL (a stale mean is a wrong direction).

**The percentage was a rank.** The detail card rendered normalised similarity as a percentage, so the top pick always read 100% and the bottom 0%, against a raw band spanning roughly 0.43–0.66. Showing raw is the `0141` precedent but has a false floor (every card would read mediocre); rescaling hits the cosine-band invariant. So the card says what the number is: **"#12 of 245"** (`tasteSimilarityRanks`, pure, pinned — 0-based renders "#0", a reversed sort presents the weakest as best). **A weight correction measured and rejected.** The first estimate (recency compressed) was wrong: across twenty runs recency had the **largest** spread (sd ~0.35 vs similarity's ~0.21, full 0–1 range), because personalised sources draw on histories spanning decades. ## F-113

**A scoring weight cannot be measured across days; toggle it and regenerate the same afternoon.** The evaluation harness references no scoring function — it ranks by raw cosine — so it says nothing about the blend, preference strength, slots or era weight. This is how the era weight (`movie_era_weight`, `0155`, shipped at 0 and never measured) got measured anyway.

**The first design was confounded.** Comparing each viewer's newest run with its predecessor, against viewers who had not regenerated as a "control", suggested era moved the mix less than run-to-run noise. ## F-117

**Comparing models was unsound because each comparison retrieved its own sources.** Repointing the role, forcing a title and reading it means every run calls `retrieveSources` itself, and live search returns different pages each time — so differences are attributable to the model, the sources, or both. `analysis/compare.ts` retrieves once, builds one prompt, and hands every model the byte-identical string; the report leads with the sources and prompt version so the reader can see the control held.

Grounding mode is refused (no shared documents; a report would look sound and not be). `runWriteAttempt` is exported and reused, so the bench runs the job's real retries, pacing, LM Studio branch and contract checks. Nothing is written to `title_analysis` (storing would retire the title and make the bench unrepeatable on the film chosen for study). Failures are results and are printed — "cannot hold the contract on a long prompt" is usually the finding. `buildTitleAnalysisAttemptFor` builds an attempt for any provider/model from the shared credential store, inheriting the role's pacing only when the provider matches (the limit is the account's). Runs are stored (`0169`) for [F-094](#f-094)'s reason.

**The first deploy proved the point about seams.** The picker reported "server did not answer" for both local providers while LM Studio served analysis fine: `discoverLocalModels(provider, fn, baseUrl?, apiKey?)` was called without the address, fell back to `localhost:1234`, which inside the API container is the container. `resolveProviderEndpoint` is now the one public answer, used both to construct a model and to probe one. The compiler caught two smaller slips: a barrel export landing in the wrong block, and a type predicate that narrows through a `const` but not a property access.

## F-118

**An OpenAI-compatible vendor still needs a name, and the community package is two SDK majors ahead.** No first-party Z.AI package exists; the community `zhipu-ai-provider` depends on `@ai-sdk/provider@^3` from 0.3.0, so `ai@5` refuses it ([F-098](#f-098) from the other direction); 0.2.2 is the last usable and frozen. Z.AI documents `https://api.z.ai/api/paas/v4/` as OpenAI-compatible, and `@ai-sdk/openai-compatible` (already pinned to spec v2) appends `/chat/completions`. The one thing the package would add, embeddings, Z.AI does not serve (checked against its docs index and pricing page; `embedding-3` belongs to the separate mainland platform). `zai.json` says `supportsEmbeddings: false`.

**Why named, not another base URL**: only a name can carry a priced catalog, a large-context tier and a declared reasoning mechanism, and `openai-compatible` is filed as a local provider, so a cloud vendor's spend would report as free. **A third reasoning mechanism, where absent is the expensive setting**: GLM-5.3 forces deep thinking on and defaults to `max`, so [F-099](#f-099)'s "absent sends nothing" means the vendor's scratchpad at full price. `GLM_REASONING_EFFORTS` (`low|high|max`) is a mechanism constant, with no `none`/`minimal` (they would save and then 400). `name: 'zai'` is load-bearing: the SDK derives its `providerOptions` namespace from `config.provider.split('.')[0]`, making F-099 rule 6 true by construction. `reasoningEffort` is a named field on the SDK's own options schema, written as `reasoning_effort` — a bare string, not nested like OpenRouter's or Google's. Pinned on a captured request body (a fake `fetch` driving the real provider): each word reaches the wire, unset is byte-identical to before, an off-vocabulary word is dropped locally.

The base URL is editable on this cloud provider deliberately (international vs mainland are separate accounts), and the `/api/paas/v4` path matters — a host-only URL 404s and reads as a dead key. Z.AI is the only cloud provider shipping a catalog *and* taking custom models (`0170`), since its models turn over fast and the docs retire superseded pages. ## F-119

**An unmetered provider is invisible, not free — and token-only money is a different kind of number.** Four silent gaps found reading the Z.AI route back a day later.

(1) **Every GLM call ran unrecorded**: the ledger had one writer, OpenRouter's. `lib/usageFetch.ts` is now the shared scaffolding (read the request for the model, tee the response, scan for `usage`, time it, write one row); a provider supplies a chunk reader and optionally a pricer. The two contract rules are pinned: metering never changes what the caller sees (a streamed body still arrives chunk by chunk) and never fails the call — the tests print "Failed to record inference call" without a database and pass anyway.

(2) **Two kinds of money.** Z.AI reports tokens only, so its cost is computed from catalog prices — a different claim from OpenRouter's billed cost. `BILLED_COST_PROVIDERS` is a provider list (a property of the API, not of a row), and `estimatedProviders` ships decided. The estimate overstates in all three failure modes (cached input is cheaper and uncatalogued; plan rates are unknowable; price changes need a catalog edit) — the safe direction; cached tokens are still recorded. Three things look like $0.00 and differ: an unlisted model (every custom model — `custom_ai_models` has no price columns) → `undefined`; nothing measured (failed calls reach the meter with empty usage) → `undefined`, or it pads `pricedCalls`; a genuinely free model → a published 0 that must survive (`!= null`). Reasoning tokens are a breakdown *of* completion tokens and are never added. Reads bind `provider = ANY($1)`, and an empty scope returns empty rather than a query that matches nothing (which looks like a quiet week). `byProvider` keeps the split visible. The OpenRouter account card is skipped when no role uses OpenRouter.

(3) **The reasoning dropdown had only ever rendered for OpenRouter.** It reads `ModelMetadata.supportedEfforts`, which only OpenRouter stamped, while the save route validates via `getSupportedReasoningEfforts` — so native Google's `thinkingLevel` models had no control, and `glm-5.3` inherited the hole. `withReasoningEfforts` fills the list from `reasoningEffortsFor`, the validator's own function. `isGlmReasoningModel` infers a mechanism from the id, and **the asymmetry is inverted from F-099's**: guessing a model takes an effort costs nothing until one is picked (unset still sends nothing), while guessing it does not costs money on every call, since GLM-5.x forces thinking at `max`. Whole GLM-5 line, `(?![0-9])` against a future `glm-50`, `[1m]` suffix matched; GLM-4.x excluded. `inferredReasoningFacts` is shared by sender and picker.

(4) **A 404 from a bare Z.AI host reads as a dead key.** `diagnoseFromUrl` names the missing `/api/paas/v4` and both platforms, read off the error's own URL (an optional `provider` argument would be passed unevenly — [F-117](#f-117)'s defect), silent when the path is already right (a different fault, usually an unreachable model id). `hint` is a separate field; the provider's words are evidence. `testProviderConnection` appends it.

Catalog re-verified 2026-09-10: prices unchanged, nothing newer than GLM-5.3, no embeddings. `glm-4.7` and `glm-4.6` are now confirmed from each guide's cURL sample, both 200K context; `glm-4.7-flash` is still inferred. The GLM-4.7 guide is missing from the vendor's own `llms.txt` but answered at its URL — **a vendor's docs index is not a complete list of its docs**.

## F-121

**The analysis grounds a recommendation reason; it does not become one.** [F-064](#f-064)'s "never merge" was read as "never touch", leaving every reason written from marketing copy, tags and a taxonomy — and a model with thin material falls back on what it remembers, [F-061](#f-061)'s canon bias by another route. ## F-122

**A rule the model can satisfy while producing the behaviour it exists to prevent is not a rule yet.** From a bench run ([F-117](#f-117)) where one model's output was, on content, the best the prompt had produced — naming specific crew, dropping unanswerable questions, spoiling nothing — yet diverged from the prompt in ways that were **gaps in the prompt, not disobedience**. "The model ignored rule N" and "rule N does not say what we think" have opposite fixes. Three of four corrections name the failing phrasing verbatim, because in each case the abstract rule already existed and had already failed.

(1) **"the sources" is not a citation.** About ten instances of "the sources describe it as…" against a rule forbidding citing, numbering or linking — which forbade the form, not the act of pointing at the retrieval. The rule now names the phrasings and restates the existing alternative (name who said it, or state it as fact), since a prohibition without an alternative is answered by dropping the sentence. (2) **The circumstances question attracted reception** — a marketing mismatch, online speculation, objections after release — and the model said so in the paragraph. The question invited "controversies that changed what it became" and its negative list named only production trivia, so reception duplicated the dispute answer two sections down. The fix is a mechanical test, *would the finished work be different if this had not happened*, not another list of nouns. (3) **Rule 3 changed direction.** "Do not write one paragraph per question" (version 5) still has its reasoning, but three consumers now want each question findable as one block — the panel's headings ([F-116](#f-116)), `selectAnalysisGrounding` ([F-121](#f-121)), and the assistant's spoiler gate. So the sentence went, merging stays allowed, and the constraint is **adjacency**. Other models told to write continuous prose can return one unlabelled block, which turns grounding off entirely. (4) **Length was following the source block** ("length follows the work and the sources" against a 64,000-char budget reads as a licence). It now follows the work, keeps the 200/900 anchors, and says most of a long block is plot summary and repeated facts. `max_tokens` is not the lever: it truncates, and truncation throws rather than storing.

Checked first and not wrong: the section headings are rendered by the panel, not written by the model (reading a panel as model output would have "fixed" a rule being followed); a missing section is correct; question order was right. Rejected: sampling penalties (they punish the crew names the specificity rule demands; `logit_bias` is tokenizer-specific across a free choice of models) and multi-round prompting (resends the source block per question, ~5× input, and breaks the single line of thought). Cost: version 7 → 8, the second full re-analysis in a week. Pinned by `prompt.test.ts`, including that the deleted sentence stays deleted.

## F-123

**Nothing could change how a model samples, and "they all take temperature" is false.** Every generation ran at the provider default (1.0 on most), including `titleAnalysis`, which writes one structured document to a contract. Measured on OpenRouter's catalogue (2026-09-11, ~440 models): `temperature` declared by ~350, `top_p` ~335, `seed` ~330, `frequency_penalty` ~240, `top_k` ~220, `reasoning_effort` ~170, `min_p` ~115. About a fifth refuse `temperature` — including current flagship Anthropic, OpenAI and Google batch models — so a control offered on that premise does nothing on a large share of the catalogue: [F-099](#f-099)'s and [F-097](#f-097)'s fault again. The model's `supported_parameters` was already cached (CACHE_VERSION 3), so gating on it cost one field and no fetch.

OpenRouter-only on purpose: `temperature` would "very likely" work elsewhere, and "very likely" is how [F-097](#f-097) shipped a mode that was sent, ignored and written into an identity. `getSamplingModelFacts` returns null for other providers, so nothing is sent by construction. Rules: an undeclared parameter is dropped and **warned** (OpenRouter silently drops it, making the setting unobservable); out of range reads as unset, never clamped; `temperature: 0` is a real value (greedy), `top_p: 0` is refused (empty nucleus).

**One role, for coverage.** A sampling value reaches a model only at call sites that pass it. `titleAnalysis` has two, both already resolving reasoning per attempt. `textGeneration` has eight, three of which choose between the text and chat roles at runtime — half-wiring it ships a knob that works on explanations and silently does nothing on playlists. `ROLES_WITH_GENERATION_PARAMS` is `['titleAnalysis']`; others join by wiring their call sites. Suggested values are placeholders, never pre-filled ("unset" and "set to the suggestion" must stay distinct), and are ours because vendor `default_parameters` are often empty (`{}` for the model this was tuned for). Excluded: `max_tokens` (truncates; already exposed as `analysisMaxOutputTokens`), penalties (punish required crew names), `seed` (a bench axis, not a role setting). Found while measuring: that DeepSeek model reasons by default at `high` through OpenRouter, which already offers a working control via F-099 — so declaring a mechanism on the native `deepseek` provider buys nothing yet. Pinned by `generationParams.test.ts` against a real catalogue read.

## F-124

**The title-analysis prompt, versions 9–17, and the bench that compares them.** Most of this entry is a lab notebook; the durable lessons come first, then the per-version record condensed.

### Durable lessons

- **A rule that changes what a QUESTION asks holds; a rule the model must remember while writing fails.** Of version 8's four fixes, the two that reshaped a question (the circumstances fence, adjacency) held; the phrase ban and the length anchor failed. This held for every version after.
- **Naming the failing phrasing verbatim is the only thing that has made a ban hold**, and even then usually for one bench before another model finds another phrasing. Explaining a rule is not naming the phrasing. **A flat ban is not self-enforcing**: "rather than" and semicolons survived explicit bans on three consecutive prompts.
- **Every recurring fault asks the model to make a judgement mid-task about material in front of it** — naming, attribution, invented effects, length. The one structural fix that worked (stripping plot sections from retrieval rather than forbidding plot) transformed the making answers in one run. Where no structural fix exists, the third option is to stop asking (the naming ban, below).
- **A same-version replay is the noise floor.** Replaying one version against itself moved several signal columns (semicolons, "rather than", named, praise, told-twice) *further* than the deltas versions 11–16 were decided on. The columns separate **models** reliably and **prompt versions** unreliably on a single run. Stable on one run: longest paragraph, reception never exceeding work, the cap flags. One local model came back byte-identical, so determinism is available per model — the first evidence for the unbuilt generation-parameter axis ([F-123](#f-123)).
- **Signals are instruments, never validators, and rewording the prompt without re-reading the signals breaks them in both directions.** `pointsAtSources` matched only "sources" while the prompt's own noun is "documents", so the forbidden act scored clean; later `spill` counted "a viewer", the exact phrase version 16 asks for, so obedience scored as a fault. **Zero on every signal is not clean** — a flat assertion carries no hedge to count — and the instrument once scored the worse reception paragraph (one sentence per critic, the aggregator's shape) as the better one. **A count nobody checks is not a measurement**: `LENGTH_CAPS` holds each version's stated limits (a table, not a parse, asserted against each edition's rule text) and flags overruns; it failed the build the day version 17 was added, which is its purpose.
- **Retrieval decides more than the prompt.** Bench after bench, a model handed thin material reached for a generated page. See the retrieval section.
- **Versions 11–15 all went live without a draft**, each a full library rewrite off one or two titles. The discipline that ends the oscillation is batching corrections into a draft and benching it on three or four *different* titles, including an obscure or non-English one, before promoting.

### Version 9 (from five version-8 analyses)

Counted by hand across five films: an invented critical split to answer the dispute question (4/5), the dispute closed by announcing it is open (4/5), sections opening by restating their question (5/5), reception leaking into other sections, one fact told under two questions (5/5), intent guessed rather than reported (3/5), the version-8 phrase ban met with synonyms ("according to one critical read", "is described as"), and length over 900 words (2/5). Version 9: (1) order before → during → after: `tradition` (*Context*), `work`, [`structure`], `circumstances` (*Making*), `reception` (*Critical Reception*); influence moved to reception; cost: the one spoiler-shaped question is read first. (2) `intent` folded into `circumstances`, requiring intent to be something someone *said*. (3) `dispute` became `reception`: consensus as consensus, a real split given each side once, no verdict. (4) Attribution as a principle with examples, not a list. (5) Open on substance; say each fact once; name people for their choices; drop thin single facts. `intent`/`dispute` stay in `AnalysisQuestionId` and both web mirrors because stored maps carry them; `questionIdsFor` no longer returns them. Other locales keep their older heading translations until translated. A self-checked paragraph ceiling was rejected: the map is written after the prose has streamed.

**Replay.** The bench retrieved once per run, so two versions could not share documents. Replay (`0171` `replay_of`) reruns a stored run's documents under another prompt: `extractPromptSources` splits the stored prompt on each recorded `[n] title — domain` label (never on `[n]` alone — scraped pages carry footnote markers at line starts), treats a missing entry as a document `buildSourceBlock` skipped for being empty, and ends the last at the final `\n\nTASK\n`; a round trip must rebuild a byte-identical block. `proseSignals.ts` counts the measured habits; nothing gates on it.

### Versions 10–15

- **10 (bench-only draft).** Terminator 2 under 8 and 9: version 9 cut words and hedges but dropped attribution — one blog's readings stated as fact, a critic's conditional "if he hoped to" turned into the director's statement — because "name a critic where their view is the point" can be satisfied by naming none. "Say each fact once" failed. Half the sources were bot walls (two Cloudflare challenges, including the one scholarly source, and two access walls), numbered as documents because the budget never cuts a short document → `blockedPage.ts`. The "told twice" signal was added. `DRAFT_EDITION` was introduced so a version is benchable before it retires the library.
- **11 (live without its own draft).** Context opens on the kind of work, not the credits; comparisons with one specific earlier work are views (the draft had named a western whose ending would spoil this one); critics' readings of a choice moved to reception; reception grouped by point; connected sentences. An outside model review was checked against the report first: most of its evidence was quoted from the wrong version.
- **12.** Two of 11's rules were ignored (reception one-sentence-per-critic; a list of vehicles, effects, score one sentence each), and moving readings out of the work answer removed its analysis (reception grew to ~40% of the words). Naming unknown sites as authorities (blogs, an essay mill) was the real fault. Version 12: mark a view without naming its holder unless a general reader would recognise it; reception at most two short paragraphs, never longer than work; the work answer says what its choices achieve again; the paragraph rule names the list shape it forbids.
- **13.** Without names, "critics" became a false plural (one scholar, two reviewers). "The effect is the answer" beside "a plain-sentence view is still a view" made every effect need a holder, so writers' views spread through every section. Weak pages (user reviews, a listing site's tags) supplied facts and readings although the model had labelled them as viewers. Version 13 names no critic, scholar or publication (the operator's call: a name means nothing to a reader who does not know it); writers' views live in reception only; `SOURCE_VALUE_RULE` weighs weak page kinds; named non-answers (quality words in the work answer, credit lists with a "so" clause, what the makers did afterwards). `duplicateSources.ts` drops a page repeating another's title (one book chapter fetched from two hosts took ~45% of the budget); a title counts only with 20+ letters left after removing the film's names and year.
- **14** (a second model joined; a Greek film read from Greek sources). The kind of page was the wrong unit: an aggregator's generated summary was repeated as "a critic argued", while a real critic quoted on a bookshop page was rightly used. A blog calling the film part of the wrong directors' body of work still supplied most of both models' form answers. Effects were invented where no document gave one. An encyclopedia's uncited "the director studied…" became "the director's own account". "More than one document" miscounted critics three ways. Money and afterwards filled the making answer; the ending was approached twice. Version 14: documents weighed by who is speaking (a critic quoted anywhere counts; a page's own summary does not; a page getting a checkable fact wrong is evidence for nothing); only effects a document describes; a maker's statement needs the maker speaking; critics counted as the documents count them; money, rights, fees and later careers are not making answers. The cheaper model wrote richer answers at a fraction of the reasoning but made several unsupported claims where the other made one — **the signals count habits, not accuracy**.
- **15** (the first controlled test: replaying the Greek film under 13 and 14). 14 fixed the invented maker statement, the split critic and the long reception; **every answer still carried an effect no document described**, one model rewriting its previous sentence nearly word for word, because 14's clause came after "name a choice, then say what it achieves" and both models followed the opening. The work question now names the choice first and adds an effect only from a document, naming the shared clause shapes ("so that", "which gives", "lets it", "the result is"). The context opening may describe the kind of work plainly (for an obscure film an encyclopedia's genre description is the only answer). First sentences say something about the film. An unlabelled answer now says why under its stat line.

### The compact variant (`analysis/promptVariants.ts`, `0179`/`0180`)

Written after a 9B local model — the only local candidate fast enough to walk a library (minutes per title against half an hour for a 27B) — answered version 15 with one paragraph on the film and two on its reception, a list of camera bodies, and a student essay promoted to "one reading held". Not disobedience: ~2,000 words of mostly conditional rules, and a small model reads the first clause of a long conditional. Compact kept the same ids, header and output contract at 61% of the instruction length: per-question paragraph budgets, the work question naming where to look, the encyclopedia-is-not-evidence clause in the same sentence as the licence, and counting paragraphs before writing the map. A variant is keyed by a string id (a pseudo-version would break "the current version is the highest number"), recorded on bench results and, once library writing was allowed, on `title_analysis.prompt_variant` (what wrote the row, never what was configured); `libraryVariantFor` refuses a variant whose base is not current and never throws.

Benched on *Requiem for a Dream* across several models: compact fixed proportions (work answers roughly doubled, reception steady, no cap breaches), fixed the rejected map, and stopped an invented maker-endorsed lineage. It cost three things, each traced to wording and fixed: "then name the tradition it belongs to" was filled by inventing a movement; "would look or sound different" was narrower than the release conditions it gates, so the NC-17 refusal was dropped; and a paragraph *floor* caused padding (one run dropped reception to make room). A second bench found **every invented effect was in the making answer and none in the work answer**: the work question carries a document requirement, while the making question asked for an effect in its own wording and offered only a counterfactual test ("would it be a different film if…"), which no document can answer. Money entered the making answer in every run because the encyclopedia welded it to the one real making fact in a single sentence. Compact also lost the naming ban twice on one model, with a name taken from the retrieval's own source titles.

**Version 15 also moved rather than removed the invented effect**: "an effect a document describes" let models launder a generated encyclopedia's effect claims, whose checkable errors all sat in the plot summary the model is told to skip — **a rule that disqualifies a document is unenforceable when the tell is in the part being skipped.**

### Version 16 (draft → current, promoted 2026-09-22)

Drafted from compact with `draftQuestions`/`draftRules` matched on exact ids and exact rule text, throwing at module load on a miss (a silent miss ships a draft that quietly *is* its base). Every number is a maximum. First bench: money left the making answer (every run → none) via a "keep the half that belongs" rule for welded clauses; the certificate came back because the question now names what a qualifying release condition looks like; "never five sentences" held. The naming ban failed on both models despite being rewritten to explain itself; the word ceiling failed (paragraphs inside the cap carrying too much), so a 100-words-per-paragraph anchor was added. The instruction was then cut 17% (to ~72% of v15) — what made it long was **four lists that disagreed** about which facts never earn their place, now one `EARNS_ITS_PLACE` list; every named phrasing kept. The test suite caught the first pass dropping the sentence permitting names.

**The naming ban was dropped** (operator's call): in every version since 13 and broken on every model, it was house style, not correctness. What replaces it is the load-bearing half — **name the right one, or write "a critic"** — because the same bench misattributed one site's biography to another, which a ban could not have prevented. Opinions still belong in reception with a person behind them.

**Promotion was proved, not asserted**: version 15 was archived by generating it from the built edition, and every prompt the build renders (ten versions × two media types) was dumped before and after — all identical. Promotion retires every stored analysis (`prompt_version < 16`). Each media type now has its own tradition, making and reception text. **Compact went with the promotion and the mechanism stayed** (an empty `PROMPT_VARIANTS` is supported): its job was done, and it never worked for its target model, which failed the output contract on every bench in three different ways — the answer to that is `fallbackModels`, not a shorter prompt. Nothing stored breaks (`libraryVariantFor` returns null for a dropped id; stored labels are formatted from the string). Twenty tests went red on the bump because they pinned "the current prompt"; they were repointed at version 15. `const DRAFT_EDITION: PromptEdition | null = null` narrows to `never` at use sites, so it needs `null as PromptEdition | null`.

The small model's failures: a paragraph map miscounted, then a 304-paragraph answer (source text copied verbatim, then one sentence repeated ~80 times) that stopped of its own accord, then a missing begin marker on a sane answer. ## F-133

**An API key was the whole account, and an unguarded route looked like one that needed no guard.**

**Scopes** (`packages/core/src/apiKeyScopes.ts`, `0182` `api_keys.scopes TEXT[]`). A key minted for a script could purge the database and read provider credentials, with none of a session's limits. (1) A scope narrows, never widens — `admin` on a non-admin's key grants nothing; a scope that could add authority would be a second permission system. (6) The `write` guard is one hook over every route, sharing `lib/requestWrites.ts` with the read-only assumed session (the method rule and both correction lists moved there; impersonation tests passed unchanged). ## F-136

**Aperture ignored the media server's library permissions, and a STRM file made that a playback leak.** Emby and Jellyfin record which libraries each account may open (`Policy.EnableAllFolders`/`EnabledFolders`); Aperture read that list only to *add* the account's generated library to it. ## F-137

## F-139

**Two different titles with the same title and year were one library row.** Reported as a search bug: "Swan Song (2021)" returned one film in global search, in the playlist seed picker and everywhere else, and a different one for a different viewer — while Emby lists two (the Mahershala Ali film and the Udo Kier film). Nothing in search deduplicates; the `movies` table held one row. Both syncs fall back to a title+year match when an item's provider id is unknown, written so that a media server re-issuing an id (a rescan, a moved file) refreshes the existing row instead of duplicating it. That key is not an identity. The second film matched the first's row, and the fallback UPDATE (`WHERE LOWER(title) = … AND year = …`) rewrote it with the second film's provider id, poster, library and ids. The next sync saw the first film's id as unknown and did the same in reverse, so the row carried whichever film was processed last; which one a viewer saw followed the row's current `provider_library_id` against their library scope ([F-136](#f-136)). Everything keyed on the row inherited the flip: watch history, ratings, the embedding (its text changed every sync, so it was re-embedded every sync), recommendations. The fix is `recommender/shared/titleYearRebind.ts` (pure, pinned): a stored row is taken over only when no external id present on both sides disagrees — TMDb, IMDb, and TVDb for series — and among eligible rows the one agreeing on the most ids wins, so a genuine re-issue finds its own row beside a same-titled different work. The fallback UPDATE now targets the chosen row by its previous provider id, never by title+year, which would update every row sharing the key, and a takeover now also refreshes `title` and `year` (they were never written on this path). **An id check alone was the first version and an audit found it incomplete.** When one of the pair was never identified by the media server, there is no id on both sides to conflict and the pair folded together again — worse, the in-memory index merged ids (`incoming ?? previous`) while the UPDATE writes an absent id as NULL, so later in the same run the other film positively agreed with a row that no longer carried its id and took it back: a ping-pong inside one sync. Two rules close it. (1) **Liveness**: the sync accumulates every provider id the server has listed so far this run (the current library's full listing is added before its batches), and a row whose own id is in that set may be taken over only when an id *positively agrees* — a re-issue means the old id is gone, so a live row belongs to someone else. The positive-agreement exception exists for one case: the same film held in two libraries (4K and HD), which keeps sharing one row exactly as before, because splitting it would let a viewer be recommended the copy they have not watched. (2) **`takeOverRow` replaces the ids**, mirroring the UPDATE. Liveness is complete within a library and order-dependent only across libraries (an item in library 1 can take a row whose owner is in library 2, not yet listed); that case converges on the next sync, since the row's new owner is then live. An existing collapsed row self-heals on the next sync: the film whose ids contradict it, or whose row is live, gets a new row.
